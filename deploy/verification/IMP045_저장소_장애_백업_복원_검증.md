# IMP-045 저장소 장애·백업·복구 검증 기록

| 항목 | 결과 |
|---|---|
| 검증일 | 2026-07-24 |
| 검증 범위 | PostgreSQL·Redis·AIStor 실제 중단과 개발용 격리 복원 |
| 자료 분류 | `SYNTHETIC_DEV_ONLY` |

| 공개 상태 화면 | `http://127.0.0.1:18480/ui/storage-recovery` |

## 1. 결론

합성자료만 사용해 PostgreSQL, Redis와 AIStor를 실제로 각각 중지하고 복구했다. 기본 저장소의 named volume은 삭제하거나 복구본으로 덮어쓰지 않았다. 복원 시험은 별도 Docker project와 다음 전용 volume에서 수행했다.

- `sec-ai-mvp-imp045-postgres-restore`
- `sec-ai-mvp-imp045-redis-restore`
- `sec-ai-mvp-imp045-aistor-restore`

측정 결과는 다음과 같다.

| 대상 | 확인 내용 | 측정 | 개발 목표 | 결과 |
|---|---|---:|---:|---|
| PostgreSQL | 논리 backup과 격리 restore, Finding 계보·artifact inventory 일치 | RPO 4초, RTO 10초 | RPO 15분, RTO 4시간 | PASS |
| AIStor | primary 재시작 hash, exact version mapping, 격리 restore SHA-256 일치 | RPO 0초, RTO 10초 | RPO 1시간, RTO 8시간 | PASS |
| Redis | 빈 broker에 PostgreSQL PENDING Outbox 재발행, 논리 결과 1건 수렴 | 재구축 57초 | 개발 측정 | PASS |

이 결과는 같은 개발 PC 안의 격리 복원 통과다. 다른 failure domain의 암호화 백업, KMS·OpenBao·SSE-KMS, 1,095일 Object Lock과 실제 기관 증적 복구는 아직 통과하지 않았으므로 운영 재해복구 승인으로 해석하지 않는다.

## 2. 정본과 복구 원칙

```text
PostgreSQL
  업무 상태·Finding 계보·Outbox의 정본

AIStor exact object version
  원본 bytes의 정본

Redis
  재생성 가능한 작업 전달 수단
```

Redis 전체 내용을 잃어도 기존 Finding과 업무 결과를 Redis에서 추측해 복원하지 않는다. PostgreSQL의 PENDING Outbox를 읽어 빈 broker에 다시 발행하고, 업무 멱등 key와 DB 고유 제약으로 같은 논리 결과가 한 건만 남도록 한다.

## 4. 실제 장애·복구 순서

```text
합성 object·DB 관계 생성
→ PostgreSQL logical dump
→ AIStor 중단
→ 비밀값 없는 장애 상태 확인
→ primary 재시작 hash 확인
→ 전용 AIStor volume에 exact object 복원·hash 비교
→ PostgreSQL 중단
→ dependency unavailable 안전 응답 확인
→ 전용 PostgreSQL volume에 restore
→ Finding 계보·artifact inventory·migration 비교
→ Redis 중단
→ 빈 전용 Redis volume 기동
→ PostgreSQL PENDING Outbox 재발행
→ 논리 결과 1건 수렴
→ 기본 Core 재연결·9개 health 확인
```

공식 Finding은 만들거나 변경하지 않았고 실제 증적, 사용자 식별값, password, license 본문과 raw payload는 시험 출력에 포함하지 않았다.

## 5. 공개 UI·API

- 화면: `/ui/storage-recovery`
- 읽기 전용 상태: `/api/v1/storage-recovery/status`
- 환경 경계: `SECAI_DEV_DEMO_ENABLED=true`에서만 제공하고 그 밖에서는 `404`

공개 응답은 component 상태, RPO/RTO, hash·계보·Outbox 일치 여부와 운영 Gate 미완료 여부만 제공한다. run ID, object key, version ID, DB backup 경로, 원본자료, credential과 stack trace는 반환하지 않는다.

현재 Codex 세션에는 in-app browser가 연결되지 않아 스크린샷 시각 검토는 수행하지 못했다. 브라우저 목록이 비어 있음을 확인한 뒤 다른 browser backend로 우회하지 않았다. 대신 실제 HTTP 200, 서버 렌더링 계약, 접근 경계와 단위시험을 검증했다.

재실행:

```powershell

  -File .\tools\verify-imp045-storage-recovery.ps1

  -File .\tools\dev.ps1 -Action All
```

첫 실행에서는 runtime role의 `alembic_version` 조회 권한 누락을 발견해 migration에 최소 `SELECT` 권한을 추가했다. 다음 실행에서는 보안용 `/tmp` tmpfs를 `docker cp`가 읽지 못하는 경계를 발견해, 기본 DB volume을 건드리지 않는 Base64 stream export로 변경했다. 마지막으로 Redis 재발행 명령이 Celery가 없는 API image를 사용한 문제를 찾아 전용 Maintenance Worker에서 실행하도록 고쳤다. 수정 후 전체 장애·복구와 회귀시험을 다시 통과했다.

## 7. Runtime과 이동 범위

개발 재검사를 위한 `postgres.dump`, Manifest와 합성 object backup은 `runtime/imp045-recovery`에 생성된다. 이 폴더는 source 산출물이 아니며 실제 secret이나 기관 증적을 넣지 않는다. 이동 묶음은 사용자 지시에 따라 생성하지 않았다. Windows Collector source와 EXE는 변경하지 않았으므로 재빌드하지 않았다.

## 8. 남은 운영 Gate

- 다른 host·계정·저장매체에 암호화된 독립 백업

- 실제 기관 증적을 사용한 Pilot 복구
- 운영 RPO/RTO 반복 측정과 승인자 서명
- Redis AOF 접근통제·폐기, image SBOM·취약점·장기 부하시험
