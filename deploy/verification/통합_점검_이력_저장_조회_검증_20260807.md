## 1. 구현 결과

- 완료된 Windows PC-01~PC-18 결과에서 비식별 표시 필드만 골라
  `windows_audit_snapshots`에 저장한다.
- 기존 `linux_audit_runs`, `switch_audit_runs`의 완료 결과와 Windows snapshot을 하나의
  repository에서 합쳐 조회한다.
- `/api/v1/audit-history`는 플랫폼·시작일·종료일·limit·offset을 지원하고 상단
  `/ui/result-center`는 50건씩 목록과 상세 링크를 표시한다.
- Windows 결과 화면은 완료 결과를 자동 제출한다. 동일 result ID·version·hash replay는
  기존 row를 반환하고 재점검의 새 ID·version은 새 row를 추가한다.
- API의 organization/owner 조건과 PostgreSQL RLS를 함께 적용해 같은 조직이어도 다른
  로그인 아이디의 결과를 반환하지 않는다.
- `audit_history_policies`는 기존 row를 수정하지 않고 새 version을 추가한다. 기본값은
  365일·Backup 필수·`HOLD`이며 물리 삭제 API는 없다.

## 2. 데이터베이스 강제 조건

신규 migration은 다음을 적용한다.

- `windows_audit_snapshots`: organization·owner user·asset·정책 FK, 결과·기준 SHA-256,
  상태 개수, 안전 projection JSON
- `audit_history_policies`: 조직별 증가 version, 30~3,650일, Backup 필수 여부,
  `HOLD|TOMBSTONE_AFTER_BACKUP`
- 두 table 모두 RLS 활성화
- Windows 결과는 `organization_id`와 `owner_user_id`가 현재 DB session scope와 모두
  일치할 때만 SELECT·INSERT
- UPDATE·DELETE·TRUNCATE 거부 trigger
- `secai_runtime`에는 SELECT·INSERT만 부여하고 DELETE grant는 0

실제 PostgreSQL 검증은 합성 fixture를 한 transaction 안에서 만들고 마지막에 rollback해
점검 이력을 남기지 않았다. Fixture 생성 후 `SET LOCAL ROLE secai_runtime`으로 낮춘 상태에서
다음 결과를 확인했다.

```json
{"database_role":"secai_runtime","delete":"REJECTED","first_append":"CREATED","fixtures_retained":false,"identical_replay":"RETURNED_EXISTING","migration":"0031_unified_audit_history","other_login_visibility":0,"owner_history_rows":1,"runtime_delete_grants":0,"unified_history_rows":3,"unified_platforms":["LINUX","SWITCH","WINDOWS"],"update":"REJECTED"}
```

실행 명령:

```powershell
docker compose --project-directory . `
  -f deploy\compose\compose.yml `
  -f deploy\compose\compose.dev.yml `
  run --rm --build migrate `
  database/verification/verify_unified_audit_history.py
```

## 5. 보존·Backup·삭제의 현재 경계

구현 완료 범위는 정책을 별도 version으로 저장하고 각 이력의 보존 예정일·Backup 요구·삭제
방식을 표시하는 단계다. 다음은 아직 완료가 아니다.

- Backup 실행·manifest·hash와 성공 상태 수집
- 정기 restore 시험과 RPO/RTO 승인
- legal hold와 2인 파기 승인
- 만료 대상 dry-run·append-only tombstone event·감사 기록
- 운영 보존 scheduler

그러므로 현재 `TOMBSTONE_AFTER_BACKUP`을 선택해도 원본 row를 자동 삭제하지 않는다.
운영 파기 Gate가 갖춰질 때까지 `EXTERNAL_VERIFICATION_REQUIRED`와 물리 삭제 금지를
유지한다.
