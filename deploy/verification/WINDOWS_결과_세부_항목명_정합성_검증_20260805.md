## 1. 원인

- PC-06은 수집기가 메신저의 고정 catalog 이름을 보존했지만 DRAFT 판정 문구를 만들 때
  설치·실행·미승인 개수만 남겼다.
- PC-08은 `bcdedit /enum OSLOADER /v`의 `winload.exe`·`winload.efi` 블록 개수만
  수집해 운영체제 표시명과 BCD 식별자를 결과에 전달할 수 없었다.
- PC-15는 ActiveStore의 Domain·Private·Public 프로필을 각각 수집했지만 규칙 결과에서
  적용 프로필 수만 표시했다.
- 항목별 AI 입력은 결과 카드의 실제 확인값을 사용하므로, 원본 판정 문구에 이름이 없으면
  AI가 이름을 추정해서는 안 되고 개수만 설명할 수밖에 없었다.

## 2. 수정

### PC-06 설치된 메신저 제품

실제 `MESSENGER_MATCH` 레코드에서 고정 catalog 표시명을 읽어 다음 세 목록을 만든다.

- 발견 메신저
- 실행 중 메신저
- 선택 기준에서 승인되지 않은 메신저

집계 개수와 상세 레코드 수가 다르거나, 실행 개수와 실행 상세 목록이 다르면 결과를
만들지 않고 자료 불완전 `ERROR`로 처리한다. 예시는 다음과 같다.

```text
설치 제품 650개 중 메신저 2개(KakaoTalk, Telegram Desktop),
실행 1개(KakaoTalk), 미승인 2개(KakaoTalk, Telegram Desktop)
```

### PC-08 Windows 부팅 항목

읽기 전용 `bcdedit` 결과에서 각 `winload` 블록의 다음 값을 함께 수집한다.

- `description` 표시명
- `identifier` 식별자

영문 필드명과 한국어 `설명`·`식별자`를 모두 해석하고, 표시명이 없는 경우에도 실제
BCD 식별자를 가진 `Windows boot entry`로 남긴다. 새 수집 형식은 집계 개수와
`BOOT_ENTRY` 수가 반드시 같아야 한다. 예시는 다음과 같다.

```text
부팅 가능한 운영체제 항목 3개(
Windows 11({current}),
Windows 11 테스트({11111111-1111-1111-1111-111111111111}),
Windows 10({22222222-2222-2222-2222-222222222222}))
```

과거 점검처럼 개수만 저장된 PC-08 결과에는 이름을 만들지 않고
`이전 점검 자료에는 항목명 없음—재점검 필요`를 표시한다. 새 항목명은 사용자가 재점검을
실행한 뒤부터 반영된다.

### PC-15 침입차단 기능 활성화

적용 프로필을 한글 표시명으로 보존한다.

```text
적용 프로필 3개(도메인, 개인, 공용), Windows 방화벽 비활성 없음
```

비활성 프로필이 있으면 `비활성 1개(공용)`처럼 개수와 이름을 함께 표시한다.

### 공통 표시·AI 계약

- 실제 목록이 1~5개이면 이름을 모두 표시한다.
- 6개 이상이면 앞 5개만 표시하고 `외 N개`로 남은 수를 정확히 표시한다.
- 결과 카드의 실제 확인값이 그대로 AI 설명 입력의 `observed_summary`가 된다.
- AI 프롬프트도 같은 5개 기준을 사용하며, 입력에 없는 이름을 만들지 않는다.
- 사용자 PDF와 기술 검증 PDF는 기존 실제 확인값 필드를 사용하므로 새 이름 문구가
  별도 추정 없이 동일하게 반영된다.
