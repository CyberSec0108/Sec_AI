# AUTO-SELECT-01 기존 플랫폼 자동 식별 검증

## 1. 검증 범위

2026-08-07 현재 이미 개발 지원 중인 다음 범위를 사용자가 세부 제품을 선택하지 않고
안전하게 연결하는 1차 구현을 검증했다.

- Windows 11 x64 → 기존 Windows PC 읽기 전용 Adapter
- Ubuntu Server 24.04 x86_64 → 기존 Ubuntu U-01~U-67 Adapter
- Rocky Linux 9 x86_64 → 기존 Rocky U-01~U-67 Adapter
- 등록된 Aruba AOS-CX 10.13 대상 → 기존 인증서 고정 REST GET Adapter

지원하지 않는 버전·architecture·불완전한 식별값·등록 정보 충돌·Adapter 다중 후보는 가장
비슷한 Adapter로 넘기지 않고 실행 전에 차단한다. LLM은 식별과 Adapter 선택에 참여하지
않으며 기존 DRAFT Audit Pack 상태도 변경하지 않았다.

## 2. 구현 결과

### 2.1 공통 계약

- `database/schemas/platform_fingerprint.schema.json`과 valid/invalid 예제를 추가했다.
- `PlatformFingerprint`, `PlatformSupportCatalog`, `AdapterSelection`을 결정론 객체로 구현했다.
- 동일 입력과 Catalog의 canonical SHA-256을 고정했다.
- exact match만 허용하고 후보 0개·2개 이상, `PARTIAL/CONFLICT/UNKNOWN`을 차단한다.

### 2.2 기존 점검 흐름 연결

- Windows 실행 context가 Windows 11 x64 Fingerprint를 만들고 기존 PC Adapter와 일치하는지
  검증한 뒤 수집한다.
- Linux 중앙 SSH preflight가 일반 권한으로 `/etc/os-release`와 `/usr/bin/uname -m`을 읽고
  Ubuntu/Rocky Adapter를 자동 선택한다. 등록된 배포판과 실제값이 다르면 중단한다.
- Switch는 사용자가 지정한 한 개의 등록 대상을 공통 Resolver에 연결했다. 현재는 Aruba
  AOS-CX 10.13만 지원하며 주변 IP 검색이나 다른 프로토콜 fallback은 추가하지 않았다.

### 2.3 Linux one-shot 공용 실행파일

- Linux 자가 점검 화면의 Ubuntu/Rocky 선택을 제거했다.
- 공용 파일명은 `secai-linux-check-x86_64`이다.
- 실행파일이 로컬 `/etc/os-release`와 architecture를 먼저 읽는다.
- 중앙 API도 전달받은 값을 별도로 정규화하고 Support Catalog로 검증한다.
- 서버가 고른 배포판의 일회용 서명 Manifest만 발급하며 실행파일이 배포판·서명·hash·만료를
  다시 확인한다.
- DB run은 최초 `AUTO` 상태로 생성되고 성공적인 식별 뒤 하나의 배포판에 원자적으로
  결합된다. 미결합 결과 제출은 `PLATFORM_NOT_IDENTIFIED`로 거부한다.

### 2.4 개발용 다운로드

- 새 Linux build: `runtime/linux-oneshot-artifacts/build-20260806T225331Z`
- 공용 artifact: `secai-linux-check-x86_64`
- 새 임시서명 release: `runtime/dev-signed-downloads/release-20260806T225533Z`
- API 검증 상태: `DEV-SIGNED-TEST`, `download_allowed=true`
- API가 확인한 공용 artifact SHA-256:
  `b4f321dafad6b504336cb2e083035db64a4725f2580286d2d35af9485316813f`

기존 Ubuntu/Rocky 전용 파일은 이전 링크 호환을 위해 카탈로그에 남겼지만 일반 다운로드
화면에는 Windows와 공용 Linux 파일만 표시한다. 이 서명은 개발시험용이며 조직용 코드서명,
운영 배포 승인 또는 공식 인증이 아니다.

## 4. 별도 확인된 기존 문제

- 전체 `database/schemas/validate_examples.py`는 이번 변경과 무관한 기존
  `valid/finding_explanation_input.json`의 `evidence_trace` 누락으로 실패한다. 새
  `platform_fingerprint` Schema 예제는 독립 검증과 Catalog 시험을 통과했다.
- `tests/unit/test_switch_product_flow.py` 전체 수집은 기존
  `build_switch_report_document` import 불일치 때문에 시작하지 못한다. Aruba 공통 Resolver는
  독립 시험에서 통과했으며 이 기록에서 기존 import 문제를 수정하거나 숨기지 않았다.

## 5. 남은 Gate

- 실제 Ubuntu/Rocky VM에서 로그인→코드 발급→다운로드→식별→수집→온라인 제출 전체 E2E
- 깨끗한 Windows VM에서 기존 PC-01~18 결과 hash 회귀
- 현재 Aruba VM에서 실제 식별값과 N-01~N-38 결과 회귀
- Windows Server, 추가 Linux 배포판, Cisco/Juniper 전용 Adapter·Pack·Fixture
- Canonical Fact·적용성 Resolver와 관리자 Catalog 검증·승인 UI
- 새 artifact hash에 대한 독립 취약점 DB 재검사·악성코드 검사와 조직용 정식 서명

이 Gate를 통과하기 전에는 1차 자동 식별 기반을 운영 지원 확대나 공식 Pack 승인으로
표시하지 않는다.
