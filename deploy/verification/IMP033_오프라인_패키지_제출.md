# IMP-033 오프라인 Package 제출 검증

## 1. 완료 범위

| 항목 | 결과 |
|---|---|
| 구현 단계 | `IMP-033` |
| 제출 방식 1 | `OFFLINE-SIGNED`, 조직 인증서 기반 `MEDIUM` |
| 제출 방식 2 | `OFFLINE-USER-SUBMITTED`, 로그인 제출자 기반 `LOW` |
| 데이터 서명 | Ed25519 + RFC 8785 JCS |
| 인증서 검증 | 고정 조직 루트, 전용 EKU, Asset SAN, 유효기간·24시간 이내 폐기 상태 |
| Package 결합 | Organization·Asset·Job·Manifest·nonce·실행·ZIP hash 12개 필드 |
| 재전송 방지 | 두 Profile이 공유하는 Organization·Asset·Job·nonce 원자 commit |
| 실제 개인키·인증서 | 저장하지 않음, 시험 중 메모리에서만 임시 생성 |
| 실제 원본 증적 | 저장하지 않음 |
| 운영 업로드 POST | 비활성 |
| 공식 Finding | 생성하지 않음 |
| 다음 단계 | `IMP-034` Windows native build |

쉽게 말하면 인터넷에 연결되지 않은 PC가 만든 점검 묶음을 USB 같은 별도 경로로 옮겨도, 서버가 “누가 만들었는지, 어느 PC와 작업의 자료인지, 중간에 바뀌지 않았는지, 이미 접수한 자료인지”를 확인하는 경계다.

## 2. 두 방식의 차이

### OFFLINE-SIGNED

조직이 발급한 장치 인증서의 내보낼 수 없는 개인키로 Package payload에 서명한다. 서버는 다음을 모두 확인해야 접수한다.

1. 인증서가 서버에 고정된 조직 루트에서 직접 발급됐는가
2. 오프라인 Package 서명 전용 EKU `1.3.6.1.4.1.55555.1.1`가 있는가
3. 인증서 조직과 Asset SAN이 payload의 Organization·Asset과 같은가
4. 인증서가 유효하고 폐기되지 않았는가
5. Ed25519 서명과 canonical payload hash가 맞는가
6. payload 12개 필드가 Descriptor·Manifest·ZIP과 정확히 같은가

성공 신뢰도는 `MEDIUM`이다. Collector EXE의 Authenticode 배포 서명과 Package 데이터 서명은 목적이 다르며 서로 대신하지 않는다.

### OFFLINE-USER-SUBMITTED

로그인한 사용자가 Web에서 Package를 올리는 방식이다. 활성 세션, CSRF와 해당 Asset·Job 권한을 확인한다. 그러나 이 정보는 “누가 올렸는가”만 증명하고 “어느 장치가 만들었는가”는 증명하지 못하므로 신뢰도는 항상 `LOW`다. 이 방식만으로 운영 공식 PASS를 자동 생성하지 않는다.

## 3. 재전송 방지

재전송 키는 제출 방식과 무관하게 다음 네 값이다.

```text
organization_id + asset_id + job_id + nonce
```

따라서 서명 방식으로 한 번 접수한 Package를 사용자 제출 방식으로 바꿔 다시 보내도 `OFFLINE_NONCE_REPLAYED`로 거부한다. 전체 Package Gate가 성공하기 전에는 사용 완료로 처리하지 않는다.

## 4. 자동 차단 시험

| 시험 | 기대 결과 |
|---|---|
| 정상 조직 인증서·서명 | `MEDIUM` 접수 |
| 서명 1byte 변조 | `OFFLINE_SIGNATURE_INVALID` |
| 전용 EKU 없음 | `OFFLINE_CERTIFICATE_WRONG_EKU` |
| 다른 Asset 인증서 | `OFFLINE_CERTIFICATE_SUBJECT_MISMATCH` |
| 고정되지 않은 루트 | `OFFLINE_CERTIFICATE_UNTRUSTED` |
| 폐기된 인증서 | `OFFLINE_CERTIFICATE_REVOKED` |
| 폐기 상태 확인 불가 | `OFFLINE_REVOCATION_UNAVAILABLE` |
| 폐기 확인 자료가 24시간보다 오래됨 | `OFFLINE_REVOCATION_UNAVAILABLE` |
| 로그인 없음 | `OFFLINE_USER_AUTH_REQUIRED` |
| CSRF 확인 없음 | `OFFLINE_CSRF_REQUIRED` |
| Asset 권한 없음 | `OFFLINE_USER_SCOPE_MISMATCH` |
| Profile을 바꾼 nonce 재전송 | `OFFLINE_NONCE_REPLAYED` |

## 5. 직접 재검증

프로젝트 루트에서 실행한다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\verify-imp033-offline-submission.ps1
```

이 스크립트는 Docker 개발 도구 이미지에서 합성 ZIP과 임시 X.509 인증서를 만들고 8개 인수 check를 수행한다. 개인키, 인증서, 원본 증적은 결과 JSON에 넣지 않는다.

전체 검증은 다음과 같다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\dev.ps1 -Action All
```

## 6. 화면과 API

- DEV 화면: `/ui/offline-submission`
- DEV 읽기 전용 API: `/api/v1/demo/offline-submission`
- 운영 업로드 POST: 없음
- DEV flag가 꺼진 환경: 두 GET 경로 모두 404

화면은 비식별 합성 인수 결과만 보여준다. 실제 조직 인증서 발급, 인증 세션·Asset RBAC, PostgreSQL 원자 replay 저장과 운영 감사 Event가 연결되기 전에는 실제 업로드 창구를 열지 않는다.

현재 Codex 앱 세션에는 연결 가능한 앱 내 브라우저가 없어 screenshot 기반 시각 검사는 수행하지 못했다. 대신 Jinja 렌더링 문구·DEV 404·민감정보 비노출 단위시험과 실제 Gateway HTTP 200, 읽기 API PASS, POST 405를 확인했다.

## 7. 보안 경계

- 공유 secret 또는 개인키를 Collector EXE, Package, 로그, 보고서에 포함하지 않는다.
- 조직 루트는 host trust store 전체가 아니라 명시적으로 고정한 trust store만 사용한다.
- self-signed 장치 인증서는 조직 소속 증명이 아니므로 허용하지 않는다.
- 폐기 상태가 확인되지 않으면 성공으로 간주하지 않는다.
- 폐기 확인 snapshot은 접수 시각 기준 24시간 이내여야 한다.
- 오류에는 안정적인 코드만 제공하고 인증서 DER, 서명 원문, 증적 원문을 노출하지 않는다.
- 접수 성공과 공식 Finding 생성을 분리한다.
- DRAFT Audit Pack을 운영 APPROVED로 변경하지 않는다.

## 8. 보류 범위

- 실제 조직 CA·장치 인증서 발급과 TPM/Windows CNG non-exportable key
- PostgreSQL replay·receipt 원자 저장 migration
- 실제 로그인 session·CSRF·Asset RBAC가 있는 업로드 POST
- HTTPS canonical hostname, Gateway 크기·속도 제한과 감사 Event
- AIStor quarantine·ClamAV 실제 연결
- Windows native build, SBOM, 취약점 검사와 Authenticode (`IMP-034~035`)
- 운영 APPROVED Audit Pack과 공식 Finding
