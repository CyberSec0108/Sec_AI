## 1. 구현 범위

고정 allowlist의 PC-07 합성 Package 세 건을 다음 실제 application 경로로 연결했다.

```text
detached descriptor + payload.zip
→ FullPackageValidator
→ EvidenceNormalizer
→ PC-07 RuleRegistry
→ FindingBuilder
→ append_or_get_finding
→ finding_versions + finding_current
→ 동일 service 기반 HTML UI / JSON API
```

실제 파일 경로나 임의 Package를 입력받지 않으며 DEV case는 `pc07-pass`, `pc07-fail-fat32`, `pc07-error-collection` 세 개뿐이다. Pack `0.1.0`은 계속 `DRAFT`이고 builder의 명시적 DEV opt-in으로만 실행된다.

## 2. 결과와 멱등성

| case | Finding status | result code | 최초 실행 | 동일 입력 재실행 |
|---|---|---|---|---|
| `pc07-pass` | `PASS` | `ALL_EVALUATED_VOLUMES_NTFS` | `CREATE` | `RETURN_EXISTING` |
| `pc07-fail-fat32` | `FAIL` | `NON_NTFS_VOLUME_FOUND` | `CREATE` | 기존 row 반환 |
| `pc07-error-collection` | `ERROR` | `VOLUME_COLLECTION_FAILED` | `CREATE` | 기존 row 반환 |

실DB에는 Finding 세 건만 존재하며 PASS case replay 뒤에도 row 수는 3이다. pure canonical hash 계약과 PostgreSQL named unique constraint를 같은 application 경로에서 확인했다.

## 3. Web·포트·보안 경계

- Gateway의 유일한 host publish는 `127.0.0.1:18480 → container 8080`이다.
- 실제 Docker·Windows listener에서 사용 중인 `8080`, `18000`, `18080`과 well-known port를 피해 `18x8x` DEV 규칙으로 `18480`을 선택했다.
- `18443`은 향후 DEV TLS용 예약 번호일 뿐 현재 listener를 열지 않는다.
- PostgreSQL `5432`, Redis `6379`, AIStor `9000`, ClamAV `3310`은 internal network에만 있고 host에 publish하지 않는다.
- DEV UI/API는 `SECAI_DEV_DEMO_ENABLED=true`일 때만 존재하며 비활성 환경에서는 `404`다.
- 상태 변경 요청은 secret file 기반 CSRF token과 same-origin 검사를 통과해야 한다.
- Gateway는 CSP, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`를 중복 없이 반환한다.
- 인증·RBAC이 연결된 운영 업무 UI가 아니므로 loopback 밖으로 노출하지 않는다.

## 4. PostgreSQL 역할 분리

`database/migrate.py`는 owner/migrator `secai_app`으로 migration을 적용하고 별도 `secai_runtime` LOGIN role의 비밀번호를 secret file로 생성·회전한다. API·Worker는 runtime role만 사용한다.

runtime grant:

- `organizations`, `assets`, `audit_jobs`, `finding_versions`: `SELECT`, `INSERT`
- `finding_current`: `SELECT`, `INSERT`, `UPDATE`
- DDL, `finding_versions` UPDATE·DELETE: 미허용

실DB 검증은 `current_user=secai_runtime`과 DDL·Finding UPDATE·DELETE의 `InsufficientPrivilege`를 확인했다. append-only trigger는 migrator role로 별도 재검증했다.

역할 분리 후 Compose 동기화 점검에서 Scheduler의 DB 환경은 runtime role인데 secret mount만 migrator 비밀번호를 가리키는 불일치도 발견했다. 아직 Scheduler가 DB task를 실행하지 않아 런타임 장애로 나타나지는 않았으며, `postgres_runtime_password` mount로 수정해 API·Worker·Scheduler의 application credential 경계를 통일했다.

## 5. 추가 발견과 반영

Probe 수집 실패 record가 정상 수집 payload를 갖지 않을 때 기존 Normalizer가 volume `subject_key`를 잃어 Rule Registry의 ERROR Finding 생성까지 진행하지 못하는 계약 gap을 발견했다.

수집 실패 자체는 `FAIL` 값으로 바꾸지 않고, allowlisted `normalized_candidate.volume_id`만 subject 식별자로 보존하도록 수정했다. 그 결과 원시 오류 의미를 유지하면서 `VOLUME_COLLECTION_FAILED` ERROR Finding의 canonical input/output hash가 안정적으로 생성된다.

## 7. 다음 단계
