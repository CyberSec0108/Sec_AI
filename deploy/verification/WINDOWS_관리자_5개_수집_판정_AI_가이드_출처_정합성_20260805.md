## 1. 실제 호스트 수집 결과

PC-01~18은 일반 권한 15개와 명시적으로 승인한 관리자 권한 5개를 합쳐
20개 native Probe를 모두 수집했다. 관리자 권한이 필요한 항목은 다음과 같다.

| Control | Probe | 확인 자료 | 실제 수집 상태 |
|---|---|---|---|
| PC-02 | `win.security.password-policy` | Windows 유효 비밀번호 정책 | `COLLECTED` |
| PC-04 | `win.network.smb-shares` | 전체 공유와 접근 권한 요약 | `COLLECTED` |
| PC-06 | `win.software.messengers` | 전체 사용자 범위 메신저 catalog 일치 결과 | `COLLECTED` |
| PC-08 | `win.boot.entries` | `winload` 기반 부팅 가능한 OS loader 수 | `COLLECTED` |
| PC-10 | `win.update.compliance` | 성공한 업데이트 이력·자동 업데이트·재시작 대기 | `COLLECTED` |

관리자 수집 영수증은
[`runtime/imp037-administrator-evidence.json`](../../runtime/imp037-administrator-evidence.json)에
비식별 hash와 상태만 남긴다. 다섯 행 모두 `error_code=NONE`,
`raw_evidence_available=false`이며 `settings_diff_count=0`이다. 일반·관리자 전체에서
권한 부족, 미지원, 조회 실패는 각각 0건이다.

`COLLECTED`는 자료를 정상적으로 읽었다는 뜻이며 보안 설정이 양호하다는 뜻은 아니다.
각 항목의 `PASS`·`FAIL`·`REVIEW`·`ERROR`는 수집 상태와 분리해 선택된 기준으로
계산한다.

최종 `build-20260805T110253Z` EXE를 기본 기준으로 다시 실행한 실제 DRAFT 판정은
다음과 같다.

| Control | 수집 | 오류 코드 | DRAFT 판정 |
|---|---|---|---|
| PC-02 | `COLLECTED` | `NONE` | `FAIL` |
| PC-04 | `COLLECTED` | `NONE` | `FAIL` |
| PC-06 | `COLLECTED` | `NONE` | `FAIL` |
| PC-08 | `COLLECTED` | `NONE` | `FAIL` |
| PC-10 | `COLLECTED` | `NONE` | `PASS` |

따라서 다섯 항목 모두 수집 실패나 기준 부족 `REVIEW`가 아니라 실제 확인값과
기본 기준으로 결정론적 판정을 마쳤다. `FAIL`은 수집 오류가 아니며 현재 시험 PC가
해당 DRAFT 기준을 충족하지 않았다는 뜻이다.

## 2. DRAFT 판정과 PC-05 기본 범위

관리자 다섯 항목은 실제 자료를 다음 기준 입력으로 변환한다.

- PC-02: 최소 비밀번호 길이, 복잡성 사용, 비밀번호 필수 여부
- PC-04: 승인된 공유 식별자의 비공개 hash, 기본 관리자 공유와 광범위 쓰기 권한
- PC-06: 고정 메신저 catalog의 설치·실행 여부와 승인 제품 목록
- PC-08: 언어 독립적인 `winload.exe`·`winload.efi` loader block 수
- PC-10: 성공한 업데이트 이력, 최근 설치 시각, 자동 업데이트와 재시작 대기

PC-05는 조직 기준이 아직 없어도 점검이 비어 있지 않도록 다음 7개 서비스를
`SecAI Windows 11 최소 기본 점검 범위 (KISA PC-05 보조)`로 사용한다.

```text
FTPSVC
MSFTPSVC
RemoteRegistry
SimpTcp
SNMP
SNMPTRAP
TlntSvr
```

이 목록은 KISA가 제품별 Windows 서비스 이름 7개를 공식 열거했다는 의미가 아니다.
조직·개인 Profile에서 업무상 필요한 범위를 조정할 수 있으며, 선택 이력과 실행 시점
criteria hash를 보존한다. 실제 서비스 record를 평가하므로 개수 0을 하드코딩해
판정하지 않는다.

관련 계약은
[`assessment_criteria.py`](../../src/security_audit/application/assessment_criteria.py),
[`current_host_regression.py`](../../src/security_audit/application/current_host_regression.py)와
[`test_windows_administrator_complete_flow.py`](../../tests/unit/test_windows_administrator_complete_flow.py)에
있다.

## 3. AI 설명 입력 계약

관리자 수집 결과는 PC-02·04·06·08·10의 기존 미수집 설명 입력을 같은 Control의
DRAFT 판정 입력으로 교체한다. 결합 과정은 다음을 보장한다.

- 안정된 `collection_status`를 사용하고 한글 표시 문구를 역해석하지 않는다.
- 수집 오류 개수와 판정 `REVIEW` 개수를 별도 집계한다.
- 다섯 항목의 실제값·기준·판정 이유·수집 한계를 AI 설명 입력에 반영한다.
- 결합 후 `explanation_input_sha256`를 다시 계산한다.
- AI는 규칙 상태를 변경하거나 공식 Finding을 만들 수 없다.

실제 token-stream API를 fake gateway와 정상 인증·MFA·CSRF를 거친 OpenRouter에서
각각 확인했다.

- fake gateway: PC-01~18 입력·canonical hash `18/18`, 설명 완료 `18/18`, 관리자
  PC-02·04·06·08·10 설명 완료 `5/5`, 종합 설명 1건, `FAILED 0`
- 실제 OpenRouter: 입력·canonical hash `18/18`, 관리자 다섯 항목의 설명
  시작·delta·완료 `5/5`. 이후 일반 항목 처리 중 16번째 요청에서
  `INVALID_GATEWAY_RESPONSE`가 발생해 전체는 15개 완료 뒤 안전하게 중단
- 두 경로 모두 비식별·합성 projection만 사용하고 원시 증적·credential·모델 본문을
  검증 로그에 남기지 않았으며 공식 Finding과 규칙 판정은 변경하지 않음

즉 관리자 권한이 필요한 다섯 항목의 수집·DRAFT 판정·AI 설명 연결은 실제 외부 모델
경로까지 `5/5` 완료했다. 다만 실제 OpenRouter 전체 18개 완주는 외부 응답 형식 오류로
완료했다고 표시하지 않으며, 애플리케이션의 18개 전체 계약은 fake gateway 종단시험을
정본으로 삼는다.

## 4. 가이드 챗 인라인·오른쪽 출처 정합성

IMP-053/054 실제 가이드 질의 화면에서 본문이 사용한 인라인 근거와 오른쪽
`답변 근거` 패널이 같은 citation ordinal과 PDF page를 가리키는지 확인해 PASS했다.

- 본문이 `[1]`만 사용하면 패널에도 `[1]`만 표시한다.
- 신규 답변은 실제 참조한 citation만 원래 ordinal로 저장한다. `[1]`, `[3]`처럼
  번호 사이가 비어도 임의로 다시 번호를 붙이지 않는다.
- 기존 대화에 검색 후보가 더 많이 저장돼 있어도 이력 응답과 UI에서 본문 참조만
  표시한다.
- `(1) 일반 점검`, `설정값(3)` 같은 순번·일반 괄호 표현은 출처로 오인하지 않는다.
- 검증된 citation이 없는 스트리밍 중 번호는 클릭 대상으로 만들지 않으며, 완료 후
  동일 citation의 PDF page만 연다.

출처 정합성은 공식 Finding, 검색 순위, Guide Catalog 승인이나 Audit Pack 승인 상태를
변경하지 않는다.
