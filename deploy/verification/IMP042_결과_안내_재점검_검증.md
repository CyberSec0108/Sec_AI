## 1. 구현 범위

- 일반 권한 15개 Probe의 실제 수집 상태를 PC-01~18의 사용자용 결과 18개로 묶는다.
- PC-07은 디스크·파티션·볼륨 세 Probe가 모두 수집되어야 `자료 확인 완료`로 표시한다.
- 관리자 권한이 필요한 PC-02·04·06·08·10은 일반 점검으로 추정하지 않고 `관리자 추가 확인 필요`로 분리한다.
- 일반 Probe 수집 실패·미지원은 보안 취약 `FAIL`로 바꾸지 않고 `추가 확인 필요`로 표시한다.
- 각 Control에 쉬운 제목, KISA 원문 쪽수, 무엇을 확인했는지, 필요한 증적과 안전한 수동 행동을 연결한다.
- `POST /v1/recheck`는 완료 상태에서만 허용하고 같은 `job_id`의 `attempt`를 증가시킨다.
- 재점검 이력은 실행 파일이 열려 있는 동안 추가 방식으로 유지하며 이전 요약을 덮어쓰지 않는다.

## 2. 결과 표현의 안전 경계

`자료 확인 완료`는 Windows 자료를 오류 없이 읽었다는 뜻이며 `보안 양호` 또는 공식 `PASS`가 아니다.

```text
COLLECTED                    → 자료 확인 완료
ERROR / UNSUPPORTED          → 추가 확인 필요
ADMINISTRATOR 전용 Control   → 관리자 추가 확인 필요
```

이 화면은 수집 상태와 다음 행동을 설명한다. 클라이언트 JavaScript가 공식 상태를 계산하지 않으며, 공식 `PASS/FAIL/REVIEW/ERROR/N/A`는 승인된 Audit Pack 규칙 엔진만 만들 수 있다. 현재 Audit Pack은 `DRAFT`이고 이번 단계는 공식 Finding을 생성하지 않는다.

## 3. 사용자 화면

`/ui/results` 한 화면에서 다음 내용을 확인할 수 있다.

1. 18개 전체 요약과 자료 확인·추가 확인·관리자 확인 개수
2. 중요도순 Control 목록과 현재 수집 상태
3. 항목을 한 번 펼쳐 보는 `KISA 근거→확인한 증적→다음 행동`
4. 같은 항목 재점검
5. 직전 점검과 달라진 수집 상태 개수, 과거 실행 요약

결과·행동·근거는 첫 화면에서 결과 화면으로 이동한 뒤 Control 상세를 한 번 펼치면 확인되므로 3번 이내 이동 기준을 만족한다.

## 4. 재점검·이력 계약

```text
COMPLETED
  └─ POST /v1/recheck
       → RUNNING
       → COMPLETED (같은 job_id, attempt + 1, sequence + 1)
```

- 완료 전 재점검은 HTTP 409로 거부한다.
- 한 시점의 활성 실행은 계속 최대 1개다.
- 첫 결과와 재점검 결과는 `sequence` 순서로 추가된다.
- 비교 대상은 수집 상태만이며 원본 레지스트리·정책·제품·볼륨 값은 이력에 넣지 않는다.
- 현재 이력은 실행 파일 프로세스의 비식별 메모리 이력이다. 운영 DB 영속 이력과 공식 Finding 버전 관리는 이후 승인 경로의 책임이다.
