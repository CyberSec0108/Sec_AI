# IMP-032 Online 인증 제출 검증

## 1. 완료 범위

| 항목 | 결과 |
|---|---|
| 구현 단계 | `IMP-032` |
| 제출 Profile | `ONLINE-AUTHENTICATED` |
| 자격증명 | 256-bit 이상 opaque random, 기본 60분·최대 120분 |
| 서버 저장 | 자격증명 원문이 아닌 versioned HMAC-SHA256 |
| 사용 범위 | Organization·Asset·Job·Manifest ID/hash·nonce·endpoint·Content-Type·schema·최대 크기 |
| 성공 사용 | 전체 Package Gate 통과 후 1회 |
| 재사용·nonce replay | 원자적 commit에서 거부 |
| 실제 증적 | 저장하지 않음, 비식별 합성 Package만 사용 |
| 운영 HTTP 발급·업로드 | 비활성 |
| 공식 Finding | 생성하지 않음 |
| 다음 단계 | `IMP-033` Offline signed Package |

쉽게 말하면 단기 Job credential은 특정 택배 상자에만 붙일 수 있는 일회용 접수표다. 다른 PC나 다른 작업 상자에 옮겨 붙이거나 이미 접수된 번호를 다시 쓰면 서버가 거부한다.

## 2. 구현 경계

현재 사람 로그인·Job 생성 권한과 Asset RBAC가 아직 구현되지 않았다. 따라서 IMP-032는 다음 경계를 선택한다.

- core credential service와 전체 Package 검증·원자적 commit을 구현한다.
- 비식별 합성 ZIP을 사용해 성공 제출을 자동시험한다.
- DEV 화면에는 비밀값 없는 인수 상태만 표시한다.
- 익명 사용자가 credential을 발급받거나 실제 PC 자료를 보내는 POST endpoint는 열지 않는다.
- Pilot 전에는 PostgreSQL 원자 저장, HTTPS, 인증된 Job 발급과 감사 Event를 추가해야 한다.

이 제한은 Online 제출을 흉내만 내기 위한 것이 아니라 인증이 없는 업로드 창구를 조기에 노출하지 않기 위한 fail-closed 경계다.

## 3. 자격증명 계약

계약 파일은 `collectors/one_shot/contracts/imp032_online_submission_policy.json`이다.

| 속성 | 구현 |
|---|---|
| random secret | `secrets.token_urlsafe(32)`, 최소 256-bit |
| 형식 | `secai_job_v1.<credential UUID>.<opaque secret>` |
| lookup·검증 | credential ID 조회 후 HMAC-SHA256 constant-time 비교 |
| hash key | 최소 256-bit, key version 기록 |
| TTL | 기본 60분, 0 초과·최대 2시간 |
| 성공 횟수 | 1회 |
| 실패 상한 | 잘못된 secret은 credential별 최대 5회 |
| 취소 | `revoked_at` 이후 거부 |
| 금지 위치 | 명령줄·Package·소스·로그·Browser storage |

자격증명 원문은 `CollectorCredentialRecord`에 존재하지 않는다. 발급 응답에서 한 번만 반환되며 이후 process memory로 전달하는 계약이다.

## 4. 정확한 Scope

다음 열 값이 모두 묶인다.

1. `organization_id`
2. `asset_id`
3. `job_id`
4. `manifest_id`
5. `manifest_sha256`
6. `nonce`
7. `endpoint_id`
8. `content_type`
9. `schema_version`
10. `max_archive_bytes`

인증 성공만으로 다른 Asset 접근을 허용하지 않는다. credential이 가리키는 Manifest와 서버가 신뢰하는 Manifest의 ID·content hash·nonce가 하나라도 다르면 Package Validator를 호출하기 전에 거부한다.

## 5. 제출 순서

```text
Bearer credential 형식·HMAC·만료·취소·사용 여부 확인
→ credential과 trusted Manifest exact binding 확인
→ 기존 FullPackageValidator 실행
   ├─ Schema·Manifest signature
   ├─ ZIP·파일 목록·hash·size
   ├─ Asset·Job·Manifest·evidence scope
   ├─ staging object binding
   ├─ malware scan
   └─ content policy
→ ONLINE-AUTHENTICATED profile 확인
→ credential·nonce 원자적 단일 commit
→ 비밀값 없는 receipt 반환
```

Package 검증에 실패하면 credential을 성공 사용으로 처리하지 않는다. 두 요청이 동시에 검증을 통과해도 원자적 commit에서 한 요청만 성공한다.

## 7. 화면·API

- DEV 화면: `/ui/online-submission`
- DEV 읽기 전용 API: `/api/v1/demo/online-submission`
- 운영 제출 POST endpoint: 없음
- DEV 외 환경: 두 경로 모두 404

화면의 `COMMITTED`는 합성 Package 인수시험 결과이며 실제 고객 증적 접수나 운영 공식 판정을 뜻하지 않는다.

연결 가능한 인앱 브라우저가 없어 screenshot 기반 시각 검사는 수행하지 못했다. 다른 브라우저 도구로 우회하지 않았고 Jinja 렌더링·필수 문구·DEV 외 404 자동시험과 재빌드된 Gateway HTTP 응답으로 확인한다.

## 8. 보안 경계

- credential 오류 응답에 token·scope 원문을 포함하지 않는다.
- secret 비교는 `hmac.compare_digest`를 사용한다.
- HMAC key가 256-bit보다 짧으면 시작을 거부한다.
- Package가 credential 최대 크기를 넘으면 전체 Validator 전에 거부한다.
- credential은 Collector가 PostgreSQL·Redis·AIStor credential을 얻는 수단이 아니다.
- 성공 receipt는 credential 원문을 포함하지 않는다.
- 접수 성공은 공식 Finding 생성과 분리한다.
- DRAFT Audit Pack을 운영 APPROVED로 바꾸지 않는다.

## 10. 보류 범위

- 인증된 사용자의 Job credential 발급 endpoint
- PostgreSQL `collector_credentials`·nonce·receipt 원자 저장 migration
- HTTPS canonical hostname·TLS 인증서와 Gateway upload 제한
- 실제 AIStor quarantine staging과 ClamAV 결과 연결
- credential issue/use/revoke 감사 Event
- 실제 PC-01~18 Package 조립·전송
- 제한 backoff와 실패 후 offline 저장 선택
- Offline signed/user-submitted Package
- Windows PyInstaller·SBOM·악성코드 검사·Authenticode
- 운영 `APPROVED` Audit Pack과 공식 Finding
