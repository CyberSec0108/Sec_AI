| 항목 | 결과 |
|---|---|

## 1. 확인한 원인

- Windows 완성 설명은 `sessionStorage`에만 저장되어 탭·접속 방식에 따라 복원되지 않을 수 있었다.
- Linux 결과 화면은 진입할 때마다 AI stream endpoint를 자동 호출했다. 서버가 cache를 반환하더라도 화면은 생성 상태로 초기화됐다.
- Switch는 완성된 append-only DB cache가 있어도 결과 화면에서 이를 먼저 읽는 API·복원 동작이 없었다.

## 2. 변경 동작

| 플랫폼 | 결과 화면 재진입 | AI 요청 |
|---|---|---|
| Windows | `result_id`, `result_version`, 관리자 결과 상태로 구분한 완성 화면을 브라우저 지속 저장소에서 복원 | 완성 cache가 있으면 호출하지 않음. `AI 설명 재생성`을 누른 경우에만 새 stream 시작 |
| Linux | owner scope의 `V4:SUMMARY`, `V4:U-01~U-67` 68개가 모두 있을 때 한 번의 DB 조회로 복원 | 완성 cache가 있으면 stream을 시작하지 않음. cache가 없을 때만 최초 자동 생성 |
| Switch | owner scope의 `V2:SUMMARY`, `V2:N-01~N-38` 39개가 모두 있을 때 한 번의 DB 조회로 복원 | 완성 cache가 있으면 모델을 호출하지 않음. cache가 없으면 기존처럼 사용자 버튼 승인 뒤 생성 |

완성된 설명 중 하나라도 없으면 완성 cache로 가장하지 않는다. DB cache 조회 자체가 실패하면 자동 모델 호출로 우회하지 않고 사용자에게 다시 확인하도록 안내한다.

## 3. 보안·무결성 경계

- Linux·Switch bulk 조회는 먼저 organization·owner user DB scope를 설정하고 현재 run의 version prefix만 parameter binding으로 조회한다.
- 새 snapshot GET API도 기존 로그인·권한·run 소유권 검사를 그대로 통과해야 한다.
- 실제 HTTP 비로그인 요청은 Linux·Switch 모두 `401`, `Cache-Control: no-store`였다.
- snapshot은 요약과 모든 Control 설명이 비어 있지 않고 각 100KB 이하일 때만 화면에 복원한다.
- 제한형 Markdown renderer와 허용 출처 번호를 그대로 사용하며 raw HTML을 직접 삽입하지 않는다.
- 기존 점검 결과 JSON, 결과 SHA-256, DRAFT 판정과 append-only AI output row를 수정·삭제하지 않는다.
- Windows browser cache key는 exact 결과 ID·version·관리자 결과 상태에 묶여 다른 점검 결과와 섞이지 않는다.

## 5. 사용자 확인 방법

1. Windows, Linux 또는 Switch 점검을 한 번 완료하고 AI 설명을 끝까지 생성한다.
2. 상단 `점검 결과`로 이동했다가 같은 장비 결과를 다시 연다.
3. 기존 점검 결과와 AI 설명이 복원되고 `0 / 전체 항목`부터 자동 생성하지 않는지 확인한다.
4. 명시적으로 `AI 설명 재생성`을 누른 경우에만 AI 영역이 생성 상태로 초기화되는지 확인한다.

Windows cache는 현재 동일 브라우저·동일 origin 기준이다. Linux·Switch cache는 중앙 PostgreSQL의 organization·owner scope에 보존되므로 다른 브라우저에서도 같은 로그인 사용자와 run일 때 복원된다.
