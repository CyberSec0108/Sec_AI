## 2. 생성 옵션

모든 lock은 다음 의미의 옵션을 사용했다.

```text
python -m piptools compile
  --generate-hashes
  --resolver=backtracking
  --strip-extras
  --allow-unsafe
  --no-emit-index-url
  --no-emit-trusted-host
  --newline=lf
```

`--allow-unsafe`는 `pip`와 `setuptools`를 누락하는 의미가 아니라 build tool lock과 PyInstaller lock에서 두 package까지 명시적으로 pin하고 hash를 기록하기 위해 사용했다.

`IMP-008`에서 RFC 8785 JCS의 ECMAScript number serialization과 UTF-16 property ordering을 직접 재구현하지 않고, Apache-2.0의 순수 Python·무의존성 package `rfc8785==0.1.4`를 공통 직접 의존성으로 추가했다. PyPI wheel과 source distribution SHA-256을 모두 lock에 기록하고 RFC 8785 section 3 공식 byte vector로 검증한다. `IMP-028`에서 Windows Collector의 Manifest content hash 계산에 필요해 `collector.in`, `collector.lock`, `collector-build.lock`에도 같은 version과 artifact hash를 추가하고 Windows CPython 3.14.6에서 `--require-hashes` clean install·공식 vector·PyInstaller import를 확인했다.

동일 검증 중 `pip-audit --strict`가 `cryptography 47.0.0`의 `GHSA-537c-gmf6-5ccf`를 탐지했다. 영향 범위를 넓히지 않도록 49 계열로 올리지 않고 공식 수정본 `48.0.1` 이상·49 미만으로 constraint를 변경했으며, Linux lock은 정확히 `48.0.1`로 다시 잠갔다.

`LIN-ONESHOT-09`의 별도 build lock은 2026-08-06 검사에서 당시 `cryptography 48.0.1`에 새로 공개된 advisory가 확인되어 `cryptography>=50,<51`로 분리 갱신하고 정확히 `50.0.0`으로 다시 잠갔다. 이는 Linux 원샷 build 범위만의 변경이며 기존 API·Worker lock을 자동 변경하지 않는다. build image는 multi-stage 최소 image와 CPython 3.14.6 공식 보안 backport 3건으로 보정했고, 최신 Grype DB에서 Critical/High 0을 확인했다. 최신 개발 release manifest는 dependency `PASS`, malware `CLEAN`, OS package `PASS`지만 조직 서명이 없어 `DEV-UNSIGNED`, `download_allowed=false`로 fail-closed 상태다.

API·Worker·DB·Mock Collector source와 Dockerfile은 구현됐다. Windows native PyInstaller EXE build와 clean Windows 11 실행은 `IMP-034`에서 이 잠금파일로 검증한다.

`IMP-046`에서 local password 저장에 사용하는 `argon2-cffi>=25.1,<26`을 `api.in`의 직접 의존성으로 선언하고 `api.lock`과 이를 포함하는 `dev.lock`을 같은 Linux CPython 3.14.6 resolver로 다시 생성했다. 수동으로 version이나 hash를 편집하지 않았으며 `argon2.PasswordHasher` import, API image hash 설치, 비밀번호 정책·검증 회귀를 통과했다.

`IMP-048`에서 별도 Milvus 운영 전략을 폐기하고 PostgreSQL+pgvector로 확정했다. 사용하지 않는 PyMilvus 직접 의존성을 `ingestion.in`에서 제거하고 `ingestion.lock`과 이를 포함하는 `dev.lock`을 같은 Linux CPython 3.14.6 resolver로 다시 생성했다. pgvector는 PostgreSQL 서버 extension이며 Python runtime은 공통 `psycopg`를 통해 제한된 검색 함수를 호출한다.

## 5. 보류 범위

- `remediation.lock`: 자동 조치가 1차 MVP에서 제외되어 미생성
- Embedding/Reranker lock: 모델과 실행 장비 미승인
- vLLM 내부 dependency: 공식 image의 CUDA/Python 조합을 유지하며 이 requirements로 덮어쓰지 않음
- WebAuthn·TOTP·OIDC package: 실제 hostname·TLS·조직 IdP와 Pilot profile이 확정될 때 직접 선언·hash lock·보안시험
- MinIO Python client: MVP S3 API adapter로 유지한다. 서버는 MinIO AIStor Free 최신 Stable 단일 노드로 확정했으며 정확한 image tag와 digest는 컨테이너 잠금표의 `LOCKED-MVP-FREE` 항목을 따른다.

## 6. 변경 절차

1. 직접 의존성 `*.in` 또는 `constraints.in` 수정
2. 동일 Runtime/platform의 dependency-builder에서 lock 재생성
3. 모든 공통 package version 충돌 검사
4. `--require-hashes` clean install과 import/test 실행
5. license와 vulnerability scan 검토
6. lock diff 승인
7. `LOCK-SHA256SUMS.txt` 재생성
8. application image 재build, SBOM·image scan·digest 갱신

lock 파일은 수동으로 version이나 hash를 편집하지 않는다.
