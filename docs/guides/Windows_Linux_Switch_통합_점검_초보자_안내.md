# Windows·Linux·스위치 점검 따라 하기

## 1. 점검 방식 선택

| 상황 | 선택할 기능 |
|---|---|
| 지금 사용 중인 Windows PC | Windows PC 점검 |
| 관리자가 회사 Linux 서버를 등록해 둠 | Linux 중앙 SSH 점검 |
| SSH 정보를 중앙에 등록하지 않고 내 Linux 서버를 점검 | Linux 원샷 자가 점검 |
| 등록된 Aruba AOS-CX 10.13 장비 | 네트워크 스위치 점검 |

사용자는 Windows 세부 버전, Linux 배포판 또는 스위치 NOS를 직접 선택하지 않습니다. 시스템이 안전한 사전 확인값을 Support Catalog와 exact 비교합니다.

## 2. 공통 준비

- 로그인과 두 번째 인증을 완료합니다.
- 점검 중 브라우저를 강제로 닫지 않습니다. 닫아도 완료된 결과는 통합 이력에서 다시 확인할 수 있습니다.
- 관리자 또는 `sudo` 권한이 필요한 경우 화면 설명을 먼저 읽고 별도 동의합니다.
- 점검 프로그램과 중앙 서비스가 표시한 SHA-256이 일치하는지 확인합니다.
- 점검 전에 장비 snapshot 또는 조직의 복구 절차를 준비합니다. Sec_AI가 설정을 바꾸지는 않지만 시험 환경을 되돌리기 위해 필요합니다.

## 3. Windows PC

### 실행

1. 홈에서 `Windows PC 점검`을 선택합니다.
2. Launcher 미연결 안내가 나오면 `점검 프로그램 다운로드`를 엽니다.
3. `Windows 10·11 x64` 카드에서 브라우저 다운로드를 누릅니다.
4. 받은 EXE를 직접 실행합니다.
5. 웹 화면의 연결 상태가 바뀌면 점검을 시작합니다.

기존 EXE가 이미 있으면 다시 받을 필요 없이 실행한 뒤 `연결 다시 확인`을 누를 수 있습니다.

### 권한

- 일반 점검은 가능한 한 일반 사용자 권한으로 실행합니다.
- 관리자 추가 점검 다섯 항목은 일반 결과 이후 별도 동의로 실행합니다.
- 동의가 만료되면 자동으로 관리자 점검을 시작하지 않습니다.

### 결과

PC-01~PC-18 결과, 관리자 추가 확인, PDF와 AI 설명을 확인합니다. Windows 발표 화면과 완성된 AI 설명은 append-only 이력으로 보존됩니다.

## 4. Linux 중앙 SSH 점검

### 관리자가 먼저 할 일

1. `계정정보 → 관리자 운영 기능 → Linux 서버 관리`를 엽니다.
2. 서버 별칭, 승인 IPv4, SSH 포트와 점검 전용 계정을 입력합니다.
3. 시스템이 서버별 Ed25519 키 쌍을 생성합니다.
4. 표시된 공개키만 대상 서버의 점검 계정 `authorized_keys`에 설치합니다.
5. 다른 신뢰 경로로 확인한 Ed25519 host key를 등록합니다.
6. `활성화`를 누릅니다.
7. 시스템이 `/etc/os-release`와 `uname -m`을 읽어 지원 대상을 확인합니다.

개인키는 DB에 저장하지 않으며 현재 개발 환경의 runtime key store를 사용합니다. 운영 전에는 KMS/HSM과 회전·폐기 절차가 필요합니다.

### 사용자가 할 일

1. `리눅스 서버 점검`을 엽니다.
2. 활성 서버의 별칭을 선택합니다.
3. Linux 기준을 확인합니다. 명령·스크립트·정규식은 입력할 수 없습니다.
4. `Linux 서버 자동 확인 및 점검 시작`을 누릅니다.
5. 67개 진행 상태를 확인합니다.

사용자가 SSH 터미널을 열거나 화면을 유지할 필요는 없습니다. 등록·활성화와 네트워크 연결은 관리자가 준비합니다.

## 5. Linux 원샷 자가 점검

### 파일 받기

1. Windows 브라우저에서 `/ui/dev-downloads`를 엽니다.
2. `Linux 서버 x86_64` 카드의 `터미널 코드 만들기`를 누릅니다.
3. 화면이 제시한 tunnel·curl 명령을 그대로 사용합니다. VM에는 브라우저가 없어도 됩니다.
4. 화면의 SHA-256과 `sha256sum` 결과를 비교합니다.

### 실행

```bash
chmod 0755 ./secai-linux-check-x86_64
./secai-linux-check-x86_64 --server-url http://127.0.0.1:18480
```

프로그램이 배포판을 자동 확인하고, 일반 권한 수집 후 필요한 추가 권한 목록을 보여 줍니다. 지원되지 않거나 서로 충돌하는 OS 식별값은 실행을 차단합니다.

### 제출

- 중앙 서비스에 연결되면 일회용 코드로 online 제출합니다.
- 연결되지 않으면 Evidence ZIP과 descriptor JSON을 만든 뒤 웹 자가 점검 화면에서 수동 업로드합니다.
- offline 결과는 장비 신원 보증 수준이 `LOW`입니다.

## 6. Aruba 스위치

### 준비

- 현재 지원 범위는 등록된 Aruba AOS-CX 10.13입니다.
- HTTPS 인증서 지문이 등록값과 같아야 합니다.
- Adapter는 허용된 REST GET 경로 18개만 사용하고 CLI 설정 변경을 실행하지 않습니다.

### 실행과 결과

1. `네트워크 스위치 점검`을 엽니다.
2. 등록 장비를 확인하고 점검을 시작합니다.
3. N-01~N-38 결과와 실제 확인값을 봅니다.
4. 필요하면 사용자용 PDF를 내려받습니다. 기술 검증용 PDF는 별도 권한이 있어야 합니다.
5. AI 설명은 사용자가 버튼을 눌러 승인한 뒤에만 시작합니다.

`REVIEW`는 수집 실패와 같지 않습니다. 조직 정책이나 외부 장비 자료가 필요한 경우입니다. AOS-CX에 적용되지 않는 항목은 `N/A`로 구분합니다.

## 7. 재점검과 이력

설정을 수정한 후에는 기존 결과를 덮어쓰지 않고 새 점검을 실행합니다. 상단 `점검 결과`에서 플랫폼과 날짜로 찾을 수 있으며 현재 로그인 아이디와 조직이 모두 일치하는 결과만 보입니다.

AI 설명도 완료본이 있으면 다시 불러옵니다. 새 설명은 사용자가 재생성 버튼을 눌렀을 때만 만듭니다.

## 8. 실패했을 때

| 증상 | 먼저 확인 |
|---|---|
| Windows Launcher 미연결 | EXE 직접 실행, 연결 다시 확인, 동의 만료 여부 |
| Linux 서버가 목록에 없음 | 관리자가 등록·공개키 설치·host key 확인·활성화를 완료했는지 |
| Linux 자동 식별 차단 | `/etc/os-release`, CPU x86_64, exact 지원 Catalog 일치 여부 |
| Linux 권한 부족 | 점검 계정의 읽기 권한과 추가 `sudo` 동의 범위 |
| Switch 인증 실패 | 인증서 지문, REST 사용자 권한, 관리망 연결 |
| AI 설명 실패 | 점검 결과는 유지됨. 모델 연결 상태를 확인하고 사용자가 재시도 |

현재 상태와 남은 운영 Gate는 [`../../구현_현황.md`](../../구현_현황.md)를 확인합니다.
