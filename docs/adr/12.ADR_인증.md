## 1. 결정

Sec_AI MVP는 외부 Identity Provider 없이 재현할 수 있는 **로컬 named account 인증**으로 시작한다. 사람 계정은 PostgreSQL에 저장한다. `DEV-LOCAL`에서는 누구나 즉시 활성 계정을 만드는 공개 회원가입을 금지하되, 로그인 전 계정 생성 요청을 `PENDING_APPROVAL`로 접수하고 관리자가 승인한 뒤에만 `ACTIVE`와 기본 `USER` 역할을 부여할 수 있다.

사람 인증의 기본 구조는 다음과 같이 확정한다.

```text
개인별 local account
→ Argon2id password 검증
→ MFA(WebAuthn 우선, TOTP 제한 허용)
→ server-side opaque session 발급
→ PostgreSQL session 정본
→ 매 요청 account·credential version·RBAC scope 재검사
→ 고위험 action은 최근 WebAuthn step-up + 업무 승인 동시 요구
```

| 결정 항목 | 확정안 |
|---|---|
| MVP 사람 identity | PostgreSQL local named account, shared account·공개 가입 금지 |
| 목표 assurance | AAL2 기술요건에 맞춘 MFA 지향. NIST 인증 획득을 주장하지 않음 |
| Password | Argon2id, 9~128자, 문자·숫자·ASCII 특수문자 조합, blocklist, 30일 변경 |
| 일반 MFA | WebAuthn 또는 TOTP |
| Privileged MFA | `SECURITY_OFFICER`, `APPROVER`, `ADMIN`은 WebAuthn 등록 필수 |
| 고위험 step-up | 최근 10분 이내 WebAuthn user verification |
| Browser session | 256-bit 이상 opaque ID를 `__Host-secai_session` cookie로 전달 |
| Session 정본 | PostgreSQL. Redis·JWT·Browser storage를 정본으로 사용하지 않음 |
| CSRF | session-bound synchronizer token + Origin/Referer + Fetch Metadata |
| 조직 인증 전환 | 정식 운영은 조직 OIDC를 우선 검토. Authorization Code + PKCE 사용 |
| 사람 API token | MVP에서 발급하지 않음 |
| Collector | 사람 session과 분리된 단기 Job·Asset 범위 credential 또는 인증 사용자 offline upload |
| Service identity | 사람 계정과 분리된 workload credential·DB role·network policy |

브라우저에는 JWT access token·refresh token을 저장하지 않는다. Cookie에는 사용자 ID, 역할, 조직, 이메일이나 JWT를 넣지 않고 무작위 session ID만 넣는다. Session이 탈취·폐기됐는지 즉시 판단하고 역할 변경을 반영하기 위해 PostgreSQL을 session 정본으로 사용한다.

MVP의 로컬 인증은 조직 표준 인증을 대체하는 장기 확정안이 아니다. Pilot 결과와 조직 IdP 가용성을 확인한 뒤 정식 운영에서는 OIDC federation을 우선 적용하되, Sec_AI의 로컬 session·RBAC·step-up 정책은 계속 최종 접근 결정을 내린다.

## 2. 적용 범위와 제외 범위

### 2.1 적용 범위

- `USER`, `SECURITY_OFFICER`, `APPROVER`, `ADMIN` 사람 계정
- 로그인·로그아웃·session 생성·회수·만료
- Password·WebAuthn·TOTP·recovery code 수명주기
- 계정 초대·활성화·잠금·비활성화·복구
- full page, HTMX fragment, JSON API, upload, download와 SSE의 session 인증
- state-changing 요청의 CSRF 방어
- 고위험 operation의 step-up authentication
- Collector 온라인 Job credential과 offline 사용자 제출 귀속
- service identity와 사람 인증의 분리
- 향후 조직 OIDC 연결 요구사항
- 인증·session·credential event 감사

### 2.2 제외 범위

- 공개 self-registration과 소셜 로그인
- Browser용 JWT access/refresh token
- 일반 사용자용 Personal Access Token·API key
- SMS·이메일 OTP를 인증 factor로 사용하는 기능
- 보안 질문·지식 기반 인증
- 얼굴·지문 template를 Sec_AI server가 직접 수집·저장하는 기능
- SAML 직접 구현, LDAP password bind와 Active Directory password 복제
- SCIM 자동 provisioning
- device posture·위험 기반 continuous authentication
- 모바일 app·native client authentication
- 자동 remediation credential

제외 기능이 필요해지면 위협모델, token 수명주기, 회수, key 관리와 감사 기준을 포함한 별도 ADR을 작성한다.

## 3. Assurance Profile

이 ADR은 인증 구현을 다음 profile로 구분한다.

| Profile | 용도 | 허용 인증 | 실제 정보 |
|---|---|---|---|
| `DEV-LOCAL` | 개발·자동화 시험 | local password + test MFA | 합성·비식별 data만 |
| `PILOT-LOCAL-MFA` | Windows 11 MVP Pilot | 모든 사람 계정 MFA, privileged WebAuthn | 승인된 Pilot data |
| `PROD-FEDERATED` | 정식 운영 목표 | 조직 OIDC + IdP MFA + local step-up 정책 | 운영 data |
| `BREAK-GLASS` | IdP·platform 비상복구 | offline 관리 authenticator + 2인 승인 | 제한된 비상 operation |

`DEV-LOCAL`에서 MFA를 끄는 설정은 production image/config에 존재하면 안 된다. 시험 자동화를 위한 test authenticator는 개발용 key와 별도 database에서만 사용하고 Pilot 배포 Gate에서 탐지·차단한다.

Sec_AI는 NIST SP 800-63B의 AAL2 요구사항을 보안 설계 기준으로 참고하지만, identity proofing·운영·조직 정책 전체를 평가하지 않은 상태에서 “AAL2 인증 완료” 또는 “NIST 인증”이라고 표시하지 않는다.

## 4. 사람 계정 모델

### 4.1 Identity 원칙

- 모든 사람은 개인별 named account를 사용한다.
- 공유 `admin`, `security`, `approver` 계정을 일상 운영에 사용하지 않는다.
- immutable 내부 `user_id`를 정본 identity로 사용한다.
- username과 email은 변경 가능한 attribute이며 authorization foreign key로 사용하지 않는다.
- username은 Unicode NFC 정규화와 승인된 case-folding 규칙으로 canonicalize하고 unique constraint를 둔다.
- email만 일치한다는 이유로 local account와 OIDC subject를 자동 병합하지 않는다.
- 인증 성공은 활성 role·organization·asset 권한을 의미하지 않는다. RBAC가 별도로 허용해야 한다.
- 사람 account와 service identity는 table, credential type, login endpoint와 cookie flow를 분리한다.

### 4.2 Account 상태

| 상태 | 로그인 | 의미 |
|---|---:|---|
| `INVITED` | 불가 | 1회 activation 대기 |
| `PENDING_APPROVAL` | 불가 | DEV-LOCAL 계정 생성 요청의 관리자 승인 대기. 역할·session 없음 |
| `ENROLLING` | 제한 | Password·MFA 등록만 가능 |
| `ACTIVE` | 가능 | 정상 계정 |
| `TEMP_LOCKED` | 불가 | 실패 횟수에 따른 시한부 잠금 |
| `RECOVERY_PENDING` | 제한 | 승인된 복구 절차만 가능 |
| `DISABLED` | 불가 | 관리자 또는 인사·보안 사유로 비활성 |
| `DELETED` | 불가 | 식별정보 최소화 후 tombstone 보존 |

Role assignment는 account 상태와 별도 versioned table에서 관리한다. `ACTIVE`라도 role·scope가 없으면 업무 resource에 접근할 수 없다.

### 4.3 계정 발급

```text
ADMIN이 named user metadata 생성
→ INVITED 상태
→ 단기·1회 activation secret을 별도 안전한 channel로 전달
→ 사용자가 Password 설정
→ WebAuthn 또는 TOTP 등록
→ recovery code 발급·확인
→ 기본 USER 또는 승인된 privileged role assignment 확인
→ 기존 pre-auth session 폐기
→ 새 authenticated session 발급
→ 독립 notification·감사 event
```

- 공개 가입 endpoint를 만들지 않는다.
- Activation secret은 최소 256-bit random value, 24시간 이내 만료, 1회 사용으로 한다.
- DB에는 activation secret 원문 대신 keyed hash와 expiry·used_at을 저장한다.
- 임시 password를 이메일·메신저로 전송하지 않는다.
- 계정 존재 여부를 activation·recovery 응답에서 노출하지 않는다.
- privileged role은 `11.RBAC_권한_매트릭스.md`의 별도 요청·승인·실행 절차를 거친다.

#### 4.3.1 현재 DEV-LOCAL 계정 생성 요청

현재 개발 UI는 다음 제한된 흐름을 구현한다.

```text
로그인 화면의 계정 생성 요청
→ username·표시 이름·사용자가 정한 password 검증
→ Argon2id hash만 저장한 PENDING_APPROVAL 계정 생성
→ role·session·자산 권한 0
→ ADMIN 계정 관리 화면에서 같은 organization 요청만 승인 또는 반려
→ 승인 시 ACTIVE + 기본 USER 역할
→ 사용자가 자신의 password와 개발용 두 번째 인증으로 로그인
```

- 요청 성공 여부로 기존 username의 존재를 과도하게 노출하지 않고 입력을 정규화·검증한다.
- 관리자는 password 원문·hash를 보거나 재설정값을 직접 지정하지 않는다.
- 관리자는 자신의 계정을 비활성화할 수 없다.
- password 변경 성공 시 `credential_version`을 증가시키고 기존 session을 모두 폐기한다.
- DEV-LOCAL 6자리 인증 코드 재발급은 ADMIN만 실행하고, 원문은 재발급 결과 화면에서 한 번만 복사할 수 있다. DB에는 keyed digest와 만료 시각만 저장하며 재발급 시 기존 session을 폐기한다.
- 관리자가 개발용 인증 코드 원문을 한 번 볼 수 있는 현재 구조는 Pilot MFA가 아니다. `PILOT-LOCAL-MFA`에서는 사용자가 최초 접속 과정에서 자신의 WebAuthn 또는 TOTP를 직접 등록하고 관리자가 인증 비밀을 알 수 없게 한다.
- 이 흐름은 `DEV-LOCAL` 합성·비식별 환경에만 허용한다. 외부 공개 가입, 이메일/SMS OTP, 관리자 발급 임시 password와 운영 배포를 허용하지 않는다.

### 4.4 Bootstrap administrator

최초 관리자 생성은 일반 Web endpoint가 아니라 배포 시 명시적으로 실행하는 one-shot bootstrap command로 한다.

- bootstrap은 사용자 ID·1회 activation secret만 만들고 고정 password를 image/config에 넣지 않는다.
- 최초 로그인에서 Password와 WebAuthn을 등록하기 전에는 다른 관리 operation을 금지한다.
- 최초 관리자 생성 성공 뒤 bootstrap 기능과 secret을 폐기한다.
- 재실행은 empty database 또는 승인된 recovery mode에서만 허용한다.
- bootstrap event, 실행자, 배포 version과 결과를 외부 audit sink에 남긴다.
- 일상적인 shared root account로 전환하지 않는다.

## 5. Password 정책

### 5.1 사용자 정책

| 항목 | 초기값 |
|---|---|
| 최소 길이 | 9 Unicode code point |
| 최대 길이 | 128 Unicode code point이면서 UTF-8 512 byte 이하 |
| 정규화 | hashing 전에 Unicode NFC |
| 허용 문자 | 공백 포함 printable Unicode. control·null은 거부 |
| 조합 규칙 | Unicode 문자 1개 이상 + ASCII 숫자 1개 이상 + 허용 ASCII 특수문자 1개 이상. 대·소문자는 별도 강제하지 않음 |
| 허용 특수문자 | ASCII punctuation 32자(`!`부터 `~` 범위의 문장부호; 아래 목록 참조) |
| Blocklist | 흔한·유출·`SecAI` 등 서비스명·username 파생 password 차단 |
| 정기 변경 | 마지막 변경 후 30일에 강제 |
| 변경 사전 알림 | 만료 7일·3일·1일 전 |
| 재사용 제한 | 최근 5개 password 금지 |
| 최소 사용 기간 | 1일. 관리자 강제 초기화·침해 대응은 예외 |
| 강제 변경 | compromise 징후, recovery, 관리자 발급 초기 credential |
| Password manager | autofill·붙여넣기 허용 |
| Password hint·보안 질문 | 금지 |

허용 ASCII 특수문자는 다음과 같다.

```text
! " # $ % & ' ( ) * + , - . / : ; < = > ? @ [ \ ] ^ _ ` { | } ~
```

이 9자·조합·30일 정책은 조직이 승인한 운영 기준이다. 최신 NIST 지침은 MFA 사용 시 최소 8자를 허용하지만 조합 강제와 증거 없는 정기 변경은 권고하지 않는다. Sec_AI는 모든 Pilot 사람 계정의 MFA, blocklist, Argon2id, 최근 5개 재사용 금지, 최소 사용 기간으로 위험을 보완한다. 따라서 이 정책을 NIST 자체 권고라고 표현하지 않으며, 운영 결과에서 예측 가능한 변형 password나 문의·잠금이 늘면 보안 책임자가 재검토한다. OIDC 사용자의 조직 password는 Sec_AI가 아니라 해당 IdP 정책을 따른다.

Password blocklist는 승인된 offline snapshot으로 운영한다. Password 또는 password hash prefix를 외부 Internet API로 전송하지 않는다. Snapshot ID·version·hash와 갱신일을 기록하고, 지나치게 큰 목록보다 로그인 throttling·MFA와 함께 운영한다.

Password 변경 시:

- 현재 password와 MFA 또는 WebAuthn step-up을 요구한다.
- 새 password가 현재 password 및 최근 5개 password와 다른지 확인한다.
- 일반 변경은 마지막 변경 후 1일이 지나야 허용해 짧은 시간에 history를 소진하는 우회를 막는다. 침해 대응·관리자 강제 초기화는 사유와 승인 기록을 남기고 예외 처리한다.
- 만료 7일·3일·1일 전에 로그인 화면과 승인된 notification channel로 알린다.
- 30일이 지나면 로그인 후 password 변경 화면 이외의 업무 접근을 차단한다. 변경 성공 뒤 MFA를 다시 검증하고 모든 기존 session을 폐기한다.
- 성공 즉시 `credential_version`을 증가시키고 다른 모든 session·recovery transaction을 폐기한다.
- password 원문을 log, trace, analytics, exception과 audit event에 남기지 않는다.

### 5.2 저장

Password는 복호화 가능한 암호문이나 SHA-256 단독 hash로 저장하지 않는다. **Argon2id** encoded hash와 algorithm·parameter version을 저장한다.

초기 parameter target:

```text
algorithm = Argon2id
memory_cost = 65536 KiB
time_cost = 3
parallelism = 1
salt = library-generated unique random salt
```

- OWASP 최소선인 19 MiB, iteration 2, parallelism 1보다 낮추지 않는다.
- 운영 CPU·memory와 동시 login 부하를 benchmark해 정상 검증 latency가 대략 250~750 ms 범위가 되도록 상향 조정한다.
- parameter 변경은 새 `password_scheme_version`으로 관리한다.
- login 성공 시 기존 parameter가 낮으면 새 parameter로 rehash한다.
- Argon2 실행 concurrency를 제한해 공격자가 memory exhaustion을 유발하지 못하게 한다.
- 존재하지 않는 username에도 사전 생성한 dummy Argon2 hash를 검증해 큰 timing 차이를 줄인다.
- `argon2-cffi`를 인증 code가 직접 사용하는 top-level dependency로 `requirements/api.in`에 명시한다. MinIO의 transitive dependency에 의존하지 않는다.

DB와 별도 secret으로 keyed post-hash를 추가하는 pepper는 HSM·Secret Manager, key rotation과 재복구 절차가 준비된 뒤 활성화한다. MVP에서 관리되지 않는 Compose environment 값을 “pepper”라고 부르며 보안을 과장하지 않는다.

## 6. MFA 정책

### 6.1 역할별 요구

| 역할 | 최초 로그인 | 정상 로그인 | 고위험 step-up |
|---|---|---|---|
| `USER` | Password + WebAuthn 또는 TOTP 등록 | Password + 등록 MFA | 해당 action이 있으면 WebAuthn 우선 |
| `SECURITY_OFFICER` | Password + WebAuthn 필수 | Password + WebAuthn | WebAuthn `userVerification=required` |
| `APPROVER` | Password + WebAuthn 필수 | Password + WebAuthn | WebAuthn `userVerification=required` |
| `ADMIN` | Password + WebAuthn 필수 | Password + WebAuthn | WebAuthn `userVerification=required` |

한 사용자가 여러 역할을 가지면 가장 강한 요구사항을 적용한다. Privileged role assignment는 WebAuthn credential이 최소 하나 이상 활성 상태가 아니면 활성화할 수 없다. Pilot에서는 privileged 사용자가 두 개의 독립된 WebAuthn authenticator를 등록하도록 권고하고, 하나만 등록했다면 recovery code와 복구 책임자를 확인한다.

### 6.2 WebAuthn

WebAuthn은 phishing-resistant factor와 step-up의 우선 수단이다. MVP에서는 **password를 없애는 passwordless 방식이 아니라 `password + WebAuthn`의 두 번째 인증수단**으로 사용한다. Windows Hello의 PIN·지문·얼굴 또는 승인된 FIDO2 roaming security key를 지원한다.

비유하면 password가 첫 번째 문 열쇠라면 WebAuthn은 특정 Sec_AI 주소에서만 작동하는 두 번째 전자열쇠다. 개인키는 TPM·보안키 같은 authenticator 밖으로 나오지 않고, Server에는 공개키와 credential metadata만 저장된다. Windows Hello PIN·지문·얼굴 원본도 Sec_AI로 전송하거나 저장하지 않는다. RP ID와 실제 site 주소가 묶이므로 가짜 로그인 site가 같은 인증 서명을 재사용하기 어렵다. Privileged 사용자는 Windows Hello와 별도 보관하는 FIDO2 보안키를 각각 등록하는 것을 권장한다.

| 항목 | 기준 |
|---|---|
| RP ID | 배포 전에 확정된 canonical hostname. 사용자 입력 금지 |
| Origin | 승인된 HTTPS origin exact match |
| Challenge | server CSPRNG 32 byte 이상, session·ceremony 결합, 5분 이내, 1회 사용 |
| User verification | privileged 로그인·step-up은 `required` |
| User presence | 항상 검증 |
| Attestation | MVP 기본 `none`; 조직 device assurance 필요 시 별도 정책 |
| Algorithm | 검토된 public-key algorithm allowlist |
| Credential | public key, credential ID, sign counter, transports, created/revoked time 저장 |
| User handle | 무작위·불변 내부 ID. username·email·주민번호 금지 |

Server는 ceremony마다 challenge, RP ID, origin, type, credential ID, signature, user presence와 user verification을 검증한다. Challenge mismatch·만료·재사용은 거부하고 감사한다.

Authenticator sign counter 감소·복제 의심은 위험 event로 기록하고 즉시 factor를 잠그거나 step-up을 추가 요구할 수 있다. 일부 authenticator가 counter를 지원하지 않는다는 이유로 정상 사용자를 무조건 영구 잠금하지 않고 credential 특성과 조직 정책을 반영한다.

Credential 추가·삭제·이름 변경은 최근 WebAuthn step-up을 요구한다. 마지막 usable privileged credential 삭제는 새 credential 등록이나 승인된 recovery 완료 전까지 금지한다.

### 6.3 TOTP

TOTP는 USER의 일반 MFA와 제한된 복구 경로에 사용할 수 있지만 phishing-resistant가 아니며 privileged 고위험 step-up을 충족하지 않는다.

| 항목 | 초기값 |
|---|---|
| Algorithm | HMAC-SHA-256 |
| Digits | 6 |
| Period | 30초 |
| 허용 clock window | 현재 step 전후 1개 |
| Replay | 같은 account·time step의 성공 code 재사용 금지 |
| 실패 제한 | login throttling과 별도 factor limit 적용 |
| Secret 저장 | 별도 application key로 AEAD 암호화, key version 기록 |
| QR/seed 표시 | enrollment 때 한 번만, 인증 page·log·support 화면 재표시 금지 |

TOTP seed는 password처럼 hash만으로 검증할 수 없으므로 복호화 가능한 상태가 필요하다. 암호화 key는 DB, source, image와 분리해 승인된 OpenBao 또는 Vault에서 짧은 수명의 file·memory 형태로 주입한다. Compose environment나 image에 넣지 않는다. Backup·restore·rotation 시험 없이는 운영 활성화하지 않는다.

SMS·email OTP, 단순 push 승인과 보안 질문은 MFA로 채택하지 않는다.

### 6.4 Recovery code

- 10개의 독립된 128-bit 이상 random recovery code를 최초 MFA enrollment 뒤 한 번 표시한다.
- 사용자가 안전한 offline 위치에 저장했음을 확인한다.
- Server는 code 원문이 아니라 salt를 포함한 slow hash를 저장한다.
- 각 code는 1회 사용이며 사용 즉시 폐기한다.
- 한 code 사용 시 사용자에게 독립 notification을 보내고 남은 code 수를 표시한다.
- 전체 code 재발급은 기존 code를 모두 폐기하고 최근 MFA/복구 승인을 요구한다.
- Recovery code만으로 privileged 고위험 action을 수행하지 못한다. factor 재등록과 session 재발급에만 제한한다.

## 7. Login 흐름과 Enumeration 방어

### 7.1 정상 흐름

```text
GET /auth/login
→ anonymous pre-session + login CSRF 발급
→ username·password POST
→ Origin/CSRF·rate limit·account 상태·Argon2 검증
→ pre-auth session ID rotation
→ MFA challenge
→ WebAuthn/TOTP 검증
→ account·credential·role assignment version 재확인
→ pre-auth session 폐기
→ 새 authenticated session + 새 CSRF 발급
→ same-origin allowlist return path로 redirect
```

- Password가 성공했어도 MFA 완료 전에는 업무 endpoint에 접근할 수 없다.
- Pre-auth session은 5분 이내 만료하고 MFA 종류·사용자 ID·시도 횟수 외 업무권한을 갖지 않는다.
- 로그인 전 입력한 return URL은 상대경로 allowlist만 허용한다.
- Authentication 성공과 privilege change 때 session ID를 반드시 회전한다.
- MFA choice 화면에서 등록 factor의 전체 식별정보를 노출하지 않는다.

### 7.2 오류 응답

Username 없음, password 불일치, account 잠금·비활성 상태는 외부에 같은 일반 메시지와 동등한 HTTP 흐름을 사용한다.

```text
로그인 정보가 올바르지 않거나 현재 로그인할 수 없습니다.
```

내부 audit event에는 `UNKNOWN_SUBJECT`, `BAD_PASSWORD`, `FACTOR_FAILED`, `ACCOUNT_DISABLED`, `RATE_LIMITED`처럼 구분된 reason code를 남기되 Browser에는 계정 존재 여부를 노출하지 않는다. 존재하지 않는 계정도 dummy password hash 검증을 수행해 큰 timing 차이를 줄인다.

Recovery 요청도 계정 존재 여부와 관계없이 같은 응답을 반환한다. Username·email enumeration을 가능하게 하는 검색·오류·응답시간 차이를 시험한다.

## 8. Login Throttling과 잠금

Rate limit은 Redis만 믿지 않고 PostgreSQL의 계정별 실패 상태와 Gateway의 IP·전체 service 제한을 결합한다. Redis 장애 시 무제한 로그인을 허용하지 않고 보수적인 local/Gateway 제한 또는 fail-closed 정책을 사용한다.

초기 정책:

| 범위 | 기준 | 처리 |
|---|---|---|
| account | 5회/5분 | 지수형 지연 시작 |
| account | 연속 10회 | 15분 `TEMP_LOCKED` |
| 반복 잠금 | 24시간 3회 | 1시간 잠금 + 보안 alert |
| source IP | 20회/5분 | `429`, Gateway 지연·차단 |
| MFA factor | 5회/5분 | 해당 pre-auth transaction 폐기 |
| Recovery | account·IP별 별도 저빈도 limit | 일반 응답, 운영 alert |
| WebAuthn challenge | 1회·5분 | 재사용·만료 거부 |

- Threshold는 부하시험 뒤 더 엄격하게 조정할 수 있지만 승인 없이 완화하지 않는다.
- 잠금은 영구 수동 잠금이 아니라 시한부이며 공격자가 타인을 쉽게 영구 차단하지 못하게 한다.
- 성공한 전체 MFA login 뒤 연속 실패 counter를 reset한다.
- 관리자 unlock은 Password·MFA를 우회하지 않으며 event를 감사한다.
- CAPTCHA는 폐쇄망·접근성·외부 의존성 때문에 MVP 기본값으로 도입하지 않는다.
- IP는 보조 신호이며 NAT 환경에서 identity를 대신하지 않는다.

## 9. Server-side session

### 9.1 Session secret

- CSPRNG로 32 byte 이상을 생성하고 base64url opaque string으로 전달한다.
- Cookie 원문은 생성 직후 Browser에만 전달한다.
- DB에는 session token 원문 대신 `HMAC-SHA-256(session_index_key, token)`을 저장한다.
- `session_index_key`는 source·DB·image와 분리하고 key version을 기록한다.
- key rotation은 이전 key의 짧은 검증기간을 두거나 모든 session을 명시적으로 폐기한다.
- Client가 Server가 발급하지 않은 session ID를 제시하면 새 session으로 수용하지 않고 거부·감사한다.
- Session ID를 URL, query, form field, localStorage, sessionStorage, HTML, SSE data와 log에 넣지 않는다.

### 9.2 Cookie

```text
Set-Cookie: __Host-secai_session=<opaque>;
            Path=/;
            Secure;
            HttpOnly;
            SameSite=Lax
```

- `Domain` attribute를 설정하지 않는다.
- Cookie expiry는 Server session 만료보다 길지 않게 한다.
- MVP에는 persistent “remember me” cookie를 제공하지 않는다.
- 인증된 page·API·fragment·SSE response는 `Cache-Control: no-store`를 사용한다.
- HTTPS에서 HTTP로 downgrade하지 않는다.
- HSTS는 canonical hostname과 인증서·subdomain 영향 검증 후 Gateway에서 활성화한다.

### 9.3 저장 필드

Session에는 최소 다음 metadata를 저장한다.

| Field | 목적 |
|---|---|
| `session_id_hash` | opaque token lookup |
| `user_id` | named subject |
| `credential_version` | Password·MFA 변경 즉시 무효화 |
| `role_assignment_version` | stale role session 차단 |
| `active_organization_id` | 현재 tenant context |
| `auth_methods` | password, webauthn, totp 등 |
| `auth_strength` | local MFA 또는 federated assurance profile |
| `authenticated_at` | 전체 login 시각 |
| `reauthenticated_at` | 최근 step-up 시각 |
| `created_at`, `last_seen_at` | absolute·idle timeout |
| `expires_at`, `idle_expires_at` | Server-side 만료 |
| `revoked_at`, `revoke_reason` | 회수 추적 |
| `csrf_secret_hash` | CSRF transaction 검증 |
| 안전한 client metadata | IP·UA의 최소화된 위험·감사 정보 |

Role·permission 전체를 Cookie에 넣지 않는다. 권한 검사는 현재 DB assignment와 자원 관계를 사용하고, cache가 있다면 role assignment version으로 즉시 무효화한다.

### 9.4 Timeout

| Session 종류 | Inactivity | Absolute | Step-up freshness |
|---|---:|---:|---:|
| USER-only | 30분 | 8시간 | 10분 |
| SECURITY_OFFICER 포함 | 30분 | 8시간 | 10분 |
| APPROVER 또는 ADMIN 포함 | 15분 | 8시간 | 10분 |
| Pre-auth MFA | 5분 | 5분 | 해당 없음 |
| Recovery | 10분 | 30분 | operation-bound |
| Break-glass | 15분 | 최대 60분 | 매 고위험 action |

- 활동은 Server가 인증·인가를 마친 **사용자의 의미 있는 foreground 요청**일 때만 inactivity timeout을 갱신한다. 예: 화면 이동, 저장, 검색, 명시적 "세션 계속" 요청이다.
- 마우스 이동·키보드 입력 자체는 Server 요청이 아니므로 session을 연장하지 않는다. 단, 그 결과로 사용자가 실제 기능을 요청하면 해당 요청 시각에 갱신된다.
- 성공한 전체 reauthentication만 absolute timeout과 step-up freshness를 갱신할 수 있다.
- 역할이 USER에서 privileged로 바뀌면 기존 session을 폐기하고 새 login을 요구한다.
- Browser heartbeat, SSE heartbeat, HTMX polling, 자동 refresh와 background API 요청은 사용자 활동으로 보지 않는다.
- 만료 5분 전에 경고하고, 사용자가 명시적으로 "세션 계속"을 선택할 때만 inactivity를 갱신한다.
- Absolute 8시간은 활동 여부와 관계없는 상한이다. 계속 사용 중이어도 8시간이 되면 전체 재인증한다.
- Absolute timeout 뒤 IdP session이 살아 있어도 Sec_AI가 요구하는 fresh authentication을 다시 확인한다.

### 9.5 Rotation과 revoke

다음 event에서 session ID를 회전하거나 폐기한다.

| Event | 처리 |
|---|---|
| Password 성공 + MFA 대기 | pre-auth ID rotation |
| MFA 성공 | pre-auth 폐기, 새 authenticated ID |
| Step-up 성공 | session ID rotation + `reauthenticated_at` 갱신 |
| Password·MFA 변경 | 다른 모든 session revoke, 현재도 rotation |
| Role·scope·organization 변경 | 관련 모든 session revoke, 재로그인 |
| Account disable·delete | 모든 session 즉시 revoke |
| Logout | 현재 session revoke + cookie 만료 |
| Logout all | 모든 session revoke + credential event 감사 |
| 의심 token replay | 관련 session revoke + 보안 alert |

Session revoke는 SSE 연결에도 반영한다. SSE 연결 시와 주기적인 authorization check에서 만료·회수·role version을 검사하고 더 이상 유효하지 않으면 연결을 종료한다.

동시 session은 USER 최대 5개, privileged account 최대 3개로 시작한다. 초과 시 가장 오래된 session을 자동 폐기하기보다 사용자에게 현재 session 목록을 보여주고 명시적으로 종료하게 하며, 정책상 필요하면 새 session 생성과 함께 오래된 session을 폐기한다.

## 10. CSRF와 Browser 경계

Cookie 인증을 사용하므로 모든 state-changing 요청은 CSRF 방어를 통과해야 한다.

### 10.1 Synchronizer token

- session마다 CSPRNG 32 byte 이상의 CSRF secret을 생성한다.
- 일반 form은 hidden field, HTMX는 `X-CSRF-Token` header로 전송한다.
- token은 session에 결합하고 다른 session·사용자에서 재사용할 수 없다.
- 로그인, logout, Password·MFA enrollment/recovery도 CSRF를 검증한다.
- session rotation 때 CSRF token도 회전한다.
- CSRF token을 authentication token, CSP nonce, approval token과 혼용하지 않는다.
- 오류 page·log·Referer에 token을 반영하지 않는다.

### 10.2 추가 검사

- `POST`, `PUT`, `PATCH`, `DELETE`는 configured public origin과 `Origin` exact match를 요구한다.
- `Origin`이 없는 승인 Browser flow는 `Referer`의 scheme·host·port exact match를 확인한다.
- 둘 다 없거나 `null`이면 state-changing 요청을 기본 거부한다.
- `Sec-Fetch-Site: cross-site`인 unsafe method를 거부한다.
- Fetch Metadata가 없는 Browser는 CSRF token + Origin/Referer 정책으로 fallback한다.
- SameSite는 defense-in-depth이며 CSRF token을 대체하지 않는다.
- GET, HEAD, OPTIONS와 SSE는 상태를 변경하지 않는다.
- CORS는 기본 비활성·same-origin이고 credential과 wildcard origin을 함께 사용하지 않는다.
- Gateway가 전달하는 `Forwarded`·`X-Forwarded-*`는 신뢰된 proxy IP의 값만 사용한다.

## 11. Step-up authentication

RBAC 승인과 step-up은 서로 다른 통제다. 승인을 받았더라도 실행자 session의 최근 강한 인증이 없으면 operation을 실행하지 않는다.

### 11.1 대상 action

- Password·MFA·recovery address·WebAuthn credential 변경
- privileged role·organization·asset scope assignment 실행
- 계정 disable, session 강제 revoke와 privileged unlock
- 원본 증적 download, 대량 export와 외부 반출
- Organization Policy·Audit Pack 활성화·폐기
- 공식 report 게시
- legal hold 설정·해제, retention 변경과 파기
- backup export·restore
- service credential·signing key rotation
- break-glass 발급·사용
- 기타 RBAC에서 `EXEC` 또는 별도 승인을 요구하는 operation

### 11.2 실행 계약

```text
RBAC permission 확인
∩ exact resource version·hash approval 확인
∩ requester/approver/executor 분리 확인
∩ 최근 10분 WebAuthn user verification 확인
∩ account·role·session 현재 상태 재확인
∩ operation-bound execution grant 확인
= 실행 허용
```

- Step-up challenge는 session, user, action category, target resource hash와 결합한다.
- WebAuthn `userVerification=required`를 사용한다.
- Password만 다시 입력하는 방식은 privileged step-up으로 인정하지 않는다.
- TOTP는 Pilot privileged 고위험 step-up으로 인정하지 않는다.
- Step-up 성공 뒤 session ID를 회전한다.
- 10분이 지나거나 target hash·role·approval이 바뀌면 다시 인증한다.
- 파기·restore·break-glass 등 최고위험 action은 step-up과 별도로 1회 execution grant를 사용한다.

## 12. Account recovery

### 12.1 금지 방식

- security question·생년월일 등 지식 기반 질문
- 관리자에게 현재 password 알려주기
- Password 또는 TOTP seed 이메일 전송
- 이메일 link 하나만으로 privileged 계정 복구
- 기존 MFA 없이 factor를 조용히 교체
- 지원 담당자가 Finding·role을 바꿔 복구를 우회

### 12.2 USER recovery

1. 일반화된 recovery 요청을 생성한다.
2. recovery code + 기존 single factor 또는 승인된 관리 절차로 본인을 확인한다.
3. 10분 recovery session에서 새 Password·MFA를 등록한다.
4. 기존 Password/MFA credential과 모든 session을 revoke한다.
5. `credential_version`을 증가시킨다.
6. 사용자에게 독립 notification과 신고 경로를 제공한다.
7. 전체 event와 실행자를 감사한다.

### 12.3 Privileged recovery

`SECURITY_OFFICER`, `APPROVER`, `ADMIN` 복구는 사용자 단독 recovery code만으로 완료하지 않는다.

```text
본인 또는 보안담당자 recovery 요청
→ 별도 APPROVER가 identity·사유·ticket 확인
→ ADMIN이 one-time recovery transaction 실행
→ 기존 credential·session·미사용 approval 실행권한 폐기
→ 새 Password + WebAuthn 등록
→ role assignment 재확인
→ 독립 notification
→ 24시간 내 사후검토
```

요청자·승인자·실행자는 같은 사람이 될 수 없다. 실제 Pilot·운영 증적에서는 `SECURITY_OFFICER` 요청자, `APPROVER` 승인자, `ADMIN` 실행자를 서로 다른 세 사람으로 지정한다. 합성 data만 쓰는 DEV에서의 역할 겸임 예외는 `11.RBAC_권한_매트릭스.md`의 제한을 따른다.

Secret·복구 책임은 다음과 같이 고정한다.

| 업무 | 책임 역할 |
|---|---|
| 인증 정책 소유 | `SECURITY_OFFICER` |
| secret·key rotation 요청 | `SECURITY_OFFICER` |
| rotation·복구 승인 | `APPROVER` |
| OpenBao/Vault 실행 | `ADMIN` |
| privileged account 복구 요청 확인 | `SECURITY_OFFICER` |
| privileged account 복구 실행 | `ADMIN` |
| 감사 검토 | 위 세 역할의 해당 거래에 참여하지 않은 독립 감사 열람자 |

OpenBao unseal share와 offline 복구 material은 서로 다른 실제 보관자에게 분산한다. 한 사람이 단독으로 privileged account 복구, WebAuthn 초기화, OIDC client secret 변경, break-glass 발급 또는 감사기록 삭제를 완료할 수 없어야 한다. 실제 성명·대체자·연락경로는 배포 전 운영명부에서 확정하고 이 ADR에는 secret 자체를 기록하지 않는다.

### 12.4 Factor 분실·변경 notification

다음 event는 등록된 독립 contact channel 또는 조직 운영 channel로 알린다.

- Password 변경·복구
- WebAuthn/TOTP 추가·삭제
- recovery code 사용·재발급
- privileged role 활성화·회수
- 새 Browser session과 의심 login
- account lock·disable

Notification에는 password, token, recovery code, TOTP seed와 원본 증적을 포함하지 않는다.

## 13. 조직 OIDC 전환

정식 운영에서 조직이 승인된 Identity Provider를 보유하면 `PROD-FEDERATED`를 우선한다. Local account는 일반 사용자의 fallback login으로 자동 전환하지 않는다.

### 13.1 Protocol

- OpenID Connect Authorization Code Flow를 사용한다.
- Confidential web client도 PKCE `S256`을 사용한다.
- exact redirect URI만 등록하고 wildcard·사용자 지정 redirect를 금지한다.
- transaction별 `state`, `nonce`, PKCE verifier를 생성하고 pre-auth session에 결합한다.
- issuer, authorization endpoint, token endpoint와 JWKS origin을 allowlist config로 고정한다.
- ID Token signature, issuer, audience, authorized party, nonce, expiry, issued-at와 authentication context를 검증한다.
- `iss + sub` 조합을 federation identity 정본으로 사용한다. Email을 stable subject로 사용하지 않는다.
- Implicit flow와 Resource Owner Password Credentials flow를 사용하지 않는다.
- Access/refresh token을 Browser에 노출하지 않는다.
- Sec_AI가 IdP token을 업무 API bearer token으로 그대로 사용하지 않고 callback 검증 뒤 local server session을 발급한다.

### 13.2 Claim·role mapping

- IdP group claim을 Sec_AI role로 무제한 자동 매핑하지 않는다.
- organization별 승인된 mapping version, 최대 부여 role와 deny rule을 관리한다.
- `APPROVER`, `ADMIN` 자동 부여는 별도 승인 없이는 금지한다.
- claim에서 사라진 role·scope는 local session을 즉시 revoke한다.
- IdP의 `acr`, `amr`, `auth_time`을 보존하되 Sec_AI가 action별 step-up 충족 여부의 최종 주체다.
- IdP session이 살아 있다는 이유로 Sec_AI absolute timeout과 최근 인증 요구를 무시하지 않는다.

### 13.3 장애·탈퇴

- IdP 검증·JWKS refresh·token exchange 실패 시 fail closed한다.
- 오래된 JWKS cache의 허용기간과 key rotation runbook을 승인한다.
- IdP logout과 Sec_AI logout은 별도 session이므로 가능한 back-channel/front-channel logout을 검토하고 local revoke를 항상 수행한다.
- 퇴직·조직 이동 event는 provisioning 또는 정기 reconciliation으로 local account·session·role을 회수한다.
- IdP 장애 시 일반 사용자를 local password로 자동 downgrade하지 않는다.
- 비상 접근은 일반 fallback이 아니라 `BREAK-GLASS` profile로만 수행한다.

### 13.4 환경별 배포 권장안과 확정 Gate

주소와 WebAuthn RP ID는 다음 초안을 기본으로 한다. `<org-domain>`은 조직이 소유·관리하는 실제 domain으로 교체한다.

| 환경 | 권장 canonical origin | 권장 RP ID |
|---|---|---|
| 단일 PC DEV | `https://localhost:8443` | `localhost` |
| 공유 DEV | `https://secai-dev.<org-domain>` | `secai-dev.<org-domain>` |
| Pilot | `https://secai-pilot.<org-domain>` | `secai-pilot.<org-domain>` |
| Production | `https://secai.<org-domain>` | `secai.<org-domain>` |

- IP 주소, `.local`, wildcard RP ID와 여러 alias origin을 사용하지 않는다. 환경마다 하나의 canonical origin과 exact RP ID를 둔다.
- 단일 PC DEV 인증서는 Browser가 신뢰하는 local 개발 CA 또는 조직 개발 CA로 발급한다.
- Pilot·Production이 내부망이면 조직 PKI/AD CS를 우선하고, Internet 공개면 공인 CA를 사용한다.
- 인증서 SAN은 exact hostname만 포함하고 Browser 경고 우회를 금지한다. private key는 OpenBao/Vault에 두며 만료 30일 전부터 알린다.

OIDC Provider 우선순위는 `기존 조직 IdP → Microsoft 환경이면 Entra ID → IdP가 없는 폐쇄망이면 별도 인증 VM/Server의 Keycloak production mode`다. Entra ID는 `common`이 아니라 tenant-specific issuer `https://login.microsoftonline.com/<tenant-id>/v2.0`를 사용한다. Keycloak을 선택하면 예시 issuer는 `https://idp.<org-domain>/realms/secai`이며 개발 mode가 아닌 production mode로 운용한다.

환경별 client는 `secai-dev-web`, `secai-pilot-web`, `secai-prod-web`으로 분리한다. Redirect URI는 각 canonical origin의 `/auth/oidc/callback` exact URI로 등록하고 wildcard를 금지한다. Authorization Code + PKCE `S256`만 허용한다.

Claim은 `(iss, sub)`를 불변 사용자 identity로 사용하고 `aud` exact match와 `exp`, `iat`, `nonce`, `auth_time`, `acr`, `amr`를 검증한다. `name`과 `email`은 표시용이고 stable key로 사용하지 않는다. Group claim은 privileged role에 직접 자동 매핑하지 않는다.

이 절의 주소·Provider는 승인된 권장 초안이다. 실제 조직 domain, CA, tenant/realm과 책임자 성명은 구현·배포 전 변경통제 기록으로 확정해야 한다. IdP 장애 시 local password로 자동 fallback하지 않는다.

SAML이 필요한 조직은 승인된 federation gateway가 OIDC로 변환하는 방식을 우선 검토하고, Sec_AI가 SAML parser·signature validation을 직접 구현하려면 별도 ADR과 보안시험을 요구한다.

## 14. Collector 인증

Collector credential은 사람 login, Browser cookie와 service account password가 아니다.

### 14.1 `ONLINE-AUTHENTICATED`

사용자가 인증·인가된 session으로 Job을 만들면 API가 Manifest와 함께 단기 upload credential을 발급한다.

| 속성 | 기준 |
|---|---|
| 형식 | 256-bit 이상 opaque random secret |
| 저장 | Server에는 keyed hash만 저장 |
| Scope | 단일 `organization + asset + job + manifest + submission endpoint` |
| TTL | 기본 60분, 최대 2시간 |
| 사용 | 한 번의 성공 package commit 후 폐기 |
| 제한 | 최대 byte, content type, package/schema version |
| 전달 | TLS, process memory. command line·package·log 저장 금지 |
| 회수 | Job 취소·Manifest 폐기·사용자 권한 회수 시 즉시 revoke |

- Collector는 Redis, PostgreSQL, AIStor credential을 받지 않는다.
- Upload credential로 다른 Job 상태 조회, Manifest 발급, Finding 조회와 S3 직접 접근을 할 수 없다.
- 서버는 credential뿐 아니라 nonce, Manifest signature/hash, asset binding, replay와 package 무결성을 다시 검증한다.
- 실패 upload가 credential을 무제한 재사용하게 하지 않고 제한된 attempt·byte budget을 둔다.

### 14.2 `OFFLINE-SIGNED`

조직 PKI가 있으면 package signature의 certificate chain, EKU, subject binding, expiry와 revocation을 검증한다. Collector EXE에 shared private key를 넣지 않는다. 인증서 발급·폐기·CRL/OCSP offline snapshot 정책은 조직 PKI ADR에서 확정한다.

### 14.3 `OFFLINE-USER-SUBMITTED`

- 사용자가 authenticated UI session과 CSRF 검증을 통해 package를 제출한다.
- Server는 package를 해당 사용자·Job·Asset에 귀속하고 `evidence_authentication=USER_SUBMITTED`로 기록한다.
- Manifest·nonce·hash·Schema·malware 검증은 온라인과 동일하게 수행한다.
- 사용자 제출은 대상 OS나 실행 identity가 조직 인증됐음을 의미하지 않는다.
- Audit Pack 또는 organization policy가 해당 assurance profile을 허용할 때만 자동 공식 판정에 사용한다.
- 고신뢰 profile이 필수인데 사용자 제출만 있으면 규칙 엔진은 `REVIEW` 또는 명시된 부족 상태를 생성하며 임의로 `PASS`하지 않는다.

### 14.4 IMP-032 구현 상태

2026-07-23 `IMP-032`에서 14.1의 core credential 계약을 구현했다. 256-bit opaque secret, versioned HMAC-SHA256 server record, 기본 60분·최대 2시간, 5회 실패 상한, revoke와 단일 성공 commit을 적용한다. Scope는 기존 기준에 Manifest content hash·nonce·Content-Type·schema version·최대 archive byte를 더해 축소만 가능하게 고정했다.

Credential을 검증한 뒤 기존 전체 Package Validator가 Schema·Manifest·ZIP·hash·Asset·evidence·staging·malware·content policy를 모두 통과해야 원자적 commit으로 credential과 nonce를 사용 완료 처리한다. Package 검증 실패는 credential 성공 사용이나 공식 Finding으로 바꾸지 않는다.

현재 `InMemoryCollectorCredentialStore`는 단위·인수시험용이며 운영 정본이 아니다. 사람 login·Job authorization이 아직 없어 credential issue와 실제 upload POST endpoint를 열지 않았다. Pilot 전에는 PostgreSQL unique constraint·transaction, HTTPS Gateway, issue/use/revoke 감사 Event와 인증된 Job 발급을 연결해야 한다. 상세 결과는 `deploy/verification/IMP032_온라인_인증_제출.md`를 따른다.

### 14.5 IMP-033 구현 상태

2026-07-23 `IMP-033`에서 14.2와 14.3의 core 계약을 구현했다. `OFFLINE-SIGNED`는 Ed25519 detached signature, RFC 8785 JCS payload, pinned organization root, 전용 EKU `1.3.6.1.4.1.55555.1.1`, Organization subject, Asset SAN, 유효기간과 접수 시각 기준 24시간 이내의 필수 폐기 확인을 모두 통과해야 한다. self-signed 장치 인증서, 폐기 상태 확인 불가와 오래된 snapshot은 fail-closed로 거부한다. EXE Authenticode 배포 서명과 Package 데이터 서명은 서로 다른 검증으로 유지한다.

`OFFLINE-USER-SUBMITTED`는 활성 사용자 session·CSRF·Asset/Job authorization을 요구하며 `LOW` assurance로 고정한다. 이 Profile은 로그인 제출자만 식별하고 장치 실행 identity를 인증하지 않는다. 현재 DRAFT Pack과 정책에서는 이 제출만으로 자동 운영 공식 PASS를 만들 수 없다.

두 Profile은 `(organization_id, asset_id, job_id, nonce)`를 하나의 replay key로 사용한다. 따라서 서명 제출 후 사용자 제출로 방식을 바꾼 재전송도 거부한다. 현재 저장소는 인수시험용 memory 구현이고 실제 CA·개인키·인증서·원본 증적을 저장하지 않으며 운영 POST endpoint도 열지 않았다. Pilot 전에는 조직 CA·TPM/Windows CNG non-exportable key, PostgreSQL transaction, 실제 session·CSRF·RBAC와 감사 Event를 연결해야 한다. 상세 결과는 `deploy/verification/IMP033_오프라인_패키지_제출.md`를 따른다.

## 15. Service identity

사람 MFA·session을 background Worker나 container에 복사하지 않는다.

| Identity 종류 | 인증 방식 | 금지 |
|---|---|---|
| API→PostgreSQL | service별 DB role과 file-mounted secret | 사람 DB role 공유 |
| Worker→PostgreSQL | Worker별 최소 DB role | 하나의 superuser credential 공유 |
| Service→AIStor | service별 access key·policy 또는 조직 표준 workload identity | Browser·Collector에 key 전달 |
| Celery→Redis | named ACL user, Queue·key pattern 최소화 | default 무인증 user |
| Gateway→API | internal network + 신뢰 proxy 정책, 향후 mTLS 검토 | 외부에서 API port 직접 접근 |
| Internal privileged operation | action·target hash·expiry가 고정된 1회 execution grant | 사람 session token 전달 |

공통 규칙:

- service identity는 `/auth/login`과 Browser cookie를 사용할 수 없다.
- 사람 role assignment endpoint에서 service role을 부여하지 않는다.
- credential은 source, image, Compose 기본값, environment dump와 log에 넣지 않는다.
- 승인된 OpenBao 또는 Vault에서 짧은 수명의 read-only file·memory 형태로 주입하고 service별로 분리한다. Compose environment와 image에는 넣지 않는다.
- rotation에는 새 credential 병행, consumer 전환, 이전 credential revoke와 감사 절차를 둔다.
- Celery message에는 credential·cookie·human access token을 넣지 않는다.
- service credential compromise는 사람 Password reset이 아니라 workload 격리·rotation·영향 audit으로 처리한다.

## 16. Browser·API 인증 경계

### 16.1 허용 mechanism

| Client | 허용 인증 |
|---|---|
| Web UI·HTMX | `__Host-secai_session` cookie + CSRF |
| SSE | 같은 session cookie, 연결·재연결 authorization |
| Browser JSON API | 같은 session cookie + CSRF |
| Collector upload | 단기 Job credential |
| Offline package upload | 사람 session + CSRF |
| Internal Worker | service identity·DB role·Queue ACL |

### 16.2 금지 mechanism

- Username/password HTTP Basic 인증
- URL query의 session·access token
- localStorage·sessionStorage의 JWT
- 무기한 API key
- Cookie와 Authorization header 중 아무 것이나 받아들이는 혼합 flow
- Proxy가 삽입한 임의 username header 신뢰
- 사용자가 정한 service URL·OIDC issuer·redirect URI
- 인증만 성공하면 organization·asset scope 검사를 생략하는 endpoint

MVP endpoint는 자신이 허용하는 authentication mechanism을 명시적으로 하나만 선택한다. 동일 endpoint가 Browser cookie와 Collector credential을 암묵적으로 모두 받지 않는다.

## 17. TLS·Gateway·Header 신뢰

- 외부 접근은 Gateway의 승인된 HTTPS port만 사용한다.
- login·MFA·session·upload는 평문 HTTP를 허용하지 않는다.
- TLS certificate 검증을 끄거나 자체 서명 오류를 무시하지 않는다.
- 조직 내부 CA를 쓰면 trust distribution과 rotation을 운영 문서로 관리한다.
- Gateway는 client가 보낸 `Forwarded`, `X-Forwarded-For`, `X-Forwarded-Proto`, identity header를 제거하고 신뢰된 값을 다시 설정한다.
- API는 Gateway network의 header만 신뢰하고 직접 접근을 network policy로 차단한다.
- canonical public origin을 server config로 고정해 Host header injection, open redirect와 CSRF target confusion을 막는다.
- Login·OIDC callback page는 third-party script·image·analytics를 포함하지 않는다.
- `Referrer-Policy`, CSP, frame restriction과 no-store는 `6.ADR_웹_UI.md`를 따른다.

## 18. 인증 data 보호

### 18.1 저장 분류

| Data | 저장 | 보호 |
|---|---|---|
| Password | Argon2id encoded hash | DB 접근 최소화, dump 보호 |
| TOTP seed | AEAD encrypted | 별도 key·version·AAD(user/factor ID) |
| WebAuthn | public key·credential metadata | private key는 authenticator 밖으로 가져오지 않음 |
| Recovery code | slow hash | 1회 사용·잔여 개수만 표시 |
| Session token | Browser 원문, DB keyed hash | no-store·HttpOnly·revoke |
| CSRF token | session-bound secret/hash | auth token과 분리 |
| Activation/Collector secret | keyed hash | TTL·scope·single use |
| OIDC token | server memory 또는 최소 encrypted transient store | Browser·log 금지, 필요 없으면 즉시 폐기 |
| Audit event | actor·method·outcome metadata | secret·원문 제외 |

### 18.2 금지 logging

- Password·Password hash 전체
- WebAuthn challenge response·signature 원문 전체
- TOTP seed·code
- recovery·activation code
- session cookie·CSRF token
- OIDC authorization code·ID/access/refresh token
- Collector upload credential
- Docker/DB/Redis/AIStor secret
- 민감 query string·전체 request body

필요한 경우 credential·session ID의 별도 audit correlation hash를 생성하되 인증 lookup hash와 다른 audit key를 사용하고 key version을 기록한다.

## 19. 감사 Event

| Event | 최소 metadata |
|---|---|
| login success/failure | subject correlation, method, outcome, reason, time, source risk metadata |
| MFA enrollment/change | user, factor type, credential correlation, actor, approval |
| session create/rotate/revoke/expire | user, session correlation, reason, auth strength |
| Password change/recovery | user, actor, method, approval, credential version |
| account invite/activate/lock/disable | target, actor, reason, time |
| role·scope 변경으로 인한 revoke | assignment version, affected session count |
| step-up success/failure | action category, target hash, method, freshness |
| OIDC callback rejection | issuer correlation, validation reason, transaction ID |

Authentication failure reason은 내부 감사에서 구분하되 UI 응답은 일반화한다. IP·User-Agent 등 client metadata는 보안 탐지에 필요한 최소 범위만 보존하고 개인정보 영향과 보존기간을 승인한다.

### 21.1 Dependency

## 24. 고려한 대안

### 24.1 처음부터 조직 OIDC만 사용

정식 운영의 선호안이지만 MVP에서는 조직 IdP 종류·claim·망 연결·MFA 정책이 확정되지 않아 Core 개발을 외부 의존성으로 막을 수 있다. Local MFA로 기능을 완성하고 provider abstraction 뒤 OIDC를 연결한다.

### 24.2 Password만 사용하는 로컬 계정

거부한다. 원본 증적, 승인, 파기와 관리자 기능을 다루는 시스템에서 Password 단일 factor는 RBAC의 강한 MFA 요구를 충족하지 못한다.

### 24.3 TOTP만 모든 MFA와 step-up에 사용

부분 채택한다. 일반 USER의 MVP MFA·제한된 복구에는 사용할 수 있지만 phishing-resistant가 아니므로 privileged 고위험 step-up에는 WebAuthn을 요구한다.

### 24.4 Browser JWT + refresh token

거부한다. SSR/HTMX same-origin application에 필요하지 않으며 즉시 revoke, role 변경, XSS·Browser storage와 token rotation 복잡도를 증가시킨다. Opaque server session이 현재 요구에 적합하다.

### 24.5 Redis session 정본

거부한다. Redis 장애·eviction·초기화가 인증 정본을 훼손하지 않도록 PostgreSQL을 사용한다. Redis는 rate limit 보조 cache일 수 있지만 account lock과 session revoke의 유일한 정본이 아니다.

### 24.6 FastAPI/Starlette signed cookie에 session 전체 저장

거부한다. 서명은 confidentiality·즉시 revoke를 제공하지 않으며 role·organization·credential version을 Cookie에 싣게 된다. Cookie에는 opaque random ID만 둔다.

### 24.7 LDAP bind·AD password 직접 검증

MVP에서 거부한다. Password 처리·가용성·망·계정 lifecycle 결합이 커진다. 조직 인증은 OIDC federation을 우선한다.

### 24.8 SMS·email OTP와 security question

거부한다. phishing·SIM swap·mail compromise·지식정보 추측 위험이 있고 privileged assurance에 적합하지 않다.

## 25. 결과와 Trade-off

### 25.1 기대 효과

- 외부 IdP 없이 MVP를 재현하면서도 Password 단일 인증을 피한다.
- role 변경·계정 비활성화·사고 시 session을 즉시 폐기할 수 있다.
- Browser token 노출과 JWT refresh 복잡도를 줄인다.
- WebAuthn으로 privileged phishing 위험과 step-up 위조를 줄인다.
- 사람, Collector와 service identity의 credential lateral movement를 차단한다.
- 향후 OIDC 전환 뒤에도 동일한 local RBAC·session·approval 통제를 유지한다.

### 25.2 비용과 제약

- WebAuthn·TOTP·복구·notification과 key 운영 구현이 필요하다.
- PostgreSQL session 조회·정리와 role version invalidation을 운영해야 한다.
- 폐쇄망 Password blocklist·WebAuthn hostname·TLS 인증서 준비가 필요하다.
- Privileged 사용자는 compatible authenticator와 복구 절차를 준비해야 한다.
- IdP federation에서도 local session과 IdP session의 만료·logout을 각각 관리해야 한다.

이 비용은 원본 증적·승인·관리 기능의 민감도와 RBAC의 책임 분리를 위해 수용한다.

- PostgreSQL local named account, role·asset assignment와 server-side opaque session

- session-bound CSRF, exact Origin/Referer와 Fetch Metadata 확인

- credential version·role assignment version 변경의 즉시 session revoke
- full page·fragment·API·SSE·download의 매 요청 인증·권한 재확인
- login·MFA·session revoke·권한 허용/거부의 비밀값 없는 감사 이벤트

`DEV-LOCAL`의 6자리 test MFA는 자동시험과 개발 PC 흐름 검증용이며 WebAuthn·TOTP 구현이나 Pilot AAL2 승인을 의미하지 않는다. localhost HTTP에서는 개발 cookie를 사용하고, HTTPS Pilot에서만 `__Host-secai_session` Secure cookie를 강제한다. 실제 hostname·TLS·RP ID·조직 OIDC·WebAuthn 등록과 복구는 위의 미완료 Gate가 끝나기 전까지 fail-closed 상태로 둔다.

상세 구현·시험 결과는 `deploy/verification/IMP046_인증_RBAC_웹_보안_검증.md`를 따른다.

### 27.2 2026-08-01 DEV-LOCAL 계정 관리 UI 상태

- 로그인 화면 안에서 계정 생성 요청을 접수하며 새 창을 열지 않는다.
- 승인 전 계정은 `PENDING_APPROVAL`이고 로그인·역할·session이 없다.
- 관리자 계정 관리 화면은 같은 조직의 승인 대기·활성·비활성 계정을 조회하고 승인·반려·중지·재활성화한다.
- 일반 사용자는 계정정보에서 자신의 표시 이름·password를 변경하고 session을 종료할 수 있다.
- 관리자만 개발용 두 번째 인증 코드를 재발급하며, 화면에는 기본적으로 마스킹하고 명시적 복사 동작에서만 1회 원문을 사용한다.
- 계정 관리 service 집중시험 6건이 잠긴 dev-tools Runtime에서 통과했다.

상세 현재 구현 기록은 [`deploy/verification/개발_로컬_계정_승인_관리_20260801.md`](../../deploy/verification/개발_로컬_계정_승인_관리_20260801.md)를 따른다.

NIST SP 800-63B-4의 password 길이 하한·blocklist, MFA·phishing resistance와 session 요구를 보안 기준으로 참고한다. 다만 9자 최소 길이, 문자·숫자·특수문자 조합과 30일 변경은 NIST 권고가 아니라 사용자가 승인한 조직 정책상 추가·변경 기준이며, 모든 Pilot 계정 MFA와 본 ADR의 보완통제를 전제로 한다. OWASP 권고에 따라 Argon2id, 일반화된 login 오류, throttling, session rotation과 다중 CSRF 방어를 적용한다. OIDC 연동은 Authorization Code + PKCE, exact redirect, state·nonce 검증을 사용한다.
