## 1. 목적

이 문서는 1차 MVP의 모든 PC Control에 대해 원문 위치, 원문 중요도, Windows 11 지원 범위, 자산·기능 적용성, 판정 선행조건, 초기 자동화 유형, 최소 수집 권한과 요구 증적을 정의한다. 이후 JSON Schema, Audit Pack, Probe, Fixture와 규칙 엔진은 이 매트릭스를 추적 기준으로 사용한다.

이 문서는 구현 설계의 출발점이다. KISA 원문에 없는 Windows 내부 경로, 권한과 제품별 수집 방식은 승인 전 VMware 실측으로 검증해야 하며 추정값을 최종 규칙으로 사용하지 않는다.

## 3. 분류 기준

### 3.1 초기 자동화 유형

| 유형 | 의미 |
|---|---|
| `AUTO` | 승인된 구조화 증적만으로 적용성과 `PASS/FAIL/ERROR`를 결정할 수 있음 |
| `AUTO-CONDITIONAL` | PowerShell·Registry·CIM/WMI·제품 Adapter로 증적 수집과 규칙 비교를 자동화함. 조직 기준·지원 Adapter·외부 기준 데이터·절차 증적 중 하나가 있어야 최종 상태를 확정함. 실행 계획서의 기존 `PARTIAL`을 대체하는 명칭 |
| `MANUAL` | 기계 판독 가능한 증적원이나 승인된 Adapter가 없어 사람의 직접 확인만으로 판정해야 함. PC-01~PC-18 현재 매트릭스에는 해당 항목 없음 |
| `AUTO-APPLICABILITY` | 기능·제품 적용 여부를 자동 확인한 후 적용 시 자동 규칙을 실행하고, 미적용 시 근거 있는 `N/A`로 처리함. 실행 계획서의 기존 `N/A-CANDIDATE`를 대체하는 명칭 |

자동화 유형은 Finding 상태가 아니다. `AUTO-CONDITIONAL`도 사람의 반복 점검을 뜻하지 않는다. 조직 기준과 Adapter가 등록되어 있으면 규칙 엔진이 자동으로 `PASS/FAIL`을 만들고, 필수 의존성이 없을 때만 `REVIEW`를 만든다.

현재 분류는 `AUTO 7`, `AUTO-CONDITIONAL 10`, `AUTO-APPLICABILITY 1`, `MANUAL 0`이다.

### 3.2 자동화 세부 축

단일 자동화 유형만으로 구현 방식을 판단하지 않는다. 다음 세 축을 별도로 기록한다.

| 축 | 코드 | 의미 |
|---|---|---|
| 증적 수집 | `NATIVE` | Windows 기본 PowerShell, Registry, CIM/WMI, 보안 정책 API로 읽기 전용 자동 수집 |
| 증적 수집 | `ADAPTER` | Defender·타사 백신·방화벽·브라우저 등 제품별 자동 Adapter |
| 증적 수집 | `REFERENCE` | Microsoft 수명주기·패치 기준 등 승인·서명된 외부 기준 데이터 자동 조회 |
| 증적 수집 | `ATTESTATION` | 조직 절차·업무 필요성처럼 책임자가 승인한 구조화 증적. 자유 형식 메모가 아니라 ID·버전·승인자·유효기간을 가진 데이터 |
| 판정 | `RULE` | 고정된 기술 기준으로 결정론적 자동 판정 |
| 판정 | `POLICY-RULE` | 버전이 지정된 조직 기준을 입력으로 결정론적 자동 판정 |
| 판정 | `ADAPTER-RULE` | 승인된 제품 Adapter의 정규화 결과로 자동 판정 |
| 판정 | `HYBRID-RULE` | 자동 수집한 기술값과 승인된 `ATTESTATION`을 함께 규칙으로 평가 |
| 판정 | `APPLICABILITY-RULE` | 적용성을 먼저 자동 판정한 뒤 `N/A` 또는 기술 규칙으로 분기 |

### 3.3 `AUTO-CONDITIONAL` 항목의 실제 자동 수집 수단

| ID | 자동 증적 수집 예 | 조건부로 남는 이유 |
|---|---|---|
| PC-02 | LSA/유효 암호 정책 조회, `secedit` 또는 정책 API 결과 정규화 | 기관 최소 길이·복잡성 기준 버전 필요 |
| PC-04 | `Get-SmbShare`, `Get-SmbShareAccess`, `Get-Acl`, `AutoShareWks` Registry | 업무상 필요한 공유와 승인 ACL 예외 목록 필요 |
| PC-05 | `Get-CimInstance Win32_Service`, 서비스 Registry, 실행 파일 서명 | 기관 필수 서비스 allowlist 필요 |
| PC-06 | Uninstall Registry, Appx/MSIX 목록, `Win32_Process`, 파일 서명 | 기관 메신저 allow/deny 목록 필요 |
| PC-10 | Windows Update Agent API, OS Build/UBR, 설치 KB·업데이트 정책 | 기준일별 필수 패치 목록과 내부 관리 절차 증적 필요. `Get-HotFix` 단독 사용은 일부 업데이트를 누락하므로 금지 |
| PC-11 | `Win32_OperatingSystem`, CurrentVersion Registry, 서명된 Microsoft 수명주기 데이터 | Edition별 지원 기준 스냅샷과 내부 관리 절차 증적 필요 |
| PC-13 | `Get-MpComputerStatus`, Windows Security Center 또는 제품 Adapter | 백신별 필드 정규화와 최신성 허용 기준 필요 |
| PC-14 | `Get-MpComputerStatus`, Windows Security Center 또는 제품 Adapter | 타사 백신 실시간 감시 상태 Adapter Coverage 필요 |
| PC-15 | `Get-NetFirewallProfile -PolicyStore ActiveStore`, Windows Security Center 또는 제품 Adapter | 타사 방화벽 건강 상태 Adapter Coverage 필요 |
| PC-17 | AutoRun/AutoPlay Registry, GPO/MDM 유효 정책 | KISA 기준에 포함된 내부 이동식 미디어 관리 절차 증적 필요 |

따라서 위 10개는 “자동화 불가”가 아니라 “자동 수집·자동 비교 + 외부 의존성”이다. 조직 기준과 Adapter가 준비되면 운영 시 사람의 반복 판정 없이 자동 처리한다.

### 3.4 요구 권한 코드

| 코드 | 의미 |
|---|---|
| `U` | 일반 사용자 읽기 권한으로 수집 목표 |
| `A` | 전체·신뢰 가능한 증적을 위해 UAC 상승된 관리자 읽기 권한 필요 |
| `U/A` | 일반 사용자로 우선 수집하고 접근 거부 또는 Coverage 부족 시 관리자 재수집 |
| `+O` | Windows 권한과 별개로 승인된 조직 정책·예외·기준 데이터 필요 |

권한 코드는 최소권한 설계 제안이다. 실제 요구 권한은 Windows 11 기준 VM에서 일반 사용자와 관리자 계정으로 각각 실행해 확정한다. 권한 부족은 `FAIL`이 아니라 `ERROR` 또는 증적 부족 `REVIEW`로 처리한다.

### 3.5 원문 중요도

`상`, `중`, `하`는 KISA 원문 553~554쪽의 표기를 그대로 기록한다. Sec_AI가 중요도를 다시 계산하거나 임의 점수로 변환하지 않는다.

- 중요도는 Dashboard 정렬, 조치 우선순위, 보고서 강조와 알림 우선순위에 사용할 수 있다.
- 중요도는 공식 `PASS/FAIL/REVIEW/ERROR/N/A` 상태를 바꾸지 않는다.
- 중요도를 숫자 점수나 자산 위험도에 반영하려면 별도 산정기준과 ADR 승인이 필요하다.

### 3.6 지원 범위·적용성·판정 선행조건

기존 `Win11 적용성` 열은 서로 다른 의미를 섞을 수 있으므로 다음 세 열로 분리한다.

| 구분 | 의미 |
|---|---|
| `Win11 지원 범위` | 원문 Control이 Windows 11을 대상으로 하며 Sec_AI MVP가 해당 OS에서 구현·인수할 범위인지 표시 |
| `자산·기능 적용성` | 특정 자산·기능·사용자가 Control의 실제 평가 대상인지 표시. 승인된 적용성 규칙이 미적용을 증명할 때만 `N/A` 허용 |
| `판정 선행조건` | 기관 기준, 평가 사용자 범위, 제품 Adapter, 외부 기준 데이터 또는 절차 증적처럼 최종 판정에 필요한 의존성 |

적용성과 판정 가능성을 혼동하지 않는다.

- 기관 기준이나 제품 Adapter가 없다는 이유만으로 `N/A`를 만들지 않는다.
- Control은 적용되지만 판정 선행조건이 없으면 `REVIEW`, 필수 증적 수집·검증에 실패하면 `ERROR`로 처리한다.
- 기능이 없거나 사용하지 않음을 승인된 `APPLICABILITY-RULE`과 구조화 증적으로 확인한 경우에만 근거 있는 `N/A`를 만든다.
- 자동 수집 가능성과 자동 판정 가능성은 `증적 수집`, `판정 모델`, `자동화 유형` 열에서 별도로 관리한다.

### 5.5 PC-16 자동 수집 기준

PC-16은 수동 판정 Control이 아니다. Windows 11의 화면보호기 정책은 사용자 범위 정책이며, 현재 사용자에 대해서는 일반 권한의 읽기 전용 PowerShell로 자동 수집·판정한다.

값별 우선순위는 다음과 같다.

1. `HKCU\Software\Policies\Microsoft\Windows\Control Panel\Desktop`의 강제 정책값
2. 강제 정책값이 없으면 `HKCU\Control Panel\Desktop`의 사용자 설정값

수집 대상 값:

- `ScreenSaveActive`: 화면보호기 활성 여부
- `ScreenSaveTimeOut`: 대기 시간(초)
- `ScreenSaverIsSecure`: 재시작 시 암호 보호 여부
- `SCRNSAVE.EXE`: 선택된 화면보호기 실행 파일. 보조 증적으로만 사용

읽기 전용 Probe 예시:

```powershell
$policyPath = 'HKCU:\Software\Policies\Microsoft\Windows\Control Panel\Desktop'
$userPath = 'HKCU:\Control Panel\Desktop'

$policy = Get-ItemProperty -LiteralPath $policyPath -ErrorAction SilentlyContinue
$user = Get-ItemProperty -LiteralPath $userPath -ErrorAction SilentlyContinue

function Get-EffectiveScreenSaverValue {
    param([Parameter(Mandatory)][string]$Name)

    if ($null -ne $policy -and $null -ne $policy.PSObject.Properties[$Name]) {
        return [pscustomobject]@{ Value = $policy.$Name; Source = 'Policy' }
    }
    if ($null -ne $user -and $null -ne $user.PSObject.Properties[$Name]) {
        return [pscustomobject]@{ Value = $user.$Name; Source = 'User' }
    }
    return [pscustomobject]@{ Value = $null; Source = 'Missing' }
}

$active = Get-EffectiveScreenSaverValue -Name 'ScreenSaveActive'
$timeout = Get-EffectiveScreenSaverValue -Name 'ScreenSaveTimeOut'
$secure = Get-EffectiveScreenSaverValue -Name 'ScreenSaverIsSecure'
$screenSaver = Get-EffectiveScreenSaverValue -Name 'SCRNSAVE.EXE'

$timeoutSeconds = if ($null -eq $timeout.Value) { $null } else { [int]$timeout.Value }
$verdict = if (
    [string]$active.Value -eq '1' -and
    $null -ne $timeoutSeconds -and
    $timeoutSeconds -ge 1 -and
    $timeoutSeconds -le 600 -and
    [string]$secure.Value -eq '1'
) { 'PASS' } else { 'FAIL' }

[pscustomobject]@{
    ControlId = 'PC-16'
    UserSid = ([System.Security.Principal.WindowsIdentity]::GetCurrent()).User.Value
    ScreenSaveActive = $active.Value
    ScreenSaveActiveSource = $active.Source
    ScreenSaveTimeOutSeconds = $timeoutSeconds
    ScreenSaveTimeOutSource = $timeout.Source
    ScreenSaverIsSecure = $secure.Value
    ScreenSaverIsSecureSource = $secure.Source
    ScreenSaverExecutable = $screenSaver.Value
    Verdict = $verdict
}
```

Probe에서는 `Get-ItemProperty`만 사용하며 `Set-ItemProperty` 또는 정책 변경 명령을 실행하지 않는다. Domain GPO가 적용된 환경은 `gpresult /scope user /z`의 RSoP 결과를 교차 증적으로 사용할 수 있다.

공유 PC의 자산 수준 결과는 사용자별 Finding을 집계한다. One-shot Collector를 각 사용자의 로그인 세션에서 실행하는 방식을 우선하며, 다른 사용자의 미로드 registry hive를 강제로 `reg load`하는 방식은 읽기 전용 원칙을 훼손하므로 기본 Probe에서 사용하지 않는다.

## 6. 공통 증적 필드

모든 Control 증적에는 최소한 다음 공통 필드를 포함한다.

- `control_id`
- `guide_version=2026`
- `asset_id`
- `os_product`, `os_edition`, `os_version`, `os_build`, `os_ubr`, `architecture`
- `collector_version`, `probe_id`, `probe_version`
- `collected_at`, `timezone`
- `execution_identity_type`, `is_elevated`
- `source_type`, `source_path_or_provider`
- `raw_value`, `normalized_value`, `unit`
- `policy_scope`, `policy_source`, `effective_value`
- `collection_status`, `error_code`
- `redaction_applied`
- `evidence_sha256`

`raw_value`는 최소화된 구조화 값이어야 한다. 비밀번호, 토큰, 인증서 개인키, 사용자 문서 내용, 브라우저 기록 원문과 불필요한 사용자 식별정보는 저장하지 않는다.

## 7. Finding 상태 연결

| 상황 | 상태 |
|---|---|
| 적용 가능하고 모든 승인 규칙 충족 | `PASS` |
| 적용 가능하고 하나 이상의 승인 규칙 위반 | `FAIL` |
| 조직 기준·제품 Adapter·사용자 범위·수동 증적 부족 | `REVIEW` |
| 권한 부족, Probe 실패, 파싱 실패, 무결성 오류 | `ERROR` |
| 기능·제품·환경이 적용되지 않음을 승인 규칙으로 증명 | `N/A` |

- 우선순위는 `ERROR → N/A → REVIEW → FAIL/PASS`의 단순 전역 순서로 구현하지 않는다. Control별 적용성 평가, 증적 완전성 검사와 규칙 평가 단계를 분리한다.
- 부분 증적만으로 `PASS`를 만들지 않는다.
- 권한 부족 또는 미지원 제품을 `FAIL`로 오판하지 않는다.
- LLM은 상태를 생성하거나 변경하지 않는다.

## 8. 첫 세로 기능 조각 선정

첫 구현 Control로 `PC-07`을 제안한다.

선정 근거:

- 원문 판단 기준이 NTFS/비-NTFS로 명확하다.
- 읽기 전용 구조화 증적 수집이 가능하다.
- 일반 사용자 권한 우선 수집을 시험할 수 있다.
- VMware에 보조 가상 디스크를 추가해 NTFS와 비-NTFS Fixture를 반복 재현할 수 있다.
- AI, 조직 정책과 외부 서비스 없이 규칙 엔진의 종단 흐름을 검증할 수 있다.

선정 조건:

- 평가 대상을 OS·고정 데이터 볼륨으로 정의한다.
- EFI/MSR/Recovery, 광학, 이동식 볼륨 제외 규칙을 문서화한다.
- ReFS, Storage Spaces, BitLocker, VHD는 승인 전 Fixture로 검증한다.
- PASS, FAIL, ERROR와 적용성 제외 Fixture를 각각 작성한다.

## 9. 승인 전 필수 검증

1. Windows 11 지원 중인 기준 이미지의 Edition, Version, Build와 SHA-256을 고정한다.
2. 각 Probe를 일반 사용자와 관리자 계정에서 각각 실행해 권한 표를 실측한다.
3. 도메인 미가입, 로컬 정책, Domain GPO, MDM 적용 시 유효 정책값 수집 방법을 구분한다.
4. PC-03의 Windows 11 정책 상태와 PC-09의 IE/IE mode 적용성을 실제 이미지에서 확인한다.
5. PC-04~06, PC-10~11, PC-13, PC-16~17에 필요한 조직 기준의 소유자와 버전을 지정한다.
6. Defender와 타사 백신·방화벽의 미지원 제품 처리 규칙을 승인한다.
7. 모든 Control에 최소 PASS/FAIL/ERROR Fixture를 정의하고 적용성 Control에는 N/A, 부분 자동화 Control에는 REVIEW Fixture를 추가한다.
8. 원문 위치, 규칙 버전, 증적 해시가 Finding에서 역추적되는지 계약 테스트로 확인한다.
