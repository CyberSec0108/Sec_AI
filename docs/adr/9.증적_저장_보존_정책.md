## 1. 정책 요약

Sec_AI의 원본 증적 저장소는 **MinIO AIStor Free 최신 Stable의 잠긴 단일 노드 image**를 납품·판매·재배포 없는 조직 내부 용도로 사용한다. 수신한 파일은 staging에서 악성코드·Schema·서명·nonce·hash·자산 범위를 검증한 후에만 원본 bucket으로 승격한다.

승인된 원본은 versioning과 Object Lock이 활성화된 bucket에 새로운 object key로 기록하고 **COMPLIANCE mode 1,095일**을 기본 보존기간으로 적용한다. 격리, 파생자료, 공식 보고서와 감사 archive를 포함한 모든 지속 보관 Bucket도 기본 보존기간을 **1,095일**로 통일한다. 원본을 수정하거나 덮어쓰지 않으며 PostgreSQL에는 object key, version ID, SHA-256, retention과 legal hold 상태를 정본 metadata로 기록한다.

1,095일은 이 프로젝트의 **MVP 운영 기준값**이며 특정 법령이 요구하는 기간이라고 주장하지 않는다. 적용 기관의 법령, 계약, 기록물·개인정보 정책이 더 긴 기간을 요구하면 긴 기간을 우선한다. 기간 단축은 보안·법무·개인정보 책임자 검토와 새 정책 version 승인을 거쳐야 하며 이미 설정된 COMPLIANCE retention은 단축할 수 없다. 미완료 multipart upload, 검증 전 staging과 사용자용 임시 export는 지속 보관 기록이 아니므로 각각 24시간 안에 정리하고, 보존 대상이 된 검증 실패 자료는 1,095일 quarantine으로 승격한다.

## 2. 목적

이 정책의 목적은 다음과 같다.

- 판정에 사용된 원본 bytes를 나중에 동일하게 재검증할 수 있게 한다.
- 관리자 계정 탈취나 애플리케이션 오류가 원본을 덮어쓰거나 조기 삭제하지 못하게 한다.
- malware·변조·만료 package가 공식 증적으로 승격되는 것을 막는다.
- 사용자·자산·조직 범위를 벗어난 원본 조회와 download를 차단한다.
- 보존기간과 legal hold가 끝난 자료는 승인된 절차로 검증 가능하게 파기한다.
- 단일 노드 장애와 ransomware에 대비해 독립 백업에서 복구할 수 있게 한다.
- AIStor 원본과 PostgreSQL `vector_store` projection을 분리해 vector 검색 권한이 원본 object에 접근하지 못하게 한다.

## 3. 적용 범위와 제외 범위

### 3.1 적용 범위

- Collector의 exact `payload.zip`
- Detached `audit_package.json`과 실행에 사용한 `collector_manifest.json`
- package 내부 원시 evidence·error JSON
- 사용자가 중앙 UI로 제출한 조직 정책·절차·예외 등 수동 증적 원본
- 업로드된 보고서 source와 승인된 공식 보고서
- 원본에서 생성한 normalized evidence·Finding·AI explanation artifact
- 격리된 실패·악성 의심 package
- object 접근·retention·legal hold·backup·restore·delete 감사 기록

### 3.2 제외 범위

- PostgreSQL table DDL과 DB 자체 backup 세부 명령
- Redis AOF와 Celery message 보존
- PostgreSQL `vector_store`의 재생성 가능한 embedding·index data
- Neo4j, Wazuh, Langfuse와 model cache
- Collector PC의 임시 file 정리
- 자동 remediation backup과 rollback artifact
- 법령·계약별 최종 보존기간 해석

Redis AOF, pgvector embedding과 AI trace는 원본 증적이 아니다. Redis, PostgreSQL `vector_store` 또는 Langfuse에 원본 package·전체 증적·비밀값을 복제하지 않는다.

## 4. 용어와 데이터 등급

| 용어 | 정의 |
|---|---|
| 원본 증적 | Collector 또는 인증 사용자에게 받은 exact bytes. 변환·정규화 전 artifact |
| 승격 | staging에서 모든 검증을 통과한 object를 불변 original bucket으로 복사하고 DB에 확정하는 절차 |
| 파생 증적 | 원본을 정규화·집계·변환해 만든 evidence, Finding, 설명 또는 report |
| 격리 object | malware 의심, 무결성·Schema·인증 실패로 공식 판정에 사용할 수 없는 수신물 |
| Retention | 정해진 시각까지 object version의 수정·삭제를 막는 기간 기반 보호 |
| Legal hold | 사건·감사·소송 등을 위해 기간 종료와 무관하게 유지하는 무기한 보호 |
| Delete Marker | versioned bucket의 일반 DELETE로 생성되는 표식. 원본 version의 영구 파기가 아님 |
| 삭제 증명 | 삭제 대상, version, hash, 승인, 결과와 검증 시각을 기록한 최소 metadata |

### 4.1 분류

| 등급 | 대상 | 기본 취급 |
|---|---|---|
| `RESTRICTED-RAW` | 원본 package, Registry·정책·제품 상태, 수동 증적 | 가장 제한된 read, download 감사, 불변 보관 |
| `RESTRICTED-QUARANTINE` | malware·변조·인증 실패 package | preview·자동 추출 금지, 보안담당자만 제한 접근 |
| `RESTRICTED-DERIVED` | normalized evidence, Finding, 공식 report | 원본 link와 RBAC 유지, 외부 공유 금지 |
| `INTERNAL-AI` | AI explanation, prompt/model metadata | 공식 판정과 분리, 짧은 보존 |
| `INTERNAL-OPS` | object audit event, backup manifest, 삭제 증명 | 본문 금지, 운영·감사 목적으로 제한 |

원본에는 자산 설정과 취약 상태가 포함되므로 개인정보가 없더라도 보안상 제한정보로 취급한다.

## 5. AIStor 제품·배포 기준

### 5.1 고정 image

```yaml
image: quay.io/minio/aistor/minio:RELEASE.2026-06-06T02-44-06Z@sha256:5dbb753c0dbe6a987dd30ce564f66c0042e291e464d10e792443451d4fec2120
platform: linux/amd64
```

상태는 `LOCKED-MVP-FREE`다. 새 Stable이 발표되어도 자동 변경하지 않는다. 변경 시 license, release note, SBOM, provenance, vulnerability, Object Lock, KMS, backup·restore와 기존 data 호환성을 다시 시험하고 `4.컨테이너_이미지_잠금.md`를 개정한다.

### 5.2 AIStor Free 제한

AIStor Free는 단일 노드이며 Enterprise의 분산 배포, server-side replication과 일부 version 관리 기능을 사용할 수 있다고 가정하지 않는다.

- 조직이 공식 경로에서 직접 내려받아 내부에서 사용하고, AIStor image·binary를 제3자에게 배포·판매·재판매·임대하지 않으며 수정·역공학하지 않는다.
- 단일 노드는 HA가 아니며 host·disk·volume 장애가 전체 저장소 장애가 될 수 있다.
- 제조사 SLA·SLO·지원 보장을 프로젝트 가용성 근거로 사용하지 않는다.
- 같은 host의 Docker volume copy나 snapshot은 독립 backup이 아니다.
- AIStor server-side site·bucket replication을 MVP backup으로 설계하지 않는다.
- Free에서 제한되는 version-specific object deletion 때문에 retention 종료 후 hard purge가 정상 동작한다고 사전 가정하지 않는다.
- `mc mirror`는 current object만 동기화하고 version history와 대부분의 metadata를 보존하지 않으므로 단독 backup으로 인정하지 않는다.
- 정확한 Free license와 잠긴 release에서 Object Lock, legal hold, lifecycle expiration, version enumeration·read와 hard purge를 기능 시험한다.

납품·판매·재배포가 없는 소규모 내부 운영은 다음 1번으로 승인한다. 사용형태나 가용성 요구가 바뀌면 2번 또는 3번을 재검토한다.

1. AIStor Free 단일 노드 위험을 명시적으로 수용하고 독립 backup·복구 시험을 유지한다.
2. AIStor Enterprise 계열로 전환한다.
3. 조직 표준 S3-compatible 저장소로 이관한다.

## 6. Bucket 구성

Bucket은 environment별로 분리하며 DEV와 Pilot/운영 credential을 공유하지 않는다.

| Bucket | Versioning | Object Lock | 기본 보존 | 용도 |
|---|---|---|---:|---|
| `secai-evidence-staging` | 비활성 | 없음 | incomplete·검증 전 임시 object 24시간 | upload·scan·검증 전 임시 object. 보존할 실패자료는 quarantine으로 승격 |
| `secai-evidence-quarantine` | 활성 | `GOVERNANCE` | 1,095일 | malware·변조·인증·Schema 실패 object. 전용 key·credential로 격리 |
| `secai-evidence-original` | 활성 | `COMPLIANCE` | 1,095일 | 승인된 package·manifest·원시 evidence·수동 증적 |
| `secai-evidence-derived` | 활성 | `GOVERNANCE` | 1,095일 | normalized evidence와 재생성 가능한 파생 artifact |
| `secai-reports-official` | 활성 | `COMPLIANCE` | 1,095일 | 승인·서명된 공식 report |
| `secai-audit-archive` | 활성 | `GOVERNANCE` | 1,095일 | 감사 bundle, backup manifest, 삭제 증명 |
| `secai-export-temp` | 비활성 | 없음 | 24시간 | 사용자가 요청한 임시 export |

`staging`과 `export-temp`의 24시간은 임시 처리·전달 수명을 뜻하며 증적 보존기간의 예외가 아니다. 원본성, 보안사고, 검증 실패 또는 감사상 보존할 가치가 확인된 자료는 임시 Bucket에 남기지 않고 해당 지속 보관 Bucket으로 승격해 1,095일을 적용한다.

### 6.1 Bucket 생성 Gate

`object-init` one-shot job은 다음을 확인하고 예상값과 다르면 실패한다.

- Bucket 이름과 environment prefix
- versioning 상태
- Object Lock 활성화와 default retention mode·기간
- bucket encryption과 KMS key ID
- bucket policy와 service access key 권한
- lifecycle rule과 event/audit 설정
- public access 없음
- anonymous list·get·put 없음
- trusted NTP와 server time 상태

원본 bucket은 가능한 한 최초 생성 시 Object Lock을 활성화한다. 기존 bucket에 나중에 활성화할 수 있는 제품 기능이 있더라도 운영 기준으로 의존하지 않는다. 잘못 만든 bucket은 이름만 바꿔 재사용하지 않고 새 bucket을 생성해 검증한 후 이관한다.

## 7. Object key와 Metadata

### 7.1 Object key

```text
org/{organization_id}/asset/{asset_id}/job/{job_id}/attempt/{execution_attempt_id}/
package/{package_id}/{artifact_type}/{sha256}.{extension}
```

- 모든 ID는 opaque UUID다.
- hostname, 사용자 이름, SID, Control 실제값과 Finding 상태를 key에 넣지 않는다.
- 경로 separator는 `/`만 사용하고 `..`, backslash, user-supplied path를 허용하지 않는다.
- 같은 key를 덮어쓰지 않는다. 논리 변경은 새 artifact ID와 새 key를 만든다.
- 조직 간 또는 자산 간 cross-scope deduplication은 접근·hold·파기 경계를 흐리므로 사용하지 않는다.
- object key 생성은 server code만 수행하고 Collector·Browser 입력을 연결하지 않는다.

### 7.2 허용 metadata

| Key | 값 |
|---|---|
| `secai-artifact-type` | `audit-package`, `manifest`, `manual-evidence`, `report` 등 고정 enum |
| `secai-schema-version` | 검증한 JSON Schema version |
| `secai-job-id` | UUID |
| `secai-asset-id` | UUID |
| `secai-sha256` | lowercase SHA-256 |
| `secai-retention-class` | 승인된 retention class ID |
| `secai-created-at` | UTC timestamp |
| `secai-validation-id` | validation 실행 UUID |

Metadata와 tag는 검색 편의 정보이며 retention·hold·업무 상태의 정본이 아니다. password, token, 사용자 이름, 원시 설정값, malware 이름과 presigned URL을 metadata에 넣지 않는다. Object Lock이 있는 bucket에서 metadata 변경은 새 version을 만들 수 있으므로 승인된 원본 metadata를 사후 수정하지 않는다.

## 8. 수신·검증·승격 절차

```text
Collector / Browser
→ Gateway·API 인증/RBAC/size 제한
→ staging에 streaming upload + SHA-256 계산
→ ClamAV scan
→ archive path·size·file count·compression 검증
→ JSON Schema·중복 key·encoding 검증
→ Manifest signature·만료·nonce·Job·Asset scope 검증
→ archive·file·evidence hash 검증
→ 금지 secret·과수집 field 검사
→ original bucket에 새 key로 copy/PUT + COMPLIANCE retention
→ HEAD로 version ID·size·hash·retention 재검증
→ PostgreSQL ACCEPTED + Queue Outbox commit
→ staging object 정리
```

### 8.1 수신 원칙

- Collector와 Browser에 AIStor access key를 주지 않는다.
- MVP upload는 API가 proxy·streaming 처리한다.
- API는 request body 전체를 memory에 올리지 않고 byte·time·file count 한도를 적용한다.
- multipart upload가 중단되면 24시간 안에 abort·정리한다.
- ClamAV가 준비되지 않았거나 scan 결과를 확인할 수 없으면 fail closed하고 승격하지 않는다.
- archive는 검증 전 preview, browser rendering, AI 분석 또는 자동 실행하지 않는다.
- object의 S3 ETag를 SHA-256으로 오해하지 않고 애플리케이션이 계산한 SHA-256을 사용한다.

### 8.2 DB와 Object 원자성

Object store와 PostgreSQL은 하나의 transaction을 공유하지 않으므로 다음 상태를 둔다.

```text
UPLOAD_RESERVED → STAGED → VALIDATING → PROMOTING
→ ACCEPTED → BACKUP_PENDING → BACKUP_VERIFIED

실패: REJECTED / QUARANTINED / ORPHAN_RECONCILE_REQUIRED
```

1. API가 먼저 PostgreSQL에 object key와 예상 hash를 예약한다.
2. 검증 후 원본 object를 작성하고 exact version ID를 받는다.
3. HEAD로 size, metadata, retention과 hash를 확인한다.
4. DB에 version ID·hash·retain-until을 기록하고 다음 Outbox event를 동일 transaction에 만든다.
5. DB commit 전후 장애는 reconciliation이 예약 row와 object metadata를 비교해 복구한다.

COMPLIANCE object는 조기 삭제할 수 없으므로 연결되지 않은 orphan을 만들지 않는 것이 중요하다. 잠긴 orphan이 생기면 숨기거나 이름을 재사용하지 않고 DB에 등록해 보존·용량·파기 대상으로 추적한다.

### 8.3 승격 실패

| 실패 | 처리 |
|---|---|
| malware 탐지·의심 | quarantine 이동, 공식 판정 금지, 보안 event |
| signature·nonce·scope 실패 | quarantine 또는 즉시 거부, replay 감사 |
| hash 불일치 | quarantine, `HASH_MISMATCH`, 원본 승격 금지 |
| Schema·encoding·archive 위반 | quarantine 승격, 공식 판정 금지, 1,095일 보존 |
| AIStor unavailable | Job `STORAGE_PENDING/FAILED`, 판정 시작 금지 |
| KMS unavailable | write·read fail closed, 암호화 우회 금지 |
| PostgreSQL unavailable | 원본 확정 중지, staging 유지 한도 내 retry |

### 9.2 기간 우선순위

```text
Legal hold
> 적용 법령·계약·사고 대응 명령
> 승인된 기관별 연장 정책
> 이 문서의 기본 기간
```

- 기간은 짧아지는 방향으로 자동 재계산하지 않는다.
- Job 삭제, 사용자 탈퇴, 자산 폐기와 UI 숨김은 원본 즉시 삭제를 의미하지 않는다.
- backup은 primary보다 먼저 만료시키지 않는다.
- 동일 evidence set의 artifact 기간이 다르면 공식 판정 재현에 필요한 범위에서 가장 긴 기간을 적용한다.
- 보존 종료 시각은 UTC로 저장하고 AIStor retention 상태와 매일 대조한다.

## 10. Object Lock과 Legal hold

### 10.1 COMPLIANCE 원본

- 원본과 공식 report는 `COMPLIANCE` mode를 사용한다.
- COMPLIANCE 기간 동안 root를 포함한 어떤 사용자도 object version을 수정·삭제하거나 retention을 단축할 수 있다고 가정하지 않는다.
- 승인된 object는 새 version으로 교정하지 않는다. 정정본은 새 artifact로 만들고 이전 원본과 관계를 기록한다.
- 모든 write는 unique key를 사용해 불필요한 noncurrent version을 만들지 않는다.
- retention date 계산은 신뢰된 NTP를 사용하며 clock drift를 경보한다.

### 10.2 GOVERNANCE 파생 자료

- 재생성 가능한 파생 artifact와 audit archive는 `GOVERNANCE`를 사용할 수 있다.
- 일반 API·Worker·관리자에게 `s3:BypassGovernanceRetention` 권한을 주지 않는다.
- Bypass는 retention operator 전용 break-glass 계정과 두 사람 승인으로만 사용한다.
- Bypass 사용은 object 내용 조회와 분리하고 반드시 감사한다.

### 10.3 Legal hold

- 보안사고, 감사, 분쟁, 조사 또는 법무 요청이 있으면 object-level legal hold를 적용한다.
- hold는 package 하나가 아니라 관련 원본·파생본·report·backup manifest의 evidence set 전체에 적용한다.
- Object legal hold는 기존 version에만 적용되므로, hold 대상 Job에서 이후 생성되는 artifact도 애플리케이션이 자동 hold 대상으로 표시한다.
- hold 설정과 해제는 보안담당자 요청 + 승인자 승인 + retention operator 실행으로 분리한다.
- hold 해제 후에도 원래 retention이 남아 있으면 삭제하지 않는다.
- hold 해제는 즉시 파기를 뜻하지 않으며 새 파기 검토를 요구한다.

## 11. 데이터 최소화와 금지 정보

불변 저장 전에 다음을 검증한다.

- Collector allowlist의 승인 field만 존재하는지
- PC-12 `DefaultPassword`가 값이 아니라 존재 여부만 담는지
- token, password, cookie, private key, connection string과 전체 Registry export가 없는지
- 자유 형식 PowerShell stdout, 사용자 문서와 browser history가 없는지
- 사용자 이름 대신 필요한 범위의 SID만 사용하는지
- hostname·serial·MAC은 승인된 asset binding 정책에서만 포함하는지
- raw 값이 판정에 필요한 최소 구조인지

COMPLIANCE object에서 뒤늦게 비밀정보가 발견되어도 조기 삭제가 불가능할 수 있다. 이 경우 즉시 접근을 차단하고 incident를 등록하며, 보안·법무·개인정보 책임자가 격리와 후속 조치를 결정한다. 공유 KMS key를 임의 폐기해 다른 증적까지 복구 불가능하게 만들지 않는다.

개발 환경에는 합성 data만 사용한다. 실제 원본을 사용하려면 TLS, KMS, Object Lock, 감사, backup·restore와 파기 Gate를 모두 통과해야 한다.

## 12. 암호화와 Key 관리

### 12.1 전송 중

- AIStor의 API·관리 통신은 내부 network에서도 TLS 1.2 이상을 사용한다.
- 인증서 검증을 끄지 않으며 내부 CA를 명시적으로 신뢰한다.
- Container healthcheck도 가능한 범위에서 인증된 TLS endpoint를 사용한다.
- 외부 host로 분리하면 API·Worker와 AIStor 사이에 mTLS 적용을 검토한다.
- AIStor S3 port와 Console port는 일반 host interface에 publish하지 않는다.

### 12.2 저장 중

- AIStor, MinIO KMS와 Vault 계열 Secret Manager를 각각 독립 container로 구성하고 SSE-KMS를 활성화한다.
- MVP 외부 HSM 후보는 운영 mode OpenBao의 Transit key다. MinIO KMS가 실제 key material을 보관하거나 export하지 않고 승인된 Transit 연산만 요청하도록 구성한다.
- OpenBao와 MinIO KMS 연동은 운영 반입 Gate에서 실증한다. Vault API 호환성 또는 복구시험이 실패하면 MinIO KMS가 공식 지원하는 HashiCorp Vault로 전환한다.
- KMS 연결 전 real evidence 저장을 허용하지 않는다.
- host의 `evidence_data` volume도 OS·storage encryption을 적용해 defense-in-depth를 구성한다.
- 평문 static HSM key file은 합성 DEV의 초기 bootstrap 시험 외에 상시 보관하지 않으며 production·real Pilot에서 사용하지 않는다.
- KMS credential과 TLS private key는 OpenBao 또는 승인된 Vault에서 짧은 수명의 read-only file·memory 형태로 주입하며 Compose environment와 image에 넣지 않는다.
- root access key, KMS key와 backup encryption key를 repository, `.env`, log와 backup data 옆에 저장하지 않는다.

### 12.3 Key lifecycle

- key owner와 object store operator를 분리한다.
- KMS key material과 설정 backup은 object data와 다른 계정·매체에 보관한다.
- key는 최소 연 1회 또는 사고·인력 변경·노출 의심 시 교체 검토한다.
- 이전 object를 해독하는 key는 해당 object와 backup의 보존기간 종료까지 복구 가능해야 한다.
- key 교체·복구 시험 없이 key ID를 변경하지 않는다.
- KMS 장애 시 AIStor가 기동·복호화되지 않을 수 있음을 장애 runbook과 RTO에 반영한다.

### 12.4 Bucket별 암호화 적용

모든 Bucket은 임시·격리·원본 여부와 관계없이 외부 KMS 또는 KES가 관리하는 **SSE-KMS**를 기본 저장 암호화로 사용한다. Client가 임의 암호화 방식을 선택하게 하지 않고 Server의 Bucket 정책이 암호화를 강제하며, 암호화 header가 없거나 승인되지 않은 key ID를 지정한 write는 거부한다.

| 보호 영역 | KMS key 경계 | 추가 보호 |
|---|---|---|
| staging·임시 export | environment별 ingestion/export key | 24시간 lifecycle, public access 금지 |
| quarantine | 원본과 분리된 quarantine 전용 key | 별도 Bucket·credential, `GOVERNANCE` 1,095일, 일반 preview·download 금지 |
| original | environment별 evidence 원본 key | `COMPLIANCE` 1,095일, versioning, legal hold |
| derived·official report | 원본과 분리 가능한 derived/report key | 목적별 최소권한 writer, 원본 write 권한 없음 |
| audit archive | audit 전용 key | application 관리자와 분리된 감사 접근권한 |
| 독립 backup | primary와 다른 backup key·계정 | 다른 failure domain, 전송·저장 암호화, 불변 media |

- DEV와 Pilot/운영은 KMS key, CA, service credential과 Bucket을 공유하지 않는다.
- quarantine key 접근자는 원본 reader와 분리하고 incident 승인 없이 decrypt하지 못하게 한다.
- PostgreSQL의 증적 metadata와 Finding도 database volume encryption과 backup encryption을 적용하고, application field 중 별도 암호화가 필요한 값은 인증·개인정보 정책에서 확정한다.
- Hash는 변경 탐지, 전자서명은 생산자·승인자 확인, 암호화는 기밀성 보호, Object Lock은 삭제·변경 방지를 담당한다. 한 기능을 다른 기능의 대체수단으로 사용하지 않는다.

### 12.5 Container와 network 분리

MVP는 운영 전환 때 애플리케이션 code나 암호화 계약을 다시 작성하지 않도록 처음부터 다음 논리 경계를 사용한다.

```text
secai-app-network
├─ Web / Worker / PostgreSQL / Redis
└─ AIStor

secai-kms-network
├─ AIStor
└─ MinIO KMS

secai-vault-network
├─ MinIO KMS
└─ OpenBao 또는 승인된 Vault
```

- Web·Worker는 MinIO KMS와 Secret Manager에 직접 접속하지 않는다.
- AIStor는 MinIO KMS에만 접속하고 Secret Manager에는 직접 접속하지 않는다.
- MinIO KMS만 제한된 identity로 승인된 HSM/Transit 연산을 요청한다.
- MinIO KMS와 Secret Manager port는 외부 host interface에 공개하지 않는다.
- 모든 container는 `privileged: false`, 최소 capability, 필요한 volume만 mount, Docker socket mount 금지와 image digest 고정을 적용한다.
- 같은 Windows 11 host의 container 분리는 개발 편의를 위한 논리 격리이며 host·Docker 관리자 침해를 막는 독립 보안경계로 간주하지 않는다.

### 12.6 OpenBao 운영 기준과 최상위 Key

- OpenBao `dev` mode는 금지하고 TLS, persistent Raft storage, seal/unseal, audit와 backup을 적용한 운영 mode로 실행한다.
- MinIO KMS의 HSM 용도 Transit key는 OpenBao 내부에서 생성하며 평문 key export를 허용하지 않는다.
- MinIO KMS의 AppRole은 지정 Transit key의 필요한 encrypt/decrypt 연산만 허용하고 key export·delete·policy 관리 권한을 주지 않는다.
- OpenBao 초기화는 Shamir 5개 share와 threshold 3을 기본값으로 하며 share는 서로 다른 담당자·기관 금고·재해복구 장소에 오프라인 보관한다.
- OpenBao root token은 초기 정책 구성과 비상 복구 외에 사용하지 않고 일상 service에 제공하지 않는다.
- Secret Manager seal·장애·인증 실패 시 MinIO KMS와 AIStor는 평문 저장으로 우회하지 않고 fail closed한다.
- 외부 Secret Manager가 정상 복구되기 전에는 HSM·CMK를 삭제하거나 기존 key ID를 교체하지 않는다.

### 12.7 개발에서 운영으로의 배치 전환

| 단계 | 배치 | 허용 data | 필수 조건 |
|---|---|---|---|
| DEV MVP | 동일 Windows 11 host의 독립 container | 합성·비식별 시험 data | 운영 mode OpenBao, TLS, 분리 network·volume, DEV 전용 key |
| PILOT | 애플리케이션 영역과 KMS·Secret Manager 보안 VM 분리 | 승인된 제한적 실제 증적 | OpenBao 호환성, backup·restore, key rotation, fail-closed 시험 통과 |
| 운영 | 별도 보안 VM 또는 server의 MinIO KMS·승인 Secret Manager | 실제 기반시설 증적 | 조직 운영승인, 독립 backup, 관측·사고대응·복구훈련 완료 |

- DEV·PILOT·PROD는 Unseal share, HSM/Transit key, KMS CMK, CA, service credential과 Bucket을 공유하지 않는다.
- endpoint는 설정으로 주입하며 code와 Schema에 `localhost`, container IP 또는 host 고정 경로를 넣지 않는다.
- 같은 host에서 실제 기관 증적을 사용하려면 별도 위험 수용 승인이 필요하고, 중요정보통신기반시설 실제 증적은 보안 VM 또는 server 분리 전 반입하지 않는다.

## 13. 접근통제

AIStor policy는 service account를 최소권한으로 분리한다. 정확한 역할별 업무 권한은 후속 RBAC 표에서 확정한다.

| 계정 | 허용 | 금지 |
|---|---|---|
| `evidence-ingest` | staging PUT·multipart abort·자기 upload HEAD | original read, retention, delete, bucket list |
| `evidence-validator` | staging GET, 승인 key의 original PUT, HEAD | delete, governance bypass, Console 관리 |
| `evidence-reader` | DB가 허가한 exact key/version GET | bucket-wide list, put, delete |
| `report-writer` | derived/report의 새 key PUT·HEAD | original write·delete |
| `retention-operator` | lifecycle·retention·legal hold의 승인된 관리 | 원본 content의 일상 조회 |
| `backup-exporter` | version·retention metadata와 exact object read | primary delete·retention 변경 |
| `audit-reader` | audit metadata·삭제 증명 read | 원본 본문 read |
| root/break-glass | 복구에 필요한 제한된 관리 | 상시 application 사용 |

- Browser·Collector는 S3 credential을 받지 않는다.
- 모든 원본 조회·download는 API가 인증, 역할, 조직, 자산과 Job scope를 다시 검사한다.
- MVP는 API proxy download를 기본으로 한다.
- Presigned URL이 필요해지면 exact version, 60초 이하, 단일 object, response header 고정과 발급·사용 감사를 요구한다.
- AIStor Console은 기본 비공개이며 운영자 관리 network에서만 일시 접근한다.
- root credential은 offline break-glass로 보관하고 정기 application call에 사용하지 않는다.
- service access key는 서비스별로 분리하고 최소 90일마다 rotation 가능성을 시험한다.

## 14. 조회·내보내기

- 조회는 항상 PostgreSQL object row에서 bucket, key, version ID와 expected SHA-256을 얻는다.
- latest version을 묵시적으로 읽지 않고 exact version ID를 지정한다.
- stream 시작 전과 필요 시 종료 후 size·hash를 확인한다.
- `Content-Disposition` filename은 server가 고정하고 object key나 user input을 그대로 사용하지 않는다.
- 원본 package는 browser inline rendering하지 않고 안전한 download로 제공한다.
- quarantine object는 일반 UI download·preview를 제공하지 않는다.
- 대량 export는 승인, 범위·만료·암호화, watermark 또는 별도 전달 통제를 적용한다.
- export 임시 file과 link는 24시간 뒤 만료하며 source retention에는 영향을 주지 않는다.

## 15. Backup 정책

### 15.1 목표

| 항목 | MVP 기준 |
|---|---|
| RPO | 마지막 성공한 version-aware 독립 backup 기준 최대 1시간 |
| RTO | 격리된 복구 환경에서 Core 조회를 8시간 안에 복구 |
| Backup 위치 | primary와 다른 host·계정·storage failure domain |
| 암호화 | 독립 backup key로 전송·저장 암호화 |
| 불변성 | primary retention과 동등한 삭제 방지 또는 offline immutable media |
| 복구 검증 | 월간 표본, 분기별 전체 시나리오 |

이 값은 MVP·소규모 내부 운영 목표이며 AIStor Free 제조사 SLA가 아니다. 정식 운영의 목표는 PostgreSQL과 원본 증적 RPO 15분·RTO 4시간이지만, AIStor Free 단일 노드로 실증하지 못하면 Enterprise 또는 다른 복제 가능한 S3 저장소로 전환한다.

### 15.2 Backup 내용

- exact object bytes
- bucket, object key와 source version ID
- SHA-256, size, media type, created·accepted time
- retention mode·retain-until과 legal hold 상태
- object metadata와 최소 tag
- PostgreSQL의 object 관계·Job·Finding·hold·delete 상태
- Audit Pack과 JSON Schema exact version
- AIStor bucket policy·configuration export
- KMS configuration과 별도 보호된 key recovery material
- signed backup inventory와 실행 log

### 15.3 실행 주기

- 승인 원본과 공식 report는 1시간 이내 독립 backup에 포함한다.
- version-aware exporter를 최소 매시간 실행해 신규·변경 artifact를 복사한다.
- 매주 primary inventory와 backup inventory 전체를 대조한다.
- 매월 offline 또는 별도 보안영역의 immutable copy를 만든다.
- 마지막 검증 backup이 1시간을 넘으면 `BACKUP_OVERDUE` 경보를 발생시키고 실제 증적 신규 접수를 제한한다.
- 공식 승인 workflow는 관련 원본의 `BACKUP_VERIFIED` 상태를 표시한다.

`mc mirror`만으로는 version history·retention·대부분의 metadata가 보존되지 않는다. MVP backup exporter는 PostgreSQL에 기록된 exact version ID별로 object를 읽고 backup target에 source version ID가 포함된 unique key로 저장하며 별도 manifest로 retention·hold metadata를 보존한다.

### 15.4 일관성

1. PostgreSQL backup checkpoint 시각과 snapshot ID를 만든다.
2. Snapshot이 참조하는 모든 `ACCEPTED` object version을 backup inventory에 포함한다.
3. Object bytes를 읽어 source SHA-256과 비교한다.
4. Backup target에서 다시 읽어 SHA-256을 비교한다.
5. 누락·불일치를 포함한 signed backup manifest를 저장한다.
6. 모든 object가 검증된 경우에만 backup 상태를 `VERIFIED`로 바꾼다.

같은 disk의 filesystem snapshot은 빠른 rollback 보조수단일 수 있지만 독립 backup count에 포함하지 않는다.

## 16. Restore 정책

### 16.1 복구 순서

```text
사고 격리·쓰기 중지
→ 새 host/volume과 잠긴 AIStor image 준비
→ TLS·KMS·bucket·policy 복구
→ PostgreSQL snapshot 복구
→ backup manifest 기준 exact object 복구
→ version·retention·legal hold metadata 재적용
→ object SHA-256 전수 검증
→ DB reference와 object inventory reconciliation
→ read-only 검증
→ 보안 책임자 승인 후 write 재개
```

- 손상된 primary 위에 바로 restore하지 않는다.
- Restore 환경은 외부 egress가 차단된 격리 network를 사용한다.
- 복구 object의 backup hash와 DB expected hash가 일치하지 않으면 해당 Job을 사용 가능으로 표시하지 않는다.
- retention과 legal hold를 복원하지 못한 backup은 완전한 복구로 인정하지 않는다.
- object version ID는 target에서 달라질 수 있으므로 source version ID와 restored version ID mapping을 보존한다.
- 복구 중 새 Finding을 만들지 않고 기존 결과는 `RECOVERY_VALIDATING` 상태로 read-only 제공한다.

### 16.2 시험

- 월 1회 무작위 object 최소 20개 또는 전체의 1% 중 큰 수를 복구해 hash를 검증한다.
- 분기 1회 AIStor node·volume 전체 손실을 가정한 복구 rehearsal을 수행한다.
- image, KMS, bucket policy 또는 Schema major 변경 전후 복구 시험을 수행한다.
- 시험은 원본 조회, Finding 관계, report download, retention·hold와 감사 event까지 확인한다.
- 결과에 실제 복구시간, 누락, hash mismatch와 개선 action을 기록한다.

## 17. 파기 정책

### 17.1 파기 후보 생성

Celery Beat는 object를 직접 삭제하지 않고 PostgreSQL에서 다음 조건을 만족하는 후보만 생성한다.

- `retain_until`이 현재 UTC보다 이전
- active legal hold 없음
- incident·감사·분쟁·승인 workflow 참조 없음
- 관련 artifact와 backup retention 관계 확인
- object key, exact version ID와 expected hash 존재
- 정책 version과 승인 가능한 담당자 확인

### 17.2 승인과 실행

```text
만료 후보
→ security officer 검토
→ approver 승인
→ retention operator dry-run
→ exact version hard delete
→ 모든 version·Delete Marker 부재 확인
→ backup purge due date 등록
→ 삭제 증명 생성·감사 archive 저장
```

- application 일반 계정과 관리자 UI는 직접 `DeleteObjectVersion`을 호출하지 않는다.
- 대량 파기는 manifest에 대상 목록과 hash를 고정한 후 두 사람 승인을 받는다.
- 일반 DELETE로 생긴 Delete Marker를 영구 파기로 처리하지 않는다.
- 삭제 완료는 exact version GET 실패만으로 판단하지 않고 version inventory에서 object version과 Delete Marker가 모두 제거되었는지 확인한다.
- lifecycle scanner는 만료 즉시 실행된다고 보장하지 않으므로 `DUE`, `DELETE_REQUESTED`, `DELETED`, `DELETE_FAILED`를 구분한다.
- backup copy는 primary 승인 삭제 후 최대 35일 안에 해당 media cycle에서 제거하고 결과를 연결한다.

### 17.3 AIStor Free 파기 Gate

AIStor Free에서 version-specific deletion이 제한되면 versioned original의 영구 파기가 불가능할 수 있다. 이 경우:

- Delete Marker 생성만으로 `DELETED`를 표시하지 않는다.
- 파기 상태를 `DELETE_BLOCKED_PRODUCT_LIMIT`로 기록한다.
- 보존 종료 전에 Enterprise upgrade 또는 영구 삭제를 지원하는 조직 S3 저장소로 검증된 migration을 완료한다.
- migration 후 source와 target의 hash·retention·hold를 대조하고 승인된 cutover·파기를 수행한다.
- 파기 가능성을 검증하지 못한 환경에는 법적 삭제기한이 있는 실제 data를 반입하지 않는다.

### 17.4 삭제 증명

삭제 후 원본 본문 대신 다음 최소 metadata를 1,095일 보존한다.

- deletion request·approval ID
- bucket, object key의 hash 또는 제한된 key, source version ID
- object SHA-256와 size
- retention class, retain-until, hold 확인 결과
- 실행자 service identity와 실행·검증 시각
- S3 request ID와 결과 code
- backup purge due/completed 시각
- deletion manifest SHA-256와 signature

## 18. Malware 격리 정책

- quarantine은 original bucket과 별도 credential·prefix가 아니라 별도 bucket으로 운영한다.
- Worker, AI, browser preview와 일반 download가 quarantine을 읽지 못하게 한다.
- 악성 의심 object를 자동 압축 해제·실행·index·embedding하지 않는다.
- 보안담당자가 사고 분석을 승인한 경우에만 격리 분석 환경으로 복사한다.
- 분석 copy에는 network·filesystem·tool sandbox를 적용한다.
- false positive 해제는 최신 signature로 재검사하고 package 전체 검증을 처음부터 다시 수행한다.
- 격리 해제 object를 원래 key로 이동하지 않고 새 validation ID와 새 original key로 승격한다.
- incident·감사·분쟁이 1,095일 이후에도 계속되면 만료 전에 legal/incident hold를 적용해 보존을 연장한다.

## 19. Audit와 관측

### 19.1 필수 감사 event

- upload 시작·완료·실패·abort
- malware scan 결과와 definition version
- Schema·signature·nonce·scope·hash 검증 결과
- staging→original 승격과 exact version ID
- read·download·export와 요청 사용자·자산 scope
- service access key 생성·rotation·폐기
- bucket policy·versioning·encryption·retention 변경
- legal hold 설정·해제
- backup·restore·hash 검증
- 파기 후보·승인·실행·실패
- root·break-glass와 governance bypass 사용

AIStor audit webhook은 모든 S3 API operation을 외부 audit receiver에 전달하도록 구성한다. `Authorization`, security token, presigned query와 불필요한 header를 filter하며 object 본문을 log에 남기지 않는다. Receiver 장애를 대비해 persistent event queue와 용량 경보를 구성한다.

### 19.2 Metric과 경보

- Bucket별 object·version·Delete Marker 수와 bytes
- locked bytes와 retention 만료 분포
- active legal hold 수
- staging·quarantine oldest age
- orphan·hash mismatch·reconciliation backlog
- backup last success, RPO age, inventory mismatch
- restore test last success와 실제 RTO
- KMS·TLS certificate·NTP 상태
- audit webhook queue와 drop·retry 수
- disk usage, inode, I/O latency와 AIStor health
- `DELETE_BLOCKED_PRODUCT_LIMIT` 수

### 19.3 용량 기준

```text
필요 원본 용량
= 일일 점검 수 × 평균 package 크기 × 1,095일
+ quarantine·derived·수동 증적·공식 report·audit archive의 1,095일 예상량
+ version·metadata overhead
+ 25% 운영 여유
```

| 사용률 | 조치 |
|---:|---|
| 70% | 경고, 90일 예측과 증설 계획 확인 |
| 80% | 위험, 신규 대량 Job·AI 파생 artifact 제한 검토 |
| 85% | 신규 Pilot 접수 admission control, 증설·이관 실행 |
| 90% | 비필수 write 중지, incident 운영. 잠긴 원본 임의 삭제 금지 |

Object Lock data는 기간 전 삭제할 수 없으므로 capacity 부족을 lifecycle 삭제로 해결하려 하지 않는다.

## 20. 장애 시 동작

| 장애 | 유지 기능 | 제한·금지 |
|---|---|---|
| AIStor unavailable | PostgreSQL의 기존 요약·Finding 조회 | 신규 원본 수신·보고서 생성·원본 download·새 판정 중지 |
| KMS unavailable | KMS 비의존 상태 페이지 | 암호화 우회, 기존 원본 복호화·신규 저장 금지 |
| ClamAV unavailable | 기존 결과 조회 | 신규 package 승격 금지 |
| PostgreSQL unavailable | AIStor health 확인 | object를 업무 정본으로 추측 연결하거나 새 승격 금지 |
| hash mismatch | 영향 없는 다른 Job 조회 | 해당 artifact 판정·AI·export 금지, incident·복구 검토 |
| disk 85% 이상 | 기존 read 우선 | 신규 접수 제한, locked object 삭제 금지 |
| backup 24시간 초과 | primary read | `BACKUP_OVERDUE`, Pilot 신규 접수·최종 승인 제한 검토 |
| audit receiver 장애 | persistent queue 범위의 S3 처리 | queue 포화 시 destructive admin operation 제한 |
| NTP 이상 | 기존 read | 새 COMPLIANCE retention write 중지 검토 |

원본을 읽을 수 없거나 hash를 확인하지 못하면 규칙 엔진은 기존 Finding을 재평가하거나 새 공식 판정을 생성하지 않는다.

### 21.5 IMP-045 개발 복구훈련 결과

2026-07-24에 실제 기관 증적 대신 `SYNTHETIC_DEV_ONLY` object로 다음 개발 Gate를 통과했다.

- AIStor primary 중단·재시작 뒤 exact version SHA-256 일치
- 같은 host의 별도 전용 volume에 object backup 복원, source version mapping과 SHA-256 일치
- PostgreSQL logical backup을 별도 전용 volume에 복원, Finding 계보·artifact inventory·migration 일치
- Redis 전체 중단 뒤 빈 broker에 PostgreSQL PENDING Outbox 재발행, 논리 결과 한 건 수렴
- PostgreSQL RPO 4초/RTO 10초, 합성 증적 RPO 0초/RTO 10초, Redis 재구축 57초
- 장애 중 공개 API에서 원본·object key·version ID·backup 경로·secret·stack trace 미노출

이 결과는 위 21.4의 “다른 failure domain”, KMS·OpenBao·SSE-KMS, Object Lock·legal hold, 실제 기반시설 증적과 node·volume 전체 손실 Gate를 체크하지 않는다. 복구본은 같은 개발 PC에 있어 독립 재해복구 사본이 아니며 `production_gate_complete=false`를 유지한다. 상세 기록과 재현 명령은 [`deploy/verification/IMP045_저장소_장애_백업_복원_검증.md`](../../deploy/verification/IMP045_저장소_장애_백업_복원_검증.md)를 따른다.

## 22. 제품 전환·Migration 조건

다음 중 하나가 발생하면 저장소 전환 검토를 의무화한다.

- HA 또는 1시간보다 짧은 증적 RPO가 필요함
- Free single-node 장애 위험을 기관이 수용하지 않음
- server-side replication이 필요함
- version-specific permanent deletion이 정책 기한 안에 불가능함
- 용량·성능·운영 지원이 MVP 범위를 초과함
- Free license 조건이나 제품 지원 상태가 변경됨
- Object Lock·KMS·audit 기능이 locked release에서 요구대로 동작하지 않음

Migration은 다음을 만족한다.

1. target 제품·license·image·S3 compatibility 승인
2. bucket·versioning·Object Lock·KMS·IAM 선구성
3. source version별 exact bytes와 metadata export
4. target SHA-256·retention·hold 재검증
5. PostgreSQL version mapping과 object reference 전환
6. read-only parallel 검증과 rollback 기간
7. 승인 후 source 파기 또는 남은 retention 유지
