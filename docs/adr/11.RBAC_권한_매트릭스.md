## 1. 결정 요약

Sec_AI의 사람 계정은 다음 네 역할을 사용한다.

| 역할 ID | 한글명 | 핵심 책임 | 자동으로 갖지 않는 권한 |
|---|---|---|---|
| `USER` | 사용자 | 할당된 자산의 점검 요청·제출·결과 확인 | 원본 증적, 조직 정책, 승인, 사용자 관리 |
| `SECURITY_OFFICER` | 보안담당자 | 조직 범위 자산·증적 검토, 정책·Audit Pack 초안, 승인 요청 | 자기 요청 승인, Audit Pack 활성화, platform root |
| `APPROVER` | 승인자 | 제출된 정확한 version·hash의 승인·반려 | 초안 수정, 승인 후 실행, platform 관리 |
| `ADMIN` | 관리자 | 계정·역할·조직·배포·backup 등 platform 운영 | 원본 증적 본문, 공식 판정 변경, 업무 자기승인 |

관리자는 최고 업무권한 역할이 아니다. `ADMIN`은 platform metadata와 운영을 관리하지만 원본 증적·조직 정책·Finding 본문을 자동으로 열람하지 않는다. 원본 업무 접근이 필요하면 별도의 `SECURITY_OFFICER` assignment와 scope, 사유, 감사가 있어야 한다.

권한은 다음 조건을 모두 만족할 때만 허용한다.

```text
ALLOW
= 인증된 활성 계정
∩ 활성화된 역할의 permission
∩ 조직·자산·Job·승인 범위
∩ 허용된 자원 상태와 version
∩ maker-checker 및 self-approval 제한
∩ 만료되지 않은 session·approval
∩ 명시적 deny 없음
```

RBAC만으로 자원 관계를 표현하지 않고 조직·자산 assignment, 소유관계, 상태와 승인 hash를 함께 확인한다. UI에서 버튼을 숨기는 것은 권한통제가 아니며 full page, HTMX fragment, JSON API, SSE, upload, download와 Celery 후속 작업에서 서버가 권한을 검사한다.

## 2. 기본 원칙

- Deny by default: 표에 없는 action은 거부한다.
- Least privilege: 역할에 필요한 최소 permission만 직접 할당한다.
- No implicit superuser: `ADMIN`도 모든 업무권한을 상속하지 않는다.
- No direct user grant: permission을 사용자에게 직접 주지 않고 역할과 scope를 통해 부여한다.
- No role hierarchy: MVP 네 역할은 서로를 자동 상속하지 않는다.
- Server enforcement: Browser, URL, HTMX header와 client state를 권한 근거로 사용하지 않는다.
- Every request: page, fragment, API, SSE reconnect, download와 export마다 재검사한다.
- Resource scope: UUID를 알고 있어도 조직·자산 관계가 없으면 접근할 수 없다.
- Separation of duty: 작성·요청, 승인, 실행을 가능한 한 다른 identity로 분리한다.
- Version-bound approval: 승인은 resource ID만이 아니라 정확한 content hash·version에 결합한다.
- Immutable official status: 사람 역할은 `PASS/FAIL/REVIEW/ERROR/N/A`를 직접 생성·수정하지 않는다.
- Auditable change: 역할, 범위, 승인, 원본 접근과 고위험 operation은 before/after metadata를 감사한다.
- Service isolation: 사람 역할을 container·Worker·Collector에 할당하지 않는다.

## 3. 범위 모델

### 3.1 범위 코드

| 코드 | 의미 |
|---|---|
| `SELF` | 현재 사용자 자신의 계정·session |
| `ASSIGNED` | 사용자에게 명시적으로 할당된 자산과 그 자산의 Job |
| `CREATED` | 사용자가 생성했으며 아직 다른 자산 범위로 이전되지 않은 draft |
| `ORG` | 역할 assignment에 지정된 organization 전체 |
| `APPROVAL` | 승인 inbox에 제출된 exact resource version과 관련 최소 증적 |
| `GLOBAL-META` | 조직을 넘는 platform metadata. 원본·Finding 본문 제외 |
| `BREAK-GLASS` | 평시 역할표 밖의 시한부 비상 operation |
| `SERVICE` | 내부 workload identity에만 허용되는 범위 |

### 3.2 자원 계층

```text
Organization
├─ User / Role Assignment
├─ Asset Group
│  └─ Asset
│     └─ Audit Job
│        ├─ Manifest / Package / Evidence
│        ├─ Finding / AI Explanation
│        └─ Report / Approval Request
├─ Organization Policy / Manual Attestation
└─ Audit Pack Assignment
```

- 모든 업무 row는 `organization_id`를 가진다.
- Asset은 하나의 organization에 속하고 사용자 assignment는 명시적 join row로 관리한다.
- Job·Evidence·Finding은 parent Asset의 organization을 변경할 수 없다.
- organization 이동은 기존 증적을 재소유시키지 않고 새 Asset을 만들며 이전 관계를 감사한다.
- `created_by`만으로 접근을 허용하지 않는다. 현재 assignment와 자원 상태를 함께 확인한다.
- `ADMIN`의 `GLOBAL-META`는 사용자 ID, 상태, 용량, service health 등을 뜻하며 evidence value·Finding rationale·조직 정책 본문은 제외한다.

### 3.3 표기

| 표기 | 의미 |
|---|---|
| `SELF` | 자기 계정만 허용 |
| `ASSIGNED` | 할당 자산 범위에서 허용 |
| `ORG` | 지정 조직 범위에서 허용 |
| `APPROVAL` | 자신에게 제출된 승인 건에서만 허용 |
| `META` | content 없이 metadata만 허용 |
| `REQ` | 실행하지 않고 승인 요청만 생성 |
| `APP` | 자기 요청이 아닌 exact version을 승인·반려 |
| `EXEC` | 유효한 승인 뒤 실행을 trigger. 실제 privileged call은 service identity가 수행 |
| `—` | 거부 |

복합 표기 `ORG·REQ`는 조직 범위에서 요청만 가능하다는 뜻이다.

### 4.1 역할 assignment 규칙

- `USER`는 기본 업무 역할이며 다른 privileged 역할과 함께 가질 수 있다.
- `SECURITY_OFFICER`와 `APPROVER`는 같은 organization에서 동시에 활성화할 수 없다.
- `APPROVER`와 `ADMIN`은 고위험 승인 domain에서 동시에 활성화할 수 없다.
- `ADMIN + SECURITY_OFFICER` 결합은 합성 data만 사용하는 DEV의 문서화된 예외로 제한하며 별도 `APPROVER`가 반드시 존재해야 한다. 실제 증적을 반입하는 PILOT·운영에서는 허용하지 않는다.
- 어떤 조합에서도 requester, approver와 executor가 동일 approval request에서 겹칠 수 없다.
- 사용자는 자기 역할이나 자기 scope를 요청·승인·실행할 수 없다.
- privileged 역할 변경은 현재 session과 refresh credential을 즉시 무효화하고 재로그인을 요구한다.
- 비활성화된 사용자의 신규 접근은 즉시 차단하되 이미 시작된 Job의 지속 여부는 보안담당자가 결정한다.

### 4.2 Bootstrap

- 최초 설치 계정은 `BOOTSTRAP-ADMIN` 상태로 생성하고 일반 업무 role로 사용하지 않는다.
- Bootstrap은 named `ADMIN`, `SECURITY_OFFICER`, `APPROVER`와 조직을 만든 뒤 폐기한다.
- Bootstrap 상태에서는 합성 data만 허용하고 Audit Pack·report·evidence deletion을 `APPROVED`로 만들 수 없다.
- 실제 증적 Pilot은 requester인 `SECURITY_OFFICER`, checker인 `APPROVER`, executor인 `ADMIN`에 해당하는 서로 다른 최소 3명의 named account가 준비된 뒤 시작한다.

### 4.3 DEV-LOCAL 계정 생성 요청·관리

로그인 전 계정 생성 요청은 인증된 `USER` permission이 아니라 좁게 허용된 pre-authentication workflow다. 요청은 구성에 고정된 단일 개발 organization에 `PENDING_APPROVAL` row만 만들며 role·scope·session을 만들지 않는다. 활성화는 서버에서 `ADMIN`의 `user.account.create` 권한을 다시 확인한 승인 동작으로만 수행한다.

- ADMIN은 같은 organization의 최소 계정 metadata와 상태만 조회한다.
- 승인 시 기본 `USER` 역할만 부여하고 privileged 역할은 별도 maker-checker 절차를 거친다.
- 반려·비활성화·재활성화·개발용 인증 코드 재발급은 CSRF와 감사 기록을 통과한다.
- ADMIN은 자신의 계정을 비활성화할 수 없고 다른 사용자의 password 원문·hash를 볼 수 없다.
- 개발용 인증 코드 원문은 재발급 응답에서 한 번만 사용할 수 있고 DB에는 keyed digest만 둔다.
- Pilot에서는 이 pre-auth workflow를 조직 초대·OIDC provisioning과 사용자 직접 WebAuthn/TOTP 등록으로 교체하며 DEV code 재발급을 비활성화한다.

### 6.1 Job 규칙

- Manifest는 요청자의 role이 아니라 `job_id + asset_id + allowed probe + nonce + expires_at`에 결합한다.
- Job 생성 뒤 사용자 역할이 회수되어도 Worker는 기록된 authorization snapshot과 현재 Job 상태로 안전한 Core 처리를 완료할 수 있다. 보안담당자는 취소할 수 있다.
- 원본 조회, report 승인, 재평가처럼 사람에게 결과를 반환하거나 고위험 상태를 바꾸는 action은 현재 권한을 다시 검사한다.
- Collector job credential은 사람 역할이 아니며 단일 Job·Asset·제출 endpoint·짧은 만료만 가진다.
- Collector와 Browser는 PostgreSQL, Redis, AIStor에 직접 연결하지 않는다.

- `ADMIN`은 저장상태·hash·size·backup·retention metadata를 볼 수 있지만 content를 볼 수 없다.
- quarantine content는 일반 역할로 접근하지 않는다. 사고 분석은 별도 incident approval과 `BREAK-GLASS` 격리환경을 사용한다.
- 원본 download는 사유, 사용자, asset, Job, object version, bytes와 결과를 감사한다.
- Presigned URL을 도입해도 이 permission 검사를 통과한 exact object version에만 60초 이하로 발급한다.

## 15. Service identity 권한표

사람 역할과 workload identity는 같은 table·token·login flow를 사용하지 않는다.

| Identity | 허용 | 금지 |
|---|---|---|
| `gateway` | API reverse proxy, rate limit, TLS 종료 | DB·Redis·AIStor credential, 업무 권한 |
| `audit-api` | 인증, RBAC, Job·approval DB 처리, staging upload, 승인된 exact object stream | bucket-wide delete, retention bypass, rule 판정 |
| `validation-worker` | staging read, scan 결과 확인, Schema·hash 검증, quarantine/original 새 key write | Finding 생성, 원본 삭제, 사용자 관리 |
| `evaluation-worker` | approved Audit Pack read, normalized evidence read, 내부 rule-engine producer 실행, Finding 새 version write | Audit Pack 수정·승인, raw export, 기존 Finding update/delete·공식 상태 override |
| `ai-worker` | Finding·redacted evidence·승인 가이드 read, AI explanation write | raw package·quarantine read, Finding write |
| `outbox-dispatcher` | pending Outbox read·publish·상태 update | 업무 content read, 사용자 action |
| `scheduler` | due candidate·stale row 조회, maintenance task 발행 | S3 delete·hold·role 변경 직접 실행 |
| `retention-operator` | 승인 token에 고정된 exact version의 retention·hold·delete | 임의 대상 선택, 원본 content 일반 read |
| `backup-exporter` | 모든 승인 object version·metadata read, backup target write | primary delete·hold 변경 |
| `object-init` | bucket·versioning·lock·KMS·policy 초기화와 검증 | 상주 실행, 원본 업무 read |
| `audit-receiver` | audit event append | 업무 DB·object read, audit event 수정·삭제 |
| `collector-job` | 단일 Job package HTTPS submit | S3·DB·Redis 직접 접근, 다른 Job 제출 |

`rule-engine`은 `evaluation-worker` 안의 결정론적 논리 모듈이며 별도 workload identity가 아니다. 공식 Finding에는 `source=rule-engine` producer provenance를 기록하되 실제 credential·network·DB 권한은 `evaluation-worker`에만 부여한다.

### 15.1 Workload 통제

- identity별 credential·network·container를 분리한다.
- 사람 session token을 Celery message에 넣지 않는다.
- task에는 opaque ID만 넣고 Worker가 DB에서 현재 상태와 service permission을 다시 확인한다.
- service identity는 사람 role assignment endpoint에 나타나지 않는다.
- service credential은 interactive login과 Browser cookie로 사용할 수 없다.
- PILOT·운영 service credential은 9번 정책에서 승인한 OpenBao 또는 승인된 Vault를 통해 발급·rotation하고 log·environment dump에 노출하지 않는다.
- 합성 DEV의 초기 bootstrap에서 Docker Secret file을 사용할 수 있지만 repository 밖에 두고 PILOT·운영 credential로 재사용하지 않는다.
- `retention-operator`는 approval ID·target hash·만료를 검증한 signed/internal execution grant가 없으면 동작하지 않는다.

## 16. API·UI Enforcement

### 16.1 공통 authorization 함수

```text
authorize(
  subject_id,
  active_roles,
  permission_id,
  organization_id,
  resource_type,
  resource_id,
  resource_version,
  resource_state,
  approval_context
)
```

Route마다 role 문자열을 직접 비교하지 않고 중앙 authorization service를 사용한다. 결과에는 allow/deny, 적용 permission, scope와 일반화된 reason code를 남긴다.

### 16.2 Endpoint

- full page와 HTMX fragment는 같은 application service와 authorization을 사용한다.
- `HX-Request`, hidden button, referer와 URL 난수성을 권한 근거로 사용하지 않는다.
- JSON API, upload, download, SSE와 static하지 않은 모든 resource를 검사한다.
- SSE connect 시 권한을 확인하고 event마다 organization·Job scope를 filter한다.
- 역할 회수·계정 비활성화 시 활성 SSE와 session을 종료한다.
- Background polling도 매 요청 검사한다.
- out-of-scope resource는 ID enumeration을 줄이기 위해 원칙적으로 `404`를 반환하고, 존재를 알아도 되는 동일 scope의 금지 action은 `403`을 사용한다.
- permission denial response에 다른 조직 이름, object key, role 구성과 내부 policy를 노출하지 않는다.

### 16.3 Repository·DB

- 모든 업무 query는 `organization_id`와 필요 시 asset assignment를 조건에 포함한다.
- ID 단독 `SELECT ... WHERE id = :id` 후 application에서 뒤늦게 scope를 검사하는 pattern을 금지한다.
- PostgreSQL Row-Level Security를 defense-in-depth로 검토하되 API authorization을 대체하지 않는다.
- 역할, permission, scope와 approval table 변경은 transaction과 audit event를 함께 기록한다.
- optimistic version과 unique constraint로 이중 승인·중복 실행을 막는다.

- Role ID와 permission ID는 표시문구 변경과 무관한 stable identifier다.

- approval request는 resource version·SHA-256 없이 `APPROVED`가 될 수 없다.

## 18. Break-glass

Break-glass는 역할이 아니며 정상 UI에 버튼으로 제공하지 않는다.

1. 보안사고·복구 등 승인된 사유와 ticket 생성
2. 보안담당자와 승인자의 서로 다른 identity 승인
3. Vault/HSM에서 named operator에게 60분 이내 credential 발급
4. 전용 관리 host·network에서 최소 operation만 수행
5. 모든 command·target·결과를 외부 audit sink에 기록
6. 사용 직후 credential 폐기·rotation
7. 24시간 안에 독립 사후검토와 incident closure

- shared root password를 일상 보관·공유하지 않는다.
- break-glass도 AIStor COMPLIANCE retention을 우회할 수 있다고 주장하지 않는다.
- 원본 content 접근이 필요 없는 장애에는 metadata·health 권한만 발급한다.
- audit sink가 동작하지 않으면 생명·안전 등 사전 정의된 예외 외에는 destructive operation을 중단한다.

- policy·Audit Pack·report 제출·승인·활성화·폐기

- authorization denial 중 수평·수직 권한 상승 의심

- UTC timestamp, correlation ID
- actor type·ID와 active role

## 20. 인증 ADR에 전달할 요구사항

RBAC 표는 인증 수단을 결정하지 않지만 인증 ADR에 다음을 요구한다.

- 모든 계정은 개인별 named identity를 사용하고 공유계정을 금지한다.
- `SECURITY_OFFICER`, `APPROVER`, `ADMIN`은 강한 MFA를 요구한다.
- privileged action은 최근 인증 또는 step-up authentication을 요구한다.
- session에는 user ID, credential version, active role·organization만 최소 저장한다.
- role·scope 변경 시 모든 관련 session·refresh token을 revoke한다.
- session token을 URL, localStorage, log와 Celery payload에 넣지 않는다.
- service identity는 사람 인증·cookie·MFA flow와 분리한다.
- Collector job credential은 단기, 단일 Job·Asset, 1회 또는 제한 사용으로 한다.
- break-glass credential은 60분 이내이며 일반 API token으로 변환할 수 없다.

## 22. 운영 전 승인 Gate

### 22.1 IMP-046 DEV-LOCAL 구현 상태

2026-07-24에 중앙 permission 상수, deny-by-default 정책과 조직·할당 자산 범위를 구현했다. full page, HTMX fragment, JSON API, SSE 연결과 download가 같은 서버 정책을 호출하며 다음 개발 검증을 통과했다.

- 할당 자산은 허용하고 다른 조직·자산은 존재정보 없이 `404`
- 범위 안에서 역할 permission이 없으면 `403`
- `USER`는 원본 증적 download가 자동 허용되지 않음
- logout 또는 role assignment version 변경 뒤 기존 session 재사용 차단
- 허용·거부 결과를 원본 session·자산 식별값 없이 감사 이벤트로 저장

이 단계는 합성 조직과 `USER` 세로 기능의 구현 완료다. 실제 원본 download, 승인·실행 maker-checker, 네 역할의 실제 named account 배치, Celery·AIStor exact-version 권한과 외부 감사 sink는 운영 전 Gate로 남는다. 상세 결과는 `deploy/verification/IMP046_인증_RBAC_웹_보안_검증.md`를 따른다.

- [ ] 네 역할과 scope가 DB·API·UI에 동일하게 구현됨
- [ ] permission ID가 route·service·test에 중앙 상수로 사용됨
- [ ] 표에 없는 새 endpoint가 deny by default로 차단됨
- [ ] 실제 증적 Pilot에 서로 다른 `SECURITY_OFFICER` requester·`APPROVER` checker·`ADMIN` executor named account가 존재함
- [ ] privileged role assignment에 maker-checker가 적용됨
- [ ] ADMIN이 원본을 자동 열람하지 못함
- [ ] 모든 원본 download와 승인 action이 감사됨
- [ ] `evaluation-worker(rule-engine producer)` 외 공식 Finding write가 DB·API에서 차단됨
- [ ] service identity의 network·DB·S3 최소권한 시험 통과
- [x] DEV-LOCAL 수평 IDOR·fragment·SSE·합성 download 보안시험 통과
- [x] DEV-LOCAL role version 변경과 session revoke 즉시 반영
- [ ] 실제 네 역할·원본 증적을 사용한 수직 권한·download Pilot 시험 통과
- [ ] break-glass runbook과 외부 audit sink 시험 통과

## 23. 변경관리

다음 변경은 이 문서의 version 증가와 보안 검토를 요구한다.

- 사람 역할 추가·삭제·상속
- permission ID 또는 scope 의미 변경
- ADMIN에게 업무 content 접근 추가
- 자기 승인 또는 승인자·실행자 결합 예외
- 자동 remediation 역할·permission 추가
- 외부 조직·다중 tenant·SSO group mapping 추가
- API token·presigned URL·service account 범위 확대
- evidence export·retention·delete 절차 변경

권한 확대는 minor 변경으로 처리하지 않고 영향에 따라 major version을 검토한다. 기존 assignment는 새 정책에 자동 승격하지 않으며 migration report와 승인 기록을 남긴다.
