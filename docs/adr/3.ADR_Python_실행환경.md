# ADR-001: Python Runtime 기준

## 현재 구현 상태 (2026-08-07 검토)

- 현재 기준 Runtime은 CPython `3.14.6`, Docker `linux/amd64`다.
- 실제 version 정본은 잠긴 requirements, Dockerfile·image와 `tools/dev.ps1` 검증이며 이 ADR의 원칙을 따른다.
- patch 또는 feature line을 변경할 때는 lock·SBOM·취약점·전체 관련 시험을 새로 통과해야 한다. Host Python만 바꿔 운영 Runtime을 변경하지 않는다.

## 1. 결정 요약

Sec_AI의 자체 개발 Python 코드는 **CPython 3.14 계열의 일반 GIL 빌드**로 통일하고, 최초 구현 기준 patch version을 **CPython 3.14.6**으로 잠근다.

이 결정은 기존 실행 계획서의 Python 3.12 권고를 최신 지원 상태에 맞게 변경하는 제안이다. 이 ADR이 승인되기 전까지 변경은 확정되지 않으며, 승인 후 이 ADR이 Python Runtime에 관한 하위 계획서의 3.12 표현보다 우선한다.

| 결정 항목 | 확정 제안 |
|---|---|
| 구현체 | CPython |
| Feature line | Python 3.14 |
| 최초 patch version | `3.14.6` |
| 실행 형태 | 일반 GIL 빌드 |
| 제외 형태 | free-threaded 빌드, 실험적 JIT 활성화, PyPy 등 대체 구현체 |
| 중앙 서비스 기준 플랫폼 | Linux container, `linux/amd64` |
| Collector 기준 플랫폼 | Windows 11 x64, `windows/amd64` |
| 개발자 로컬 환경 | 동일한 CPython patch version과 서비스별 가상환경 |
| patch 변경 | 검증·잠금파일 재생성·승인 후 허용 |
| feature line 변경 | 별도 ADR 또는 본 ADR 개정 승인 필요 |

## 2. 배경

상위 실행 계획서는 자체 개발 서비스와 Collector를 Python 3.12로 통일하고, 구현 시점에 정확한 patch version과 이미지 digest를 보안 지원 상태를 확인해 잠그도록 요구한다.

2026-07-21 현재 확인 결과는 다음과 같다.

- Python 3.12의 최신 보안 릴리스는 `3.12.13`이지만 3.12 계열은 source-only security 단계다.
- Python 3.12의 마지막 Windows binary installer 제공 버전은 `3.12.10`이다.
- 따라서 Windows Collector를 3.12로 고정하면 최신 보안 patch가 반영되지 않은 installer를 사용하거나, CPython 자체 빌드·검증·유지보수 책임을 프로젝트가 부담해야 한다.
- Python `3.14.6`은 현재 안정적인 maintenance release이고 Windows x64 installer가 제공된다.
- Python 3.14는 약 2027년 10월까지 정기 bugfix와 binary installer를, 약 2030년 10월까지 source-only security fix를 제공할 예정이다.
- PyInstaller는 6.15.0부터 Python 3.14 지원을 명시하고 있으며 현재 안정 문서도 Python 3.8 이상을 지원 대상으로 안내한다.

Sec_AI는 Windows Collector의 재현 가능한 빌드와 보안 patch 적용이 모두 중요하므로, 이미 source-only 단계인 3.12보다 3.14를 기준선으로 선택한다.

## 3. 적용 범위

### 3.1 이 ADR을 적용하는 코드

- FastAPI API와 Static/Jinja2/HTMX 제공 코드
- Celery Worker와 Celery Beat의 자체 개발 task 코드
- Audit Pack loader, JSON Schema validator, 공식 규칙 엔진
- 증적 검증·정규화·판정·보고서 생성 코드
- 자체 개발 관리 CLI, migration/ingest 도구와 운영 보조 script
- Windows 11 One-shot Collector의 Python source와 PyInstaller build environment
- 공통 library와 test code

### 3.2 이 ADR을 적용하지 않는 제품

다음 공식 제품 container의 내부 Runtime은 공급자가 시험한 구성을 유지하며 Python 3.14로 재작성하거나 강제 교체하지 않는다.

- PostgreSQL
- Redis
- MinIO
- ClamAV
- PostgreSQL의 pgvector 확장
- Neo4j
- vLLM
- Wazuh
- 그 밖의 승인된 third-party infrastructure image

공식 image 위에 자체 Python application을 추가하는 경우에는 그 자체 코드가 이 ADR의 적용 대상이다. 예외가 필요하면 8절의 절차를 따른다.

## 4. Runtime 잠금 규칙

### 4.1 공통 규칙

1. 개발, CI, test, 운영 container와 Collector build runner는 동일한 승인 patch version을 사용한다.
2. `python:3.14`, `python:3.14-slim`, `latest`처럼 움직이는 tag만으로 Runtime을 식별하지 않는다.
3. source repository에는 승인된 version을 기계 판독 가능한 Runtime lock manifest로 기록한다. manifest 형식과 위치는 3단계 산출물에서 확정한다.
4. CI는 실행 초기에 CPython과 정확한 patch version을 검사하고 다르면 build를 실패시킨다.
5. free-threaded build와 실험적 JIT는 기본 운영 범위에서 활성화하지 않는다.
6. `PYTHONPATH`나 사용자 site-package에 의존하지 않으며, 서비스별 격리 환경에서 실행한다.
7. 결정론적 규칙은 Python hash, locale, timezone, 파일 나열 순서 같은 환경 의존 값에 결과가 달라지지 않아야 한다.

CI의 최소 Runtime 검사는 다음 의미를 만족해야 한다.

```python
import sys

assert sys.implementation.name == "cpython"
assert sys.version_info[:3] == (3, 14, 6)
```

### 4.2 Linux container

- 3단계에서 `3.14.6`을 포함한 정확한 base image tag와 multi-architecture manifest 또는 `linux/amd64` image digest를 기록한다.
- Dockerfile의 `FROM`은 승인된 digest까지 고정한다.
- build 시점의 tag 해석 결과가 아니라 잠금표의 digest를 배포 기준으로 사용한다.
- application process는 non-root 사용자로 실행하고, Runtime에 불필요한 compiler와 package manager는 최종 image에서 제거한다.
- build stage와 runtime stage를 분리하고, 운영 환경의 온라인 `pip install`을 금지한다.

정확한 image repository, OS variant, tag와 digest는 후속 `requirements/` 및 컨테이너 이미지 잠금표에서 확정한다. 이 ADR은 digest를 추정해 미리 기록하지 않는다.

### 4.3 Windows 11 Collector build

Collector는 Linux에서 cross-build하지 않고 신뢰된 Windows 11 x64 runner에서 만든다.

| 항목 | 잠금값 |
|---|---|
| Python installer | `python-3.14.6-amd64.exe` |
| 배포처 | Python Software Foundation 공식 배포 경로 |
| SHA-256 | `14b3e9a710a3fcf0bd9b55ab6b60412bd91227563f813fc49040cabc0209e0bd` |
| Runtime 형태 | CPython 3.14.6 일반 GIL, x64 |
| packaging | version과 hash가 잠긴 PyInstaller |
| build OS | 승인된 Windows 11 x64 runner image |

Build runner는 다음을 지켜야 한다.

- installer의 SHA-256과 제공되는 Sigstore bundle을 검증한다.
- Windows 서명 검사가 가능한 경우 publisher와 signature 상태도 검증한다.
- PyInstaller 및 모든 build dependency는 3단계의 별도 hash lock을 사용한다.
- build 결과에 Python version, PyInstaller version, source commit, lockfile hash, build runner image ID와 생성 시각을 기록한다.
- 실행 파일에 조직 code-signing을 적용하고 서명 전·후 artifact hash를 기록한다.
- 운영 PC에 Python을 별도로 설치하지 않는다.

## 5. 의존성 관리와의 경계

Python Runtime 결정과 application package 결정은 분리한다.

- 이 ADR은 `CPython 3.14.6`을 정한다.
- 3단계 산출물은 서비스별 direct dependency, transitive dependency, marker, wheel, hash와 container image digest를 정한다.
- package는 `pip-tools`로 compile하고 `pip --require-hashes` 방식으로 설치한다.
- 중앙 서비스, 공통 개발 도구와 Collector build dependency는 서로 다른 입력·잠금파일로 분리한다.
- 승인되지 않은 source distribution의 즉석 compile과 직접 `pip install -U`를 배포 절차에서 금지한다.

3단계에서 필수 package가 Python 3.14.6을 지원하지 않는 사실이 확인되면 이 ADR을 자동으로 무효화하거나 3.12로 조용히 하향하지 않는다. 해당 dependency의 교체, 격리, version 조정 또는 Runtime 예외를 비교한 뒤 ADR 개정 승인을 받는다.

## 6. Patch update 정책

`3.14.x`의 새 patch release는 새 기능 계열 도입이 아니라 유지보수 변경으로 취급하되, 자동 반영하지 않는다.

다음 조건을 모두 통과해야 patch version을 올릴 수 있다.

1. Python 공식 release와 지원 상태 확인
2. 배포 artifact의 SHA-256과 Sigstore 검증
3. package hash lock 재생성 및 변경 검토
4. unit, integration, API, Worker, 규칙 결정성 test 통과
5. Windows Probe와 PyInstaller build/run smoke test 통과
6. container vulnerability scan과 SBOM 생성
7. 이전 결과 package 및 Audit Pack에 대한 regression test 통과
8. Runtime lock, image lock, build manifest와 운영 문서 동시 갱신
9. 변경 승인과 rollback artifact 보존

보안 취약점이 공개된 경우 위험도, 실제 노출 여부와 upstream fix를 확인해 긴급 patch 절차를 적용한다. 지원 중인 binary가 없는 Runtime을 계속 유지하기 위해 임의 source build를 도입하지 않는다. 불가피한 source build는 별도 예외 승인, 재현 가능한 build recipe, compiler/toolchain 잠금, SBOM, 서명과 독립 검증을 요구한다.

## 7. Feature line upgrade 정책

Python `3.15` 이후 계열로의 변경은 다음을 포함하므로 본 ADR 개정 또는 별도 ADR이 필요하다.

- language와 standard library의 비호환 변경
- package와 native wheel 지원 상태
- PyInstaller hook와 bootloader 호환성
- container base image와 OS library 변경
- 성능, 메모리와 동시성 특성
- 기존 Audit Pack 결과의 결정성 회귀

지원 종료 12개월 전부터 차기 feature line을 평가하고, 지원 종료 전에 운영 전환을 완료한다.

## 8. 예외 정책

Runtime 예외는 다음 정보를 가진 승인 기록 없이는 허용하지 않는다.

- 대상 component와 owner
- 예외가 필요한 package 및 재현 가능한 실패 근거
- 선택 Runtime의 정확한 version과 artifact/image digest
- 보안 지원 종료일
- network와 data 접근 범위
- 보완 통제와 취약점 monitoring 방법
- 만료일, 제거 조건과 migration 일정

예외 component는 별도 process 또는 container로 격리하고 Core 서비스의 Runtime을 함께 낮추지 않는다. `latest`, EOL Runtime, 검증되지 않은 개인 build는 예외로도 허용하지 않는다.

## 9. 검토한 대안

| 대안 | 결정 | 이유 |
|---|---|---|
| CPython 3.12.13 | 채택하지 않음 | 최신 보안 patch지만 source-only이고 Windows installer가 없어 Collector build chain 부담이 커짐 |
| CPython 3.12.10 | 채택하지 않음 | 3.12의 마지막 Windows installer지만 최신 3.12 보안 patch가 아님 |
| CPython 3.13.14 | 채택하지 않음 | 현재 installer는 있으나 정기 bugfix와 binary 제공 종료가 약 2026년 10월로 가까움 |
| CPython 3.14.6 | 채택 제안 | 현재 maintenance release, Windows x64 installer 제공, PyInstaller 지원, 더 긴 binary 지원 기간 |
| 차기 prerelease | 채택하지 않음 | MVP 운영 기준으로 안정 release가 아니며 의존성·packaging 검증 범위가 불필요하게 커짐 |
| 서비스별 3.12/3.13/3.14 혼용 | 채택하지 않음 | lock, image, 취약점 대응, 개발환경과 장애 분석 복잡도를 증가시킴 |

## 10. 결과와 trade-off

### 10.1 기대 효과

- 중앙 서비스와 Collector가 같은 language/runtime 기준을 사용한다.
- Windows 공식 installer를 사용하면서 최신 maintenance patch를 적용할 수 있다.
- 3.12를 자체 build해야 하는 공급망·운영 부담을 피한다.
- patch와 image를 기계적으로 검증할 수 있어 재현성과 감사 가능성이 높아진다.
- Runtime 예외가 Core 전체로 전파되지 않는다.

### 10.2 비용과 위험

- 기존 계획서의 3.12 예시와 문구를 후속 문서에서 3.14 기준으로 정합화해야 한다.
- 일부 package의 Python 3.14 wheel 또는 PyInstaller hook 호환성을 3단계에서 실제 설치·build test로 확인해야 한다.
- Python 3.14의 annotation 동작과 제거된 API가 기존 prototype에 영향을 줄 수 있다.
- exact patch와 digest 잠금 때문에 patch update 때 lockfile, image와 artifact를 함께 재생성해야 한다.

## 11. 승인 전 검증과 승인 조건

문서 승인과 실제 build 착수 사이에 다음 최소 검증을 수행한다.

- [ ] Linux `amd64`에서 Core 필수 package의 Python 3.14.6 wheel/설치 가능성 확인
- [ ] FastAPI API와 Jinja2 render smoke test
- [ ] Celery Worker/Beat와 Redis integration smoke test
- [ ] PostgreSQL driver, JSON Schema validator와 MinIO client import/test
- [x] Windows 11 x64에서 Collector dependency 설치와 PyInstaller build 성공 (`IMP-034`)
- [ ] 생성된 Collector를 clean Windows 11 VM에서 실행
- [ ] PowerShell/Registry/CIM Probe의 Unicode, 권한 부족과 timeout 처리 확인
- [x] SBOM과 vulnerability scan 결과 검토 (`IMP-034`, 알려진 취약점 0건)

필수 dependency의 호환성 실패가 발견되면 승인 조건 미충족으로 기록하고 3단계 진행 중 이 ADR을 개정한다.

## 12. 승인 시 변경되는 기준

승인자는 다음 변경을 함께 승인한다.

1. 실행 계획서의 `Python 3.12 계열` 권고를 Sec_AI 구현에서는 `CPython 3.14 계열`로 대체한다.
2. 최초 구현 patch version을 `3.14.6`으로 잠근다.
3. 공식 third-party product container의 내부 Runtime은 이 결정에서 제외한다.
4. exact container tag와 digest, Python package version과 hash는 3단계 산출물에서 확정한다.
5. 3단계 호환성 gate 실패 시 무단 하향 없이 ADR을 재검토한다.
