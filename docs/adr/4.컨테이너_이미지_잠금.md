## 1. 잠금 원칙

- `latest`, minor-only tag와 tag 단독 참조를 운영에 사용하지 않는다.
- multi-platform index digest는 출처 추적용으로 기록한다.
- 실제 단일 플랫폼 배포는 `linux/amd64` manifest digest를 사용한다.
- Compose와 Dockerfile에는 `repository:tag@sha256:<platform-digest>` 형식을 사용한다.
- registry mirror로 반입할 때 원본 digest, 반입 artifact hash, mirror digest와 서명 검증 결과를 함께 기록한다.
- 이 표의 `LOCKED`는 manifest를 식별했다는 뜻이며 vulnerability scan과 운영 승인까지 자동으로 의미하지 않는다.

## 3. 해결이 필요한 Gate

### 3.1 Evidence object store — `LOCKED-MVP-FREE`

MVP 원본 증적 저장소는 **MinIO AIStor Free 최신 Stable의 단일 노드 구성**으로 확정한다. 2026-07-21 확인 시 MinIO 공식 최신 Stable은 `RELEASE.2026-06-06T02-44-06Z`이며, `linux/amd64` 배포 manifest digest를 잠갔다.

```yaml
image: quay.io/minio/aistor/minio:RELEASE.2026-06-06T02-44-06Z@sha256:5dbb753c0dbe6a987dd30ce564f66c0042e291e464d10e792443451d4fec2120
platform: linux/amd64
```

선정 근거와 제한은 다음과 같다.

- 이 release는 확인된 인증 우회 취약점의 최초 수정 기준인 `RELEASE.2026-04-11T03-20-12Z`보다 새롭다.
- AIStor Free는 standalone 단일 노드만 사용하며 분산 clustering, 고가용성 및 replication을 MVP 요구사항으로 주장하지 않는다.
- AIStor Free에는 SLA, SLO와 제조사 지원 보장이 없다. 납품·판매·재배포 없이 조직 내부 단일 노드로 사용하는 위험을 승인하며 독립 backup과 복구시험을 필수로 한다. HA·복제 또는 더 짧은 복구목표가 필요하면 AIStor Enterprise나 조직 표준 S3 저장소 전환을 재승인한다.
- 조직이 공식 경로에서 직접 내려받아 사용하고, AIStor image·binary를 제3자에게 배포·재판매·임대하지 않으며 소프트웨어를 수정·역공학하지 않는다.
- 과거 `minio/minio` Community Edition image와 floating `latest` tag 사용을 금지한다. 가이드 vector projection은 별도 object store 없이 PostgreSQL+pgvector를 사용한다.
- image 잠금은 보안 배포 승인과 동일하지 않다. Core Compose 반입 전에 AIStor Free license 수용, 공식 SBOM 보관, vulnerability scan, 서명·provenance 확인, 기동·Object Lock·backup/restore 시험을 통과해야 한다.
- 8단계 원본 증적 저장·보존 정책에서 bucket versioning, Object Lock mode와 보존 기간, 암호화, 감사, 관리자 권한 및 운영 전환 조건을 확정한다.

공식 Stable이 변경되어도 이 digest를 자동 변경하지 않는다. 변경은 5장의 절차에 따라 새 release를 검토·승인한 경우에만 수행한다.

### 3.2 Redis license — `LOCKED-RSALV2-INTERNAL`

Redis 8.8.0은 공식 안정 release와 image digest를 기술적으로 잠갔으며 **RSALv2를 조직 내부 사용 license로 선택**한다. Redis는 Sec_AI의 Celery Broker로만 사용하고 납품·판매·재배포하지 않으며, 제3자에게 Redis 자체 기능을 관리형 서비스로 제공하지 않고 source를 수정하지 않는다. Redis port는 외부에 공개하지 않고 license·copyright notice를 보존한다. 사용 형태가 외부 제공·재배포·수정으로 바뀌면 즉시 재검토하며, 승인되지 않으면 Valkey 등 호환 대안을 `ADR-QUEUE.md`에서 비교한다.

### 3.3 Project-built image — `PENDING-BUILD`

`audit-api`, `audit-worker`, `audit-scheduler`가 사용할 최종 자체 image는 source와 Dockerfile이 아직 없어 결과 digest를 만들 수 없다. 다음 조건을 통과한 뒤 `audit-core` image를 별도로 잠근다.

- locked base image 사용
- 해당 서비스 lock을 `pip --require-hashes`로 설치
- unit/integration test 통과
- non-root/read-only 실행 검증
- SBOM 생성과 vulnerability scan
- image signing 및 provenance 생성

### 3.4 Model gateway — `LOCKED-DEV-CONNECTOR`

`IMP-050`에서 `sec-ai-mvp/model-gateway:0.1.0`을
`sha256:b19e4a468ce18e050796dc793498b54ad69d69be1d4f01a2f6127427d379abbc`로
잠갔다. 이 image는 vLLM 엔진이나 모델 weight가 아니라 현재 OpenRouter와 향후
로컬 vLLM의 OpenAI 호환 API에 접속하는 내부 connector다.

Bookworm 기반 후보는 수정 가능한 OpenSSL Critical·High 취약점이 남아 채택하지
않았다. 같은 CPython 3.14.6의 공식 Alpine 3.23 image로 바꾸어 OpenSSL 3.5.7을
확인했고, CPython `html.parser` 서비스 거부 취약점은 3.14 공식 보안 commit
`07efb08123ba9367a7107325adb9d5626dca1ca9`의 파일을 SHA-256
`5c5ed245889135564e75dfed9a47aeb6b4d3e5a2e9614d918a986767e3747539`로
고정해 backport했다.

Grype의 CPython binary version 판정에는 High 1건·Medium 3건이 남지만 High는
위 exact backport로 실제 코드를 수정했다. Medium은 사용하지 않는 IMAP/POP
command 경로 2건과 Linux container에 적용되지 않는 Windows 설치 경로 1건이다.
원본 scan과 항목별 판단은 `deploy/verification/model-gateway/`에 보존한다.
따라서 검토 후 조치 가능한 Critical·High는 0건이다.

### 3.5 vLLM GPU 준비 image — `PREPARED-NOT-ACTIVE`

`PRODUCT-AI-09`에서 공식 `vllm/vllm-openai:v0.23.0`의 `linux/amd64`
platform digest
`sha256:3a1e7f5904e1a1192a02aa0086ceaffc33985d7044c7bb25b3a43d61bdbe3ac0`을
사용한 얇은 GPU wrapper
`sec-ai-mvp/vllm-openai-gpu:0.23.0`을 만들었다. project image digest는
`sha256:48f9f370497eee3748a693c01030c82dbcee87a0db52f5e7901c9744787f4a00`이다.

container는 opt-in `local-vllm` profile, host port 없음, internal
`model_net`, read-only model volume과 `/models/NOT_CONFIGURED`로 구성하고
실행하지 않은 `Created` 상태로 둔다. CPU image는 만들지 않는다.

SBOM을 생성했지만 수정 가능한 항목만 대상으로 한 Grype 결과가
Critical 13·High 181·Medium 317·Low 81·Negligible 2건이므로
`FAIL-RUNTIME-USE-BLOCKED`다. 모델 weight가 없으므로 모델 파일 hash·license·악성
파일 검사는 수행 대상이 없으며, 승인 모델 반입 시 별도 수행한다. 취약점과
GPU·driver·CUDA·모델 승인이 해소되기 전에는 이 image/container를 시작하거나
로컬 AI 완료로 표시하지 않는다.

## 4. Deferred·준비 image

| 범위 | 상태 | 잠그지 않은 이유 |
|---|---|---|
| AI Gateway | `LOCKED-DEV-CONNECTOR` | IMP-050 OpenAI 호환 connector 생성·실제 연결 검증, 현재 OpenRouter 사용·host port 없음 |
| Embedding, Reranker | `DEFERRED` | 별도 model·license·CPU/GPU 실행 기준 미승인 |
| vLLM GPU | `PREPARED-NOT-ACTIVE` | image·중지 container는 준비했으나 취약점·GPU·driver·CUDA·승인 모델 Runtime Gate 미통과 |
| Neo4j | `DEFERRED` | Graph profile은 1차 MVP 기본 범위 밖 |
| Wazuh | `DEFERRED` | Managed profile은 One-shot MVP 이후 |
| Remediation Runner | `DEFERRED` | 자동 조치가 1차 MVP에서 제외됨 |
| Prometheus/Grafana/Loki/Alloy | `DEFERRED` | 운영 관측 제품 세트와 보존 정책 미승인 |

가이드 검색은 ADR-016에 따라 PostgreSQL 18.4와 pgvector 0.8.2가 함께 들어 있는 공식 image의 `linux/amd64` digest를 잠근다. Milvus·etcd·Milvus 전용 object store는 도입하지 않는다. ADR-017의 model-gateway는 별도로 잠근 Python 3.14.6 Alpine base와 API dependency lock을 사용하는 연결 전용 image이며 vLLM package·모델 weight를 포함하지 않는다. 준비한 GPU vLLM image의 실행은 취약점 Gate를 해소하고 CUDA와 대상 GPU driver 호환표·승인 모델을 확인한 뒤 별도 승인한다.

## 5. 변경 및 검증 절차

1. 공식 release/support/security 상태 확인
2. exact tag의 index와 `linux/amd64` manifest digest 조회
3. license와 provenance 확인
4. image pull 또는 폐쇄망 반입 후 digest 재검증
5. SBOM 생성과 vulnerability scan
6. health/readiness 및 backup/restore test
7. Compose에서 tag+platform digest 사용
8. 잠금 YAML과 이 문서를 동시에 갱신
9. 이전 image의 rollback 가능 기간과 폐기 기록 유지

Tag가 같은 digest를 계속 가리킬 것이라고 가정하지 않는다. 갱신 검토 때 tag mapping이 달라져도 승인된 digest는 자동 변경하지 않는다.
