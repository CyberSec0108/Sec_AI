## 1. 결정

Sec_AI의 일반 사용자 제품 목표를 다음 한 문장으로 고정한다.

> 사용자가 점검 버튼을 누르면 자신의 PC에서 KISA 가이드 점검에 필요한 내용을 읽기 전용으로 수집하고, 결정론적 규칙이 안전 여부를 판정하며, AI가 실제 확인값·판정 이유·KISA 원문을 결합해 사용자가 이해하고 행동할 수 있도록 설명한다.

다음 네 기능은 별도 제품처럼 분리하지 않고 하나의 흐름으로 연결한다.

```text
일반 사용자 점검 버튼
→ 내 PC의 승인된 항목을 읽기 전용으로 수집
→ 승인된 Audit Pack 규칙으로 안전 여부 판정
→ 판정 항목에 맞는 KISA 페이지·문단 검색
→ 별도 AI 분석 화면으로 이동
→ LLM이 PC-01부터 PC-18까지 실제 결과·규칙 이유·KISA 근거를 토큰 단위로 설명
→ 18개 항목 뒤 전체 종합 설명 생성
→ 상세 판정 화면에서 후속 질문·재점검
→ 사용자·관리자 목적에 맞는 결과 보고서 생성
```

규칙 엔진은 공식 판정 권한을 유지하고 LLM은 판정을 생성하거나 변경하지 않는다. LLM의 제품 가치는 판정 결과를 필터링해 다시 보여주는 데 있지 않고, 사용자의 실제 PC 상태를 근거와 함께 설명하고 다음 행동을 안내하는 데 있다.

## 2. 배경과 문제

`IMP-047~054`에서 원문 계보, pgvector 검색, 모델 connector, 대화 계약, 질문 화면과 사용성 시험을 구현했다. 그러나 현재 사용자 경험은 다음 이유로 최초 제품 목표에 미달한다.

1. 수집·규칙 판정·KISA 질문 기능이 화면과 application flow에서 분리돼 있다.
2. 점검 결과가 LLM의 설명 입력으로 충분히 구조화되지 않았다.
3. 결과 설명이 상태·기준·짧은 조치 문구에 머물러 사용자가 위험과 우선순위를 이해하기 어렵다.
4. LLM이 사용자의 실제 PC 결과보다 별도 KISA 질문에 집중해 단순 문서 검색 또는 필터링 제품처럼 보인다.
5. 점검 결과 화면에서 재점검과 PC 점검 화면 복귀가 안정적이지 않다.
6. `대화 기록`이 별도 상단 메뉴이면서 KISA 질문 화면의 최근 대화와 중복된다.
7. theme과 panel 제어가 글자 버튼 중심이라 화면이 복잡하다.
8. 최근 대화의 이름 변경·삭제·보관·이동·고정 기능이 없다.

따라서 `IMP-052~054`의 기술 계약·보안·화면 시험 완료 이력은 유지하지만, 그것만으로 “AI PC 보안 도우미 제품 완성”을 의미하지 않는다. 단계 J의 VM 인수 전에 아래 제품 정합성 보완 Gate를 통과해야 한다.

## 3. 공식 판정과 AI 설명의 권한 경계

### 3.1 규칙 엔진

승인·서명된 Audit Pack과 결정론적 allowlist Rule Engine만 다음 상태를 결정한다.

- `PASS`
- `FAIL`
- `ERROR`
- `REVIEW`
- `N/A`

LLM은 이 값을 바꾸거나 누락된 값을 추정해 `PASS`로 보완하지 않는다.

### 3.2 LLM

LLM은 규칙 엔진이 만든 결과를 입력으로 받아 다음 역할만 수행한다.

- 무엇을 확인했는지 쉬운 말로 설명
- 실제 확인값과 기준값 비교
- 판정 이유와 제한사항 설명
- 취약 상태가 발생시키는 보안 위험 설명
- 사용자가 할 수 있는 조치와 조직 담당자에게 요청할 조치 구분
- KISA 원문과 승인된 추가 공식 자료 인용
- 여러 항목의 공통 원인과 함께 개선하면 좋은 항목의 관계 분석
- 규칙 중요도·현재 상태·사용자 영향에 따른 AI 권장 처리 순서 제시
- 이전 점검과 재점검의 변화·남은 위험·개선 효과 요약
- 사용자용·기술 검증용 보고서의 읽기 쉬운 설명 초안 작성
- 현재 결과를 문맥으로 사용하는 후속 질문 응답

### 3.3 금지

- LLM 출력으로 공식 Finding·Audit Pack·증적 변경
- 근거가 없는데 KISA 기준인 것처럼 생성
- 수집 실패·권한 부족·미지원 상태를 `FAIL` 또는 `PASS`로 임의 변환
- 사용자 확인 없이 PowerShell·설정 변경·관리자 상승 실행
- 모델의 일반 지식을 공식 판정 근거로 표시

### 3.4 모델 실행 경계

최종 제품의 모델 실행 profile은 `LOCAL_VLLM_FULL_CONTEXT`로 고정한다. 실제 점검 결과 설명, 결과 문맥 후속 질문과 PDF 설명은 승인된 로컬 vLLM endpoint에서 처리하고 외부 전송을 허용하지 않는다.

현재 OpenRouter 연결은 `VLLM_COMPATIBILITY_TEST_DOUBLE`이다. OpenAI 호환 요청·응답·SSE·오류·모델 설정 전환을 미리 검증하는 시험 대역일 뿐이며, 로컬 vLLM의 개인정보 보호·폐쇄망·성능·모델 파일·라이선스 인수를 대신하지 않는다.

- OpenRouter에는 합성 입력 또는 사용자가 승인한 현재 시험 환경의 비식별·정규화 점검 결과와 해당 결과에 검색된 KISA 문단만 보낸다.
- 실제 PC 원본 증적·사용자/조직/Asset 식별자·전체 레지스트리 dump·전체 KISA 원문은 보내지 않는다.
- OpenRouter 시험 성공을 로컬 AI 완료나 외부 전송 0으로 표시하지 않는다.
- 최종 로컬 profile에서 OpenRouter로 자동 fallback하지 않는다.
- 실행 응답과 보고서에는 `runtime_profile`, provider, model, revision과 로컬/시험 여부를 감사 가능한 계보로 남긴다.

## 4. 점검 설명 입력 계약

각 결과는 LLM에 보내기 전에 최소한 다음 비식별 구조로 변환한다.

| 필드 | 의미 |
|---|---|
| `control_id`·`title` | KISA 점검 항목 |
| `observed_summary` | 사용자가 이해할 수 있는 실제 확인 내용 |
| `normalized_facts` | allowlist된 canonical 확인값 |
| `collection_method` | 레지스트리·Windows API·CIM·명령 등 확인 방식의 사용자용 분류 |
| `execution_tool` | 값을 읽은 승인 Collector·Probe·제한된 실행 도구 |
| `source_location` | 레지스트리 경로·API/provider·설정 위치 등 비밀값을 제외한 실제 확인 위치 |
| `rule_status` | 규칙 엔진의 불변 판정 |
| `judgement_explanation` | 실제값과 기준값의 차이를 설명하는 사용자용 자연어 판정 이유 |
| `result_code` | 개발자·관리자 추적용 내부 판정 이유 코드 |
| `expected_summary` | 적용된 KISA 또는 조직 기준 |
| `collection_limitations` | 권한 부족·미지원·미수집 항목 |
| `importance` | 승인된 중요도 |
| `kisa_citations` | guide version·page·section·chunk hash |
| `supplementary_sources` | 승인된 제품 공식 문서 |
| `allowed_actions` | 사용자 수동 조치·관리자 요청·재점검 범위 |
| `explanation_input_hash` | 설명 입력의 canonical hash |

원본 증적, SID, 사용자명, hostname, token, password와 비밀값은 모델 입력에 포함하지 않는다. 현재 시험 환경에서는 사용자가 승인한 비식별·정규화 실제 점검 결과를 `VLLM_COMPATIBILITY_TEST_DOUBLE`에 사용할 수 있다. 운영 PC의 원본 증적과 전체 문맥은 허용하지 않으며, 최종 제품의 실제 결과 처리는 `LOCAL_VLLM_FULL_CONTEXT`와 외부 egress 0 Gate를 통과해야 한다.

### 4.1 실제 확인 내용·판정 이유·판정 이유 코드의 구분

- `내 PC에서 확인한 내용`은 Collector가 실제로 읽은 값이다. 예: “암호 복잡성 사용 여부를 확인하지 못했습니다.”
- `판정 이유`는 그 실제값과 적용 기준을 비교해 사용자가 이해할 수 있게 쓴 문장이다. 예: “암호 복잡성 설정을 확인할 자료가 없어 안전 여부를 확정할 수 없습니다.”
- `판정 이유 코드`는 같은 분기를 테스트·감사·장애 분석에서 정확히 찾기 위한 내부 식별자다. 예: `PASSWORD_COMPLEXITY_NOT_OBSERVED`.

판정 이유 코드는 PowerShell 명령이나 레지스트리 값 자체가 아니며, 내 PC에서 확인한 내용도 아니다. 일반 사용자 결과 화면과 사용자용 PDF에는 내부 코드를 기본 표시하지 않는다. 역할이 허용된 기술 정보 화면과 기술 검증용 PDF에서만 실제 확인 방법·도구·위치·Probe version과 함께 표시한다. 내부 코드를 단독으로 보여 주어 사용자가 판정 근거로 오해하게 해서는 안 된다.

## 5. AI 설명 출력 계약

항목별 설명은 최소 다음 순서로 표시한다.

1. `판정 결과`
2. `무엇을 확인했나요`
3. `확인 방법`
4. `내 PC에서 확인한 내용`
5. `KISA 권고 기준`
6. `왜 이런 결과가 나왔나요`
7. `어떤 위험이 있나요`
8. `무엇을 하면 되나요`
9. `확인하지 못한 내용`
10. `근거와 출처`
11. `이 결과를 AI에게 질문`

전체 점검에는 별도의 AI 종합 요약을 제공한다.

- 현재 PC의 전반적인 상태
- 우선 확인할 항목 3개 이내
- 여러 결과가 서로 어떤 영향을 주는지에 대한 관련 위험 분석
- `공식 판정`과 구분된 `AI 권장 우선순위` 및 선정 이유
- 사용자가 바로 할 수 있는 일
- 관리자·조직 담당자 확인이 필요한 일
- 점검 오류와 확인하지 못한 범위
- 이전 점검이 있으면 개선·악화·미변경 항목과 남은 위험

AI 설명에는 `규칙 엔진의 공식 판정`, `KISA 근거`, `AI의 해석·권장`을 각각 표시한다. LLM의 풍부한 일반 지식은 위험 시나리오·용어 풀이·조치 시 주의점·후속 질문 제안에 적극 사용하되, 공식 판정이나 KISA 문구로 가장하지 않는다.

답변은 한 줄의 긴 문단으로 출력하지 않고 짧은 문단, 제목과 목록으로 구성한다. 생성 중에는 근거 찾기·결과 비교·설명 작성 단계를 표시하고 SSE 완료 즉시 화면을 갱신한다.

### 5.1 긴 결과와 화면 스트리밍

- 기본 사용자 흐름은 기존 결과 화면 안의 일괄 생성 영역이 아니라 `/ui/ai-analysis` 별도 화면을 사용한다.
- PC-01부터 PC-18까지 Control 순서를 고정하고, 한 Control의 모델 응답을 기다렸다가 완성 문장을 한꺼번에 찍지 않는다. upstream OpenAI 호환 SSE의 `delta`가 도착하는 즉시 해당 Control 카드에 이어 붙인다.
- 각 Control 호출 전에는 승인된 결과 projection과 해당 Control의 KISA 페이지·절·문단만 조합한다. 다른 Control의 원본 증적이나 사용자·조직·Asset 식별자를 다음 호출로 누적하지 않는다.
- PC-18 설명이 끝난 뒤에만 전체 종합 설명을 별도 호출하고, 종합 설명도 `delta` 단위로 표시한다.
- 화면 이벤트 순서는 `ANALYSIS_STARTED → SEARCHING_KISA_EVIDENCE → CONTROL_STARTED → CONTROL_DELTA* → CONTROL_COMPLETED`를 PC-01~18에 반복한 뒤 `SUMMARY_STARTED → SUMMARY_DELTA* → SUMMARY_COMPLETED → ANALYSIS_COMPLETED`로 고정한다. 안전하게 중단된 경우 `FAILED`를 보낸다.
- 모델이 생성 중인 설명은 `AI 초안 생성 중` 상태이며 공식 판정이나 PDF 정본이 아니다. `CONTROL_COMPLETED` 전의 부분 문장을 KISA 원문 또는 완료된 조치로 오인하게 표시하지 않는다.
- 규칙 상태와 citation은 서버가 가진 불변 입력에서 별도로 표시하고 모델 token으로 다시 만들지 않는다. 모델이 판정 변경을 제안해도 UI의 공식 상태는 바뀌지 않는다.
- 빠른 설명은 최대 8,000 output token, 정밀 설명은 최대 16,000 output token으로 제한한다. 모델 호출 제한 시간은 240초, 내부 API 대기 제한은 260초로 두며 장시간 SSE 경로는 읽기 300초·쓰기 30초, response buffering·cache off를 유지한다.
- `finish_reason=length`는 연결 실패가 아니라 `OUTPUT_TOKEN_LIMIT_REACHED`로 구분한다. 일부 Control 설명이 생성됐더라도 전체 분석 완료나 공식 결과 변경으로 저장하지 않는다.
- 기존 `/api/v1/result-explanations/from-scan/stream`의 최대 6개 validated batch 방식은 호환용 API로 유지한다. 기본 화면은 `POST /api/v1/result-explanations/from-scan/token-stream`을 사용하며 두 계약을 혼용하지 않는다.

### 5.2 관리자 추가 점검 결과 결합

사용자가 점검 시작 전 관리자 5개 항목을 안내받고 동의했으면 일반 권한 수집이 끝난 뒤 Windows UAC에서 다시 `예`를 선택해야 관리자 Probe가 실행된다. 관리자 결과를 받기 전에는 AI 분석을 시작하지 않고, 수신된 관리자 결과는 허용된 설명 필드만 일반 결과에 병합한다. 병합 뒤 explanation input의 canonical hash를 다시 계산하며, 관리자 원본 출력·명령 전문·식별자는 모델에 전달하지 않는다. UAC 취소·수집 실패는 `PASS` 또는 `FAIL`로 추정하지 않고 기존 공식 상태와 수집 한계를 그대로 보존한다.

## 6. 지식과 근거 우선순위

LLM이 사용할 수 있는 지식은 다음 순서로 구분한다.

1. KISA 승인 원문: 공식 점검 설명의 1차 근거
2. Microsoft 등 제품 공급자의 승인된 공식 문서: 설정 위치·제품 동작의 보조 근거
3. 승인된 공공 보안기관 자료: 위험과 대응의 보조 설명
4. 모델의 일반 지식: 이해를 돕는 추가 설명

2~4번은 KISA 판정 근거와 시각적으로 구분한다. 모델 일반 지식만으로 KISA 기준, 실제 PC 값 또는 공식 상태를 만들지 않는다. 근거가 부족하거나 서로 충돌하면 답변을 줄이고 `근거 부족` 또는 `기준 확인 필요`를 표시한다.

## 7. 사용자 정보구조

일반 사용자 상단 메뉴는 다음 다섯 개를 기본으로 한다.

1. `원클릭 점검`
2. `점검 결과`
3. `가이드 질의`
4. `도움말`
5. `계정정보`

### 7.1 PC 점검

- Launcher 연결 여부와 무관하게 화면 이동은 항상 가능
- 첫 화면의 장비 카드는 `PC 점검`, `리눅스 서버 점검`, `네트워크 스위치 점검`으로 구성하고 현재 구현된 PC만 실행한다. 미구현 장비와 `에이전트 활용`은 `준비 중`으로 표시하며 동작하는 버튼을 제공하지 않는다.
- `점검 시작`, 최근 점검, `결과 보기`, `다시 점검`
- 실행 가능 여부만 Launcher 상태의 영향을 받음
- 점검 중·완료·오류와 다음 행동을 같은 영역에 표시
- 점검 중에는 PC-01~18 각각의 `대기·확인 중·확인 완료·관리자 확인` 상태와 현재 확인 내용을 진행 막대 아래에서 보여 준다.
- 정상 기능에 `사용 가능`, 개발 진행 중이라는 문구나 내부 IMP 번호를 사용자 화면에 표시하지 않는다.

### 7.2 점검 결과

- 점검 완료 직후에는 별도 AI 분석 화면을 먼저 열고 PC-01~18 항목 설명과 마지막 종합 설명을 실제 token stream으로 보여 준다.
- 상세 점검 결과 화면은 그대로 유지하고 AI 분석 화면에서 이동할 수 있게 한다.
- AI 종합 요약
- 우선순위 결과
- 규칙 판정과 AI 설명의 명확한 구분
- 확인한 증적 요약·기준·이유·위험·조치·출처
- 항목별 `AI에게 질문`
- `PC 점검으로 돌아가기`와 `다시 점검`

### 7.3 가이드 질의

- 현재 점검 결과에서 시작한 질문은 해당 결과 문맥을 유지
- 일반 KISA 질문과 특정 결과 질문을 화면에서 구분

### 7.4 공통 제어

- theme 전환은 해·달 icon을 사용
- 대화 panel은 sidebar/hamburger icon 사용
- 출처 panel은 문서·인용 icon 사용

- 모바일에서는 좌우 panel을 overlay drawer로 전환

## 9. PDF 결과 보고서와 AI 활용 명세

동일한 불변 결과 snapshot에서 목적이 다른 두 종류의 결과 PDF와 AI 모델 활용 명세를 생성한다.

### 9.1 사용자용 PDF

- 전체 점검 요약, 항목별 판정, 무엇을 확인했는지, 확인 방법, 실제 확인 내용
- 쉬운 말의 판정 이유, 위험, 다음 행동, KISA 페이지·문단 출처
- AI 설명임을 알리는 표시와 `DRAFT` 경계
- 내부 `result_code`, 원본 증적 경로, 명령 전문, 레지스트리 원시 dump, SID·hostname·비밀값 제외

### 9.2 기술 검증용 PDF

- 사용자용 내용과 함께 승인된 Probe·Adapter·Rule·Pack version
- 비밀값을 제거한 실행 도구·확인 위치·수집 시각·수집 제한
- 내부 `result_code`, canonical input/output hash, citation·모델·prompt 계보
- 원본 증적 자체가 아닌 권한이 허용된 증적 식별자·hash

### 9.3 AI 모델 활용 및 라이선스 기술 명세

기술 검증용 PDF의 부록과 별도 내려받기 문서로 같은 내용을 제공한다.

- 활용 유형: 외부 공개 모델 연결·추가 미세조정·자체 학습 중 실제 해당 유형
- Runtime 구분: `VLLM_COMPATIBILITY_TEST_DOUBLE` 또는 `LOCAL_VLLM_FULL_CONTEXT`
- provider·base model·served model·revision·모델 라이선스·공식 저장소
- vLLM image version·digest·SBOM과 모델 weight hash·출처·악성 파일 검사
- 추가 학습 여부, 사용 데이터셋·전처리·가중치 공개 위치와 배포 방식
- 실제 제품에서 AI가 수행하는 종합 분석·위험 설명·우선순위·후속 질문·보고서 초안 범위
- AI가 수행하지 않는 공식 판정·설정 변경·Finding/Pack write 범위
- 입력 데이터 종류·비식별화·외부 전송 여부·배치 위치
- prompt·retrieval·model·input/output hash와 생성 시각
- 개발 과정의 AI 코딩 보조 사용 범위는 Runtime 모델 활용과 구분해 기록

현재 OpenRouter 시험은 “유형 1 운영 적용”이 아니라 호환성 시험으로 기록한다. 최종 제품 명세는 로컬 vLLM model·revision·license·weight와 외부 전송 0 Gate가 확인된 후 확정한다.

두 PDF와 명세는 자산 소유권과 역할을 서버에서 확인하고, 기술 검증용과 명세 상세본은 관리자 또는 승인된 검증 역할에만 허용한다. 생성·다운로드·실패를 감사 기록에 남기며 CSRF, 직접 객체 참조(IDOR), 파일명 주입, 다른 사용자·Asset 혼합을 차단한다. 문서에는 report version·result version·생성 시각·SHA-256을 넣고, 재생성은 기존 파일을 덮어쓰지 않는 append-only 이력으로 남긴다.

## 11. 단계 Gate

- `IMP-052` 완료는 근거 기반 설명 계약과 보안 경계를 검증했다는 뜻이며 현재 결과 화면의 설명 품질 완료를 뜻하지 않는다.
- `IMP-053` 완료는 KISA 질문 API·화면 연결 완료이며 점검 결과와 AI 상담의 통합 완료를 뜻하지 않는다.
- `IMP-054` 완료는 당시 정의된 화면·접근성 조건부 인수이며 본 ADR의 제품 목표 인수를 대체하지 않는다.
- `PRODUCT-AI-01~09`가 모두 통과하기 전에는 “AI 기반 PC 보안 점검 제품 완료”로 표시하지 않는다.
- OpenRouter `VLLM_COMPATIBILITY_TEST_DOUBLE`과 GPU image 준비만으로 로컬 vLLM 추론 완료를 표시하지 않는다.
- `PRODUCT-AI-09`가 끝나기 전에는 `IMP-055` clean VM 제품 회귀를 시작하지 않는다.
- clean VM·조직 서명·SmartScreen·Pilot Gate는 계속 `IMP-055~062`에서 수행한다.
- 2026-08-01 후속 구현의 실제 token stream·별도 AI 분석 화면·관리자 결과 병합 검증은 [`PRODUCT_AI_실제_토큰_스트림_검증_20260801.md`](../../deploy/verification/PRODUCT_AI_실제_토큰_스트림_검증_20260801.md)를 따른다. 이 후속 구현은 `PRODUCT-AI-09` 완료 이력을 보완하지만 `IMP-055` clean VM Gate나 `LOCAL-VLLM-RUNTIME-GATE`를 완료시키지 않는다.

## 12. 최종 인수 기준

초보 사용자가 PowerShell이나 Docker 명령 없이 다음 과업을 완료해야 한다.

1. 1~2번의 선택으로 PC 점검을 시작한다.
2. 점검 후 가장 중요한 결과와 실제 확인 내용을 찾는다.
3. 왜 이런 판정인지 KISA 근거와 함께 이해한다.
4. 자신이 할 일과 관리자에게 요청할 일을 구분한다.
5. AI 권장 우선순위와 여러 결과의 관련 위험을 공식 판정과 구분해 이해한다.
6. 해당 결과를 문맥으로 AI에게 위험·조치·우선순위를 후속 질문한다.
7. PC 점검 화면으로 돌아가 재점검하고 이전 결과와 달라진 점을 확인한다.
8. 대화 이름을 변경·이동·삭제하고 필요한 대화를 다시 찾는다.
9. 사용자용 PDF를 내려받아 판정·실제 확인 내용·확인 방법·KISA 근거와 AI 설명을 읽는다.
10. 승인된 관리자는 기술 검증용 PDF와 AI 모델 활용 명세를 내려받고 내부 이유 코드·도구·위치·계보·model/revision/license·배치 위치를 추적한다.

각 과업은 실제 Chrome desktop·mobile 크기, keyboard와 SSE 환경에서 검증한다. 현재 환경의 제품 과업은 비식별 입력만 허용한 OpenRouter 시험 경로에서 검증하고 외부 전송 사실을 표시한다. 승인된 로컬 vLLM에서의 동일 과업과 외부 egress 0은 `LOCAL-VLLM-RUNTIME-GATE`에서 별도로 확인한다. 규칙 판정과 AI 설명의 혼동, 잘못된 출처, 다른 사용자·Asset 문맥 누출, PDF 권한 우회와 false PASS는 0이어야 한다.

## 13. 결과

이 결정으로 다음 장점이 생긴다.

- Collector·Rule·RAG·LLM이 하나의 사용자 가치 흐름으로 연결된다.
- 공식 판정의 결정론과 AI의 설명력을 함께 유지한다.
- 점검 결과가 단순 상태 필터가 아니라 종합 분석·관련 위험·우선순위·이해·행동·후속 질문의 출발점이 된다.
- 별도 대화 기록 탭과 중복 UI를 줄이고 핵심 메뉴를 단순화한다.
- 사용자는 읽기 쉬운 결과 보고서를, 관리자는 재현 가능한 기술 검증 보고서와 AI 모델 활용·라이선스 명세를 받는다.

추가 비용은 점검 설명 DTO·RAG 결합·대화 관리 API·UI 재구성·PDF 생성과 권한·감사 검증·제품 과업 재검증이다. 이 비용은 VM 인수 전에 지불한다. 현재 구조를 그대로 VM에서 검증하면 기술적 동작은 확인할 수 있어도 최초 제품 목표의 실패를 고착시키기 때문이다.

## 14. 2026-08-01 실제 UI E2E와 출력 정책 보완

실제 Chrome UI에서 로그인·두 번째 인증 후 `/ui/ai-analysis`가 PC-01부터 PC-18까지 token delta를 순서대로 표시하고 마지막 종합 설명을 완료해 `18 / 18`이 되는 것을 확인했다. 검증 화면과 hash는 [`PRODUCT_AI_스트림_UI_종단간_및_출력_정책_20260801.md`](../../deploy/verification/PRODUCT_AI_스트림_UI_종단간_및_출력_정책_20260801.md)에 기록한다.

현재 API는 18개 Control, 입력 구조·canonical hash·공식 상태·citation과 prompt injection 패턴을 먼저 검증한다. 근거 조회 실패를 무조건 전체 stream 중단으로 바꾸던 `RESULT_AI_EVIDENCE_NOT_FOUND` 경로와 일반 문자열 기반 출력 재검사·재시도·fallback은 제거했고, upstream model delta는 공식 판정과 분리된 설명으로 그대로 전송한다. 브라우저는 이를 `secai.restricted-markdown.v3` 제한 AST로 표시하고 실패 시에만 `textContent`로 전환한다. 이는 판정·입력·citation 검증을 제거했다는 뜻이 아니며 model 출력이 공식 상태나 Finding을 바꿀 수 없다는 기존 계약은 유지한다.

`KNOWLEDGE-01~03`에서 system prompt와 UI·PDF를 `secai.result-knowledge.v1` 계약으로 확장했다. 모델은 실제 비식별 점검 결과·공식 규칙·KISA 근거를 우선하고, 모델 일반 지식은 위험 배경·용어 풀이·주의점 보충에만 적극 사용할 수 있다. 일반 지식은 실제값·KISA 문구·공식 판정을 만들거나 바꾸지 못한다.

```text
실제 확인값
→ 공식 규칙 상태·이유
→ 승인된 KISA 근거
→ 승인된 제조사/OS 문서
→ 모델 일반 지식(보조 설명 표시)
```

항목별 인라인 인용은 `[1]` 실제 확인값, `[2]` 공식 규칙, `[3]` KISA 원문, `[4]` AI 일반 보안지식으로 고정한다. 각 항목 아래 출처 목록에는 한글 문서명·정확한 쪽수·세부 항목·출처 등급·한계를 표시하고, 영문 내부 식별자는 사용자 제목에서 제외한다. 생성 뒤 별도 평가 계층은 알 수 없는·누락 인용, 근거 없는 정밀 주장, 출처 충돌, 최신성과 거부·보류를 기록하지만 설명을 이용해 규칙 판정을 다시 계산하지 않는다. 검증은 [`KNOWLEDGE_01_03_지식_출처_분리_검증_20260802.md`](../../deploy/verification/KNOWLEDGE_01_03_지식_출처_분리_검증_20260802.md)를 따른다.

Markdown 가독성 보완은 raw HTML 허용이 아니라 현재 `secai.restricted-markdown.v3` 제한 AST·sanitizer·CSP/Trusted Types 시험으로 구현했다. v3는 상한이 있는 표와 계약에 존재하는 `[n]`만 출처 버튼으로 만들고 알 수 없는 번호는 일반 텍스트로 둔다. Linux·Switch와 Agent/MCP 조치는 결과 설명 계약을 재사용하되 각각 별도 evidence·Pack·승인·rollback Gate를 둔다. 상세 후속 계획은 제안 ADR 19와 루트 발전 계획을 따른다.

## 15. 복수 기준 결과 설명 제안

향후 AI 결과 화면은 실제 확인값을 한 번만 표시하고 그 아래에 `KISA 공식 기준`, `조직 승인 기준`, `사용자 개인 기준`의 결과를 구분해 설명한다. 기준 간 충돌은 오류가 아니라 비교 결과로 표시하며 source ID·version·Profile hash·effective date를 함께 남긴다. AI는 기준을 초안으로 구조화하고 차이를 쉬운 말로 설명할 수 있으나, 공식 상태를 합치거나 우선순위를 임의 결정할 수 없다.

사용자 정의 기준은 `PERSONAL_DRAFT/PERSONAL_ACTIVE`에서 시작하고 조직·공식 승격은 별도 승인 Gate를 거친다. 결과 PDF도 기준별 판정과 공식성 등급을 분리한다. 상세 계약은 제안 ADR 20을 따른다.
