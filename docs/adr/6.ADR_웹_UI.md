# ADR-003: Web UI 기술 및 보안 기준

## 현재 구현 상태 (2026-08-07 검토)

- FastAPI·Jinja2와 정적 JavaScript/CSS 기반 UI가 Windows·Linux·Switch·통합 결과·가이드·취약점·관리자 화면으로 확장됐다.
- 장시간 작업과 AI 설명은 polling 또는 SSE/token stream을 사용하며, 완성된 결과와 AI 설명은 화면 재진입 시 복원한다.
- 사용자·가이드·모델 출력은 `textContent` 또는 제한 Markdown renderer로 표시한다. CSP·CSRF·IDOR·keyboard·focus·모바일·주야간 theme 계약을 유지한다.
- 실제 화면 경로와 상태 정본은 `apps/api`, `apps/web`와 `product_features.py`다. 이 초기 ADR의 예시 URL이 다르면 현재 source를 우선하고 변경 이유를 검증 기록에 남긴다.

## 1. 결정 요약

Sec_AI의 1차 MVP Web UI는 **FastAPI가 제공하는 server-rendered Jinja2 HTML + Static asset + 로컬 vendoring한 HTMX**로 구현한다. 별도 SPA, Node.js runtime container, npm package installation, frontend bundler와 외부 CDN을 두지 않는다.

| 결정 항목 | 확정 제안 |
|---|---|
| Rendering | Jinja2 server-side rendering(SSR) |
| HTTP application | FastAPI의 `audit-api` |
| 부분 갱신 | 로컬 HTMX `2.0.10` |
| 진행 상태 | 동일 출처 SSE, 불가 시 제한된 HTMX polling |
| 정적 자산 | API image에 포함된 version·hash 고정 파일 |
| Node.js | 개발·build·운영 runtime 모두 기본 범위에서 사용하지 않음 |
| 외부 CDN | 금지: JS, CSS, font, icon을 외부 origin에서 실행 시점에 받지 않음 |
| 권한 | 모든 full page·fragment·API·SSE·download에서 서버 측 재검사 |
| Browser 기준 | 지원 중인 Windows 11의 최신 조직 승인 Microsoft Edge |
| UI 역할 | 자산·점검·업로드·Finding·근거·검토 흐름 제공 |
| 공식 판정 | UI가 생성·변경하지 않으며 Audit Pack 규칙 엔진 결과를 표시 |

## 2. 배경과 목표

첫 MVP의 UI는 대규모 client application이 아니라 다음 보안점검 업무를 정확하고 추적 가능하게 제공해야 한다.

- 로그인과 현재 사용자·역할 확인
- 허용된 자산 목록·등록
- 점검 Job 생성과 Collector 다운로드
- 결과 package 업로드
- Job 진행 상태 확인
- Finding 목록과 상세 조회
- 실제값, 기준값, 증적 hash, Collector·Probe·Audit Pack version과 KISA 근거 표시
- 역할 범위 안의 검토 의견과 승인 요청
- 오류와 제한 상태의 명확한 표시

1~2인 개발 규모와 폐쇄망 운영을 고려하면 별도 JavaScript build 생태계와 frontend container를 추가하는 것보다 FastAPI와 Jinja2가 HTML을 생성하고 HTMX가 필요한 부분만 갱신하는 구조가 단순하고 검증 가능하다.

## 3. 적용 범위와 제외 범위

### 3.1 적용 범위

- Core Gate A의 자산·점검·업로드·Finding 최소 UI
- Gate B의 로컬 AI 설명 표시와 근거 연결
- 사용자, 보안담당자, 승인자, 관리자의 역할별 화면
- Jinja2 full-page template과 HTMX fragment template
- 정적 CSS, HTMX, 최소한의 프로젝트 JavaScript
- same-origin REST/HTML endpoint와 SSE 상태 구독
- 키보드·screen reader를 고려한 기본 접근성

### 3.2 제외 범위

- React, Vue, Angular, Svelte 등 별도 SPA
- Node.js runtime, npm/yarn/pnpm, Vite/Webpack/Rollup build pipeline
- 외부 CDN, Google Fonts, 외부 icon·analytics·tag manager
- Jupyter, Streamlit, Gradio를 사용자용 운영 UI로 노출
- WebSocket 기반 양방향 명령 channel
- offline-first PWA, service worker와 browser background sync
- 복잡한 client-side state store와 browser DB
- UI에서 LLM output 또는 사용자 입력을 명령으로 실행
- UI 요소를 숨기는 방식만으로 권한 통제
- 1차 MVP의 고급 dashboard, 대규모 chart와 drag-and-drop workflow designer

## 4. 요청 및 Rendering 구조

```text
Browser
→ Gateway(:443, TLS·rate limit·보안 header)
→ audit-api(FastAPI 인증·RBAC·자산 범위 검사)
   ├─ /ui/...          Jinja2 full page와 HTMX fragment
   ├─ /api/v1/...      JSON·upload·상태 변경 API
   ├─ /events/v1/...   읽기 전용 SSE
   └─ /static/...      hash 고정 local asset
→ Application service
→ PostgreSQL / Evidence store / Queue
```

- Browser가 `audit-api` container port에 직접 연결하지 않고 Gateway를 유일한 기본 진입점으로 사용한다.
- HTML route도 API와 같은 application·repository·RBAC service를 사용한다. UI 전용 우회 query를 만들지 않는다.
- full page와 fragment는 presentation 차이일 뿐 동일한 인증·권한 검사를 통과한다.
- HTMX가 없는 요청에도 핵심 조회·form 제출이 동작하도록 가능한 범위에서 progressive enhancement를 유지한다.
- `HX-Request` header는 응답 형식을 고르는 힌트일 뿐 신뢰 또는 권한 근거로 사용하지 않는다.

## 5. URL과 Template 계약

### 5.1 Route 영역

| 영역 | 예시 | 응답 |
|---|---|---|
| Page | `/ui/assets`, `/ui/findings/{id}` | 완전한 HTML document |
| Fragment | `/ui/fragments/jobs/{id}/status` | 교체 가능한 제한된 HTML fragment |
| API | `/api/v1/assets`, `/api/v1/audit-jobs` | version 지정 JSON 또는 upload 응답 |
| Event | `/events/v1/audit-jobs/{id}` | `text/event-stream` |
| Static | `/static/vendor/...`, `/static/app/...` | version/hash 고정 asset |

Page와 fragment route를 섞어 동일 URL이 요청 header에 따라 전혀 다른 보안 의미를 갖게 하지 않는다. 공통 application service를 호출하되 route와 response contract를 명시적으로 분리한다.

### 5.2 Template 구조

```text
apps/web/
├─ templates/
│  ├─ layouts/
│  │  └─ base.html
│  ├─ pages/
│  │  ├─ login.html
│  │  ├─ assets/
│  │  ├─ audit_jobs/
│  │  └─ findings/
│  ├─ fragments/
│  │  ├─ forms/
│  │  ├─ tables/
│  │  ├─ status/
│  │  └─ errors/
│  └─ components/
├─ static/
│  ├─ vendor/htmx/2.0.10/htmx.min.js
│  └─ app/
│     ├─ app.css
│     ├─ htmx-config.js
│     └─ job-events.js
└─ tests/
```

- `pages`는 layout을 포함한 완전한 문서, `fragments`는 지정 target에만 삽입 가능한 조각으로 구분한다.
- fragment에 `<html>`, `<head>`, executable `<script>` 또는 전역 event handler를 포함하지 않는다.
- component는 presentation만 담당하고 DB query나 권한 결정을 template에서 수행하지 않는다.
- template context는 명시적인 view model만 전달하고 ORM entity 전체, session object와 secret configuration을 넘기지 않는다.

## 6. HTMX와 정적 자산 잠금

### 6.1 HTMX 기준

2026-07-21 확인 기준 공식 안정 release인 **HTMX 2.0.10**을 사용한다. 4.x beta는 MVP에 사용하지 않는다.

| 항목 | 값 |
|---|---|
| Upstream | `bigskysoftware/htmx` |
| Version | `2.0.10` |
| Release tag | `v2.0.10` |
| Local path | `/static/vendor/htmx/2.0.10/htmx.min.js` |
| 공식 SRI SHA-384 | `H5SrcfygHmAuTDZphMHqBJLc3FhssKjG7w/CeCpFReSfwBWDTKpkzPP8c+cLsK+V` |
| 확장 | 초기에는 사용하지 않음 |

실제 vendoring 시 다운로드한 byte의 SHA-256, size, upstream URL, license와 확인일을 `static/vendor/assets.lock.yml` 같은 기계 판독 가능한 asset 잠금표에 기록한다. 공식 SRI와 local SHA-256 검증 전에는 운영 image를 build하지 않는다.

```html
<script
  src="/static/vendor/htmx/2.0.10/htmx.min.js"
  integrity="sha384-H5SrcfygHmAuTDZphMHqBJLc3FhssKjG7w/CeCpFReSfwBWDTKpkzPP8c+cLsK+V"
  defer></script>
```

### 6.2 금지 사항

- `unpkg`, `jsDelivr` 등 CDN을 runtime source로 사용하지 않는다.
- `latest`, minor-only URL이나 branch의 raw file을 asset reference로 사용하지 않는다.
- HTMX extension, hyperscript 또는 다른 frontend library를 검토 없이 추가하지 않는다.
- browser가 시작 시 외부 source map·font·script를 요청하지 않는다.
- vendored file을 직접 수정하지 않는다. 변경이 필요하면 project JS에서 수행하고 vendor hash를 유지한다.

### 6.3 프로젝트 asset

- project CSS·JS는 사람이 검토 가능한 source 그대로 관리하며 MVP에서는 minifier·bundler를 필수화하지 않는다.
- 정적 파일명 또는 query에 content hash를 사용해 cache busting한다.
- vendor·project asset의 SHA-256, license와 provenance를 release SBOM 또는 별도 asset manifest에 포함한다.
- production image에서 test fixture, npm cache, source map과 불필요한 example asset을 제외한다.

## 7. HTMX 보안 설정

초기 설정은 외부 local script 파일에서 적용하고 inline script를 사용하지 않는다.

```javascript
htmx.config.selfRequestsOnly = true;
htmx.config.allowEval = false;
htmx.config.allowScriptTags = false;
htmx.config.historyCacheSize = 0;
```

- HTMX request는 same-origin으로 제한한다.
- `hx-vals="js:..."`, JavaScript trigger filter, `hx-on:*`과 response 내 script 실행을 사용하지 않는다.
- 민감한 page·fragment가 localStorage history snapshot에 남지 않도록 HTMX history cache를 비활성화한다.
- `hx-get`은 조회만 수행하고 상태 변경은 CSRF가 검증되는 `POST`, `PUT`, `PATCH`, `DELETE`로 제한한다.
- `hx-confirm`은 사용자 편의 기능이며 서버 authorization·업무 승인 절차를 대신하지 않는다.
- server가 반환한 `HX-Redirect`, `HX-Location`, `HX-Retarget`은 고정된 same-origin route만 사용하며 사용자 입력 URL을 그대로 반영하지 않는다.

## 8. XSS와 HTML 출력 정책

### 8.1 기본 원칙

- HTML, attribute와 URL context에 맞는 Jinja2 autoescape를 기본으로 유지한다.
- 사용자 입력, Collector 값, 명령 출력, 파일명, 가이드 원문과 AI 설명을 기본적으로 text로 출력한다.
- 일반 template에서 Jinja2 `|safe`, `Markup`, `innerHTML` 직접 대입을 금지한다.
- 승인된 고정 UI icon·markup만 별도 typed component에서 관리하고 보안 review와 test 없이 safe HTML type을 확대하지 않는다.
- `javascript:`, protocol-relative URL, 외부 redirect와 사용자 입력으로 만든 `data:` URL을 허용하지 않는다.
- AI 출력은 신뢰된 HTML이 아니다. 1차 MVP에서는 plain text로 표시하고, Markdown이 필요해지면 allowlist sanitizer와 별도 보안 결정을 거친다.

### 8.2 HTMX fragment

HTMX는 server가 반환한 HTML을 DOM에 삽입하므로 fragment도 full page와 동일한 출력 encoding을 적용한다. 원본 증적이나 AI 응답을 template source로 compile하지 않으며, 사용자 제어 문자열로 `hx-*` attribute 또는 target selector를 만들지 않는다.

Stored·reflected·DOM XSS test에는 최소 다음 입력을 포함한다.

- asset 이름과 사용자 표시명
- 업로드 파일명과 오류 message
- Collector raw/normalized value
- 검토 의견
- KISA 발췌와 AI 설명
- pagination·sort·filter query

## 9. Content Security Policy와 Browser header

운영 Gateway는 최소 다음 의미의 CSP를 HTTP response header로 적용한다.

```text
default-src 'self';
script-src 'self';
style-src 'self';
img-src 'self' data:;
font-src 'self';
connect-src 'self';
object-src 'none';
base-uri 'none';
frame-ancestors 'none';
form-action 'self';
```

- `'unsafe-inline'`과 `'unsafe-eval'`을 추가하지 않는다.
- inline `<script>`, inline event handler와 style attribute를 사용하지 않는다.
- CSP는 `<meta>`가 아니라 Gateway/API HTTP header로 제공한다.
- production HTTPS에서는 HSTS를 Gateway에서 적용한다. 개발 HTTP 환경에는 HSTS를 잘못 적용하지 않는다.
- `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`와 최소 `Permissions-Policy`를 설정한다.
- embedding 요구가 승인되기 전까지 `frame-ancestors 'none'`으로 clickjacking을 차단한다.
- CSP 완화가 필요하면 report-only 관찰, 위반 근거와 보안 승인을 거쳐 변경한다.

## 10. 인증, session과 CSRF 경계

정확한 인증 수단, session 저장·만료와 cookie 정책은 인증 ADR에서 확정한다. Web UI는 server-side session cookie를 사용하는 경우 다음 계약을 요구한다.

- cookie에 `Secure`, `HttpOnly`, 승인된 `SameSite`와 최소 scope 적용
- token·session ID를 URL, HTML, localStorage 또는 JavaScript-readable cookie에 저장하지 않음
- 로그인·로그아웃·계정 비활성화·역할 변경 시 session lifecycle 정책 적용
- 인증 후 원래 URL redirect는 same-origin allowlist path만 허용
- 401은 로그인 또는 session 만료 화면, 403은 권한 부족으로 구분하고 자원 존재 여부를 과도하게 누설하지 않음

모든 state-changing form과 HTMX request는 server가 session에 결합해 발급한 CSRF token을 검증한다.

- 일반 form에는 hidden input을 사용한다.
- HTMX request는 외부 `htmx-config.js`의 `htmx:configRequest` handler가 meta 또는 form의 token을 `X-CSRF-Token` header에 추가한다.
- server는 token과 함께 `Origin` 및 가능한 경우 `Referer`의 same-origin 여부를 defense-in-depth로 검사한다.
- GET, HEAD와 SSE endpoint는 상태를 변경하지 않는다.
- CORS는 기본 비활성·same-origin이다. credential과 `Access-Control-Allow-Origin: *`를 함께 사용하지 않는다.

CSRF token을 CSP nonce, authentication token 또는 업무 승인 token과 혼용하지 않는다.

## 11. 서버 권한과 객체 범위

다음 모든 endpoint는 인증 사용자, 역할, 조직과 자산 scope를 서버에서 확인한다.

- full page
- HTMX fragment
- JSON API
- SSE stream
- Collector·report download
- 원본 증적·첨부파일 download
- 검토 의견·승인·관리 action

화면에서 button, menu, field를 숨기는 것은 사용자 경험을 위한 표현일 뿐 authorization이 아니다. Browser가 ID, route, HTMX header와 form field를 변경해도 다른 사용자의 자산, Job, Finding, 증적 또는 감사 로그를 읽거나 수정할 수 없어야 한다.

관리자 역할도 모든 보안 조치 승인 권한을 자동으로 받지 않는다. 역할 세부 권한은 RBAC 표에서 확정하며 UI는 서버가 반환한 capability view model에 따라 표시한다.

## 12. SSE와 진행 상태

Job 진행 상태는 동일 출처의 읽기 전용 SSE endpoint로 제공한다.

```text
GET /events/v1/audit-jobs/{job_id}
Content-Type: text/event-stream
```

- native `EventSource`를 최소 local JS로 사용하며 별도 HTMX SSE extension을 초기 도입하지 않는다.
- cookie 인증과 서버의 자산 범위 authorization을 매 연결·재연결에서 검사한다.
- access token, session ID와 민감정보를 query string에 넣지 않는다.
- event에는 상태, sequence, 발생 시각, correlation ID와 최소 message만 포함한다.
- 원본 증적이나 상세 오류 stack은 event로 보내지 않고 권한이 검증된 상세 endpoint에서 조회한다.
- heartbeat, 최대 연결시간, 동시 연결 수, reconnect와 `Last-Event-ID` 정책을 둔다.
- proxy buffering을 비활성화해야 하는 route를 제한하고 다른 response에는 적용하지 않는다.
- SSE가 차단된 환경은 제한된 간격의 HTMX GET polling으로 degrade하고 상태 변경 polling은 하지 않는다.

Worker나 AI 장애 상태는 `PENDING`, `RUNNING`, `COMPLETED`, `FAILED`, `DEGRADED` 등 업무 상태로 표시하되 Finding의 공식 판정을 변경하지 않는다.

## 13. Upload와 Download

### 13.1 Upload

- HTML `multipart/form-data`와 잠긴 `python-multipart`를 사용하되 client 검증은 편의 기능으로만 취급한다.
- Gateway와 API 모두 요청 size, file count, filename, content type, archive nesting과 압축 해제 size를 제한한다.
- extension이나 browser MIME만 신뢰하지 않고 서버가 magic·Schema·hash·서명과 ClamAV를 검증한다.
- 검증 전 package를 template에서 preview하거나 정적 경로로 제공하지 않는다.
- upload 진행·오류 화면에 로컬 전체 path와 민감한 server path를 노출하지 않는다.
- 중복 제출과 nonce 재사용은 server에서 거부하고 감사 이벤트를 남긴다.

### 13.2 Download

- Browser가 MinIO endpoint나 내부 관리 port에 직접 연결하지 않는다.
- Collector, report와 증적 download는 server authorization을 통과한 route로 제공한다.
- `Content-Disposition: attachment`, 안전한 server 지정 filename과 `nosniff`를 사용한다.
- 사용자 파일명을 response header에 넣을 때 CR/LF와 path 문자를 제거하고 RFC에 맞게 encoding한다.
- 장기 유효 공개 URL을 만들지 않는다. presigned URL을 도입하려면 짧은 만료, 최소 scope, 로그 redaction과 별도 승인을 요구한다.

## 14. Cache와 민감정보

- 인증된 page, fragment, JSON, SSE와 download response는 원칙적으로 `Cache-Control: no-store`를 사용한다.
- login·logout response와 오류 page에 secret·token·내부 stack trace를 포함하지 않는다.
- version·content hash가 고정된 public static asset만 장기 `immutable` cache를 허용한다.
- Browser storage에 session, Finding 원문, 증적, AI prompt와 개인정보를 저장하지 않는다.
- HTMX history cache와 service worker를 사용하지 않는다.
- server access log에서 session·CSRF token, upload 본문과 민감 query parameter를 제거한다.

## 15. UI 상태와 오류 표현

UI는 다음 상태를 구분해 표시한다.

| 구분 | 예시 |
|---|---|
| Finding | `PASS`, `FAIL`, `REVIEW`, `ERROR`, `N/A` |
| Job | `PENDING`, `UPLOADED`, `VALIDATING`, `EVALUATING`, `COMPLETED`, `FAILED` |
| AI 설명 | `NOT_REQUESTED`, `PENDING`, `READY`, `DEGRADED`, `UNAVAILABLE` |
| 접근 | `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND` |

- 색상만으로 상태를 표현하지 않고 text·icon·accessible label을 함께 사용한다.
- `ERROR`를 `FAIL`로, `REVIEW`를 취약 또는 양호로 표현하지 않는다.
- AI 설명의 불확실성과 근거 누락을 표시하며 공식 판정과 시각적으로 분리한다.
- 예상 가능한 사용자 오류에는 correlation ID를 제공하되 stack trace, SQL, filesystem path와 내부 host를 노출하지 않는다.
- destructive 또는 승인 action은 대상·영향·현재 version을 다시 표시하고 이중 제출을 서버 idempotency로 통제한다.

## 16. 접근성과 Browser 지원

- semantic HTML, 명시적 label, fieldset, table caption과 heading 순서를 사용한다.
- keyboard만으로 로그인, 자산 등록, Job 생성, upload와 Finding 조회가 가능해야 한다.
- focus indicator를 제거하지 않고 HTMX swap 후 focus·오류 summary를 관리한다.
- 진행 상태는 적절한 `aria-live` 영역을 사용하되 과도한 알림을 피한다.
- 최소 대비, 확대와 reduced-motion 설정을 존중한다.
- 1차 기준은 지원 중인 Windows 11의 조직 승인 Microsoft Edge이며, 최신 Chrome과 Firefox에서 핵심 흐름 smoke test를 수행한다.
- Internet Explorer와 구형 EdgeHTML 지원을 위해 CSP나 보안 기능을 완화하지 않는다.

## 17. 개발·배포 경계

- UI는 `audit-api` application image에 포함하고 별도 frontend container를 만들지 않는다.
- 개발 reload와 source bind mount는 `compose.dev.yml`에서만 허용한다.
- 운영 image는 non-root, read-only root filesystem과 필요한 임시 directory만 쓰기 가능하게 구성한다.
- Jinja2 template와 static asset 변경은 application image rebuild·test·SBOM·digest 갱신을 요구한다.
- 운영환경에서 template나 vendor JS를 volume으로 즉석 교체하지 않는다.
- Uvicorn을 Browser에 직접 공개하지 않고 Gateway가 TLS·size limit·rate limit과 header를 담당한다.
- 개발용 debug, template auto-reload, verbose error와 API documentation 공개 범위는 운영에서 비활성 또는 관리망 제한한다.

## 18. Version update 정책

### 18.1 Python Web dependency

FastAPI, Jinja2, Uvicorn과 `python-multipart` 변경은 `requirements/*.in` 수정, `pip-tools --generate-hashes`, clean install, template·upload·보안 회귀시험과 lock 승인을 거친다.

현재 잠금 기준은 다음과 같다.

- FastAPI `0.139.2`
- Jinja2 `3.1.6`
- Uvicorn `0.51.0`
- python-multipart `0.0.32`

### 18.2 HTMX와 정적 자산

HTMX patch·minor도 자동 교체하지 않는다. 다음 절차를 통과해야 한다.

1. 공식 stable release·license·security 상태 확인
2. upstream release tag와 download byte 검증
3. local SHA-256·SRI·size·출처를 asset lock에 기록
4. release note와 HTMX 보안 설정 호환성 검토
5. full page·fragment·CSRF·CSP·SSE·history 회귀시험
6. Stored/Reflected XSS 및 cross-user authorization 시험
7. 운영 image rebuild, SBOM·scan·digest 갱신과 승인

HTMX 3.x/4.x 같은 major 변경은 이 ADR 개정 또는 대체 ADR이 필요하다.

## 19. 검토한 대안

## 20. 결과와 trade-off

### 20.1 기대 효과

- API와 UI가 같은 인증·권한·업무 service를 사용
- Node runtime·frontend container·대규모 client dependency 제거
- 외부 CDN 없이 폐쇄망에서 동일하게 동작
- server-side autoescape와 엄격한 CSP 적용이 단순
- HTML fragment 단위로 빠른 MVP 개발과 회귀시험 가능
- JavaScript 장애 시에도 주요 form·navigation fallback 가능

### 20.2 비용과 위험

- 대규모 client visualization·복잡한 offline interaction에는 부적합
- fragment route가 늘어나면 template contract와 권한시험이 증가
- HTMX swap 경계에서 XSS·focus·오류 처리를 별도로 검증해야 함
- API와 UI가 같은 process 자원을 사용하므로 template rendering·SSE 부하 제한 필요
- exact HTMX byte와 project static asset을 Python requirements와 별도로 잠가야 함

## 24. 2026-08-01 AI token stream과 제한 Markdown 후속 결정

실제 Chrome의 `/ui/ai-analysis`에서 PC-01~18과 마지막 종합 설명이 `18 / 18` 완료되는 것을 확인했다. 당시 token delta는 `textContent`로 표시되어 Markdown 기호가 그대로 보였으나, 2026-08-02 후속에서 `secai.restricted-markdown.v3` 제한 AST·실제 token stream·등록 출처·제한 표 렌더링으로 보완했다. 현재 기준은 [`가이드_대화_UI_스트리밍_검색_기준선_20260802.md`](../../deploy/verification/가이드_대화_UI_스트리밍_검색_기준선_20260802.md)를 따른다.

후속 UI는 다음 순서만 허용한다.

```text
model token stream
→ 원문 누적 buffer
→ 완료된 block 단위 Markdown parser
→ heading·paragraph·strong·em·list·table·code·안전한 link allowlist
→ HTML sanitizer
→ Trusted Types/CSP를 만족하는 DOM 반영
```

- raw HTML과 inline style은 입력 단계에서 비활성화한다.
- `javascript:`, `data:`와 미승인 외부 link, event handler, iframe, object, SVG script는 제거한다.
- streaming 중 미완성 문법은 plain text로 표시하고 block이 닫힌 뒤 해당 block만 다시 렌더링한다.
- sanitizer 실패 시 전체 답변을 plain text로 되돌리고 공식 판정·인용은 그대로 보존한다.
- `innerHTML` 직접 대입과 Jinja2 `|safe`로 model 출력을 우회하지 않는다.

현재 UI E2E와 출력 정책은 `deploy/verification/PRODUCT_AI_스트림_UI_종단간_및_출력_정책_20260801.md`, 상세 후속 단계는 제안 ADR 19를 따른다.
