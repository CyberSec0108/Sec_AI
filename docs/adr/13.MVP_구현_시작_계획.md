## 1. 결론

다음 단계는 추가 기술을 선정하는 단계가 아니라 **실제 구현 기반과 첫 결정론적 세로 기능을 만드는 단계**다.

가장 먼저 다음 결과를 만들어야 한다.

```text
PC-07 합성 점검 package
→ JSON Schema·hash·scope 검증
→ normalized evidence 생성
→ 승인 전용 Audit Pack rule 평가
→ PASS/FAIL/ERROR와 적용성 제외 결과 생성
→ Finding version·근거·input/output hash 저장
→ 최소 API 또는 test application에서 결과 조회
```

이 흐름을 AI, pgvector 검색, vLLM, Neo4j, Wazuh와 실제 Windows Collector 없이 먼저 완성한다. 첫 세로 기능이 통과한 뒤 PC-01~PC-18 전체 Audit Pack·Fixture·규칙을 확대하고, 그다음 One-shot Collector와 VMware 실측을 연결한다.

즉시 시작 순서는 다음과 같다.

1. 1차 문서 승인·미해결 Gate 기록
2. repository·품질도구·Core Compose 최소 골격 생성
3. 기존 JSON Schema와 example을 잠긴 환경에서 검증
4. PC-07 Audit Pack·Fixture 작성
5. package validation·normalization·rule engine 구현
6. PostgreSQL·AIStor·Celery·FastAPI 최소 연결
7. PC-01~PC-18 확대
8. Windows Collector와 현재 Windows 11 개발 PC 읽기 전용 실측
9. 현재 Docker Core 복구·보안시험
10. KISA 원문 준비 → 질문 근거 찾기 → 출처 검증 → OpenRouter 호환성 시험 → 최종 로컬 vLLM 답변 → 대화 기능 순으로 KISA 질의응답 완성
11. 실제 KISA 질문답변·점검 결과 설명을 현대형 Chat과 사용자 친화 점검 UI에 연결
12. 점검 결과 설명 DTO → 결과별 KISA 근거 → 적극적 AI 설명 API → 결과 화면 → 후속 질문 → 재점검 → 대화 관리 → 사용자용·기술 검증용 PDF와 AI 모델 활용·라이선스 명세 → 로컬 vLLM 최종 제품 인수 순으로 제품 정합성 보완
13. clean Windows 11 VM 회귀·조직 서명·SmartScreen·Pilot 최종 인수

## 4. 구현 원칙

- 첫 목표는 화면 수가 아니라 검증 가능한 end-to-end decision path다.
- PC-07 하나로 걷는 골격을 만든 뒤 동일 구조로 PC-01~PC-18을 확대한다.
- JSON Schema와 Audit Pack은 API·Collector·Worker가 공유하는 계약이다.
- Audit Pack에는 임의 Python·shell·network 실행을 허용하지 않는다.
- package 위변조는 Finding `ERROR`가 아니라 수신 거부·격리다.
- 검증된 package 안의 수집 실패만 Control `ERROR`로 판정한다.
- AI는 Finding을 생성·변경하지 않는다.
- Guide Catalog의 `APPROVED`와 Audit Pack의 `APPROVED`를 같은 승인으로 취급하지 않는다.
- LLM의 mapping·rule·Fixture 산출물은 Schema-valid `DRAFT` 제안이며 승인·서명 전에는 Rule Engine에서 실행하지 않는다.
- 현재 Windows `win.*` 계약은 `IMP-038~046`에서 사용자 실행·복구·권한 경계까지 안정화하고, canonical fact 전환은 계약 versioning과 회귀시험을 거쳐 점진적으로 수행한다.
- UI·API·Worker는 domain rule을 중복 구현하지 않는다.
- PostgreSQL은 업무 상태와 Outbox의 정본, AIStor는 원본 object의 정본이며 Redis는 재생성 가능한 전달수단이다.
- Queue 중복 전달을 전제로 모든 task와 Finding 저장을 멱등하게 만든다.
- 실제 비밀정보·운영 `.env`·원본 증적·VM image를 Git에 넣지 않는다.
- 사용하지 않는 AI·Graph·Wazuh·remediation service folder와 container를 먼저 만들지 않는다.

## 6. 단계별 실행계획

### 단계 A. 문서 기준선 승인·동결

목표: 구현 중 다시 논쟁하지 않을 최소 기준과 남은 위험을 식별한다.

작업:

1. ADR 1~12의 승인자·결정·일시를 기록한다.
2. 서로 충돌하는 상위 문구를 확인한다.
3. 승인된 문서 hash를 `docs/adr/README.md` 기준선과 대조한다.
4. 승인된 Redis 내부 사용 조건과 AIStor·인증 dependency의 남은 기술시험을 issue로 등록한다.
5. PC-07 선정과 상태 의미를 승인한다.
6. 변경관리·예외 승인 방식과 code review 책임자를 지정한다.

완료 Gate:

- Runtime·PC 범위·Schema·공식 판정·RBAC·인증 결정에 owner가 있다.
- unresolved item마다 차단 단계와 기한이 있다.
- 승인되지 않은 항목을 운영 완료로 표시하지 않는다.

### 단계 B. Repository·품질·Core Compose 골격

목표: 같은 잠금파일로 build·lint·type·test·Health를 반복 실행한다.

산출물:

- root metadata 5종
- 최소 package·app folder
- Ruff, mypy, pytest, coverage 설정
- Schema validation command
- API·Worker·Scheduler Dockerfile
- `compose.yml`, `compose.dev.yml`
- Gateway, API, Worker, Scheduler, PostgreSQL, Redis, AIStor, ClamAV service skeleton
- Health·Readiness endpoint와 dependency health check
- CI 또는 동일 의미의 local verification script

필수 기준:

- CPython 3.14.6과 image digest를 build에서 검증한다.
- `pip --require-hashes`로 service lock을 설치한다.
- container는 non-root, read-only root filesystem을 기본으로 한다.
- 운영 Compose에 source bind mount와 `--reload`를 사용하지 않는다.
- PostgreSQL·Redis·AIStor·ClamAV port를 일반 사용자망에 공개하지 않는다.
- secret 기본값을 Compose에 넣지 않는다.

완료 Gate:

```text
format/lint PASS
type check PASS
unit smoke PASS
schema validation PASS
docker compose config PASS
CPU Core compose start PASS
Gateway Health·Readiness PASS
secret scan 0건
```

### 단계 C. 데이터 계약 실행 Gate

목표: 작성된 Schema가 실제 locked runtime에서 producer·consumer 계약으로 동작하는지 확인한다.

작업:

1. `database/schemas/validate_examples.py`를 locked dev container에서 실행한다.
2. 8개 Schema 자체 검사와 valid/invalid example을 검증한다.
3. duplicate JSON key, remote `$ref`, unknown property를 거부한다.
4. RFC 8785 JCS test vector를 만든다.
5. archive path·size·file count·compression ratio 검증 계약을 추가한다.
6. Schema version 호환·거부 정책을 contract test로 고정한다.
7. Finding·Audit Pack에 ADR 10이 요구한 lineage field 보강 여부를 migration 전에 결정한다.

완료 Gate:

- Schema validator가 clean container에서 통과한다.
- Collector와 Server가 공유할 test vector가 있다.
- package integrity failure와 Control ERROR가 다른 test로 존재한다.
- Schema 변경이 필요하면 코드보다 먼저 version·example을 갱신한다.

### 단계 D. PC-07 Audit Pack·Fixture

목표: 첫 Control의 적용성·증적·판정·근거를 실행 가능한 Pack으로 만든다.

PC-07 기준:

- 원문: 2026 KISA `07. PC`, 571~572쪽
- 판단: 평가 대상 고정 volume이 모두 NTFS면 PASS, 하나라도 비-NTFS면 FAIL
- 제외: EFI/MSR/Recovery, 광학·이동식 volume
- 검토 대상: ReFS, Storage Spaces, BitLocker, VHD
- 기본 권한: 일반 사용자 우선

필수 Fixture:

| Fixture | 내용 | 기대 결과 |
|---|---|---|
| `PC-07-PASS` | 모든 평가 volume NTFS | `PASS` |
| `PC-07-FAIL` | 평가 대상 중 비-NTFS volume 존재 | `FAIL` |
| `PC-07-ERROR` | 필수 volume 정보 수집 실패 | `ERROR` |
| `PC-07-EXCLUDED` | 제외 partition만 비-NTFS | 평가 집합 제외·정상 결과 |
| `PC-07-EDGE-REFS` | ReFS 처리 | 승인된 기대 상태 |
| `PC-07-EDGE-VHD` | VHD·가상 volume | 승인된 기대 상태 |

Audit Pack에는 다음을 포함한다.

- Control ID·제목·중요도·원문 page
- target OS·architecture·version
- exact Probe requirement와 normalized field
- applicability·exclusion rule
- evaluation rule ID·version·parameter
- result/reason code
- Fixture reference와 expected status
- Pack version·content hash·approval 상태

완료 Gate:

- 임의 code 없이 Schema-valid Pack이 생성된다.
- 원문 대조 검토가 기록된다.
- PASS/FAIL/ERROR와 edge Fixture가 reviewer 승인을 받는다.
- 동일 Pack version에 다른 content hash를 허용하지 않는다.

### 단계 E. Pure deterministic Core

목표: DB·Queue·AI 없이 입력 bundle을 Finding으로 변환한다.

구현 순서:

1. strict JSON loader와 duplicate key 방어
2. Schema registry와 offline `$ref`
3. package inventory·path·size·hash validation
4. normalized evidence mapper
5. evidence completeness evaluator
6. applicability evaluator
7. allowlist rule registry
8. PC-07 operator와 decision builder
9. Finding Schema·canonical input/output hash
10. replay·determinism test harness

Rule Engine interface:

```text
evaluate(canonical_input, exact_pack, engine_version)
→ immutable finding candidate
```

금지:

- `eval`, `exec`, dynamic import와 arbitrary regex
- filesystem·network·DB·LLM 직접 접근
- 현재 시간·locale·directory order 암묵 의존
- 부분 증적 `PASS`
- package 위변조를 Control `ERROR`로 변환

완료 Gate:

- 동일 입력 100회 결과 hash가 같다.
- PC-07 모든 Fixture가 기대 상태를 반환한다.
- DB·Redis·AIStor·AI 없이 unit test가 통과한다.
- result code, actual/expected field, evidence hash와 원문 위치를 추적할 수 있다.

### 단계 I. 현재 OS·로컬 AI·사용자 경험

2026-07-23 사용자 승인에 따라 VM보다 현재 Windows 11 개발 PC에서 먼저 시험한다. 현재 PC는 개발 도구와 기존 설정이 있는 환경이므로 clean baseline이 아니며, 이 시험은 VM 인수와 운영 승인을 대체하지 않는다.

목표:

- 현재 OS에서 PC-01~18 읽기 전용 Probe와 전체 판정 경로를 먼저 검증
- Worker·Queue·Outbox와 AIStor·Redis·PostgreSQL 장애·복구 검증
- 인증·RBAC·Web 보안 검증
- KISA 원문 페이지를 근거로 답하는 AI 설명 계약을 OpenRouter 시험 대역으로 먼저 검증하고 최종 제품은 로컬 vLLM으로 연결
- 점검 결과와 무관한 KISA 가이드 질문도 받을 수 있는 Chat 제공
- Guide Catalog·exact version·license·scope filter로 향후 다른 가이드 확장
- Guide source와 공식 Control의 mapping을 Guide 승인과 분리된 versioned artifact로 관리
- 플랫폼 원본 증적·정규화된 보안 사실·Control 판정 입력을 분리하는 점진적 확장 계약
- 질문 근거 찾기·출처 표시·로컬 AI·대화 기록·중단·재시도 계약을 확정한 뒤 개발 검증 페이지를 초보 사용자 중심의 점검·결과·Chat UI로 개편
- LLM은 공식 판정을 바꾸지 않지만 전체 종합·관련 위험·AI 권장 우선순위·사용자/관리자 조치·재점검 변화·후속 질문·보고서 설명에 적극 활용

사용자 관점의 순서는 다음과 같다.

```text
믿을 수 있는 KISA 원문 준비
→ 질문과 관련된 페이지 찾기
→ 찾아낸 근거·인용 정확도 시험
→ OpenRouter 시험 대역으로 API·SSE·오류 계약 확인
→ 내 PC의 로컬 vLLM이 실제 결과와 근거를 사용해 답변
→ 대화 저장·중단·편집·재시도 연결
→ KISA Q&A와 점검 결과 쉬운 설명을 실제 화면에 제공
→ 결과 PDF와 AI 모델 활용·라이선스 명세 제공
```

내부 기술로는 `Guide Catalog·정본 corpus → 승인형 문서 반입(Ingest) → PostgreSQL+pgvector 검색·rerank → 질의응답 평가 → Runtime·모델 capability → Conversation API → 통합·불변성` 순서다. pgvector가 사용자 기능보다 우선한다는 뜻이 아니라, 답변 전에 관련 원문을 찾기 위한 내부 사서 역할이 먼저 필요하다는 뜻이다.

`GUIDE_QA`용 문서 승인은 공식 Audit Pack 승인을 의미하지 않으며, LLM의 mapping·rule·Fixture 제안은 내부 DRAFT로만 검증한다. 그 뒤 UI를 `첫 화면의 할 일 → 단계형 전체점검 → 새 대화·대화 기록·입력창·실시간 답변 → 쉬운 결과·AI 설명·본문 출처 → 접힌 기술정보` 순서로 개편한다. FastAPI·Jinja2·로컬 HTMX와 서버 권한검사는 유지한다. 세부 기능과 후속 확장은 `docs/plans/대화_RAG_제품_계획.md`와 ADR 15를 따른다.

완료 Gate:

- 현재 OS 설정 diff 0, false PASS 0
- 장애 후 중복·유실 0과 원본·Finding 계보 재현
- 초보 사용자가 점검 시작, 권한 차이, 결과와 다음 행동을 이해
- UUID·hash·raw JSON은 기본 화면에서 숨기고 필요할 때만 펼침
- page·절·chunk 인용과 근거 없음 처리
- 점검 결과와 무관한 KISA 가이드 질문을 exact 문서·version·page 인용으로 답변
- 대화 streaming·중단·편집·재생성·분기·history가 권한·감사·보존 계약을 지킴
- 다른 가이드는 Catalog·Ingest·평가 등록으로 추가되고 Core code를 복제하지 않음
- Guide 승인만으로 공식 Rule이 활성화되지 않고, 공식 Pack은 별도 Fixture·결정론·서명·승인 Gate를 통과
- LLM 제안만으로 Audit Pack이나 Finding 상태가 변경된 사례 0
- AI output이 공식 상태를 변경하지 못함
- OpenRouter 시험 입력은 합성·승인된 비식별 최소 범위이고 로컬 vLLM 완료로 오표시하지 않음
- 최종 제품은 `LOCAL_VLLM_FULL_CONTEXT`에서 실제 결과 설명·후속 질문·보고서를 처리하고 외부 egress 0을 검증
- AI 종합·관련 위험·권장 우선순위·조치가 공식 판정과 구분돼 표시됨
- 사용자용·기술 검증용 PDF와 AI 모델 활용·라이선스 명세의 권한·감사·hash·append-only Gate 통과

## 10. DB·API 최초 구현 범위

최초 migration은 모든 미래 table을 만들지 않고 다음 최소 table로 시작한다.

- organizations
- users, local credentials, MFA credentials, sessions
- roles, role assignments, asset assignments
- assets
- audit_jobs, workflow_steps, task_attempts
- manifests, package submissions, evidence artifacts
- normalized evidence records
- Audit Pack releases·assignments
- Finding versions·current projection
- Outbox events
- audit events

원본 bytes는 PostgreSQL에 넣지 않고 AIStor exact object version·hash를 참조한다. Redis result backend를 업무 정본으로 사용하지 않는다.

API는 resource ID를 받았다는 이유로 접근을 허용하지 않고 organization·asset·role·state·version을 함께 확인한다. UI route, HTMX fragment, JSON API, SSE와 download가 같은 authorization service를 사용해야 한다.

1인이 여러 책임을 수행해도 승인 대상에서는 작성자와 승인자를 가능한 한 분리하고, 분리하지 못한 예외를 기록한다.

## 14. 다음 단계 진입·중단 기준

다음 단계로 진행:

- 현재 단계의 automated test와 보안 Gate가 통과했다.
- 산출물 version·hash·owner가 기록됐다.
- known defect가 false PASS, 권한 우회, 증적 변조와 직접 관련되지 않는다.
- 보류 defect의 영향과 종료기한이 승인됐다.

진행 중단:

- 원문 기준이 합의되지 않아 PASS/FAIL 의미가 바뀔 수 있다.
- package 신뢰 경계·Schema·hash 검증이 우회된다.
- 사람이거나 AI가 공식 Finding을 직접 변경할 수 있다.
- 다른 organization 자원 접근이나 session revoke 실패가 재현된다.
- 운영 image·dependency·secret provenance를 설명할 수 없다.
- 실제 증적을 반입하려는데 license·retention·인증 Gate가 미완료다.

## 15. 전체 일정 사용 원칙

source 계획서의 1~2인 기준 14~18주는 Core·Collector·VMware·AI 설명까지 포함한 초기 참고값으로 유지한다. 본 계획은 날짜보다 Gate를 우선한다.

일정 단축이 필요하면 다음을 미룬다.

- dashboard 시각화와 고급 report format

다음은 줄이지 않는다.

- 공식 판정 재현성
- RBAC·MFA·CSRF·session revoke
- 원본 증적 version·hash·retention 계보
- Fixture·VMware 회귀

## 16. 승인 후 첫 명령의 의미

이 계획 승인 후 첫 작업은 AI model download나 전체 Compose 실행이 아니다. 먼저 locked 개발 image에서 다음 의미의 검증이 가능하도록 repository를 만든다.

```powershell
docker compose -f deploy\compose\compose.dev.yml config
docker compose -f deploy\compose\compose.dev.yml run --rm api-dev `
  python database\schemas\validate_examples.py
docker compose -f deploy\compose\compose.dev.yml run --rm api-dev `
  python -m pytest tests\unit tests\contract
docker compose -f deploy\compose\compose.dev.yml run --rm api-dev `
  python -m ruff check .
docker compose -f deploy\compose\compose.dev.yml run --rm api-dev `
  python -m mypy src apps
```

실제 service name과 command는 구현 시 확정하되, host의 우연한 Python package나 전역 환경에 의존하지 않고 잠긴 container에서 같은 검증이 실행돼야 한다.

## 20. 2026-08-06 현재 상태와 후속 Gate

이 문서의 초기 세로 기능 순서는 완료 이력으로 유지한다. 현재 개발 환경에서는 `PRODUCT-AI-01~09`, Windows PC-01~18 결과·token stream·PDF·후속 질문, 제한 Markdown과 지식 출처 분리를 구현했다. clean Windows 11 VM·조직 서명·SmartScreen·Pilot의 `IMP-055~062`는 계속 별도 Release Gate다.

후속 사용자 승인에 따라 ADR 19·20 범위의 개발 구현도 일부 선행했다.

- Ubuntu 24.04·Rocky Linux 9 읽기 Adapter와 KISA UNIX U-01~U-67 제품 흐름
- Linux 진행·결과·AI·PDF·후속 질문과 안전 기본값·실행 snapshot
- 개인/조직 Criteria Profile·선택 이력·KISA 기본값 되돌리기
- 32차원 rollback generation과 BGE-M3 1024차원·Reranker 병렬 검색
- Cisco IOS XE·Aruba AOS-CX 공통 계약·fail-closed 합성 Adapter

이는 Linux 운영 Pack·서명·snapshot 반복 재현성, BGE 품질 benchmark, Switch 공식 image·실장비, 로컬 vLLM 또는 Agent/MCP 실행 완료를 뜻하지 않는다. 정확한 다음 작업은 루트 `구현_현황.md`, 플랫폼 경계는 ADR 19, Criteria 경계는 ADR 20을 따른다.
