# ADR-004: 비동기 작업 Queue

## 현재 구현 상태 (2026-08-07 검토)

- PostgreSQL Outbox, Redis 전달, Worker redelivery와 결과 멱등성의 개발 흐름이 연결돼 있으며 관리자 화면에서 최근 복구 상태를 확인할 수 있다.
- Queue는 공식 판정 정본이 아니다. 재전달돼도 동일 결과를 중복 생성하지 않고, DB commit과 message 전달 사이 실패를 Outbox 기준으로 복구한다.
- 운영 부하·장애·Redis 교체·장기 정지 인수는 별도 Gate다. 현재 개발 복구시험을 운영 고가용성 완료로 해석하지 않는다.

## 1. 결정 요약

Sec_AI의 1차 MVP 비동기 처리는 **Celery Worker + Celery Beat + Redis Broker**로 구현한다. 다만 Redis와 Celery 상태를 업무 정본으로 취급하지 않는다. Job, 단계, 시도, 판정 결과와 실패 상태의 정본은 PostgreSQL에 기록하고, 원본 증적은 AIStor에 보존한다.

| 결정 항목 | 확정 제안 |
|---|---|
| 작업 실행 | Celery `5.6.3` |
| Message broker | Redis `8.8.0`, RSALv2 내부 사용, 정확한 image digest 고정 |
| 결과 backend | 사용하지 않음. `task_ignore_result=True` |
| 업무 상태 정본 | PostgreSQL |
| 원본 증적 정본 | AIStor의 version·hash가 고정된 object |
| 전달 보장 | At-least-once, 중복 전달 가능성을 명시적으로 수용 |
| 중복 방지 | PostgreSQL 멱등 key·고유 제약·단계 상태 전이 |
| 발행 안정성 | PostgreSQL Transactional Outbox + Dispatcher |
| 예약 작업 | 별도 단일 Celery Beat process |
| 직렬화 | JSON만 허용. Pickle, YAML 등 임의 객체 역직렬화 금지 |
| Queue 분리 | Core validation, rule evaluation, AI explanation, maintenance |
| 실패 격리 | PostgreSQL의 failed/quarantined 상태와 승인된 재실행 절차 |
| 외부 노출 | Redis host port 미공개, 내부 network와 ACL만 허용 |
| 공식 판정 | Queue나 Worker가 임의 결정하지 않고 Audit Pack 규칙 엔진 결과를 저장 |

핵심 원칙은 다음과 같다.

> Celery는 “한 번만 실행”을 보장하는 시스템이 아니라, 실행해야 할 작업을 신뢰성 있게 전달하는 장치다. Sec_AI는 중복 실행되어도 결과가 훼손되지 않는 작업과 PostgreSQL 상태 전이로 정확성을 확보한다.

## 2. 배경과 목표

점검 package 검증, 정규화, 규칙 평가, 보고서 생성과 AI 설명은 HTTP 요청 안에서 모두 끝내기 어렵다. 실행 시간이 길고 외부 의존성이 있으며, Worker나 Broker가 재시작되어도 사용자 요청과 결과가 유실되지 않아야 한다.

1차 MVP의 Queue는 다음 목표를 만족해야 한다.

- API 응답 시간과 장시간 점검 작업을 분리한다.
- Worker가 비정상 종료되어도 미완료 작업을 발견하고 다시 실행할 수 있다.
- 동일 message가 두 번 전달되어도 Finding이나 결과가 중복 생성되지 않는다.
- Redis 장애 중에도 이미 저장된 결과 조회는 계속 가능해야 한다.
- Core 규칙 평가와 선택적 AI 설명의 자원·장애 영향을 분리한다.
- task payload와 event에 원본 증적, 비밀번호, token 또는 민감한 PC 설정값을 싣지 않는다.
- 모든 상태 변화와 재실행을 감사 가능하게 남긴다.
- 폐쇄망에서도 image, package와 설정을 고정해 재현 가능하게 운영한다.

## 3. 적용 범위와 제외 범위

### 3.1 적용 범위

- 업로드 완료 후 package malware scan·구조 검증·schema 검증
- 증적 hash 확인과 정규화
- PC-01~PC-18 적용성 확인과 Audit Pack 규칙 평가
- Finding·report materialization
- 선택적 로컬 AI 설명 생성
- 보존 기간 점검, Outbox 재발행, stale 실행 복구 등 예약 작업
- API/UI에 표시할 비동기 Job 상태 갱신

### 3.2 제외 범위

- Collector가 Redis에 직접 접속하거나 task를 발행하는 구조
- Redis에 원본 증적, 공식 판정 또는 장기 보존 결과를 저장하는 구조
- Celery message를 사용자 또는 Collector가 직접 생성하는 기능
- 1차 MVP의 자동 remediation 실행
- Redis를 인터넷 또는 사용자 PC network에 공개하는 구성
- 장기 예약을 Celery `eta`·`countdown` message로 보관하는 방식
- Flower, Celery remote control, third-party dashboard의 기본 배포
- Kafka, RabbitMQ, Kubernetes operator 기반의 대규모 분산 운영
- Exactly-once 전달을 보장한다는 표현

## 4. 논리 구조와 책임 경계

```text
Browser / Collector
        │ HTTPS
        ▼
Gateway → audit-api
            │ 동일 PostgreSQL transaction
            ├─ audit_job / workflow_step 기록
            └─ outbox_event 기록
                     │
                     ▼
              Outbox Dispatcher
                     │ JSON message
                     ▼
                 Redis Broker
           ┌─────────┼──────────┐
           ▼         ▼          ▼
      Core Worker  AI Worker  Maintenance Worker
           │         │          │
           ├─────────┴──────────┤
           ▼                    ▼
      PostgreSQL 정본       AIStor 원본 증적

Celery Beat ──주기 trigger──> maintenance Queue
```

### 4.1 구성요소 책임

| 구성요소 | 책임 | 책임이 아닌 것 |
|---|---|---|
| `audit-api` | 인증·RBAC·자산 범위 확인, Job과 Outbox 원자적 기록 | Redis 발행 성공을 업무 저장 성공과 동일시하지 않음 |
| Outbox Dispatcher | 미발행 event를 Redis에 전달하고 발행 상태 기록 | 업무 규칙 판정 |
| Redis | Celery message 전달, 짧은 수명의 전송 상태 | 공식 Job 상태, 증적, 판정 결과의 정본 |
| Core Worker | package 검증·정규화·규칙 평가 | 인증 우회, 임의 명령 실행, AI의 공식 판정 반영 |
| AI Worker | 승인된 자료로 선택적 설명 생성 | PASS/FAIL 변경, Core Worker 자원 고갈 |
| Maintenance Worker | reconciliation, 보존 점검, 제한된 운영 작업 | 무제한 자동 재실행 또는 증적 임의 삭제 |
| Celery Beat | 주기 trigger 발행 | 장기 업무 상태와 schedule 실행 결과의 정본 |
| PostgreSQL | Job·단계·시도·Outbox·판정 상태의 정본 | 원본 binary 증적 보관 |
| AIStor | 원본 증적과 파생 artifact의 version·hash 보존 | Queue message 처리 |

### 4.2 Workflow 경계

- Celery는 workflow 단계의 **실행 trigger**만 전달한다.
- 단계의 현재 상태, 허용된 다음 상태와 입력 version은 PostgreSQL이 관리한다.
- LangGraph를 사용하는 AI 내부 workflow가 있더라도 전체 점검 Job의 정본은 PostgreSQL이다.
- Celery chain, chord 또는 result backend를 공식 workflow 상태로 사용하지 않는다.
- Worker는 단계 완료와 다음 Outbox event를 가능한 한 동일 DB transaction에 기록한다.

## 5. Queue와 Worker 분리

초기 논리 Queue는 다음과 같이 분리한다. Queue별 별도 Worker process를 사용하며 한 process가 모든 Queue를 소비하지 않는다.

| Queue | 주요 작업 | 기본 소비자 | Network·자원 원칙 |
|---|---|---|---|
| `core.validation` | malware scan 결과 확인, package·schema·hash 검증, 정규화 | Core validation Worker | DB·AIStor 접근, AI network 접근 금지 |
| `core.evaluation` | 적용성, Audit Pack 규칙 평가, Finding 생성 | Core evaluation Worker | DB·AIStor 접근, 결정론적 실행 우선 |
| `ai.explanation` | 선택적 설명·요약·RAG 처리 | AI Worker | AI profile network만 허용, CPU/GPU·동시성 별도 제한 |
| `maintenance` | Outbox reconciliation, stale task 복구, 보존 점검 | Maintenance Worker | 관리자용 task allowlist만 허용 |

다음 규칙을 적용한다.

- Queue 우선순위 기능에 정확성을 의존하지 않고, 별도 Queue와 Worker 용량으로 격리한다.
- Core 평가가 AI backlog 때문에 지연되지 않아야 한다.
- AI Queue가 중지되어도 Core 결과는 완료할 수 있으며 AI 상태는 `SKIPPED`, `PENDING` 또는 `FAILED`로 별도 표시한다.
- Worker는 Linux container의 prefork pool을 기본으로 사용한다. Eventlet·gevent 도입은 별도 ADR 없이는 허용하지 않는다.
- 각 Worker는 non-root, read-only root filesystem, 제한된 임시 directory와 최소 network만 사용한다.
- 자동 조치용 Queue와 Worker는 1차 MVP에 만들지 않는다.

## 6. Task message 계약

### 6.1 허용 payload

Task message에는 작업을 다시 조회하는 데 필요한 opaque identifier와 version만 싣는다.

```json
{
  "schema_version": "1.0",
  "task_name": "secai.core.evaluate_package",
  "job_id": "018f...",
  "workflow_step": "RULE_EVALUATION",
  "package_id": "018f...",
  "asset_id": "018f...",
  "expected_input_version": 3,
  "idempotency_key": "job:018f...:RULE_EVALUATION:v3",
  "correlation_id": "018f...",
  "created_at": "2026-07-21T00:00:00Z"
}
```

### 6.2 금지 payload

- 원본 증적 file 또는 base64 binary
- 비밀번호, access token, cookie, API key, Redis·DB·AIStor credential
- 사용자 입력 전문, PC 설정 원문, Registry dump 또는 PowerShell 전체 출력
- LLM prompt 전문과 AI response 전문
- ORM object, Python object, callback, executable code
- 사용자가 지정한 module·function·command·Queue 이름
- 신뢰되지 않은 URL, file path 또는 shell argument

Worker는 `job_id`와 권한이 검증된 관계를 기준으로 PostgreSQL·AIStor에서 입력을 다시 조회하고, `expected_input_version`, object version과 SHA-256을 확인한 후 실행한다. 존재하지 않거나 scope가 다른 identifier는 재시도하지 않고 보안 event로 기록한다.

### 6.3 직렬화와 task 등록

- `task_serializer='json'`, `accept_content=['json']`만 허용한다.
- Pickle, YAML, msgpack과 사용자 정의 역직렬화기는 활성화하지 않는다.
- Celery protocol 2와 UTC timestamp를 사용한다.
- Worker image에 등록된 allowlist task만 실행한다.
- task name과 routing key는 server code가 결정하며 HTTP 요청값을 그대로 사용하지 않는다.
- message schema version을 검증하고 지원하지 않는 version은 `QUARANTINED` 처리한다.
- message 서명보다 내부 network, broker 인증, 등록 task allowlist, schema 검증과 최소 payload를 우선한다. 별도 message 서명이 필요해지면 key 운영을 포함한 ADR로 추가한다.

## 7. 신뢰성 모델

### 7.1 At-least-once와 멱등성

Redis transport와 late acknowledgement를 사용하면 Worker 비정상 종료 시 동일 task가 재전달될 수 있다. 모든 task는 다음 조건을 만족해야 한다.

1. `idempotency_key`는 논리 작업마다 결정적으로 생성한다.
2. PostgreSQL에 동일 `task_type + idempotency_key`의 성공 결과를 하나만 허용하는 고유 제약을 둔다.
3. 실행 시작 전 현재 단계와 `expected_input_version`을 compare-and-set 방식으로 확인한다.
4. 이미 성공한 task는 부작용을 다시 만들지 않고 기존 결과 reference를 반환한다.
5. Finding은 `job_id + control_id + audit_pack_version + evidence_set_hash` 같은 업무 key로 중복을 방지한다.
6. AI 설명도 입력 hash와 model·prompt version을 key로 관리하고 공식 판정과 분리한다.

파일 생성은 임시 object에 먼저 쓰고 hash를 검증한 다음 정식 object key/version을 DB에 연결한다. DB commit 전에 생성된 orphan object는 보존 정책에 따른 reconciliation 대상이며 즉시 덮어쓰지 않는다.

### 7.2 Transactional Outbox

API가 DB에는 Job을 기록했지만 Redis 발행 직전에 종료되는 dual-write 문제를 방지하기 위해 Outbox pattern을 사용한다.

```text
1. API transaction 시작
2. audit_job 또는 workflow_step 기록
3. outbox_event 기록
4. transaction commit
5. Dispatcher가 미발행 event 조회
6. Redis publish
7. outbox_event의 published_at 기록
```

- `5`~`7` 사이에 장애가 나면 같은 event가 다시 발행될 수 있으므로 소비자는 반드시 멱등해야 한다.
- Dispatcher는 row locking 또는 lease를 사용해 병렬 instance 간 경쟁을 통제한다.
- `published_at`은 정확히 한 번 발행되었다는 증거가 아니라 마지막 확인 상태다.
- 미발행 Outbox의 가장 오래된 age를 핵심 장애 지표로 감시한다.
- Redis가 복구되면 Dispatcher와 reconciliation이 backlog를 다시 발행한다.

API는 Job과 Outbox commit 후 `202 Accepted`를 반환할 수 있다. Broker 장애 중에는 상태를 `DISPATCH_PENDING`으로 명시하며, Outbox backlog가 운영 한도를 넘으면 새 비동기 Job을 `503 Service Unavailable`로 제한한다.

### 7.3 Acknowledgement와 Worker 종료

초기 공통 설정 원칙은 다음과 같다.

| 설정 | 초기값 | 이유 |
|---|---:|---|
| `task_acks_late` | `True` | 작업 완료 뒤 ACK하여 Worker 손실 시 재전달 허용 |
| `task_acks_on_failure_or_timeout` | `True` | 알려진 실패는 ACK하고 명시적 retry 정책만 적용 |
| `task_reject_on_worker_lost` | `True` | Worker process 손실 시 idempotent task 재전달 |
| `worker_prefetch_multiplier` | `1` | 장시간 task의 불공정 선점 완화 |
| `broker_connection_retry_on_startup` | `True` | Broker 시작 순서 차이 허용 |
| `visibility_timeout` | `3600`초 | 초기 상한. 모든 task hard limit보다 충분히 크게 유지 |
| `worker_soft_shutdown_timeout` | `30`초 | 종료 시 진행 task의 재전달 가능성 개선 |

`task_reject_on_worker_lost=True`는 반복 crash task를 message loop로 만들 수 있다. 따라서 crash 횟수와 시도를 PostgreSQL에 기록하고 한도를 넘으면 `QUARANTINED`로 전환한다. 무한 재시도는 허용하지 않는다.

Compose의 `stop_grace_period`는 Worker soft shutdown timeout보다 길게 설정한다. 배포·종료 절차는 새 task 소비를 먼저 중지하고 실행 중인 task가 종료되도록 drain한 후 container를 내린다.

### 7.4 실행 시간과 Visibility timeout

- 모든 task는 soft·hard time limit를 명시한다.
- 초기 `visibility_timeout`은 1시간이며 가장 긴 hard limit는 50분 미만으로 제한한다.
- 장시간 AI 작업은 작은 단계로 분할하며, 1시간을 넘는 단일 task를 만들지 않는다.
- `eta` 또는 `countdown`은 visibility timeout보다 짧은 일시적 지연에만 사용한다.
- 수 시간·수 일 뒤 실행할 업무는 PostgreSQL의 due time과 Beat 조회로 처리한다.
- visibility timeout을 늘려서 장애를 숨기지 않고 task 크기와 외부 timeout을 먼저 제한한다.

실제 task별 시간 제한은 package 크기 제한과 성능 시험 결과를 기준으로 구현 설정표에 고정한다.

## 8. 재시도·실패·격리 정책

### 8.1 재시도 분류

| 실패 유형 | 예 | 처리 |
|---|---|---|
| 일시적 | Redis·DB·AIStor timeout, 일시적 AI endpoint 오류 | 지수 backoff + jitter, 최대 5회 |
| 영구적 입력 오류 | schema 불일치, hash 불일치, 지원하지 않는 package version | 재시도 없음, `FAILED_VALIDATION` |
| 보안 오류 | signature 실패, scope 불일치, 금지된 path·payload | 재시도 없음, `QUARANTINED` + 감사 event |
| 규칙 오류 | Audit Pack bug, 지원하지 않는 control mapping | 제한된 재현 후 `FAILED_RULE`, 운영 검토 |
| 자원 오류 | memory limit, disk full, 반복 Worker crash | 자동 반복 중지, `QUARANTINED` |
| 사용자 취소 | 실행 전 또는 안전한 단계 경계에서 취소 | `CANCEL_REQUESTED` 후 `CANCELLED` |

- retry는 예상 가능한 exception type에만 적용한다.
- `autoretry_for=(Exception,)` 같은 포괄적 재시도는 금지한다.
- 각 시도에는 `attempt_no`, 시작·종료 시각, Worker ID, error code와 retry 예정 시각을 기록한다.
- stack trace와 message에는 secret·증적 원문을 남기지 않는다.
- 동일 task의 최대 자동 시도 후에는 사용자에게 일반 오류가 아니라 운영 검토가 필요한 상태임을 표시한다.

### 8.2 Dead-letter 대체

Redis/Celery 조합에 broker 고유 Dead Letter Queue가 있다고 가정하지 않는다. 실패 message를 Redis list에 장기 보존하는 대신 PostgreSQL에 다음 상태와 최소 진단 정보를 기록한다.

- `FAILED`
- `QUARANTINED`
- `CANCELLED`
- `RETRY_SCHEDULED`
- `STALE_RECONCILE_REQUIRED`

재실행은 권한 있는 사용자가 원인을 확인한 뒤 새 `idempotency_key`가 아니라 동일 논리 작업의 새 attempt로 요청한다. 입력 version이나 Audit Pack version이 바뀌면 새 논리 작업으로 기록해 이전 결과를 보존한다.

## 9. Celery Beat와 정기 작업

- MVP에서는 **Beat process를 정확히 하나** 실행한다.
- `worker -B`로 Worker에 Beat를 내장하지 않는다.
- 정기 schedule은 version 관리된 code/config에 정의하고 운영 중 UI에서 임의 cron을 생성하지 않는다.
- Beat는 직접 업무를 처리하지 않고 `maintenance` Queue에 identifier만 발행한다.
- 정기 작업은 PostgreSQL advisory lock 또는 lease와 멱등 key로 중복 실행을 방지한다.
- Beat local schedule file은 업무 정본이 아니다. 필요하면 전용 writable volume에 두되 backup 대상 업무 데이터로 취급하지 않는다.
- 보존 만료 대상은 Beat message가 아니라 PostgreSQL의 `due_at`을 기준으로 다시 조회한다.

초기 정기 작업 후보는 Outbox 재발행, stale 실행 탐지, 보존 만료 후보 생성, malware definition 상태 점검이다. 원본 증적의 실제 삭제는 별도 저장·보존 정책과 승인 절차가 확정된 후에만 활성화한다.

## 10. Redis 운영·보안 기준

### 10.1 Image와 license Gate

Redis는 컨테이너 잠금표에 고정된 다음 image를 사용한다.

```yaml
image: redis:8.8.0@sha256:5d2c689b4b55fc3fab4b0cc8aaa950f85b508c76c1e0f35a90d8f411d55a8b2b
platform: linux/amd64
```

현재 상태는 `LOCKED-RSALV2-INTERNAL`이다. Redis 8 계열의 선택 license 중 RSALv2를 적용하고, Sec_AI 조직 내부의 Celery Broker로만 사용한다.

- 납품·판매·재배포, Redis 자체 기능의 외부 관리형 서비스 제공과 source 수정은 하지 않는다.
- Redis port를 외부에 공개하지 않고 license·copyright notice를 보존한다.
- 사용 형태가 외부 제공·재배포·수정으로 바뀌면 license를 재검토하고 그 전에는 해당 배포를 중단한다.
- 기술 검증과 license 결정은 서로 다른 기록으로 유지한다. License 결정은 완료됐지만 SBOM·취약점·ACL·복구시험은 구현 Gate다.
- 조건이 바뀌어 RSALv2를 유지할 수 없으면 Valkey를 대안으로 검토하되 image만 조용히 교체하지 않는다.
- Valkey 전환 시 Celery/Kombu 호환성, ACL, persistence, 장애 복구, 성능, SBOM, vulnerability와 새 digest를 다시 검증하고 이 ADR을 개정한다.

### 10.2 Network와 인증

- Redis `6379`를 host에 publish하지 않는다.
- Redis는 외부 egress가 없는 내부 `app_net`에만 연결한다.
- Collector, Browser, Gateway와 AI endpoint는 Redis에 직접 접근할 수 없다.
- Redis `default` user의 무인증 전체 명령 허용을 사용하지 않는다.
- Celery broker용 named ACL user와 rate-limit용 user를 분리하고 서로 다른 secret을 사용한다.
- ACL은 허용된 command·key pattern만 부여한다. 실제 Celery/Kombu가 사용하는 command와 key를 integration test로 관찰한 뒤 최소 allowlist를 고정한다.
- credential은 OpenBao 또는 승인된 Vault에서 짧은 수명의 read-only file·memory 형태로 주입하고 URL, Compose environment, image, log와 healthcheck process argument에 노출하지 않는다.
- 동일 host 내부 network MVP에서도 ACL을 적용한다. 다중 host 또는 신뢰 경계 밖 통신은 Redis TLS를 의무화한다.
- 개발용 보호 해제 설정을 production Compose에 복사하지 않는다.

Redis logical database 번호는 보안 경계가 아니다. 같은 instance를 rate limit에 함께 사용하더라도 named user와 key namespace를 분리하고, 자원 경합이 Core Queue에 영향을 주면 별도 instance로 분리한다.

### 10.3 Persistence와 memory

Redis는 정본이 아니지만 Broker 재시작 시 불필요한 message 손실을 줄이기 위해 다음 초기 정책을 적용한다.

- 전용 volume에 AOF를 활성화한다.
- 초기 `appendfsync everysec`를 사용하고 장애·성능 시험으로 확정한다.
- `maxmemory-policy noeviction`을 사용해 broker key의 묵시적 퇴출을 허용하지 않는다.
- memory 경보와 Queue·Outbox backlog 한도를 두고, 한도 초과 시 새 작업을 명확히 제한한다.
- Redis backup을 업무 복구의 유일한 수단으로 삼지 않는다.
- Redis 전체 손실 시 PostgreSQL Outbox와 실행 상태 reconciliation으로 미완료 task를 재구성한다.
- 복구 뒤 중복 message가 생길 수 있으므로 멱등성 검증을 필수로 한다.

RDB snapshot을 함께 사용할지는 RPO/RTO·disk latency 시험 후 운영 설정표에서 확정한다. AOF 파일에는 task identifier와 routing metadata가 남을 수 있으므로 volume 접근, backup 접근과 폐기 절차도 보호 대상이다.

## 11. Celery 초기 보안 설정 기준

아래는 구현 시 반영할 기준이며 secret 값을 포함하지 않는다.

```python
app.conf.update(
    task_serializer="json",
    accept_content=["json"],
    task_protocol=2,
    enable_utc=True,
    timezone="UTC",
    task_ignore_result=True,
    task_store_errors_even_if_ignored=False,
    task_acks_late=True,
    task_acks_on_failure_or_timeout=True,
    task_reject_on_worker_lost=True,
    worker_prefetch_multiplier=1,
    broker_connection_retry_on_startup=True,
    worker_enable_remote_control=False,
    worker_send_task_events=False,
    task_send_sent_event=False,
    worker_soft_shutdown_timeout=30.0,
    broker_transport_options={
        "visibility_timeout": 3600,
    },
)
```

- `broker_url`은 source·image에 넣지 않고 secret file을 읽어 process 시작 시 구성한다.
- task event와 remote control은 민감한 argument 노출과 불필요한 제어면을 줄이기 위해 기본 비활성화한다.
- 필요 시 운영 metric은 application·PostgreSQL 상태와 제한된 Redis metric에서 수집한다.
- debugging을 위해 event를 일시 활성화하려면 변경 승인, payload 검토, 짧은 보존과 종료 확인이 필요하다.
- 전역 time limit만 믿지 않고 task type별 soft·hard limit를 명시한다.
- 위 설정 이름과 동작은 locked Celery `5.6.3` integration test에서 재검증한다.

## 12. 상태 모델과 API/UI 표시

세부 DB schema는 후속 `database/schemas`에서 확정하되 최소한 다음 상태를 구분한다.

| 계층 | 예시 상태 | 용도 |
|---|---|---|
| Job | `CREATED`, `DISPATCH_PENDING`, `RUNNING`, `SUCCEEDED`, `PARTIAL`, `FAILED`, `CANCELLED` | 사용자에게 보이는 전체 점검 상태 |
| Step | `PENDING`, `QUEUED`, `RUNNING`, `SUCCEEDED`, `FAILED`, `SKIPPED`, `QUARANTINED` | workflow 단계별 상태 |
| Attempt | `STARTED`, `RETRY_SCHEDULED`, `SUCCEEDED`, `FAILED`, `WORKER_LOST`, `TIMED_OUT` | 실행과 재시도 추적 |
| Outbox | `PENDING`, `PUBLISHED`, `RETRY_PENDING` | broker 발행 추적 |

- Celery의 내부 task state를 사용자 API의 정본으로 직접 노출하지 않는다.
- UI의 SSE는 PostgreSQL Job·Step 상태를 전달하며 Redis result backend를 조회하지 않는다.
- 상태 응답에는 `job_id`, 현재 단계, 진행 여부, 일반화된 error code, retry 가능 여부와 갱신 시각을 포함한다.
- stack trace, broker message, 내부 host, credential, 원본 증적값은 UI에 노출하지 않는다.
- cancel은 message 삭제를 보장한다는 뜻이 아니다. DB에 `CANCEL_REQUESTED`를 기록하고 Worker가 안전한 단계 경계에서 확인한다.

## 13. 장애 시 동작

| 장애 | 기대 동작 |
|---|---|
| Redis 중단 | 새 Job은 DB·Outbox에 `DISPATCH_PENDING`으로 기록 가능, 기존 결과 조회 유지, backlog 한도 초과 시 503 |
| Worker 강제 종료 | 미완료 message 재전달 가능, 동일 멱등 key로 기존 상태 확인 후 재실행 |
| API 종료 직후 | commit된 Outbox를 Dispatcher가 나중에 발행 |
| Redis data 전체 손실 | PostgreSQL 미완료 단계와 Outbox를 reconciliation해 재발행 |
| PostgreSQL 중단 | Worker는 결과를 Redis에 정본으로 남기지 않고 명시적 일시 실패·제한된 retry |
| AI endpoint 중단 | Core 판정 유지, AI 단계만 retry 후 `FAILED` 또는 `SKIPPED` |
| AIStor 중단 | 원본이 필요한 단계 중지, hash 없이 판정 진행 금지 |
| 반복 poison task | 자동 재시도 중단, PostgreSQL `QUARANTINED`, 운영 검토 |
| Redis memory 한도 | eviction 금지, publish 실패를 명시하고 API admission 제한 |
| Beat 재시작·중복 trigger | DB lease·멱등 key로 한 번의 논리 작업만 반영 |

장애 복구의 기준은 “Redis가 비어 있지 않음”이 아니라 PostgreSQL의 모든 비종료 Job이 유효한 완료, 실행, retry, quarantine 또는 dispatch 상태 중 하나로 수렴하는지다.

## 14. 관측성과 감사

### 14.1 필수 metric

- Queue별 대기 message 수와 oldest age
- Outbox pending 수와 oldest age
- task type별 처리 시간, 성공률, retry·timeout·quarantine 수
- `RUNNING` 상태의 stale age
- Worker process·concurrency·restart 수
- Redis 연결 오류, memory, rejected write, eviction 수, AOF 상태와 disk latency
- API admission 제한 횟수
- AI Queue와 Core Queue backlog의 분리 지표

### 14.2 Log와 audit event

구조화 log에는 다음 최소 식별자만 허용한다.

- `correlation_id`
- `job_id`
- `task_name`
- `task_execution_id`
- `attempt_no`
- `worker_id`
- 일반화된 `error_code`

task argument 전문, broker URL, secret, 증적값과 LLM prompt·response는 기록하지 않는다. 수동 재실행, quarantine 해제, cancel, schedule 변경과 운영자 override는 별도 감사 event로 남긴다.

### 15.4 IMP-044 구현 검증

2026-07-24에 PostgreSQL `workflow_steps`, `outbox_events`, `task_executions`, `workflow_results`와 identifier-only Queue message Schema를 구현했다. Redis publish 뒤 Outbox 완료 표시 전에 중단되는 경계를 재현하고, 실행 중인 Maintenance Worker 자식 프로세스를 실제 `SIGKILL`한 뒤 redelivery를 확인했다.

세 번의 task 시도에서 Worker 손실 1회, 논리 결과 1건, 중복 결과와 공식 Finding 증가는 0건이었다. 공개 상태 API는 Job·event·delivery ID, Worker PID와 원본 payload를 반환하지 않는다. 전체 기록과 재현 명령은 [`deploy/verification/IMP044_작업자_대기열_아웃박스_복구_검증.md`](../../deploy/verification/IMP044_작업자_대기열_아웃박스_복구_검증.md)를 따른다.

이 통과는 IMP-044 개발 Gate에 한정된다. 당시 체크되지 않은 Redis 전체 손실과 PostgreSQL·AIStor backup/restore는 IMP-045에서 합성 개발 범위로 추가 검증했다. poison task 격리, 장기 schedule, 부하·용량과 운영 backup Gate는 계속 남아 있으므로 Queue를 Pilot·production 승인 상태로 바꾸지 않는다.

### 15.5 IMP-045 Redis 전체 손실 재구축 검증

2026-07-24에 기본 Redis를 실제로 중지하고 빈 전용 Redis volume을 기동했다. PostgreSQL의 PENDING Outbox를 빈 broker에 다시 발행했고, 전용 Maintenance Worker가 같은 업무 멱등 key를 처리해 논리 결과 한 건으로 수렴했다. Redis 재구축과 pending 작업 회복은 57초가 걸렸으며 기존 Finding 증가와 원본 payload·credential 공개는 0건이었다.

이 시험으로 Redis가 업무 정본이 아니며 PostgreSQL에서 전달 상태를 재구축할 수 있음을 확인했다. 다만 같은 개발 PC의 합성자료 시험이므로 Redis AOF 독립 backup, 장기 backlog·용량, poison task 격리와 운영 재해복구 승인은 아직 완료하지 않았다. 상세 기록은 [`deploy/verification/IMP045_저장소_장애_백업_복원_검증.md`](../../deploy/verification/IMP045_저장소_장애_백업_복원_검증.md)를 따른다.

## 16. 대안 비교

| 대안 | 결정 | 이유 |
|---|---|---|
| Celery + Redis | 채택 | Python 생태계, 현재 lock·container 구성과 일치하며 MVP 운영 복잡도가 낮음 |
| Celery + RabbitMQ | 보류 | broker 기능은 강하지만 별도 제품 운영·보안·backup 범위가 증가함 |
| Valkey broker | 조건부 대안 | Redis 사용 형태가 바뀌어 RSALv2를 유지할 수 없을 때 검토. 호환성·운영 시험과 별도 image lock 필요 |
| FastAPI `BackgroundTasks` | 기각 | API process 종료·재배포에 대한 durable queue와 독립 Worker 운영을 제공하지 않음 |
| 동기 HTTP 처리 | 기각 | 장시간 작업, timeout, 재시도와 자원 격리에 부적합 |
| Redis result backend | 기각 | 업무 결과 정본이 이중화되고 Redis 장애가 결과 조회에 전파됨 |
| Celery canvas를 workflow 정본으로 사용 | 기각 | 결과 backend 의존과 상태 추적 복잡도 증가. PostgreSQL workflow 상태를 정본으로 유지 |
| Kafka | 보류 | 1차 MVP 규모 대비 운영 복잡도가 과도함 |
| RQ·Dramatiq | 보류 | 현재 확정된 Celery lock과 운영 자료를 변경할 명확한 이점이 아직 없음 |

## 17. 결과와 후속 영향

### 17.1 장점

- API와 장시간 작업이 분리되고 Worker를 독립 확장할 수 있다.
- Redis 손실이나 중복 전달이 공식 판정과 증적 유실로 직접 이어지지 않는다.
- AI 기능 장애와 부하를 Core 규칙 평가에서 격리할 수 있다.
- Outbox, 멱등 key와 실행 이력으로 장애 원인과 재실행을 추적할 수 있다.
- Queue message에서 민감정보와 실행 가능한 객체를 제거해 공격 표면을 줄인다.

### 17.2 비용과 제약

- Outbox Dispatcher, reconciliation과 task execution schema를 추가 구현해야 한다.
- At-least-once 특성 때문에 모든 task와 artifact 생성 경로에 멱등성 시험이 필요하다.
- Redis AOF, ACL, memory와 Worker drain을 운영해야 한다.
- Celery event 기반 dashboard를 기본으로 사용할 수 없으므로 PostgreSQL 중심의 관측 화면이 필요하다.
- 외부 납품·재배포·관리형 서비스 또는 Redis source 수정 요구가 생기면 license 재승인이나 Valkey 재검증이 필요하다.

### 17.3 후속 산출물 반영 사항

`database/schemas`에는 최소한 다음 개념을 반영한다.

- `audit_jobs`
- `workflow_steps`
- `task_executions`
- `outbox_events`
- `audit_events`
- Finding 업무 고유 key와 input·output hash
- lease, retry, quarantine, cancel과 optimistic version 필드

원본 증적 저장·보존 정책에는 Redis AOF가 업무 원본이 아니며 message metadata가 남는 운영 artifact라는 점, AIStor artifact의 임시 object·orphan reconciliation과 보존 기준을 반영한다.
