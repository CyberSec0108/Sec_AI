### 2.1 Windows 11 범위 해석

- Windows 11을 최초 개발·실행·인수 시험의 기준 OS로 사용한다.
- 정확한 Edition, Build, patch level, ISO 출처와 SHA-256은 VMware 기준 이미지 생성 시 별도 이미지 명세에 고정한다.
- 기준 이미지는 결정 시점에 Microsoft가 지원하는 버전이어야 한다.
- Windows 10은 KISA 2026 가이드의 적용 대상 분석에는 포함할 수 있지만, 1차 MVP의 필수 실행·인수 환경에는 포함하지 않는다.
- Windows Server, Linux, macOS는 1차 MVP의 공식 판정 대상이 아니다.
- OS 또는 기능 적용성이 없는 항목을 억지로 `PASS`나 `FAIL`로 판정하지 않고, 승인된 적용성 규칙에 따라 근거 있는 `N/A` 또는 `REVIEW`로 처리한다.

### 2.2 Pilot 이후 확장 경계

Linux 서버, Network Switch와 Agent/MCP 조치는 1차 Windows MVP의 포함 범위가 아니다. 다음 항목은 `IMP-055` clean Windows 11 VM Gate 이후 별도 승인·구현·인수를 거쳐야 한다.

- Linux 1차: Ubuntu Server 24.04 LTS
- Linux 2차: RHEL 9와 OpenSCAP 결과 Adapter
- Switch 1차: Cisco IOS XE의 NETCONF/RESTCONF 구조화 수집
- Switch 2차: HPE Aruba AOS-CX REST API 구조화 수집
- 표시 보완: 제한 Markdown parser·sanitizer·브라우저 XSS Gate
- 조치 보완: Agent/MCP `PLAN_ONLY` 후 승인형 좁은 도구·rollback·재점검·감사

각 플랫폼은 자체 Control Source Mapping, Guide/Audit Pack, Collector/Adapter, Fixture와 권한·증적 계약을 가져야 한다. 제안과 상세 단계는 `19.ADR_다중_플랫폼_점검_마크다운_보조_조치.md`와 `docs/plans/플랫폼_확장_및_보조_조치_계획.md`를 따른다. 승인 전에는 UI의 `준비 중`을 `사용 가능`으로 바꾸지 않는다.

## 3. 1차 MVP 포함 범위

### 3.1 점검과 판정

- `PC-01`~`PC-18` 모든 Control을 Audit Pack에 등록한다.
- 각 Control에 가이드 버전, 원문 위치, 적용 조건, 요구 증적, 자동화 유형, 판정 규칙을 연결한다.
- 자동화 가능한 항목은 결정론적으로 `PASS` 또는 `FAIL`을 판정한다.
- 조직 정책이나 사람의 판단이 필요한 항목은 `REVIEW`로 분리한다.
- 적용 대상이 아닌 항목은 적용성 근거와 함께 `N/A`로 처리한다.
- 수집 또는 검증 실패는 `ERROR`로 처리하며 `FAIL`로 오판하지 않는다.
- 동일한 증적과 동일한 Audit Pack 버전은 항상 동일한 판정을 생성한다.

> 18개 전체 구현은 모든 항목을 강제로 자동 `PASS/FAIL` 처리한다는 뜻이 아니다. 18개 모두를 근거 있게 처리하고 결과 상태를 구분할 수 있어야 한다.

### 3.2 수집기와 입력

- Windows 11용 One-shot Collector를 단일 실행 파일로 제공한다.
- 수집기는 승인된 Probe만 읽기 전용으로 실행하고 대상 설정을 변경하지 않는다.
- 일반 사용자 권한으로 가능한 수집과 관리자 권한이 필요한 수집을 구분한다.
- 권한 부족, 미지원 설정, 수집 실패를 구조화된 오류로 기록한다.
- 온라인 HTTPS 업로드와 폐쇄망용 오프라인 결과 파일 생성을 지원한다.
- 초기 세로 기능 구현과 회귀시험에는 정상·취약·오류 합성 패키지를 사용한다.
- 패키지의 스키마, 크기, 해시, 서명, 생성 시각, 자산 귀속과 중복 제출을 검증한다.
- 자격증명, 토큰, 불필요한 개인정보와 사용자 파일 원문은 수집하지 않는다.

### 3.3 중앙 Core 서비스

기본 CPU 환경에서 다음 Core 기능이 동작해야 한다.

- Gateway
- FastAPI API와 동일 서비스에서 제공하는 Static/Jinja2/로컬 HTMX UI
- Celery Worker와 Celery Beat
- Redis
- PostgreSQL
- 증적 저장용 MinIO AIStor Free 최신 Stable(단일 노드)
- 업로드 검사 용도의 ClamAV

Core 서비스는 자산 등록, 점검 작업 생성, 패키지 제출, 검증, 판정, 결과 저장과 조회를 제공한다. 데이터 및 관리 포트는 외부에 직접 공개하지 않고 Gateway를 유일한 기본 진입점으로 둔다.

### 3.4 최소 사용자 기능

- 인증된 사용자 로그인
- Windows 11 자산 등록과 허용 범위 내 조회
- 점검 작업 생성
- 결과 패키지 제출
- 점검 결과 목록 조회
- 결과 상세에서 실제값, 기준값, 판정, 가이드 근거와 처리 오류 조회
- 사용자·자산 범위에 대한 서버 측 권한 검사
- 인증, 제출, 조회, 판정과 관리 작업의 감사 로그

구체적인 역할별 권한과 인증 방식은 별도 RBAC 표와 인증 ADR에서 확정한다.

### 3.5 로컬 AI 설명

관련 계획서의 범위 표현을 다음 두 인수 게이트로 해석해 확정한다.

| 게이트 | 범위 | 통과 조건 |
|---|---|---|
| Gate A: Core 인수 | 수집·검증·Audit Pack·규칙 판정·저장·최소 UI | AI 없이 전체 18개 Control을 근거 있는 상태로 처리 |
| Gate B: 1차 MVP 완성 인수 | Gate A + KISA RAG + 로컬 Embedding/Reranker/vLLM 설명 | 설명에 가이드 위치가 연결되고 AI 장애·출력이 공식 판정을 변경하지 않음 |

- AI 기능은 Gate A 이후 MVP 후반에 연결한다.
- AI가 없어도 또는 AI 서비스가 장애여도 Core 판정과 조회는 정상 동작해야 한다.
- AI 입력은 최소화하고 자격증명, 토큰, 불필요한 원본 증적을 포함하지 않는다.
- AI 출력은 설명과 조치 제안으로 한정하며 명령으로 직접 실행하지 않는다.

## 4. 1차 MVP 제외 범위

다음 항목은 별도 범위 변경 승인 없이 1차 MVP에 추가하지 않는다.

- Wazuh Manager·Indexer·Dashboard 및 Agent/SCA 기반 지속 점검
- 소프트웨어 CVE 매칭과 백신·EDR 제품 연동
- Neo4j GraphRAG
- 다수 조직·다수 장비용 고급 통합 대시보드와 고급 시각화
- 승인형 자동 조치, Playbook 실행, 재점검 자동화와 롤백 실행기
- Wazuh Active Response
- SSH·WinRM을 이용한 중앙 직접 원격 점검
- Windows Server, Linux, macOS의 공식 점검 판정
- LLM이 생성한 PowerShell·Shell 명령의 실행
- LLM에 의한 `PASS/FAIL/REVIEW/ERROR/N/A` 생성 또는 변경
- 외부 상용 LLM API와 외부 AI SaaS를 이용하는 기본 운영 경로
- 운영 중 인터넷에서 모델·가이드·실행 파일을 자동 다운로드하는 기능
- 사용자 PC가 PostgreSQL·pgvector, Redis, AIStor, vLLM 등 내부 서비스에 직접 접속하는 구조

## 5. 첫 세로 기능 조각

전체 18개 항목을 범위에서 제외하지 않은 상태로, 다음 순서로 첫 성공 경로를 만든다.

1. 자동 판정에 적합한 대표 PC Control 1개를 `MVP_CONTROL_MATRIX.md`에서 선정한다.
2. 해당 Control의 정상·취약·오류 합성 증적을 작성한다.
3. JSON Schema로 입력을 검증한다.
4. Audit Pack 규칙 엔진이 AI 없이 `PASS/FAIL/ERROR`를 판정한다.
5. 결과 상세에서 실제값, 기준값, 규칙 버전과 가이드 위치를 조회한다.
6. 이 경로를 분류별로 확장해 `PC-01`~`PC-18` 전체 Coverage를 달성한다.

## 6. 필수 보안 경계

- 수집, 판정, AI 설명, 조치 실행의 책임과 실행 권한을 분리한다.
- 수집기는 서버가 전달한 임의 명령을 실행하지 않는다.
- 공식 상태는 Audit Pack 규칙 엔진만 확정한다.
- 원본 증적은 MVP에서 MinIO AIStor Free 최신 Stable 단일 노드에 저장하고, 구조화된 결과·사용자·자산·버전·감사 정보는 PostgreSQL에 저장한다.
- MVP의 AIStor Free는 고가용성이나 제조사 SLA를 제공하는 운영 확정안이 아니다. 정식 운영 전에는 AIStor Enterprise 또는 조직 표준 S3 저장소 전환 여부를 재승인한다.
- 비밀정보는 소스, 이미지, Compose 기본값, 로그와 AI trace에 저장하지 않는다.
- 모든 API는 UI 표시 여부와 무관하게 인증, 역할, 자산 범위를 서버에서 검사한다.
- 변조, 만료, 재전송, 스키마 오류 또는 권한 위반 패키지를 거부하고 감사 로그를 남긴다.
- Core는 CPU-safe 구성이어야 하며 GPU는 선택형 구성에서만 사용한다.

## 7. 1차 MVP 인수 기준

### 7.1 Gate A: Core

- Windows 11 VMware 기준 이미지와 취약 스냅샷에서 반복 시험할 수 있다.
- `PC-01`~`PC-18` 모든 Control이 `PASS/FAIL/REVIEW/ERROR/N/A` 중 하나로 근거 있게 처리된다.
- 자동 판정 Control의 실제 결과가 승인된 Fixture의 기대 결과와 일치한다.
- 모든 Finding에서 원본 증적, Audit Pack·규칙 버전과 KISA 가이드 위치를 역추적할 수 있다.
- 동일 입력과 동일 버전으로 재실행한 판정 결과가 100% 일치한다.
- 수집기가 점검 대상 설정을 변경하지 않는다.
- 권한 부족을 취약 상태로 오판하지 않는다.
- 변조·만료·재전송 패키지와 다른 사용자 자산 접근이 차단된다.
- Worker 중단 후 작업이 유실되지 않고 복구된다.
- 단위·계약·E2E·보안 테스트 결과를 제출할 수 있다.
- 외부 인터넷과 AI 서비스 없이 Core 업무 흐름이 동작한다.

### 7.2 Gate B: 1차 MVP 완성

- 승인된 KISA 원문만 검색 대상으로 사용한다.
- AI 설명에 Control ID, 가이드 버전과 원문 위치가 연결된다.
- 근거가 부족한 경우 AI가 추정 판정을 만들지 않고 제한 상태를 표시한다.
- AI 출력이나 AI 서비스 장애가 Gate A의 공식 판정 결과를 변경하지 않는다.

## 8. 범위 변경 통제

다음 변경은 이 문서의 개정과 승인 후 수행한다.

- 첫 지원 OS 또는 필수 OS 버전 추가
- KISA 가이드 버전 또는 점검 영역 변경
- `PC-01`~`PC-18` Control의 제외
- Wazuh, CVE, GraphRAG, 원격 점검 또는 자동 조치의 1차 MVP 편입
- 외부 AI 서비스 사용
- 공식 판정 주체 또는 판정 상태 모델 변경
- Gate A 또는 Gate B 인수 기준 완화

일정이 부족한 경우 PC Control 수, 무결성 검증, 적용성 근거, 판정 재현성, 서버 권한 검사를 줄이지 않는다. 우선 고급 UI, 보고서 서식, 운영 관측과 후속 연동의 일정을 조정한다.
