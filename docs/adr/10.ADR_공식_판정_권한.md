# 공식 판정 주체 아키텍처 ADR

## 현재 구현 상태 (2026-08-07 검토)

- 공식 상태를 만들 수 있는 주체는 승인·서명된 Audit Pack과 결정론 규칙 엔진뿐이라는 결정은 그대로 유효하다.
- 현재 Windows·Linux·Switch Pack과 결과는 개발용 `DRAFT`이며 조직 운영 `APPROVED` Pack이나 공식 Finding으로 승격되지 않았다.
- Collector, UI, RAG, LLM, 알려진 취약점 후보와 Agent/MCP는 판정 상태를 만들거나 바꿀 수 없다.
- AI 설명·공개 CVE 후보·조직 보완 입력은 각각 별도 데이터로 보존하며 공식 판정과 합쳐 쓰지 않는다.

## 1. 결정

Sec_AI에서 공식 `PASS`, `FAIL`, `REVIEW`, `ERROR`, `N/A` Finding을 생성하는 유일한 주체는 **승인된 Audit Pack을 실행하는 결정론적 규칙 엔진**으로 한다.

여기서 공식 판정 주체는 하나의 사람이나 단일 파일이 아니라 다음 결합을 뜻한다.

```text
공식 판정 주체
= 승인·서명·활성화된 exact Audit Pack
∩ allowlist 기반 결정론적 Rule Engine
∩ 검증·고정된 입력 Evidence/Policy/Reference snapshot
∩ 전용 evaluation-worker service identity
∩ append-only Finding 저장 경로
```

- **Audit Pack**은 어떤 Control을 어떤 증적과 기준으로 평가할지 정의하는 versioned policy다.
- **Rule Engine**은 Audit Pack DSL을 제한된 연산자로 해석하는 순수 판정 code다.
- **Evaluation Worker**는 입력을 고정하고 엔진을 실행한 뒤 공식 Finding을 저장하는 실행 경계다.
- 사람, Collector, API, AI/LLM, Wazuh, PostgreSQL trigger는 공식 상태를 직접 만들거나 변경할 수 없다.

MVP에서 Rule Engine은 별도 HTTP microservice로 분리하지 않고 `core.evaluation` 전용 Worker image 안의 독립 Python package로 실행한다. 다만 validation Worker·AI Worker와 process, Queue, database role, network permission을 분리한다. 향후 독립 서비스화하더라도 이 ADR의 판정 권한과 데이터 계약은 유지한다.

이 문서의 “공식”은 **Sec_AI 내부 감사 결과의 정본**이라는 뜻이다. KISA의 인증·법적 적합성 확인이나 외부 감사인의 최종 의견을 대신한다는 뜻이 아니다. KISA 원문과 Audit Pack이 충돌하면 원문을 기준으로 Pack을 폐기·수정하고 새 version으로 재평가한다.

## 2. 배경과 결정 이유

보안점검 결과는 같은 입력에 같은 결과가 나와야 하고, 나중에 왜 그런 결과가 나왔는지 재현할 수 있어야 한다. 자연어 판단이나 운영자 임의 수정으로 공식 상태를 만들면 다음 문제가 발생한다.

- 동일한 증적이 실행 시점이나 질문 표현에 따라 다른 상태가 될 수 있다.
- 가이드 version, 기관 정책, 외부 기준 데이터가 바뀌었을 때 과거 결과를 재현하기 어렵다.
- AI 환각, prompt injection, 모델 장애가 공식 판정에 영향을 줄 수 있다.
- 승인자·관리자에게 판정 변경 권한이 집중되어 자기승인과 결과 조작 위험이 생긴다.
- 수집 실패를 취약점으로 오인하거나 부분 증적으로 잘못 `PASS` 처리할 수 있다.
- Queue 중복 전달이나 Worker 재실행으로 Finding이 중복되거나 덮어써질 수 있다.

따라서 판정 기준은 code와 분리된 Audit Pack으로 version 관리하고, 실행은 외부 AI나 network에 의존하지 않는 결정론적 엔진으로 제한한다.

| Organization Policy | 기관 기준값, allow/deny list, 허용 예외와 적용 범위 | 승인된 exact version·hash |
| Reference Snapshot | OS 수명주기·제품 식별 등 외부 기준의 시점 고정 사본 | 저장된 snapshot ID·조회일·hash |
| Normalized Evidence | 검증된 package에서 정규화한 Control별 최소 증적 | Schema-valid artifact와 SHA-256 |
| Evaluation Input Set | 한 판정에 사용한 Pack, evidence, policy, reference, subject와 기준 시점의 고정 집합 | canonical input SHA-256 |
| Finding | Rule Engine이 생성한 공식 Control별 결과 version | PostgreSQL append-only row + artifact hash |
| AI Explanation | Finding을 설명하는 비공식 파생 artifact | Finding과 분리된 record |
| Review Resolution | `REVIEW`에 대한 사람의 검토 의견·정책·증적 보완 기록 | 별도 approval/attestation record |
| Risk Acceptance | `FAIL`을 수용하기로 한 업무 승인 | Finding과 분리된 예외·승인 record |

Finding의 공식성은 화면 표시나 관리자 권한이 아니라 **승인된 입력 계보, engine identity, hash와 append-only 저장**으로 증명한다.

## 4. 책임 경계

### 4.1 구성요소별 책임

| 구성요소 | 허용 책임 | 금지 책임 |
|---|---|---|
| Collector | 읽기 전용 Probe 실행, 구조화 증적·오류 생성, package 서명 | `PASS/FAIL` 생성, 조직 기준 추정, 상태 변경 |
| API | 인증·RBAC·Job 생성, upload 접수, 상태 조회, Outbox 기록 | 사용자 입력을 공식 상태로 저장, Pack 규칙 실행 우회 |
| Validation Worker | malware·서명·nonce·hash·Schema 검증, quarantine, 정규화 | Finding 상태 생성, AI 호출, Pack 승인 |
| Audit Pack Builder | Pack 초안·Fixture·manifest 생성 | 자기 승인, 운영 활성화, 임의 code 삽입 |
| Security Officer | 정책·Pack 초안 검토, 승인 요청, 결과 검토 | 자기 요청 승인, Finding 직접 수정 |
| Approver | exact Pack/policy version·hash 승인 또는 반려 | 승인 대상 내용 수정, 자기승인, 판정 override |
| Administrator | 승인된 Pack 배포·활성화 trigger와 platform 운영 | 원본 내용 기본 열람, 공식 상태 직접 변경 |
| Evaluation Worker | 고정 입력 조회, Rule Engine 실행, Finding 새 version 저장 | Pack 수정·승인, AI 사용, 사람 역할 대행 |
| Rule Engine | 적용성·완전성·규칙을 순수 함수로 평가 | DB·network·filesystem·shell·LLM 직접 접근 |
| AI Worker | 승인된 Finding·마스킹 자료를 이용한 설명 생성 | 상태 생성·수정, raw package 접근, 명령 실행 |
| UI/Report | 공식 Finding을 원문 그대로 표시하고 파생 상태를 구분 | client-side 계산으로 공식 상태 변경 |
| Remediation Runner | 향후 승인된 playbook만 별도 경계에서 실행 | Finding을 `PASS`로 변경, LLM 자유 명령 실행 |

### 4.2 판정 권한의 기술적 강제

- 공식 Finding create 권한은 `evaluation-worker` database role에만 부여한다.
- API·AI·사람 session database role에는 공식 Finding `INSERT/UPDATE/DELETE` 권한을 주지 않는다.
- 공식 Finding row는 생성 후 update·delete하지 않는다. 정정과 재점검은 새 version을 생성한다.
- `source`는 `rule-engine`으로 고정하고 `producer_name`, `producer_version`, runtime image digest를 기록한다.
- 애플리케이션 authorization과 별개로 PostgreSQL GRANT, constraint, trigger 또는 append-only repository guard를 적용한다.
- UI에서 버튼을 숨기는 것만으로 판정 권한을 통제하지 않는다.

### 5.1 배포 구조

MVP의 `core.evaluation` Worker는 다음 특성을 가진다.

- 승인된 CPython 3.14.6 runtime과 platform별 hash-locked dependency를 사용한다.
- `core.validation`, `ai.explanation`, `maintenance` Queue를 소비하지 않는다.
- 인터넷과 AI network에 접근하지 않는다.
- PostgreSQL에서는 evaluation input read와 Finding append에 필요한 최소 권한만 가진다.
- AIStor에서는 승인된 normalized/derived artifact의 exact object version read만 허용한다.
- read-only root filesystem, non-root user, 제한된 temp, CPU·memory·time limit를 적용한다.
- 승인된 rule registry와 Audit Pack trust store만 image 또는 read-only mount로 제공한다.

Rule Engine은 evaluation Worker 안에서 library call로 실행하되 domain 경계는 다음처럼 분리한다.

```text
evaluation-worker adapter
├─ input_resolver       # DB/object version을 exact input으로 고정
├─ pack_verifier        # Schema·hash·signature·approval·activation 확인
├─ rule_engine          # I/O 없는 deterministic evaluation
├─ finding_builder      # finding.schema.json 생성·canonical hash 계산
└─ finding_repository   # append-only transaction·Outbox 기록
```

## 6. 공식 판정 입력 계약

### 6.1 필수 입력

한 Control·subject의 판정은 최소한 다음 항목을 고정한다.

| 입력 | 고정 방법 |
|---|---|
| `job_id`, `asset_id`, `organization_id` | PostgreSQL 관계와 row version |
| Control·subject | `control_id`, `scope`, `user_sid` 또는 `subject_key` |
| Audit Pack | Pack ID, semantic version, content SHA-256, signature, approval ID |
| Rule Engine | package version, source revision, image digest 또는 build artifact hash |
| Evidence set | 각 evidence ID·SHA-256·object version과 정렬된 set hash |
| Organization Policy | policy ID·version·hash·승인·유효기간 |
| Manual Attestation | attestation ID·version·hash·승인·scope·유효기간 |
| Reference Snapshot | snapshot ID·수집 기준일·hash·서명 또는 provenance |
| Evaluation context | `evaluation_as_of`, target OS/edition/build, locale·timezone이 필요하면 명시적 값 |
| Schema | schema ID·version |

현재 시각, 최신 웹 페이지, mutable alias, process environment와 DB의 “현재값”을 암묵적 입력으로 사용하지 않는다. 시간 기준 판정은 Job에 고정된 `evaluation_as_of`와 Reference Snapshot으로 평가한다.

### 6.2 Canonical input

1. 모든 입력은 승인된 JSON Schema로 검증한다.
2. evidence·policy·reference 목록은 안정된 key로 정렬한다.
3. JSON은 RFC 8785 JCS 기준으로 canonicalize한다.
4. canonical bytes의 SHA-256을 `rule_result.input_sha256`으로 기록한다.
5. 동일 canonical input과 동일 engine artifact는 동일 canonical output을 만들어야 한다.

`evaluated_at`, Worker instance ID, task attempt number처럼 실행마다 달라지는 운영 metadata는 판정 함수 입력·output hash에서 분리한다. 단, 감사 record에는 별도로 남긴다.

### 6.3 허용 입력과 금지 입력

허용 입력:

- Schema-valid normalized evidence
- 승인된 exact organization policy·attestation
- 저장·검증된 외부 reference snapshot
- 서명·승인·활성화된 exact Audit Pack
- 평가에 필요한 최소 asset metadata

금지 입력:

- LLM 출력, prompt 또는 vector similarity score
- 현재 인터넷 검색 결과나 갱신 가능한 외부 API 응답
- 검증되지 않은 raw package 값
- Queue message 본문에 실린 임의 rule·parameter·path
- 사용자 자유 형식 식을 `eval`, `exec`, shell 또는 template code로 실행한 값
- 승인 없이 수정 가능한 환경변수 기준값
- `latest`, `current`처럼 exact version으로 해석되지 않는 reference

## 7. 판정 처리 순서

### 7.1 단계

```text
1. 입력 envelope·관계 검증
2. Package/Artifact 신뢰성 확인
3. Audit Pack 승인·서명·활성 상태 확인
4. exact Control·subject와 Evidence set 선택
5. 필수 증적 완전성·품질 평가
6. 적용성 규칙 평가
7. Control 판정 규칙 평가
8. Finding Schema 검증·canonical output hash 생성
9. 멱등 key 확인 후 append-only 저장
10. Finding-created Outbox event 원자적 기록
```

판정 상태에 단순한 전역 우선순위 하나를 적용하지 않는다. 예를 들어 증적 오류가 있어도 해당 기능이 적용되지 않음을 별도의 신뢰 가능한 증적으로 이미 증명할 수 있는지는 Control별 적용성 규칙이 결정한다. 모든 분기는 Audit Pack의 Fixture로 고정한다.

### 7.2 수신 거부와 `ERROR`의 구분

| 상황 | 처리 | Finding 생성 |
|---|---|---|
| package 서명·nonce·manifest·전체 hash 불일치 | 신뢰 경계에서 거부 또는 quarantine | 없음 |
| package path·Schema 위반 또는 asset scope 불일치 | 거부 또는 quarantine + 보안 감사 | 없음 |
| 미승인·서명 불일치·폐기 Pack | 평가 시작 금지, 운영 오류 | 없음 |
| 검증된 package 안의 필수 Probe가 `PERMISSION_DENIED` 보고 | Control별 `ERROR` | 생성 |
| 검증된 evidence의 parse·timeout·수집 실패 | Control별 `ERROR` | 생성 |
| 필수 기관 기준 또는 승인 attestation 부재 | Control별 `REVIEW` | 생성 |
| 적용하지 않음을 승인 규칙으로 증명 | `N/A` | 생성 |

검증에 실패한 package에서 억지로 `ERROR` Finding을 만들지 않는다. 위변조된 입력을 특정 자산의 공식 결과로 연결할 수 없기 때문이다.

## 8. 공식 상태 의미

| 상태 | 생성 조건 | 만들면 안 되는 경우 |
|---|---|---|
| `PASS` | 적용 대상이며 필수 증적이 완전하고 승인된 모든 규칙 충족 | 일부 subject 미수집, 정책·reference 부재, 수집 오류 |
| `FAIL` | 적용 대상이며 신뢰 가능한 증적이 하나 이상의 명시된 위반 조건 충족 | 권한 부족, Adapter 미지원, 제품 식별 불명확 |
| `REVIEW` | 업무 판단·기관 정책·제품 Adapter·사용자 범위·attestation이 부족하거나 허용된 규칙이 불확정 | 단순 시스템 timeout을 사람 판단으로 숨기는 경우 |
| `ERROR` | 필수 증적을 기술적으로 얻거나 해석하지 못했고 error code가 존재 | 설정 위반 자체, 신뢰할 수 없는 package 전체 |
| `N/A` | 기능·제품·환경이 적용되지 않음을 승인된 적용성 규칙과 증적으로 입증 | 증적이 없다는 이유만으로 미적용 추정 |

추가 규칙:

- `PASS/FAIL`은 `applicability.status=APPLICABLE`이어야 한다.
- `N/A`는 `applicability.status=NOT_APPLICABLE`과 reason code를 가져야 한다.
- `ERROR`는 `NONE`이 아닌 error code를 하나 이상 가져야 한다.
- `REVIEW`는 누락된 policy·attestation·Adapter·subject 범위를 machine-readable reason code로 남긴다.
- 부분 증적만으로 `PASS`를 생성하지 않는다.
- 사람이 `REVIEW`를 `PASS`로 클릭해서 바꾸지 않는다. 보완 증적이나 승인 정책을 새 입력 version으로 추가한 뒤 재평가한다.
- 위험 수용·예외 승인은 `FAIL`을 `PASS`로 변경하지 않고 별도 risk acceptance 상태로 표시한다.

## 9. Subject와 집계

공식 Finding의 단위는 원칙적으로 `job + control + subject + input set`이다.

| Subject scope | 예 | 판정 단위 |
|---|---|---|
| `ASSET` | PC-01, PC-12, PC-15 | 자산 전체 |
| `USER` | PC-16 사용자별 화면보호기 | SID별 개별 Finding |
| `VOLUME` | PC-07 파일시스템 | 평가 대상 volume별 또는 명시된 aggregate |
| `PRODUCT` | PC-13·14 백신 | 승인된 product identity별 |
| `POLICY` | 기관 정책·절차 결합 Control | policy scope별 |

자산·Job 종합 상태는 개별 Finding을 임의로 덮어쓰지 않는 파생 projection이다. 집계가 필요하면 Audit Pack에 versioned aggregation rule과 누락 subject 처리 규칙을 둔다.

예를 들어 PC-16은 수집된 사용자마다 Finding을 만들고, 평가 대상 사용자 목록 중 미수집 SID가 있으면 자산 집계를 `REVIEW`로 표시한다. 한 사용자의 `PASS`를 공유 PC 전체의 `PASS`로 확대하지 않는다.

## 10. Audit Pack 수명주기

### 10.1 상태와 역할

현재 Schema의 Pack 상태는 `DRAFT`, `APPROVED`, `REVOKED`를 사용한다. Schema·Fixture 검증 성공은 별도의 pipeline 결과이며 상태를 임의로 추가하지 않는다.

```text
DRAFT
  │ schema·lint·fixture·security test
  ▼
validation passed
  │ SECURITY_OFFICER 제출
  ▼
APPROVER exact hash 승인
  │ ADMIN deployment trigger
  ▼
organization assignment에서 active exact version
  │ 취약점·기준 오류·서명키 사고
  ▼
REVOKED (신규 평가 금지, 과거 결과 보존)
```

| 단계 | 주체 | 필수 통제 |
|---|---|---|
| 작성 | Audit Pack Builder·보안담당자 | 원문 page, Control ID, evidence requirement, rule, Fixture |
| 검증 | CI + 별도 검토자 | Schema, allowlist, deterministic replay, PASS/FAIL/ERROR 및 조건별 REVIEW/N/A Fixture |
| 승인 | 승인자 | exact content hash·서명·원문 대조 기록 |
| 배포 | 관리자 | 승인 hash와 배포 artifact hash 일치 확인 |
| 활성화 | 전용 service | 조직·대상·유효기간에 exact Pack assignment 생성 |
| 폐기 | 승인 workflow | 신규 평가 차단, 영향 Finding·재평가 대상 식별 |

### 10.2 Pack 불변성

- 승인 후 Pack content는 수정하지 않는다.
- 변경은 semantic version을 증가시킨 새 Pack으로 만든다.
- 동일 version에 다른 content hash를 허용하지 않는다.
- `latest` alias는 UI 편의 표시로만 사용할 수 있고 평가 task에는 exact ID·version·hash를 넣는다.
- Pack revocation은 과거 Finding을 삭제하지 않는다.
- Pack rollback도 과거 version을 다시 활성화하는 새 승인 event로 기록한다.
- 평가 시작 뒤 active Pack이 바뀌어도 해당 Job은 고정된 Pack으로 끝내거나 명시적으로 취소 후 새 Job을 만든다.

### 10.3 서명과 key

- 승인 Pack은 `audit_pack.schema.json`의 signature 계약을 사용한다.
- 서명 알고리즘은 `Ed25519`로 고정하고 서명 입력은 RFC 8785 JCS canonical bytes로 만든다.
- immutable signing envelope에는 최소 `schema_id`, `pack_id`, `pack_version`, Pack payload와 content SHA-256, `approval_id`, 승인 시각을 포함한다. 배포 시각·활성 assignment·실행 횟수 같은 운영 metadata와 signature field 자체는 제외한다.
- private signing key는 9번 정책의 OpenBao/Vault Transit에 non-exportable key로 보관하고 Pack 작성자·배포 관리자·Evaluation Worker에 제공하지 않는다.
- 승인자는 exact hash와 원문 대조를 승인한 뒤 제한된 signing workflow만 호출하고, key custodian은 Pack 내용 작성·자기승인을 할 수 없다.
- Evaluation Worker trust store에는 운영 Pack 서명 검증에 필요한 public key만 둔다.
- private signing key는 Worker image, Git, Compose environment, PostgreSQL과 AIStor 일반 bucket에 넣지 않는다.
- key rotation은 최소 연 1회 검토하고 노출 의심·담당자 변경·알고리즘 문제 발생 시 즉시 수행한다. `key_id`, 유효기간, 폐기 시점과 과거 검증 정책을 기록한다.
- 이전 public key와 검증 metadata는 해당 key가 서명한 Pack·Finding·backup의 보존이 끝날 때까지 유지한다.
- 서명 검증 실패는 `FAIL/ERROR` Finding이 아니라 평가 거부·보안 event다.

## 11. Rule DSL과 엔진 보안

### 11.1 허용 모델

Audit Pack은 JSON 또는 제한된 YAML 표현을 사용할 수 있으나, runtime에 전달하기 전 동일한 JSON Schema와 canonical JSON으로 변환한다. Rule은 `rule_id`, `rule_version`, bounded `parameters`로 등록된 구현을 참조한다.

허용 연산자는 명시적으로 registry에 등록한다.

- 존재·부재, boolean 비교
- exact string·enum 비교
- 정수·시간·기간의 범위 비교
- collection all/any/count와 allow/deny membership
- version 비교와 승인된 product Adapter 결과 비교
- 명시적인 적용성 분기
- 증적 완전성·오류 code 평가
- 승인된 aggregation function

### 11.2 금지 기능

- Python `eval`, `exec`, dynamic import, pickle, 임의 plugin import
- shell, PowerShell, subprocess 또는 OS command 실행
- filesystem path, URL, database query를 Pack이 직접 지정하는 기능
- network·DNS·현재 웹 검색
- Jinja 등 template expression을 판정 code로 실행
- 임의 정규식. 필요하면 사전 등록하고 길이·복잡도·timeout을 제한
- 무제한 recursion, loop, collection expansion과 사용자 정의 code
- floating-point 근사에 정확성을 의존하는 기준값
- 모델 score·embedding similarity·자연어 문장 자체를 공식 상태로 변환

### 11.3 결정론성

Rule Engine은 다음 계약을 만족하는 순수 함수로 취급한다.

```text
evaluate(canonical_input, engine_version) -> canonical_decision
```

- locale, host timezone, dictionary insertion order, process ID와 random seed에 의존하지 않는다.
- 시간 연산은 UTC의 고정 `evaluation_as_of`를 사용한다.
- 정렬 순서와 동률 처리 규칙을 명시한다.
- 정수·decimal·version 비교 방법을 고정한다.
- 동일 입력 replay 시험에서 byte-equivalent decision hash를 요구한다.
- engine 변경으로 결과가 달라지면 engine version을 올리고 영향 Fixture를 검토한다.

## 12. Finding 저장과 변경 모델

### 12.1 Append-only

공식 Finding은 수정 가능한 현재 상태 row가 아니라 versioned decision record다.

```text
Finding v1 (Pack 1.0.0, evidence set A) = FAIL
   └─ remediation / new collection
Finding v2 (Pack 1.0.0, evidence set B) = PASS

Finding v1은 보존되고 v2가 current projection이 된다.
```

- 과거 Finding의 status, evidence refs, Pack refs와 hash를 update하지 않는다.
- `current`는 별도 projection 또는 pointer이며 원본 version을 삭제하지 않는다.
- 재점검, 정책 보완, Pack 변경, engine 변경은 새 Finding을 만든다.
- 새 Finding은 predecessor·reason(`RECHECK`, `POLICY_UPDATED`, `PACK_UPDATED`, `ENGINE_UPDATED`, `CORRECTION`)을 연결한다.
- 화면과 report는 Pack version, evidence set hash, evaluated time과 superseded 여부를 함께 표시한다.

### 12.2 멱등성

논리 멱등 key는 최소 다음 값을 포함한다.

```text
job_id
+ control_id
+ canonical subject key
+ audit_pack id/version/hash
+ evidence_set_sha256
+ policy/reference snapshot hashes
+ engine version/artifact hash
```

동일 key의 성공 Finding은 하나만 허용한다. Celery task가 재전달되면 새 Finding을 만들지 않고 기존 ID·hash를 반환한다. 입력이 하나라도 바뀌면 새 논리 평가로 기록한다.

### 12.3 원자성

다음 항목은 하나의 PostgreSQL transaction으로 기록한다.

1. evaluation attempt 완료 상태
2. 공식 Finding row와 lineage
3. current projection의 compare-and-set 갱신
4. 감사 event metadata
5. `finding.created` Outbox event

AI 설명 event는 이 transaction의 성공 뒤 별도 Queue로 발행한다. AI 실패 때문에 Finding transaction을 rollback하지 않는다.

## 13. AI·사람·조치와의 경계

### 13.1 AI

- AI 입력은 이미 생성된 Finding과 승인·마스킹된 최소 증적이다.
- AI Schema는 `official_finding_status`를 표시 목적으로 복사할 수 있지만 `official_status_unchanged=true`여야 한다.
- AI 출력에는 공식 status write field나 Finding repository credential을 제공하지 않는다.
- AI가 Finding과 다른 상태를 문장으로 주장하면 output validation에서 차단하거나 명확한 비공식 경고로 격리한다.
- vLLM, pgvector 검색 projection, Neo4j, Embedding, Reranker와 Langfuse가 모두 중단되어도 Core 판정은 계속되어야 한다.
- AI 결과의 `FAILED`, `SKIPPED`, `UNAVAILABLE`은 Finding 상태와 별도다.

### 13.2 사람 검토

사람은 공식 판정을 직접 변경하지 않고 다음 별도 action을 수행한다.

| 사람 action | 공식 Finding에 미치는 영향 |
|---|---|
| 검토 의견·annotation 추가 | 없음 |
| 조직 정책·allowlist 승인 | 새 input version으로 재평가 가능 |
| manual attestation 승인 | 새 evidence version으로 재평가 가능 |
| 위험 수용·예외 승인 | `FAIL` 유지, 별도 risk 상태 표시 |
| 오탐 신고 | 기존 Finding 유지, Pack/Adapter 수정 검토 후 새 평가 |
| 판정 이의제기 | dispute record 생성, 공식 상태 직접 수정 없음 |
| report 승인 | exact Finding set의 게시 승인, 개별 상태 변경 없음 |

### 13.3 자동 조치

- `FAIL`은 자동 조치 명령이 아니다.
- 조치 계획·승인·실행은 별도 remediation domain과 service identity가 담당한다.
- 조치 성공만으로 기존 Finding을 `PASS`로 바꾸지 않는다.
- 조치 뒤 새 Collector evidence와 Rule Engine 재평가로만 새 `PASS` Finding을 만들 수 있다.

## 14. Queue·재시도·장애 처리

`7.ADR_대기열.md`의 at-least-once 모델을 적용한다.

| 실패 | 처리 | 자동 재시도 |
|---|---|---:|
| DB·AIStor 일시 timeout | attempt 실패 기록 후 backoff | 제한적으로 허용 |
| Worker loss | 동일 멱등 key로 재전달 | 허용 |
| Pack Schema·서명·승인 오류 | 평가 차단, 보안/운영 event | 금지 |
| Rule parameter·operator 미지원 | `FAILED_RULE`, Pack 격리 검토 | 금지 |
| Rule Engine 내부 exception | attempt `FAILED_RULE`; 공식 Finding은 만들지 않거나 Pack에 정의된 안전한 ERROR 경계 사용 | 제한 후 격리 |
| valid evidence의 Probe 오류 | 정상 Rule 입력으로 Control `ERROR` 생성 | task 재시도 대상 아님 |
| output Schema 위반·hash 불일치 | 저장 금지, Worker build 또는 Pack 격리 | 자동 반복 금지 |
| AI 장애 | Finding 유지, AI 상태만 실패 | Core에 영향 없음 |

Rule Engine bug를 자산 취약점 `ERROR`로 위장하지 않는다. Engine/Pack 실행 자체가 실패하면 evaluation attempt를 `FAILED_RULE`로 기록하고 운영자가 원인을 해결한 뒤 같은 입력으로 재현한다. Control별 `ERROR`는 승인된 Rule이 신뢰 가능한 수집 오류 evidence를 해석해 만든 결과다.

## 15. RBAC와 Service Identity 연결

`11.RBAC_권한_매트릭스.md`를 다음과 같이 적용한다.

MVP에서 실제 credential과 database role을 갖는 workload identity는 `evaluation-worker` 하나다. `rule-engine`은 그 Worker 안에서 실행되는 I/O 없는 논리 모듈이며 Finding의 `source=rule-engine`과 producer provenance로 식별한다. 따라서 RBAC의 `rule-engine` 행은 별도의 로그인·token·DB 계정을 추가한다는 의미가 아니라 공식 판정 기능의 논리 권한을 뜻한다. 구현 전에 RBAC 표도 이 구분에 맞춰 `evaluation-worker(rule-engine producer)`로 병합 표기한다.

| Operation | USER | SECURITY_OFFICER | APPROVER | ADMIN | evaluation-worker |
|---|---:|---:|---:|---:|---:|
| Finding 조회 | 할당 자산 | 조직 | 승인 건 최소 범위 | metadata | 입력·저장에 필요한 범위 |
| Finding 생성 | — | — | — | — | 허용 |
| Finding update/delete | — | — | — | — | — |
| Pack 초안 | — | 허용 | — | metadata | — |
| Pack 승인 | — | 요청 | 승인·반려 | — | 검증만 |
| Pack 활성화 trigger | — | 요청 | 승인 | 실행 | exact assignment read |
| AI 설명 생성 | — | 요청 가능 | — | 운영 trigger | — |
| 재평가 요청 | 할당 자산 범위 | 조직 범위 | — | 운영 재처리 | 실제 실행 |

ADMIN은 platform 운영자이지 판정 최고권한자가 아니다. Break-glass를 사용해도 기존 Finding을 수정하지 않으며, 복구가 필요하면 exact backup 복원 후 새 correction/re-evaluation record를 만든다.

## 16. 감사와 재현

각 공식 Finding은 다음 질문에 답할 수 있어야 한다.

1. 어떤 KISA 원문 version·page를 기준으로 했는가?
2. 어떤 Audit Pack ID·version·hash·서명을 사용했는가?
3. 누가 Pack을 작성·검토·승인·활성화했는가?
4. 어떤 engine version·image/build hash가 실행했는가?
5. 어떤 evidence·policy·attestation·reference version을 사용했는가?
6. 적용성, 완전성, 평가의 각 result code는 무엇인가?
7. input/output canonical hash는 무엇인가?
8. 어떤 task attempt와 correlation ID에서 생성됐는가?
9. 이전·다음 Finding과 변경 이유는 무엇인가?
10. AI 설명·사람 검토·위험 수용이 공식 상태와 분리되어 있는가?

감사 log에는 evidence 원문, 비밀번호, token, 전체 Registry dump와 AI prompt 전문을 남기지 않는다. ID, version, hash, result code, actor/service identity와 시각 중심으로 기록한다.

재현 bundle은 다음 최소 자료를 사용한다.

- Rule Engine artifact 또는 재빌드 가능한 source revision·dependency lock
- Audit Pack exact bytes·signature·approval metadata
- Schema versions
- normalized evidence·policy·reference exact versions
- canonicalization과 hash algorithm
- 기대 Finding과 output hash

## 17. 운영 관측

다음 metric과 alert를 사용하되 민감한 evidence value는 label에 넣지 않는다.

| Metric | 목적 |
|---|---|
| evaluation latency·throughput | 성능·용량 확인 |
| status count by control/pack version | 결과 분포와 release 영향 탐지 |
| `FAILED_RULE` count | Pack·engine 결함 탐지 |
| Pack signature/approval rejection count | 공급망·배포 오류 탐지 |
| idempotent replay hit count | Queue 중복과 복구 상태 확인 |
| input/output hash mismatch count | 무결성 이상 탐지 |
| REVIEW·ERROR age | 미해결 정책·수집 문제 추적 |
| active Pack assignment drift | 승인 hash와 배포 상태 불일치 탐지 |

새 Pack 배포 뒤 status 분포가 승인된 baseline을 벗어나면 자동 rollback하지 않고 신규 Job 발행을 일시 중지하고 보안담당자·승인자가 영향도를 검토한다. 이미 생성된 Finding은 삭제하지 않는다.

## 18. 시험 기준

### 18.1 Audit Pack Gate

- PC-01~PC-18의 ID·원문 page·중요도·자동화 유형이 Coverage Matrix와 일치한다.
- 모든 Control에 PASS, FAIL, ERROR Fixture가 있다.
- `AUTO-CONDITIONAL`에는 REVIEW Fixture가 있다.
- 적용성 Control에는 N/A Fixture가 있다.
- 모든 rule/operator/parser/probe ID가 allowlist에 존재한다.
- Pack content hash·signature·approval이 검증된다.
- 승인 뒤 1 byte 변경한 Pack은 거부된다.
- 중복 Control ID, 동일 version·다른 hash, 미지원 Schema는 거부된다.

### 18.2 결정론성·회귀

- 동일 input bundle을 같은 engine으로 100회 실행해 같은 decision hash를 얻는다.
- evidence JSON property order와 collection 입력 순서를 바꿔도 같은 canonical 결과가 나온다.
- host locale·timezone을 바꿔도 고정된 `evaluation_as_of` 결과가 같다.
- process 재시작·Worker 재전달 후 Finding이 중복되지 않는다.
- 이전 Pack과 새 Pack을 동일 Fixture에 실행해 의도한 차이만 snapshot diff에 나타난다.
- 과거 Finding의 재현 bundle로 동일 상태·result code·output hash를 재생한다.

### 18.3 상태 경계

| 시험 | 기대 결과 |
|---|---|
| 완전한 준수 evidence | `PASS` |
| 명시적 위반 evidence | `FAIL` |
| 기관 기준 부재 | `REVIEW` |
| valid Probe의 권한 부족 | `ERROR` |
| 미적용을 증명하는 evidence | `N/A` |
| evidence 일부 누락 | `PASS` 금지 |
| package 서명 변조 | Finding 없이 quarantine |
| Pack 서명 변조 | 평가 시작 금지 |
| LLM이 반대 상태 출력 | 공식 Finding 불변, AI output 차단/격리 |
| 사람이 API로 status update | `403` 또는 endpoint 부재 |

### 18.4 보안·권한

- API, ADMIN, SECURITY_OFFICER, APPROVER DB role이 Finding을 직접 insert/update/delete하지 못한다.
- Evaluation Worker가 승인되지 않은 Pack·다른 조직 evidence를 읽지 못한다.
- Pack DSL에서 shell, network, filesystem, dynamic import와 무제한 표현을 실행할 수 없다.
- UUID 변조로 다른 organization Finding·evidence를 평가하거나 조회할 수 없다.
- Redis message의 rule ID·path·Queue 조작이 server-side fixed workflow를 우회하지 못한다.
- AI Worker credential로 Finding repository에 write할 수 없다.

### 18.5 장애·복구

- Redis·AI·pgvector 검색·Neo4j 장애 중에도 이미 저장된 Finding 조회가 가능하다.
- AI 전체 미기동 상태에서 PC-01~PC-18 규칙 시험을 수행할 수 있다.
- Finding 저장 직전 Worker kill 후 같은 task 재전달이 중복 결과를 만들지 않는다.
- DB commit 뒤 Outbox publish 전 장애를 reconciliation으로 복구한다.
- 폐기 Pack으로 신규 평가는 차단하되 과거 Finding 재현은 가능하다.

## 19. 현재 Schema·구현에 미치는 영향

현재 `database/schemas`는 다음 핵심 경계를 이미 반영한다.

- `finding.source=rule-engine`
- Audit Pack ID·version·SHA-256
- rule ID·version·input/output SHA-256
- evidence refs·evidence set SHA-256
- AI의 `official_status_unchanged=true`
- `PASS/FAIL/REVIEW/ERROR/N/A`와 적용성·error code 제약

구현 전에 다음 보강을 Schema/DDL backlog로 등록한다. 이 ADR 승인만으로 기존 Schema 파일을 묵시적으로 변경하지 않는다.

| 보강 항목 | 이유 |
|---|---|
| Finding의 `evaluation_context.evaluation_as_of` | 시간 의존 기준 재현 |
| engine artifact/image digest | 실행 binary provenance |
| policy·reference snapshot ref의 명시적 hash·version | 외부 기준 고정 |
| `supersedes_finding_id`와 change reason | append-only lineage |
| REVIEW reason code와 missing requirement refs | 사람 검토 원인 명확화 |
| evaluation attempt 상태·error domain | Rule 실행 실패와 Control ERROR 분리 |

## 20. 고려한 대안

### 20.1 LLM이 직접 판정

거부한다. 비결정성, prompt injection, 근거 재현, 모델 version drift와 장애 격리 요구를 만족하지 못한다. LLM은 설명 계층으로만 사용한다.

### 20.2 보안담당자 또는 승인자가 상태를 직접 선택

거부한다. 사람 검토가 필요한 경우에도 공식 상태는 Rule Engine이 `REVIEW`로 생성하고, 사람의 정책·attestation·예외는 별도 versioned 입력이나 승인 record로 남긴다.

### 20.3 Control별 Python code에 기준값 하드코딩

주 대안으로 채택하지 않는다. Engine operator 구현은 code로 관리하되 원문 위치, 기준 parameter, 증적 요구와 적용성은 Audit Pack으로 분리한다. 새로운 실행 code가 필요한 operator 추가는 engine release와 보안 검토를 요구한다.

### 20.4 Wazuh SCA 결과를 공식 판정으로 직접 수용

거부한다. Wazuh는 지속 수집·Adapter가 될 수 있지만 결과를 공통 normalized evidence로 변환하고 동일 Audit Pack으로 재평가해야 한다. One-shot Collector와 같은 증적에는 같은 판정 규칙을 적용한다.

### 20.5 별도 Rule Engine HTTP microservice

MVP에서는 보류한다. 별도 network hop, 인증서, API version과 장애 지점이 늘어난다. 전용 Worker process와 Python package 경계로 먼저 구현하고 독립 확장·다른 언어 runtime이 필요할 때 별도 ADR로 재검토한다.

### 20.6 PostgreSQL trigger가 판정 계산

거부한다. 복잡한 적용성·Fixture·Pack version 관리가 DB에 결합되고 외부 저장소 없이 단위 재현하기 어렵다. DB trigger는 append-only·권한 제약을 보조할 수 있지만 판정 logic의 주체가 아니다.

## 21. 결과와 Trade-off

### 21.1 기대 효과

- AI와 외부 검색 장애가 공식 판정에 영향을 주지 않는다.
- 동일 입력과 engine으로 결과를 재현할 수 있다.
- KISA 기준·기관 정책·Adapter 변경의 영향 범위를 version별로 추적할 수 있다.
- 사람·관리자·AI에 의한 직접 상태 변경을 차단한다.
- Collector와 Wazuh의 입력 경로가 달라도 공통 규칙을 적용할 수 있다.
- Queue 중복·Worker 장애에도 공식 Finding 중복과 덮어쓰기를 방지한다.

### 21.2 비용과 제약

- Audit Pack 작성·서명·Fixture·승인 pipeline이 필요하다.
- 외부 reference와 조직 정책도 snapshot·version 관리해야 한다.
- append-only Finding과 current projection을 함께 운영해야 한다.
- Rule DSL operator가 제한되므로 새 기준 표현에 engine release가 필요할 수 있다.
- 사람의 빠른 수동 override 대신 보완 입력과 재평가 workflow를 사용해야 한다.

이 비용은 보안 판정의 설명 가능성, 무결성, 재현성과 책임 분리를 위해 수용한다.

## 22. 단계별 구현 순서

1. 이 ADR과 상태 의미를 승인한다.
2. Schema 보강 항목과 PostgreSQL append-only DDL을 확정한다.
3. Audit Pack signing envelope·key 운영 정책을 확정한다.
4. canonical input resolver와 allowlist Rule Engine 최소 구현을 만든다.
5. 대표 Control 하나로 PASS/FAIL/ERROR/N/A 또는 REVIEW 경계를 종단 검증한다.

7. evaluation Worker DB role·network·Queue 격리를 적용한다.
8. 멱등 저장·Outbox·재현 bundle을 구현한다.
9. AI 없이 전체 회귀·권한·장애 시험을 통과한다.

## 27. Agent/MCP 조치와 공식 판정의 분리

Agent 또는 MCP server는 기존 Finding을 수정하거나 공식 `PASS/FAIL/REVIEW/ERROR/N/A`를 직접 만들 수 없다. 조치 제안, 승인, 실행, rollback과 사후 재점검은 각각 append-only record로 남기며, 상태 변화는 새 evidence를 수집하고 같은 승인 Audit Pack을 다시 실행해 새 Finding version으로만 표현한다.

자유 shell 도구와 관리자 token의 모델 전달은 금지한다. 실행 가능한 도구는 version이 고정된 remediation pack의 좁은 동작, 사전조건, 대상 scope, dry-run, 승인자, timeout, rollback과 사후 검증을 모두 선언해야 한다. 상세 제안은 ADR 19를 따른다.
