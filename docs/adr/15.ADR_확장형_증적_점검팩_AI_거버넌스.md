# ADR-015: Windows 우선 확장형 Evidence·Adapter·Audit Pack·AI 보조 거버넌스

## 현재 구현 상태 (2026-08-07 검토)

- Evidence·Adapter·Guide Catalog·Audit Pack·AI 역할 분리는 Windows뿐 아니라 Linux·Aruba·가이드 RAG·취약점 후보에도 적용된다.
- Guide Catalog `APPROVED`는 검색 허용을 뜻하며 Audit Pack `APPROVED` 또는 공식 Finding을 뜻하지 않는다.
- LLM이 만든 mapping·rule·Fixture·prompt는 검증·승인 전 실행 불가능한 `DRAFT`다.
- 현재 지원 Catalog의 exact 식별과 Pack/Adapter compatibility를 유지하며 미지원 플랫폼에 자동 fallback하지 않는다.

## 1. 결론

Sec_AI는 Windows 11 PC-01~18 MVP를 먼저 완성했다. 이후 사용자 범위 승인과 ADR 19·20에 따라 Linux와 복수 기준 기반을 개발 환경에서 부분 구현했으며, 플랫폼별 운영 Pack·build·서명·VM/실장비·Pilot Gate 전에는 운영 지원으로 표시하지 않는다.

현재 MVP 이후의 확장은 다음 원칙으로 수행한다.

1. 플랫폼 원본 증적, 정규화된 보안 사실, Control 판정 입력을 분리한다.
2. 새 제품과 수집 방식은 조건문을 계속 추가하지 않고 versioned Adapter·Mapping registry로 등록한다.
3. Guide Catalog의 문서 승인과 공식 Audit Pack 승인을 서로 다른 생명주기로 관리한다.
4. LLM은 가이드 분석·매핑·규칙·Fixture의 `DRAFT` 제안을 만들 수 있지만 공식 Finding이나 승인 Pack을 생성·변경하지 못한다.
5. 공식 판정은 계속 승인·서명된 Audit Pack과 결정론적 allowlist Rule Engine만 수행한다.
6. 알 수 없는 제품·기준·매핑과 불완전한 증적은 LLM 추정으로 보충하지 않고 `REVIEW`, `ERROR` 또는 평가 거부로 닫는다.

이 ADR의 registry 전체가 완료됐다는 의미는 아니다. Windows 계약과 사용자 실행·복구·권한 경계는 안정화됐고, Linux 공통 계약·Criteria Profile·BGE 검색 generation은 versioned 구조로 부분 전환됐다. Switch 실장비, 조직 승인 Pack v2, 운영 credential과 Agent/MCP 실행은 계속 별도 Gate다.

## 2. 배경과 문제

현재 구현은 Windows 11 x64와 KISA PC-01~18을 빠르고 안전하게 검증하기 위해 다음 항목을 의도적으로 고정했다.

- `win.*` Probe ID
- Windows Registry·PowerShell·CIM/WMI 수집 경로
- Microsoft Defender·Windows Firewall DRAFT Adapter
- Windows patch·lifecycle reference
- Windows 11 전용 Manifest와 Collector build

이 선택은 MVP에는 적합하지만, 새 Windows Edition·보안제품·가이드·조직 기준을 같은 방식의 분기와 전용 rule module로 계속 추가하면 다음 문제가 발생한다.

- 같은 보안 의미를 수집 방식마다 반복 구현
- 제품·버전 조합에 따른 조건문 증가
- 가이드 검색용 승인과 공식 판정용 승인의 혼동
- LLM이 작성한 설명이나 규칙 초안이 공식 상태로 오인될 가능성
- 새 기준을 추가할 때 기존 Core를 복제하거나 광범위하게 수정
- 미지원 상태를 임의 `PASS`로 만드는 false assurance

따라서 Windows MVP를 중단하거나 즉시 다중 OS로 확대하지 않으면서도, 이후 변경 비용을 제한하는 명확한 계약과 승인 경계가 필요하다.

## 4. 계층 분리 결정

### 4.1 플랫폼 원본 증적

Collector와 제품 Adapter가 실제 시스템에서 읽은 결과다.

예:

- Windows Registry 값
- PowerShell·CIM/WMI 결과
- Defender 상태
- Windows Firewall effective profile
- Windows build·Edition

원본 증적은 source Probe·Adapter·version·권한·수집 상태·시간·hash를 보존한다. 원본 필드 이름을 공식 Control 규칙이 무제한으로 직접 참조하게 만들지 않는다.

### 4.2 정규화된 보안 사실

서로 다른 수집 경로가 같은 의미를 제공할 때 규칙 엔진이 사용할 versioned 의미 계약이다.

예:

| 보안 사실 ID 예시 | 의미 |
|---|---|
| `identity.password.minimum_length` | 유효 비밀번호 최소 길이 |
| `identity.password.maximum_age_days` | 유효 비밀번호 최대 사용일 |
| `endpoint.antimalware.realtime_protection` | 실시간 보호 유효 상태 |
| `network.host_firewall.profile_state` | 적용 대상 방화벽 Profile 상태 |
| `system.patch.compliance_state` | 승인 기준 대비 patch 준수 상태 |

실제 ID와 field는 Schema 변경 단계에서 확정한다. 이 ADR의 예시를 곧바로 현재 Schema의 유효 값으로 사용하지 않는다.

정규화된 사실에는 최소 다음 의미가 필요하다.

- `fact_id`와 `fact_schema_version`
- 평가 subject와 scope
- typed value와 unit
- source Probe·Adapter ID/version
- 수집 상태와 assurance
- 관측 시각 또는 기준 snapshot
- 원본·정규화 hash 계보

기존 `normalized_evidence.schema.json`을 다음 version에서 확장하는 방식을 우선 검토하며, 동일 의미의 병렬 정본 Schema를 불필요하게 만들지 않는다.

### 4.3 Control 판정 입력

Audit Pack은 필요한 `fact_id`, 정확한 version 범위, 완전성 조건, 적용성, 조직 정책·외부 reference와 허용 operator를 선언한다.

Rule Engine은 다음 입력만 받는다.

```text
검증된 canonical facts
+ exact Audit Pack version·content hash
+ exact policy/reference snapshot
+ engine version
→ immutable Finding candidate
```

Rule Engine은 raw shell output, 자유 텍스트 LLM 결과, 임의 Python과 network를 직접 사용하지 않는다.

## 5. Registry 책임

| Registry | 책임 | 금지 |
|---|---|---|
| Probe Registry | 실행 가능한 exact Probe, 권한, 제한, source hash | 사용자 입력 명령, 임의 dynamic import |
| Adapter Catalog | 제품·버전 식별, 지원 범위, 수집 capability | 미등록 제품 자동 PASS |
| Evidence Mapping Registry | Probe/Adapter output을 canonical fact로 변환 | LLM 자유 매핑의 Runtime 실행 |
| Rule Registry | 승인 operator ID·version·parameter 평가 | `eval`, `exec`, shell, network, LLM 접근 |
| Guide Catalog | 문서 version·hash·license·분류·조회 scope | Guide 승인만으로 공식 Rule 활성화 |
| Audit Pack Registry | Control·fact·rule·Fixture·승인·서명 lifecycle | 서명 없는 DRAFT 운영 활성화 |

모든 Registry는 closed allowlist를 기본으로 하고, 동일 ID/version에 다른 content hash를 허용하지 않는다.

Adapter capability에는 최소 다음 항목을 기계 판독 가능하게 기록한다.

- Adapter ID·version·publisher
- 지원 OS·Edition·제품·제품 version 범위
- 생성 가능한 Probe·canonical fact ID
- 필요한 최소 권한
- timeout·출력·민감정보 제한
- assurance와 알려진 제약
- `DRAFT/APPROVED/RETIRED/REVOKED` 상태
- 검증 Fixture와 source/build hash

## 6. Guide Catalog와 Audit Pack 분리

하나의 가이드는 RAG 검색 대상으로 승인될 수 있지만 공식 판정 기준으로 승인되지 않을 수 있다.

| 대상 | 승인 의미 | 결과 |
|---|---|---|
| Guide Catalog `APPROVED` | 저장·검색·인용 가능한 exact 문서 version | `GUIDE_QA`에서 검색 가능 |
| Control Source Mapping `APPROVED` | 가이드 절·페이지와 내부 Control 의미 연결 검토 완료 | Pack 작성 근거로 사용 가능 |
| Audit Pack `APPROVED` | Schema·Fixture·결정론·서명·승인 Gate 완료 | 공식 Rule Engine에서 평가 가능 |

다음 등식을 금지한다.

```text
Guide APPROVED ≠ Audit Pack APPROVED
RAG 검색 성공 ≠ 공식 판정 근거 완성
LLM 제안 완료 ≠ Rule 승인
```

새 가이드가 들어와도 처음에는 질의응답·비교 용도로만 사용할 수 있다. 공식 판정에 사용하려면 별도의 Control mapping과 Audit Pack release가 필요하다.

## 7. LLM 보조 작성 결정

### 7.1 허용 역할

LLM은 검토 가능한 `DRAFT` artifact를 만드는 보조도구로 사용할 수 있다.

- 가이드의 Control 후보·페이지·절 추출
- 기존 Control·canonical fact와의 매핑 후보
- 지원되는 allowlist operator와 parameter 제안
- PASS/FAIL/ERROR/REVIEW/N/A Fixture 후보
- 경계조건·충돌·근거 부족 목록
- 기존 Finding의 쉬운 설명과 조치 초안
- 여러 가이드의 차이 요약

### 7.2 금지 역할

- 공식 Finding 생성·수정·삭제
- Audit Pack 승인·서명·운영 활성화
- 임의 operator·Python·PowerShell·shell 생성 후 실행
- raw package·secret·credential·불필요한 개인정보 접근
- 근거 없는 매핑을 확정 사실로 표시
- 미지원 제품·수집 실패·기준 부재를 `PASS`로 추정
- 사람 승인자의 identity를 대행

### 7.3 DRAFT 제안 계약

LLM 제안에는 최소 다음 계보를 기록한다.

- proposal ID·version·status
- exact Guide ID/version/page/section/chunk hash
- 대상 Control·fact·operator 후보
- 제안 parameter와 Fixture
- 불확실성·충돌·미해결 항목
- model ID/digest·capability profile
- prompt template version·retrieval profile
- 입력·출력 canonical hash
- 작성자·검토자·승인 상태

LLM 출력은 자유 code가 아니라 Schema-valid data proposal이어야 한다. Runtime Rule Registry가 지원하지 않는 operator는 자동 거부한다.

## 8. 승인 workflow

```text
Guide 원본 반입·hash·license·분류 확인
→ Guide Catalog DRAFT
→ 악성코드·OCR·page mapping·검색 품질 검증
→ Guide Catalog APPROVED
→ 사람 또는 LLM의 Control Mapping DRAFT
→ 원문 대조·충돌·적용성 검토
→ Audit Pack DRAFT
→ Schema·allowlist·Fixture·결정론·false PASS 시험
→ 보안 검토자와 승인자 승인
→ exact content hash 서명
→ Audit Pack APPROVED release
→ Rule Engine allowlist 등록
```

LLM 장애나 미사용 상태에서도 이 workflow를 사람이 완료할 수 있어야 한다. LLM은 필수 신뢰 주체가 아니다.

## 9. Fail-closed 상태

| 상황 | 처리 |
|---|---|
| Package hash·서명·scope·nonce 실패 | 평가 진입 전 거부·격리, Control Finding 없음 |
| Probe 수집 실패·권한 부족 | `ERROR` 또는 증적 부족 `REVIEW`, `FAIL` 추정 금지 |
| 제품 Adapter 미지원 | `REVIEW`, 미설치가 명백히 증명된 별도 규칙이 없으면 `FAIL` 금지 |
| 조직 기준·reference 부재 | `REVIEW` 또는 Pack 정의에 따른 평가 불가 |
| 적용 대상 아님이 신뢰 가능하게 증명됨 | Pack의 명시적 규칙으로만 `N/A` |
| LLM 근거 부족·모델 장애 | AI artifact `FAILED/SKIPPED/UNAVAILABLE`, Finding 불변 |
| LLM과 공식 Finding 상태 불일치 | AI 출력 차단·격리, Finding 불변 |
| Guide 간 충돌 | 출처별 차이 표시, 임의 통합 금지 |
| Rule/Mapping version 미지원 | evaluation attempt 실패·Pack 격리 검토 |

## 10. 단계별 적용

### 10.1 현재 `IMP-038~046`

- 현재 Windows `win.*` Probe와 DRAFT Pack을 대규모 재설계하지 않는다.
- 실제 Package→Normalizer→Rule→Finding 경로, false PASS 0, 오류·권한·공격·복구 경계를 먼저 확정한다.
- 향후 canonical fact 후보와 현재 Probe 직접 결합 지점을 문서화하되 현재 IMP의 완료 범위를 확대하지 않는다.
- `IMP-040~043`에서 초보자용 점검·결과·재점검 기능을 먼저 연결하되 운영 서명·공식 Finding·자동 설정 변경은 열지 않는다.
- 향후 AI 화면은 `PREVIEW`로 먼저 배치할 수 있지만 비식별 고정 예시만 사용하며 수집·저장·제출·판정을 호출하지 않는다.

### 10.2 `IMP-047~052`

사용자에게는 “KISA 문서를 반입한다”, “pgvector를 구축한다”가 아니라 다음 기능 순서로 설명한다.

| IMP | 사용자에게 보이는 의미 | 내부 기술 책임 |
|---|---|---|
| `IMP-047` | 믿을 수 있는 KISA 원문 준비 (완료) | Guide Catalog에 exact source·version·license·scope와 page mapping 구현 |
| `IMP-048` | KISA 질문에 필요한 근거 찾기 | 승인형 Ingest, PostgreSQL+pgvector·Embedding·Reranker와 scope filter |
| `IMP-049` | KISA 질문별 정답 근거·인용 검증 | 대표 질문 평가셋, 검색·인용·근거 부족·문서 충돌 시험 |
| `IMP-050` | 내 PC에서 답변할 AI 연결 계약 (완료) | 현재 OpenRouter `VLLM_COMPATIBILITY_TEST_DOUBLE`·향후 `LOCAL_VLLM_FULL_CONTEXT`, CPU/GPU·license·resource·자동 fallback 금지 |
| `IMP-051` | 대화 기록·중단·재시도 기능 만들기 | Thread·Message·Citation·streaming·branch·history 계약 |
| `IMP-052` | KISA Q&A와 점검 결과 쉬운 설명 완성 | `GUIDE_QA`, `FINDING_EXPLAIN`, prompt injection·상태 불변 회귀 |

Guide source와 Control의 매핑은 공식 Pack과 분리된 DRAFT/승인 artifact로 설계한다. LLM capability matrix에는 일반 사용자의 `GUIDE_QA`, `FINDING_EXPLAIN`과 내부 작성자용 `AUDIT_PACK_DRAFT_ASSIST`를 분리한다. 작성 보조는 기본 비활성이고 공식 write credential을 갖지 않으며, 근거 부족·문서 충돌·proposal 계보를 별도로 시험한다.

OpenRouter는 OpenAI 호환 API·SSE·오류 계약을 합성 또는 승인된 비식별 최소 입력으로 확인하는 시험 대역이다. 실제 PC 결과 전체 문맥의 설명·후속 질문·보고서는 최종 로컬 vLLM profile에서 처리하고 외부 egress 0을 검증한다. 시험 대역 통과를 로컬 vLLM 또는 제품 완료로 표시하지 않는다.

`IMP-047` 구현 기준선은 exact PDF SHA-256·873쪽, `07. PC` 41쪽 Page Map과 PC-01~18 Control Source Mapping이다. `IMP-048`에서 사용자가 프로젝트 내부 검색과 파생 text·chunk·embedding 저장을 승인해 Guide Catalog만 `APPROVED`로 전환하고 실제 PC 41쪽을 적재했다. Mapping·Audit Pack은 계속 `DRAFT`이며 Guide 승인으로 자동 승격되지 않는다. 외부 재배포와 규칙 활성화도 계속 허용하지 않는다.

### 10.3 `IMP-053~054`

- `IMP-053 — 실제 KISA 질문답변 챗 화면 열기`: 검증된 KISA 질문답변·출처·대화 기록을 실제 사용자 챗 화면으로 연다.
- `IMP-054 — 초보 사용자 최종 사용성 확인`: 처음 사용하는 사람이 질문·출처·점검 결과를 스스로 찾는지 확인한다.
- 사용자 화면에서 공식 Finding, AI 설명, 작성자용 DRAFT 제안을 시각적으로 분리한다.
- 일반 사용자 UI에는 승인되지 않은 규칙 제안을 공식 기준처럼 표시하지 않는다.
- 기술·작성자 기능은 별도 권한과 화면 경계가 승인되기 전까지 노출하지 않는다.
- API·권한·감사·자동시험이 연결된 기능만 `LIVE`로 전환하고, 나머지는 `PREVIEW/BLOCKED/HIDDEN` 상태를 유지한다.

### 10.4 `IMP-055~062`

- 현재 Windows 공식 판정·Collector·서명·복구·RBAC·AI 상태 불변을 clean VM에서 인수한다.
- 이 ADR의 확장 계약이 Windows Pilot Gate를 우회하거나 다중 OS 완료를 의미하지 않게 한다.

### 10.5 Pilot 이후

1. Windows 제품 Adapter 추가 workflow
2. 두 번째 공식 보안가이드의 Audit Pack 작성·승인 세로 기능
3. LLM DRAFT 제안 품질과 사람 검토 시간 측정
4. canonical fact contract의 점진적 version 전환
5. 이후 별도 다중 OS ADR 승인

## 11. 호환성과 migration 원칙

- `IMP-038` 이전 결과와 Pack hash를 다시 쓰지 않는다.
- 기존 Audit Pack version을 수정하지 않고 새 version으로 release한다.
- 기존 `win.*` Evidence를 새 canonical fact로 바꿀 때 명시적 Mapping version과 dual-read 회귀기간을 둔다.
- 같은 입력의 과거 Finding은 당시 Pack·Mapping·Rule·Reference version으로 재현 가능해야 한다.
- migration 중 canonical fact가 없거나 불일치하면 기존 결과를 추정 변환하지 않는다.
- 새 계약이 안정화되기 전 기존 Windows path를 제거하지 않는다.
- 기존 migration file을 수정하지 않고 필요한 경우 새 migration을 추가한다.

## 12. 시험과 완료 기준

- 동일 canonical input 100회 결과 hash가 같다.
- Adapter·Mapping·Rule ID/version/hash가 Finding에서 역추적된다.
- 미등록 Adapter·Mapping·operator가 모두 거부된다.
- 일부 증적, 미지원 제품, 기준 부재에서 false PASS가 0건이다.
- Guide 승인만으로 Audit Pack이 활성화되지 않는다.
- LLM proposal만으로 공식 Finding 또는 Pack 상태가 변경되지 않는다.
- LLM 없이도 기존 공식 판정과 Pack 승인 workflow가 동작한다.
- 모델·prompt·Guide version 변경 시 proposal 계보가 분리된다.
- retired/revoked Guide·Adapter·Pack이 신규 기본 평가에 사용되지 않는다.
- 다른 조직의 Guide·proposal·Finding에 접근할 수 없다.

## 13. 결과와 trade-off

### 13.1 장점

- Windows MVP 일정과 안정성을 유지한다.
- 새 제품·가이드 추가 시 Core 복제와 조건문 증가를 줄인다.
- LLM 성능을 작성 생산성에 활용하면서 공식 판정 재현성을 보존한다.
- 가이드 검색과 공식 감사 기준을 혼동하지 않는다.
- 향후 다중 OS 전환 시 교체 대상이 Collector·Adapter·Mapping으로 제한된다.

### 13.2 비용

- Registry·version·Fixture·승인 artifact가 늘어난다.
- 초기에 직접 조건문을 추가하는 것보다 작성 절차가 길다.
- canonical fact 설계와 기존 Windows 규칙 migration에 별도 회귀가 필요하다.
- LLM 제안에도 평가셋·감사·보존·권한 관리가 필요하다.

이 비용은 보안 판정 제품에서 false PASS, 모델 drift, 재현 불가와 승인 우회 위험을 줄이기 위해 수용한다.

## 14. 거부한 대안

### 14.1 LLM이 원본 증적을 직접 읽고 공식 판정

비결정성, prompt injection, 모델 drift, 근거 재현과 권한 분리를 만족하지 못하므로 거부한다.

### 14.2 모든 새 제품·기준을 Python 조건문으로 직접 추가

빠른 초기 구현은 가능하지만 결합도·회귀 범위·승인 추적이 계속 증가하므로 장기 방향으로 거부한다.

### 14.3 Guide Catalog 승인만으로 공식 판정에 사용

검색·인용 품질 검증은 완전성·적용성·Fixture·결정론·서명을 보장하지 않으므로 거부한다.

### 14.4 현재 즉시 공통 모델로 전면 재작성

`IMP-038`의 실제 Windows 판정 검증 전에 대규모 추상화를 하면 현재 동작과 오류 경계를 잃을 수 있으므로 거부한다. 현재 Core 안정화 후 contract-first 방식으로 점진 전환한다.

### 14.5 초기 MVP 단계에서 다중 OS 동시 개발

초기에는 Collector·권한·패키징·서명·VM Matrix가 검증되지 않아 보류했다. 이후 사용자 범위 승인과 ADR 19에 따라 Linux 개발 구현만 선행했으며 운영 지원 승격은 여전히 보류한다.

## 15. 승인 및 변경관리

다음 변경은 이 ADR version 증가와 영향 분석을 요구한다.

- canonical fact의 의미·type·단위 변경

- 두 번째 OS 공식 지원 착수

## 16. ADR 19 후속 승인·부분 구현

두 번째 OS 공식 지원은 본 ADR의 재검토 대상이다. 현재 Ubuntu Server 24.04 LTS와 Rocky Linux 9 개발 경로, Cisco IOS XE·HPE Aruba AOS-CX 공통 계약을 부분 구현했다. 공통 canonical fact를 사용하되 플랫폼별 원본 locator·권한·수집 실패 의미를 잃는 억지 정규화는 금지한다.

Markdown 렌더링과 Agent/MCP 조치는 evidence 또는 공식 Finding의 의미를 바꾸는 기능이 아니다. Markdown은 표시 계층, Agent/MCP는 승인형 remediation 계층으로 분리하고 LLM은 계속 공식 판정과 Pack 승인 권한을 갖지 않는다. 상세 제안과 단계 Gate는 ADR 19 및 루트 발전 계획을 따른다.

## 17. ADR 20 후속 승인·부분 구현 — 복수 기준과 일반 사용자 Builder

기존 `Guide Catalog → Control Source Mapping → Audit Pack` 분리는 유지한다. 일반 사용자가 KISA Pack의 rule을 직접 고치게 하지 않고, 기준 출처·Control Catalog·Profile·signed Audit Pack v2를 별도 lifecycle로 둔다.

Windows 개인/조직 Profile·선택 이력·KISA 되돌리기와 Linux 안전 기본값·구조화 편집·실행 snapshot을 개발 환경에 구현했다. 개인 기준은 KISA 결과를 덮어쓰지 않고 기준별 결과를 병렬 표시한다. 범용 Builder, 조직 공통 기준, 공식 Pack v2는 관리자·보안 검토, Fixture·100회 결정론·false PASS·서명·승인을 추가로 통과해야 한다. LLM은 Schema-valid `DRAFT`와 Fixture 후보만 제안한다. 상세 계약은 ADR 20과 `사용자_정의_점검기준_안내.md`를 따른다.
