# ADR-020: 복수 점검기준 Catalog·Profile과 일반 사용자 무코드 Builder

## 현재 구현 상태 (2026-08-07 검토)

- Windows 개인/조직 Profile, Linux 제한 숫자·승인 목록, Switch 26개 안전 기준과 N-12·N-17 조직 보완값 편집·초기화·실행 snapshot이 구현됐다.
- 사용자가 command·shell·정규식·임의 REST path·판정 코드를 작성하는 범용 무코드 Builder는 아직 제공하지 않는다.
- 조직 입력과 장비 수집값을 분리하고, 기준 version/hash를 실행 결과에 고정한다. 이후 기준 변경으로 과거 결과를 다시 쓰지 않는다.
- 자연어·AI 규칙 제안은 Schema·Fixture·보안시험·검토·승인·서명 전 실행 불가능한 `DRAFT`다.

## 1. 결정

Sec_AI는 `Guide → Control Source Mapping → Audit Pack`의 기존 분리를 다음 네 계층으로 일반화한다.

```text
Criteria Source Catalog
→ Control Catalog
→ Criteria Profile
→ signed Audit Pack v2
```

- Source Catalog는 KISA, 법령, 산업표준, 제조사 Baseline, 조직정책과 사용자 자체 기준의 출처·version·hash·license·authority를 보존한다.
- Control Catalog는 출처별 요구사항·parameter·평가 목적을 기계 판독 가능한 Control로 표현한다.
- Criteria Profile은 하나 이상의 Catalog에서 Control을 선택하고 적용 대상·parameter·예외·우선순위·충돌 처리를 정의한다.
- Audit Pack v2는 Profile을 지원되는 canonical fact·allowlist rule·Fixture에 연결한 실행·서명 산출물이다.

현재 KISA/Windows 전용 `audit_pack.schema.json`은 v1 재현 정본으로 유지한다. hard-coded `const`를 직접 완화하지 않고 신규 Schema·migration·Adapter로 점진 전환한다.

### 1.1 2026-08-06 구현 상태

현재 개발 환경에는 다음이 구현되어 있다.

- 개인/조직 범위 Criteria Profile과 version·소유자·적용 대상 분리
- 허용된 Windows 기준 값만 조정하는 무코드 form
- 로그인 사용자의 활성 기준 선택과 변경 이력
- 점검 시작 시 선택 기준의 exact snapshot 보존
- 관리자가 개인 값을 수정한 뒤 KISA 제품 기본값으로 되돌리는 reset
- 기준 미등록 시 KISA 안전 기본값 사용
- Linux 비밀번호·잠금·세션 수치와 승인 계정·허용 포트·SUID/SGID 경로의 비어 있지 않은 안전 기본값
- Linux 구조화 값 편집·초기화·로컬 보관과 점검 실행 시 exact snapshot·SHA-256 보존
- raw PowerShell·shell·Registry path·SQL·Python·임의 operator 입력 차단

다음은 남아 있다.

- 자연어 DRAFT와 대표 Template 5개에 대한 초보 사용자 인수
- 조직 검토·승인·RLS와 공식 Audit Pack v2 서명·폐기·rollback
- Linux·Switch parameter catalog와 플랫폼별 적용성
- 동일 입력 100회 compiled hash, 공식 KISA v1 회귀 hash와 전체 false PASS Gate

현재 Profile은 공식 KISA 결과를 덮어쓰지 않으며, 결과와 PDF에는 선택한 기준과 실행
시점 snapshot을 구분해 표시한다.

## 2. 일반 사용자 작성 결정

일반 사용자는 JSON과 규칙 코드를 작성하지 않고 Template 또는 자연어로 DRAFT 기준을 만든다. Builder가 노출하는 선택지는 승인된 `observable_fact_catalog`와 allowlist operator로 제한한다.

허용 예:

- 숫자 최소·최대·범위
- boolean 사용/사용 안 함
- 승인 목록 포함·금지 목록 불포함
- 날짜·만료 기간
- 모든 대상/하나 이상의 대상 충족

금지 예:

- 자유 PowerShell·shell·SQL·Python
- 사용자 정규식의 Runtime 실행
- 임의 파일·Registry 경로 입력 후 수집
- LLM이 새 Probe나 operator를 Runtime에 등록

## 3. 활성화 등급

| 등급 | 생성자 | 판정 성격 | 승인 |
|---|---|---|---|
| `PERSONAL_DRAFT` | 일반 사용자 | 미리 보기 | 없음 |
| `PERSONAL_ACTIVE` | 일반 사용자 | 자신의 장비 참고 결과 | 본인 확인 |
| `ORG_REVIEW` | 조직 사용자 | 조직 적용 후보 | 검토 대기 |
| `ORG_ACTIVE` | 기준 검토자·보안 승인자 | 조직 기준 결과 | 역할 분리·Fixture·서명 |
| `OFFICIAL_PACK` | Pack 작성·승인 역할 | 공식 Finding | ADR 10의 전체 Gate |

`PERSONAL_*` 결과는 `사용자 기준` label과 profile ID/version을 항상 표시한다. 공식 KISA Finding과 집계하거나 덮어쓰지 않는다.

## 4. 출처 우선순위와 충돌

기본 authority 순서는 법령·의무 규정→승인된 조직 필수정책→국가 가이드→산업표준/제조사→사용자 기준이다. 실제 순서는 조직 profile에서 승인하되 낮은 authority가 높은 authority의 필수 최소값을 완화할 수 없다.

- 출처별 결과를 각각 보존한다.
- `stricter_wins`는 승인된 동일 의미·동일 단위 parameter에만 적용한다.
- 의미·단위·대상·유효기간이 다르면 자동 병합하지 않는다.
- 충돌을 해결하지 못하면 `REVIEW`이며 LLM 추정으로 통합하지 않는다.
- 결과와 PDF에 source/profile/pack ID·version·content hash를 기록한다.

## 5. AI 역할

AI는 자연어를 Schema-valid DRAFT로 변환하고 중복·충돌·누락·쉬운 설명·Fixture 후보를 제안할 수 있다. AI는 다음 권한이 없다.

- 기준 승인·서명·조직 활성화
- unsupported fact/operator 생성
- 공식 Finding 변경
- 출처나 citation 조작
- 자유 code·명령 생성 후 실행

AI가 없어도 Template Builder와 승인 workflow가 동작해야 한다.

## 6. 데이터·감사

- 신규 Schema와 신규 migration만 사용한다.
- 모든 DRAFT·검토·승인·거부·활성화·폐기는 append-only version과 감사 event로 남긴다.
- organization·owner RLS와 서버측 역할 검사를 적용한다.
- 같은 ID/version에 다른 content hash를 허용하지 않는다.
- Profile 변경은 과거 결과를 바꾸지 않고 새 version·새 evaluation을 만든다.
- 출처 원문 이용조건과 redistribution 여부를 별도 보존한다.

## 7. 안전한 Compile 흐름

```text
Wizard/자연어 입력
→ user criteria DRAFT Schema
→ fact/operator/단위/범위 검증
→ source·license·authority 검증
→ 충돌·적용성 분석
→ 합성 Fixture 미리 보기
→ 개인 활성화 또는 조직 검토 요청
→ 사람 승인·결정론·false PASS·서명 Gate
→ Audit Pack v2 release
```

## 8. 완료 Gate

- 비개발자가 대표 Template 5개를 JSON·명령 없이 작성
- 자연어 DRAFT의 unsupported fact/operator 자동 활성화 0
- 사용자 기준과 공식 기준 혼합 표시 0
- 다른 사용자·조직 DRAFT 접근 0
- 동일 입력 100회 compiled hash 1개
- 수집 실패·권한 부족·미지원 false PASS 0
- 승인 없는 조직·공식 Pack 활성화 0
- version 변경 후 과거 결과 hash 변경 0
- KISA v1 PC-01~18 기존 회귀 hash 불변

### 8.1 Switch 안전 기본 기준 구현 경계

Aruba N-01~N-38 개발 경로는 회사·기관 정책으로 조정 가능한 26개 항목의 판정 기준을
`KisaNetworkAssessmentProfile`의 닫힌 구조로 제공한다. 기본값은 KISA 안전 조건을 따라
로그인 실패 잠금 상한 5회와 보안 설정 필수 적용으로 채운다. 일반 사용자는 숫자 범위와
`필수 적용/조직 예외 검토`만 바꿀 수 있고 명령·정규식·JSON·SQL은 입력할 수 없다.

기준 변경은 장비 수집값 변경이 아니다. 매 실행은 선택 기준의 canonical hash를 저장하지만
REST projection, `observed_summary`와 Evidence는 장비에서 읽은 값만 유지한다. 기준만 있고
실제 값이 없으면 조직 보완 판정 입력이 없는 평가 경로에서 REVIEW다. 조직 기본 Profile의
중앙 승격·승인은 기존 `ORG_REVIEW → ORG_APPROVED` Gate를 따르며 현재 브라우저 보존값은
운영 승인 Profile이 아니다.

2026-08-06 AOS-CX 수집기는 구조화 GET을 13개로 확대했지만 Criteria Profile은 수집기와
계속 분리한다. 안전 합성 projection에서 실제값 기반 PASS 19·REVIEW 11·N/A 8로 바뀌어도
기준 선택이 projection이나 Evidence를 채우지는 않는다. 로그인 배너·timestamp·TFTP·TCP
keepalive와 조직·외부 증적이 연결되기 전에는 해당 항목을 기준값만으로 PASS로 만들지 않는다.

사용자 후속 결정에 따라 26개 안전 기준과 별도로 REST 미확정 11개 항목에 조직 보완 판정값을
제공한다. 기본값은 모두 `PASS`지만 이는 장비에서 수집한 사실이 아니라 개발용 조직 입력이다.
사용자는 `PASS/FAIL/REVIEW/N/A` 중 하나만 선택할 수 있고 자유형 근거·명령·JSON은 입력할 수
없다. 규칙 엔진은 장비 직접 판정이 REVIEW일 때만 이 값을 적용하며, 결과에는
`ORGANIZATION_INPUT`, 장비 수집값 아님 표시, 11개 snapshot과 실제 적용 항목을 저장한다.
조직 입력이 있어도 REST `observed_summary`와 Evidence는 변경하지 않는다. 승인된 조직
Profile로 승격하기 전에는 공식 Finding을 생성할 수 없다.

2026-08-06 전 항목 수집 확대 후에는 위 11개 입력을 당시 이력으로 보존하고 현재 조직 입력을
N-12 보안 패치·벤더 권고 검토 이력과 N-17 SNMP 업무 사용 승인 두 개로 축소한다. N-04·05·
10·16·19·23은 장비 직접 사실로 판정하고 N-13·21·25는 AOS-CX 비적용 N/A로 분리한다.
현재 실행 입력은 안전 기준 26개와 조직 판정 2개, 총 28개다. 브라우저 저장 key v3와 실행
snapshot/hash를 사용하며 과거 37개 입력 결과는 append-only로 보존한다.

## 9. 거부한 대안

### 9.1 사용자가 직접 JSON Audit Pack 편집

내부 ID·Schema·operator 지식이 필요하고 안전하지 않은 값과 승인 우회를 막기 어려워 일반 사용자 기능으로 거부한다.

### 9.2 자연어를 바로 규칙으로 실행

비결정성·prompt injection·false PASS·명령 실행 위험 때문에 거부한다. 자연어는 검토 가능한 DRAFT까지만 허용한다.

### 9.3 여러 출처 결과를 하나의 PASS/FAIL로 즉시 합치기

출처의 authority·적용성·단위·유효기간이 달라 설명과 감사가 불가능하므로 거부한다. 출처별 상태를 유지하고 승인된 Profile만 통합 정책을 정의한다.
