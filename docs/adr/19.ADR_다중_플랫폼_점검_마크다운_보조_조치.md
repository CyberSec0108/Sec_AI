## 1. 결정 요약

Sec_AI는 Windows PC 점검 Core를 복제하지 않고 다음 네 축으로 확장한다.

1. Linux 서버는 `Ubuntu Server 24.04 LTS`와 `Rocky Linux 9`을 별도 Collector·Adapter·Audit Pack으로 추가한다. RHEL 계열 검증은 Rocky 9로 수행하되 Red Hat 상표·지원 범위를 대신한다고 표시하지 않는다.
2. 네트워크 스위치는 `Cisco IOS XE`와 `HPE Aruba Networking AOS-CX` 두 계열을 첫 지원 대상으로 삼는다.
3. AI 설명은 제한된 Markdown 문법과 계약에 등록된 `[1]` 출처 참조만 파싱·정화해 표시한다. 모델 출력이나 원문 HTML을 그대로 DOM에 삽입하지 않는다.
4. Agent 또는 MCP는 점검 결과를 바탕으로 조치안을 작성하고 승인된 조치만 실행하는 제어면으로 사용한다. LLM 자유 출력, 자유 shell과 임의 네트워크 명령을 실행하지 않는다.

Windows·Linux·Switch의 공식 상태는 각각 승인·서명된 Audit Pack을 실행하는 결정론적 규칙 엔진만 생성한다. LLM, Agent와 MCP는 공식 판정 권한을 갖지 않는다.

않는다.

### 2.1 Windows 우선 알려진 취약점 점검 결정

2026-08-06 사용자 지시에 따라 취약점 기능은 Switch보다 Windows를 먼저 제공한다. 홈에서는
`CVE`나 `에이전트 활용` 대신 `알려진 취약점 점검`이라는 쉬운 이름을 사용한다.

- Collector는 OS release·build·UBR·architecture와 고정 read-only 원천의 KB·registry
  프로그램·AppX·Python·Node.js·Java 구성요소를 읽고 공용 Feed에 직접 접속하지 않는다.
- 중앙 API만 고정된 NVD CVE API endpoint에 exact CPE를 보내며 임의 URL 입력을 받지 않는다.
- NVD 결과는 영향 **후보**다. Microsoft 보안 권고·KB/build 적용성 확인 전에는 확정 취약점이나
  공식 Finding으로 승격하지 않는다.
- Feed snapshot은 append-only로 저장한다. 72시간까지 `CURRENT`, 7일까지 `STALE`, 이후
  `EXPIRED`이며 오래되거나 없는 자료로 `안전`이나 0건을 확정하지 않는다.
- 현재 오프라인은 중앙 서버가 마지막 정상 DB snapshot을 재사용하는 장애 폴백이다. 완전 폐쇄망
  반입용 Ed25519 서명 Bundle·anti-rollback·원자적 교체는 별도 Gate로 유지한다.
- 선택 requirements/lock 파일은 Browser가 로컬에서 이름·버전만 추출한다. 파일 원문·경로는
  API나 외부 AI로 보내지 않는다.
- 중앙 API는 Windows를 NVD, PyPI/npm/Maven exact version을 OSV와 비교한다. 검토된 CPE가
  없는 일반 프로그램은 임의 문자열 매칭하지 않고 `추가 식별 필요`로 남긴다.
- OSV `querybatch`의 exact 이름·버전 일치 후보는 상세 설명 개수나 개별 상세 조회 실패와
  무관하게 보존한다. CVSS·공개일·긴 설명 보강은 고유 후보 100건을 우선 처리하며,
  미보강 후보는 삭제하거나 안전으로 바꾸지 않고 `점수 산정 전`으로 표시한다.
- 결과 카드는 한국어 제목·일반 설명·CVSS·공개일·최종 수정일·제공 기관을 우선 표시한다.
  사용자 요청 때 공개 후보 한 건만 AI에 보내 쉬운 한국어 설명을 만들며 공식 Finding은 불변이다.
- AI/Agent는 후보를 만들거나 상태를 바꾸지 않는다. 홈의 Agent 카드는 제거하고 향후 검증된
  occurrence에 대한 `PLAN_ONLY` 조치안부터 별도 승인한다.

## 3. 공통 확장 구조

새 장비를 추가할 때 다음 공통 흐름을 사용한다.

```text
Asset type·platform·version 식별
→ 승인 Manifest와 읽기 전용 Collector/Adapter
→ 원본 Evidence package·hash·서명
→ platform별 Normalizer와 canonical fact
→ platform별 승인 Audit Pack·결정론 규칙
→ append-only Finding
→ KISA·공급자 문서 근거 검색
→ LLM의 쉬운 설명·우선순위·후속 질문
→ 선택적 승인형 Remediation Plan
→ 사용자·관리자 승인
→ 제한된 실행 Broker
→ 재점검·전후 증적·감사·rollback 결과
```

공통 Core가 아는 것은 자산 범위, Evidence 계보, Pack 생명주기, 공식 상태, 권한, 감사와 설명 계약이다. 배포판·벤더별 명령, parser, 설정 의미와 조치 방법은 Adapter·Probe·Remediation Pack에 둔다.

## 4. Linux 서버 결정

### 4.1 첫 지원 순서

1. Ubuntu Server 24.04 LTS x86_64
2. RHEL 9 x86_64

두 배포판은 패키지 관리자, 보안 모듈, 공급자 기준과 지원 수명이 다르므로 동일 Pack의 조건문으로 합치지 않는다. 공통 fact는 공유할 수 있지만 `linux-ubuntu-24.04`와 `linux-rhel-9` Audit Pack을 별도 version·hash·Fixture로 승인한다.

### 4.2 수집 방식

개발실의 첫 세로 기능은 비운영 시험 자격증명과 SSH host-key 고정을 사용한 원격 읽기 전용 수집으로 검증할 수 있다. Pilot부터는 다음 경계를 적용한다.

- 대상 서버 전용 서비스 계정
- 비밀번호보다 짧은 수명의 인증서 또는 조직 승인 SSH key 우선
- host key 또는 host certificate 검증 필수
- root 직접 로그인 금지
- 일반 권한 Probe 우선, 필요한 항목만 exact sudoers allowlist
- 자유 shell·명령 문자열 조합·파이프·redirection 금지
- Probe ID·version에 고정된 argv와 parser만 실행
- timeout, stdout/stderr 상한, locale 고정과 secret masking
- 수집 전후 설정 diff와 process tree 종료 검증

운영 배포형은 대상 서버에서 실행하는 서명된 Linux one-shot Collector와 중앙에서 Manifest를 발급하는 구조를 기본으로 한다. Agentless SSH는 초기 도입과 제한된 환경의 선택 profile로 유지하며 자격증명 보관·회수·감사 Gate를 별도로 둔다.

### 4.3 첫 점검 영역

- 계정·암호·잠금 정책
- SSH daemon과 root·password 로그인 정책
- sudo와 관리자 권한 위임
- 중요 파일·디렉터리 소유권과 권한
- 불필요 서비스·열린 포트
- firewall 상태
- 패키지·보안 업데이트·재시작 필요 상태
- auditd·system journal·원격 로그
- SELinux 또는 AppArmor 상태
- 시간 동기화
- 부팅·kernel parameter·core dump
- 악성 파일 자동실행 지점과 예약 작업

KISA 서버 항목을 1차 공식 근거로 매핑하고, 배포판 공급자 문서와 승인된 CIS/SCAP profile은 보조 근거와 교차검증으로 관리한다. 공급자 도구의 `pass/fail`을 Sec_AI 공식 Finding으로 직접 복사하지 않고 원본 rule ID·profile version·결과를 Evidence로 정규화한 뒤 승인 Pack으로 다시 평가한다.

## 5. 스위치 결정

### 5.1 첫 지원 제품

- Cisco IOS XE
- HPE Aruba Networking AOS-CX

AOS-CX는 Cisco와 다른 벤더·API·구성 모델을 가지면서 REST 기반의 구조화된 읽기 경로를 제공하므로 두 번째 계열로 선택한다. 특정 장비 이름만 보고 parser를 선택하지 않고 vendor, network OS, version, model과 capability handshake를 모두 확인한다.

### 5.2 읽기 전용 수집 우선순위

1. NETCONF/RESTCONF 또는 AOS-CX REST API의 구조화된 `GET`
2. 공급자 YANG/API가 지원하지 않는 항목에 한해 승인된 SSH `show` 명령
3. 수동 업로드는 신뢰 수준이 낮은 별도 profile

점검 단계에서는 configuration mode, `POST`, `PUT`, `PATCH`, `DELETE`, reload와 write memory를 호출하지 않는다. REST/NETCONF가 장치에서 비활성인 경우 사용자가 임의로 켜게 유도하지 않고 SSH read-only Adapter 또는 `확인 필요`로 처리한다.

### 5.3 첫 점검 영역

- 로컬 관리자·AAA·RADIUS/TACACS+ 정책
- SSH/HTTPS 사용과 Telnet/HTTP 비활성
- SNMPv3와 community 노출
- 관리망·VRF·ACL·허용 source
- NTP·syslog·audit trail
- firmware·보안 권고·지원 수명
- 사용하지 않는 interface 상태
- VLAN·trunk·native VLAN 기본 위험
- STP 보호, DHCP snooping, Dynamic ARP Inspection 등 적용 가능한 보호 기능
- 설정 backup·변경 이력·복구 가능성

벤더별 지원 여부와 syntax가 다르므로 공통 Control이 있더라도 Evidence Adapter와 applicability rule은 분리한다. 지원하지 않는 기능은 `FAIL`로 추정하지 않는다.

### 5.4 네트워크 자격증명

- 자격증명을 source, DB 평문, log, LLM prompt와 PDF에 저장하지 않는다.
- OpenBao 등 승인된 secret store에서 job 범위의 짧은 credential을 발급한다.
- TLS certificate, SSH host key, 장치 ID와 대상 IP를 Job에 묶는다.
- 장비별·명령별 최소 권한 계정을 사용한다.
- 동시 접속, 명령 수와 출력 크기를 제한한다.
- 수집 결과에 credential이나 전체 running-config를 기본 포함하지 않는다.

2026-08-06 개발 UI는 운영 secret store 이전의 제한된 시험 경로로서 비밀번호를 요청 메모리에서만
사용한다. 서버 등록 asset key 하나만 허용하고 host·port·certificate pin 입력은 받지 않으며,
PostgreSQL에는 organization·owner 범위 결과와 event만 저장한다. migration
`0025_switch_audit_ui`의 RLS·활성 실행 unique, 결과 hash 재검증과 실제 credential column 0을
확인했다. 운영 전환 때는 화면 비밀번호 입력을 기본 경로로 유지하지 않고 승인 secret store의
짧은 job credential로 교체한다.

같은 날 결과 카드를 Windows·Linux 통합 카드 구조로 전환하고 AI 종합·항목별 token stream을
연결했다. `0026_switch_audit_ai_outputs`는 과거 SW-01~06 V1 설명을 append-only로 보존하며 organization·owner
RLS와 `SELECT/INSERT` 권한만 사용한다. 모델 처리는 화면 진입만으로 자동 시작하지 않고 사용자가
비식별 결과 문맥 전송 안내를 본 뒤 `AI 설명 생성하기`를 눌러야 요청 Schema의
`result_context_processing_approved=true`가 충족된다.

실제 확인값은 항목별 의미를 잃는 공통 성공/실패 문장을 사용하지 않는다. REST projection에서
사용자·서버 식별자는 버리고 SSH/SNMPv3/syslog/NTP/session의 상태·개수·제한값만 보존한다.
과거 결과의 canonical JSON과 hash는 수정하지 않으며, 표시와 AI 공개 입력에서 같은 항목별
보정 함수를 사용해 화면과 설명의 확인값이 어긋나지 않게 한다.

후속 N-01~N-38 확장은 승인된 KISA 2026 네트워크 장비 Source Mapping의 p.391~466을
사용한다. Guide Catalog 승인을 Audit Pack 승인으로 해석하지 않으며 benchmark는
`SECAI-KISA-2026-N01-N38-AOSCX-DRAFT`의 최초 전체 Coverage는 `0.2.0-DRAFT`였고,
조직 보완 판정 입력을 추가한 버전은 `0.3.0-DRAFT`, 전 항목 직접 수집을 확대한 현재 버전은
`0.4.0-DRAFT`다. REST projection이 직접 판정하는
항목과 추가 증적이 필요한 항목을 분리하고, 수집하지 않은 값을 기본값으로 추정해 PASS로
만들지 않는다. migration `0027_switch_n01_n38_ai_keys`는 과거 V1 cache key를 보존하면서
N-01~N-38 V2 key만 추가한다.

2026-08-06 후속 결정으로 Switch도 Linux와 같은 안전 기본 판정 기준 편집 경계를 사용한다.
26개 구조화 기준은 로그인 실패 잠금 5회 이하와 각 보안 설정의 필수 적용 여부로 채우며,
회사·기관은 허용된 숫자·선택지만 수정한다. 선택 기준은 실행 시작 시 canonical snapshot과
SHA-256으로 고정한다. 기준은 기대값과 결정론 규칙의 입력일 뿐 REST `observed_summary`,
Evidence와 수집 hash를 채우거나 덮어쓰지 않는다. 실제 값이 없는 항목을 기준만으로 PASS로
만드는 구현은 금지하며 REVIEW 감소는 추가 read-only Adapter 또는 승인된 조직 증적으로만 한다.

2026-08-06 수집 범위 확대 결정으로 AOS-CX v10.13 고정 GET에 interfaces, user groups,
ACLs와 logging filters를 추가한다. 원문 설정은 저장하지 않고 포트·VRF·RBAC·로깅·DNS·CoPP의
개수와 boolean만 비식별 projection에 남긴다. N-09·14·22·24·27·31·33·36은 이 실제값으로
결정론 판정하고 AOS-CX에 없는 legacy service는 N/A로 분리한다. 활성 포트 description은
기술적 관찰값일 뿐 업무상 필요성 승인으로 간주하지 않으며 조직 용도대장과 대조되지 않으면
REVIEW다. 안전 합성 projection의 REVIEW는 26개에서 11개로 감소하지만 로그인 배너·timestamp·
TFTP·TCP keepalive와 조직·외부 증적은 계속 별도 source를 요구한다.

2026-08-06 사용자 후속 결정으로 REST 직접 판정 후 REVIEW인 N-04·05·10·12·13·16·17·19·
21·23·25에 닫힌 `조직 보완 판정 입력`을 제공한다. 기본값은 모두 PASS이며 사용자는
PASS/FAIL/REVIEW/N/A로 수정하거나 초기화할 수 있다. 이 값은 운영 편의를 위한 개발용
조직 판정이고 REST Evidence가 아니다. 장비 규칙이 PASS·FAIL·N/A를 확정하면 조직 입력은
적용하지 않으며, 적용 시 result code와 결과 카드에 `ORGANIZATION_INPUT`과 `장비 수집값 아님`을
표시한다. Profile이 없는 평가 경로는 REVIEW를 유지하고, 실행 시 37개 입력의 snapshot·hash와
조직 입력 실제 적용 항목을 보존한다. 이 DRAFT 편의값을 승인된 조직 증적이나 공식 Finding으로
승격하려면 승인자·유효기간·증적 hash·서명이 추가로 필요하다.

2026-08-06 추가 지시로 장비에서 확인 가능한 기술 항목을 조직 기본값으로 대신하지 않도록
수집 계약을 v5로 확대한다. 기존 13개 구조화 GET에 system status, 전체 사용자, hot patch,
최근 event log와 running-config text GET을 더해 총 18개 고정 GET을 사용한다. running-config는
배너 존재·식별정보 노출 여부만 추출하고 원문·ciphertext·SNMP 비밀은 저장하지 않는다.
N-04·05·10·16·19·23은 직접 PASS/FAIL로 전환하고, AOS-CX에 Cisco식 전역 기능이 없는
N-13·21·25는 N/A로 분리한다. 장비 밖 이력이 필요한 N-12 권고 검토와 N-17 SNMP 업무 승인만
조직 입력으로 유지한다. 현재 입력은 안전 기준 26개와 조직 판정 2개, 총 28개이며 browser
storage v3와 실행 snapshot/hash에 고정한다. 카드의 별도 판정 출처 행은 표시하지 않지만 상단
안내·판정 이유·내부 result code에서 조직 입력 경계를 보존한다.

## 6. AI 지식과 표시 결정

### 6.1 지식 우선순위

AI 설명의 입력 우선순위는 다음으로 고정한다.

1. 대상 장비에서 실제 수집한 비식별 Evidence
2. 규칙 엔진의 불변 공식 상태와 자연어 판정 이유
3. 승인된 KISA 원문과 정확한 page·section·paragraph
4. 승인된 공급자·공공 보안기관의 보조 문서
5. 모델의 일반 지식

모델 일반 지식은 위험 배경, 용어 풀이, 조치 시 주의점과 후속 질문에 적극 사용할 수 있지만 실제값, KISA 문구와 공식 판정을 만들 수 없다. 화면과 PDF에는 `내 장비 증적`, `KISA 근거`, `공급자 보조 근거`, `AI 일반 설명`을 구분한다.

2026-08-02 `KNOWLEDGE-01~03`에서 Windows PC-01~18 token stream에 출처 등급과 모델 일반지식 보충을 활성화했다. 2026-08-05에는 Linux U-01~U-67에도 같은 화면 계약을 적용해 AI 직접 출처를 `[1] 실제 확인값`·`[2] KISA 근거`·`[3] AI 일반 보안지식`으로 통일했다. 공식 판정 권한은 규칙 엔진에만 유지하고 관련 문장 뒤 인라인 번호와 항목별 한글 출처 목록을 연결한다. 내부 guide·chunk 식별자는 기술 추적 데이터에만 보존한다. 2026-08-06 Switch도 N-01~N-38에 같은 카드·Markdown·문장 뒤 인용 형식을 재사용한다. `[1]`은 실제 스위치 확인값, `[2]`는 KISA 2026 공식 원문 위치와 개발용 AOS-CX 판정 매핑, `[3]`은 AI 일반 보안지식이다. KISA 원문의 출처 등급과 아직 승인되지 않은 `0.4.0-DRAFT` Adapter/Audit Pack 상태를 함께 표시한다. 조직 보완 판정 입력은 KISA 원문이나 장비 증적이 아니므로 AI가 `[1]` 실제값으로 바꾸어 설명하지 않게 한다. 실제 외부 모델 E2E는 별도 전송 승인 뒤 검증한다.

### 6.2 제한형 Markdown

2026-08-02 `MARKDOWN-01~03` 후속에서 현재 `secai.restricted-markdown.v3` 제한 AST renderer와 sanitizer를 구현했다. 모델 delta는 다음 allowlist로 해석하며 실패하거나 100KB를 넘으면 일반 텍스트로 전환한다.

- 허용: 짧은 제목, 문단, 굵게, 기울임, 순서/비순서 목록, inline code, 열·행 상한이 있는 표
- 조건부 허용: `https` 또는 same-origin 링크, 고정된 `rel="noopener noreferrer"`
- 금지: raw HTML, image, iframe, style, script, event attribute, `javascript:`·`data:` URL, SVG와 자동 실행 code
- token을 누적한 원문 buffer를 짧은 간격으로 다시 파싱하고 정화한 결과만 DOM에 반영
- 완료 event에서 최종 parse를 한 번 더 수행
- parser 또는 sanitizer 실패 시 plain `textContent`로 즉시 fallback
- CSP와 Trusted Types는 추가 방어이며 sanitizer를 대체하지 않음

현재는 신규 외부 parser 의존성 없이 프로젝트 내부 고정 AST와 DOM API를 사용한다. allowlist와 sanitizer를 통과하지 않은 `innerHTML` 사용을 금지한다. 장기적으로는 모델이 Markdown을 임의 구성하게 하기보다 `sections[]` 구조화 출력 DTO를 만들고 UI가 heading·list DOM을 생성하는 방식을 우선한다.

## 7. Agent/MCP 승인형 조치 결정

### 7.1 역할

Agent는 다음을 할 수 있다.

- 취약 결과와 근거를 읽어 조치 후보 작성
- 영향·중단 가능성·권한·재부팅 필요 여부 설명
- 실행 전 현재값·예상 변경·rollback 계획 작성
- 승인된 조치 도구 호출 요청
- 실행 뒤 재점검과 전후 비교 설명

Agent는 다음을 할 수 없다.

- LLM이 만든 shell·PowerShell·CLI 문자열 직접 실행
- 규칙 엔진의 공식 Finding 수정
- 사용자 승인 없이 관리자 권한 취득
- 서명되지 않은 Remediation Pack 실행
- 다른 조직·자산·장비로 scope 확대
- 안전 검증 없이 `모두 자동 수정`

### 7.2 MCP 도구 경계

MCP는 범용 terminal 대신 다음과 같은 좁은 업무 도구를 제공한다.

- `assessment.get_result`
- `remediation.get_candidates`
- `remediation.preview`
- `remediation.request_approval`
- `remediation.apply_approved`
- `remediation.verify`
- `remediation.rollback`

각 tool은 JSON Schema, organization·asset·result version, action ID·version, precondition hash와 idempotency key를 검증한다. `apply_approved`는 LLM이 직접 승인할 수 없으며 Web UI의 재인증·역할·명시적 동의와 로컬/장비 Broker의 정책 확인을 모두 요구한다.

HTTP 기반 MCP는 OAuth 2.1 계열 권한, audience가 제한된 짧은 token, HTTPS, PKCE와 안전한 token 저장을 사용한다. 내부 로컬 stdio 방식은 credential을 명령 인자로 전달하지 않고 제한된 실행 환경에서만 사용한다.

### 7.3 조치 트랜잭션

모든 조치는 다음 상태를 갖는다.

```text
DRAFT_PLAN
→ PREVIEWED
→ USER_APPROVED
→ PRIVILEGE_APPROVED
→ APPLYING
→ VERIFYING
→ COMPLETED | FAILED | ROLLED_BACK | MANUAL_RECOVERY_REQUIRED
```

실행 전 snapshot·backup·precondition을 확인하고, 적용 뒤 같은 Control을 재점검한다. 예상값과 다르거나 연결이 끊기면 자동 성공으로 기록하지 않는다. Windows는 UAC가 있는 로컬 privileged broker, Linux는 exact sudoers action, Switch는 벤더가 지원하는 candidate/checkpoint/confirmed change와 사전 검증을 우선한다.

## 8. 데이터·감사 계약

새 Schema는 기존 migration을 수정하지 않고 새 version으로 추가한다.

- `asset_platform_profile`: 자산 종류·OS/NOS·version·capability
- `canonical_fact`: 플랫폼 중립 fact와 원본 Evidence locator
- `remediation_action`: 서명된 action ID·version·platform·precondition·apply·verify·rollback
- `remediation_plan`: 결과 version에 묶인 제안·위험·예상 영향
- `remediation_execution`: 승인자·실행자·시간·전후 hash·상태
- `mcp_tool_audit`: client·tool·scope·request hash·정책 결정·result hash

원본 credential, 전체 switch configuration, secret이 포함된 명령 출력과 LLM의 숨은 사고 과정은 저장하지 않는다.

## 10. 거부한 대안

### 10.1 하나의 범용 shell Agent

권한 범위, 명령 의미, 재현성, rollback과 감사가 보장되지 않으므로 거부한다.

### 10.2 Windows 규칙에 Linux·Switch 조건문 추가

증적 의미와 적용성, 공급자 version이 달라 회귀와 승인 범위를 통제할 수 없으므로 거부한다.

### 10.3 AI Markdown을 raw HTML로 바로 출력

모델·검색 문서·사용자 입력을 신뢰할 수 없고 DOM XSS 위험이 있으므로 거부한다.

### 10.4 점검과 동시에 자동 수정

증적이 바뀌고 서비스 중단·접속 상실이 발생할 수 있으며 사용자가 판단 전에 상태를 변경하므로 거부한다.

## 11. 결과와 trade-off

이 결정은 장비별 Adapter·Pack·Fixture와 조치 Pack을 추가로 관리해야 하므로 구현 속도가 느려진다. 대신 Windows MVP의 결정론·근거·권한·감사 경계를 유지하면서 Linux와 두 스위치 계열을 확장하고, LLM의 설명 능력과 Agent 자동화가 공식 판정·무승인 변경으로 번지는 것을 막는다.

## 14. 복수 기준 Profile 선행조건

Ubuntu/Rocky와 Cisco/Aruba를 확장하기 위한 ADR 20의 Profile·선택 이력·실행 snapshot·KISA 되돌리기 기반은 구현했다. 조직 승인·Audit Pack v2 서명은 남아 있다. 장비별 원본 증적과 canonical fact를 기준 Profile이 참조하도록 하며, 일반 사용자 Builder가 shell·PowerShell·NETCONF XML·REST payload를 직접 작성하거나 실행하지 않게 한다.

Linux·Switch의 개인 기준도 먼저 참고 결과로만 제공한다. 조직·공식 승격에는 제품·OS version, 수집 권한, 적용성, Fixture, false PASS, 서명과 폐기 절차가 필요하다. 이 선행조건은 플랫폼별 Adapter·Pack을 생략하거나 PC 규칙을 재사용하라는 뜻이 아니다.
