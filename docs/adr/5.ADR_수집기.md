# ADR-002: Windows One-shot Collector

## 현재 구현 상태 (2026-08-07 검토)

- Windows PC-01~PC-18 일반 수집과 동의형 관리자 5개 Probe, portable EXE·Launcher 연결이 개발 환경에서 동작한다.
- 현재 다운로드 파일은 조직 운영 서명이 아닌 `DEV-SIGNED-TEST`이며 clean Windows 10·11, 조직 Publisher·SmartScreen Release Gate는 남아 있다.
- Linux one-shot은 같은 안전 원칙을 따르지만 별도 Manifest·Package·sudo 동의 계약과 공용 x86_64 launcher로 구현돼 있다.
- 모든 Collector는 고정 argv, timeout·출력 상한·locale·redaction과 설정 diff 0을 유지하며 사용자 입력 command를 실행하지 않는다.

## 1. 결정 요약

Sec_AI의 최초 수집기는 **Windows 11 x64용 Python One-shot Collector**로 구현하고, 신뢰된 Windows 11 x64 build runner에서 **PyInstaller 단일 실행 파일**로 생성한다.

Collector는 설치형 Agent나 중앙 서버 컨테이너가 아니다. 사용자가 점검 시점에 실행하는 서명된 프로그램이며, 대상 시스템에서 승인된 읽기 전용 Probe를 실행한 뒤 구조화된 증적 패키지를 HTTPS로 제출하거나 오프라인 파일로 저장하고 종료한다.

| 결정 항목 | 확정 제안 |
|---|---|
| 최초 지원 OS | Windows 11 x64 |
| 실행 형태 | 설치하지 않는 One-shot 단일 EXE |
| 구현 언어 | CPython 3.14.6 일반 GIL build |
| 패키징 | PyInstaller 6.21.0, Windows x64 native build, one-file |
| 기본 권한 | 표준 사용자, 실행 manifest는 `asInvoker` |
| 관리자 권한 | 필요한 Probe만 별도 실행 안내; 자동·은닉 권한 상승 금지 |
| Probe 공급 | Collector release에 내장된 version 고정 allowlist |
| 주요 수집 경로 | Python Windows API, Registry, 고정 PowerShell, CIM/WMI, 승인된 Windows CLI |
| 실행 정책 | 읽기 전용, `shell=False`, 고정 executable·인수, timeout·출력 제한 |
| 판정 책임 | Collector는 증적만 생성하며 공식 `PASS/FAIL/REVIEW/ERROR/N/A`를 만들지 않음 |
| 결과 전달 | 인증된 HTTPS push 또는 오프라인 패키지 |
| 업데이트 | 자동 self-update 없음; 새 코드서명 release를 다시 배포 |
| 장기 상주 | 금지: service, scheduled task, startup 등록, inbound listener 없음 |

## 2. 배경과 목표

1차 MVP는 Windows 11의 KISA 2026 `PC-01`~`PC-18`을 평가한다. 중앙 서버가 사용자 PC에 직접 WinRM·PowerShell 명령을 실행하는 구조는 공격 표면과 자격증명 위험이 크고 폐쇄망에서도 사용할 수 없다.

One-shot Collector는 다음 목표를 만족해야 한다.

- 별도 Python 설치 없이 깨끗한 Windows 11 x64에서 실행
- 일반 사용자 권한으로 수집 가능한 항목을 우선 수집
- 관리자 권한이 필요한 항목과 조직 기준이 필요한 항목을 구분
- PowerShell, Registry, CIM/WMI 등을 이용해 자동화 가능한 증적을 구조화
- 네트워크 연결 여부와 관계없이 동일한 데이터 계약 사용
- 대상 설정을 변경하지 않고 실행 후 상주 구성요소를 남기지 않음
- 수집기·Probe·Manifest·Schema·Audit Pack 버전을 추적
- 패키지 변조, 만료, 재전송과 다른 자산·작업 제출을 서버에서 탐지

## 3. 적용 범위와 제외 범위

### 3.1 적용 범위

- Windows 11 x64 로컬 One-shot 실행
- KISA 2026 `PC-01`~`PC-18`에 필요한 최소 구조화 증적
- 합성 결과를 만드는 Mock Collector
- 표준 사용자 및 명시적 관리자 실행 profile
- 온라인 HTTPS 제출과 폐쇄망용 오프라인 결과 생성
- Collector EXE·Manifest·Probe·결과 패키지의 무결성 정보
- 개인정보·비밀정보 최소화와 안전한 로컬 로그

### 3.2 제외 범위

- Windows Server, Windows 10, Linux와 macOS 공식 지원
- 서비스 설치, 지속 모니터링, 자동 시작과 background polling
- Wazuh Agent, EDR 또는 원격 관리 Agent 대체
- 중앙 서버가 전달한 PowerShell·Shell·Python 코드 실행
- SSH, WinRM, SMB admin share를 이용한 중앙 직접 점검
- 사용자 동의 없는 UAC 상승 또는 자격증명 입력 자동화
- 설정 변경, 자동 조치, 레지스트리·정책 수정과 remediation 실행
- LLM 호출, RAG 검색 또는 공식 판정 생성
- PostgreSQL·pgvector, Redis, AIStor, Neo4j, vLLM 직접 접속
- 브라우저 기록, 사용자 문서 원문, 비밀번호·토큰·개인키 수집

## 4. 실행 및 신뢰 흐름

```text
서버가 Job과 만료되는 서명 Manifest 발급
→ 사용자가 서명된 Collector EXE와 Manifest 준비
→ Windows가 EXE Authenticode 서명 검증
→ Collector가 내장 공개키로 Manifest 서명·만료·대상·nonce 검증
→ 지원 OS, Collector 호환 version과 현재 권한 확인
→ 실행할 Control·Probe와 권한 요구사항을 사용자에게 표시
→ 내장 allowlist에서 Probe ID와 version을 선택
→ 읽기 전용 수집, timeout·출력 크기 제한, 민감정보 최소화
→ 구조화 증적과 실행 오류를 패키징
→ 파일별·전체 hash와 인증 profile 기록
→ 인증된 HTTPS push 또는 오프라인 파일 저장
→ 메모리·임시파일 정리 후 종료
→ 서버가 악성코드·Schema·hash·인증·nonce·자산·중복을 재검증
→ 중앙 규칙 엔진만 공식 Finding 상태 확정
```

Collector가 Manifest를 검증하더라도 서버는 결과를 신뢰한 것으로 간주하지 않는다. 서버는 모든 경계 검증을 독립적으로 다시 수행한다.

## 5. Manifest와 Probe 신뢰 모델

### 5.1 역할 분리

| 구성요소 | 허용 책임 | 금지 책임 |
|---|---|---|
| Server Manifest | Job·자산·Control·Probe ID, 만료, nonce, 제출 위치와 요구 권한 지정 | 실행할 명령 문자열·script body 전달 |
| Collector | Manifest 검증, 내장 Probe 실행, 증적 최소화·패키징 | Audit Pack 규칙 판정, 임의 코드 실행 |
| Probe | 하나의 version 고정 읽기 전용 수집 계약 수행 | 설정 변경, 자격증명 수집, 공식 Finding 생성 |
| Audit Pack | 적용성·증적 요구·결정론적 판정 규칙 정의 | Collector EXE에 새 실행 코드를 동적 주입 |
| Rule Engine | 검증된 증적과 승인 규칙으로 공식 상태 확정 | 대상 PC에서 명령 실행 |

### 5.2 내장 allowlist

- 각 Probe는 변경되지 않는 `probe_id`, `probe_version`, 지원 OS·Build 범위와 요구 권한을 가진다.
- allowlist에는 executable의 canonical absolute path, 고정 인수 template, 허용 출력 형식, timeout, 최대 출력 크기와 민감정보 필드가 포함된다.
- Manifest는 내장된 Probe ID와 고정된 parameter enum만 선택할 수 있다. 자유 형식 command, path, Registry key, WMI query 또는 PowerShell text를 전달할 수 없다.
- allowlist에 없거나 version이 맞지 않는 Probe는 `PROBE_NOT_ALLOWED`로 거부한다.
- 새 Probe나 실행 로직 변경은 Collector를 새로 build·서명·배포한다. Audit Pack 변경만으로 대상 PC의 실행 코드가 바뀌지 않는다.

### 5.3 Probe 구현 우선순위

1. Python 표준 library와 Windows API의 읽기 전용 호출
2. `winreg` 등 명시적인 Registry 읽기
3. 고정 PowerShell/CIM 명령의 JSON 출력
4. 출력 형식이 안정적인 승인 Windows 기본 CLI
5. 제품별 read-only Adapter

PowerShell은 주 실행 언어가 아니라 필요한 경우에만 사용하는 Probe Adapter다. 프로필과 사용자 module 영향을 제거하고, 고정된 script 또는 명령만 비대화형으로 실행한다. 서버 입력을 command line에 삽입하지 않는다.

## 6. Process 실행 안전 기준

외부 process를 사용하는 Probe는 다음을 모두 지킨다.

- Python `subprocess`에서 `shell=False` 사용
- `cmd.exe /c`, `powershell -EncodedCommand`, `Invoke-Expression`, 동적 script download 금지
- executable은 Windows system directory 또는 승인된 제품 path의 canonical path로 고정
- 인수는 문자열 조립이 아닌 고정 list로 전달
- 작업 directory와 필요한 환경변수를 명시하고 사용자 `PATH` 우선 탐색 금지
- PowerShell은 `-NoProfile`, `-NonInteractive`와 고정 코드 경로 사용
- stdout과 stderr를 분리하고 UTF-8/UTF-16 등 예상 encoding을 엄격하게 처리
- Probe별 timeout, process tree 종료, 최대 출력 bytes와 parser depth 제한
- exit code, timeout, parse 결과와 요구 권한을 구조화하여 기록
- 실행 command의 비밀값 없는 식별 정보만 감사 가능하게 기록하고 원문 전체 로그 남발 금지

초기 제한값은 Probe metadata에서 관리한다. 기본 timeout은 30초, 개별 승인 상한은 120초, 단일 stream 출력 상한은 1 MiB로 시작하고 실제 Windows 11 Fixture 측정 후 변경한다. 제한 변경은 Probe version 증가와 회귀시험을 요구한다.

## 7. 권한 모델

### 7.1 기본 실행

- Collector 실행 manifest는 `asInvoker`로 만들고 일반 사용자 권한을 기본값으로 한다.
- 현재 token의 사용자 SID, integrity level, elevation 여부와 관리자 group membership을 구분한다.
- PC-16 같은 사용자 범위 정책은 해당 사용자의 로그인 session에서 수집한다.
- 다른 사용자의 미로드 Registry hive를 `reg load`로 강제 연결하지 않는다.
- 관리자 권한이 없다는 이유로 UAC 우회, service 생성, scheduled task 생성 또는 credential prompt 자동화를 수행하지 않는다.

### 7.2 관리자 Probe

- `2.MVP_점검항목_매트릭스.md`에서 `A`가 필요한 Probe는 실행 전에 이유, 수집 항목과 예상 시간을 표시한다.
- 표준 사용자 실행에서 관리자 Probe는 실행하지 않고 `PERMISSION_DENIED`와 `requires_elevation=true`를 기록한다.
- 관리자가 명시적으로 다시 실행한 결과는 별도 `execution_attempt_id`와 package로 제출한다.
- 일반 권한 package와 관리자 package는 서버가 같은 Job 아래에서 검증·집계하며, 로컬 process 사이에 관리자 token이나 결과 파일을 공유해 권한 경계를 우회하지 않는다.
- 권한 부족은 Collector의 collection error이며 취약 설정을 의미하는 `FAIL`이 아니다.

### 7.3 조직 기준과 수동 증적

`+O`가 있는 Control의 기관 기준·예외·절차 문서는 Collector가 사용자 디스크에서 탐색하거나 수집하지 않는다. Manifest는 승인된 정책의 ID와 version만 참조하며, 수동 증적은 인증된 중앙 UI의 별도 흐름에서 제출·승인한다.

## 8. 증적과 판정 경계

Collector는 다음 공통 필드를 가진 최소 구조화 증적을 생성한다.

- `control_id`, `guide_version`
- `job_id`, `asset_id`, `manifest_id`, `manifest_hash`, `nonce`
- `collector_version`, `probe_id`, `probe_version`
- OS product·edition·version·build·UBR·architecture
- `execution_attempt_id`, 실행 identity 유형, 사용자 SID, elevation 여부
- `collected_at`, timezone와 로컬 clock 상태
- source type·provider·path, raw value, normalized value와 unit
- policy scope·source·effective value
- `collection_status`, `error_code`, redaction 여부
- 개별 evidence SHA-256와 package hash

`raw_value`는 명령 stdout 전체가 아니라 판정에 필요한 최소 구조화 값이다. PC-12의 `DefaultPassword`처럼 민감한 값은 내용이 아닌 존재 여부만 기록한다. 사용자 이름 대신 필요한 범위에서 SID를 사용하고, hostname·serial·MAC 주소는 자산 연결 정책이 승인한 경우에만 수집한다.

Probe 또는 Collector가 진단용 후보 상태를 계산하더라도 이를 공식 Finding으로 내보내지 않는다. 공식 `PASS`, `FAIL`, `REVIEW`, `ERROR`, `N/A`는 서버의 승인된 Audit Pack 규칙 엔진만 생성한다.

## 9. 결과 패키지와 인증 profile

### 9.1 공통 패키지 요구사항

- JSON Schema version과 Collector 호환 version
- Manifest 원본 또는 검증 가능한 참조와 hash
- 증적 JSON, 오류 JSON, 파일별 hash 목록과 package 전체 hash
- 생성 시각, 만료, nonce, Job·Asset·실행 attempt 식별자
- Collector·Probe build provenance와 인증 profile
- UTF-8, 경로 traversal이 불가능한 고정 package layout
- 압축 해제 전후 size, file count와 nesting 제한

단순 SHA-256은 무결성 비교값이지 전자서명이 아니다. package 인증은 다음 profile 중 하나를 명시해야 한다.

| Profile | 사용 상황 | 서버 처리 |
|---|---|---|
| `ONLINE-AUTHENTICATED` | Collector가 인증된 HTTPS session에서 단기 Job credential로 직접 push | TLS·credential·nonce·hash·자산 권한 검증 후 수신 |
| `OFFLINE-SIGNED` | 조직이 발급한 사용자·장비 인증서의 non-exportable private key를 사용할 수 있음 | 인증서 chain·용도·폐기·서명·nonce 검증 후 수신 |
| `OFFLINE-USER-SUBMITTED` | 관리되지 않은 장비로 서명 identity가 없음 | 암호화·hash·Manifest 검증과 인증 사용자 귀속 후 낮은 assurance로 수신; 공식 판정 사용 여부는 인증 ADR에서 확정 |

Collector EXE 안에 장기 shared secret이나 package-signing private key를 넣지 않는다. 실행 시 생성한 self-signed key만으로 조직이 인증한 장비 서명이라고 주장하지 않는다.

오프라인 package의 exact archive, 서명·암호화 envelope와 algorithm은 `database/schemas` 및 인증 ADR에서 확정한다. 확정 전 개발용 package는 실제 운영 서명 완료로 표시할 수 없다.

### 9.2 온라인 전송

- Collector가 시작하는 outbound HTTPS만 허용하고 inbound port를 열지 않는다.
- TLS 인증서 검증을 비활성화하거나 자체 판단으로 오류를 무시하지 않는다.
- 제출 endpoint는 build 또는 서명 Manifest의 승인 origin에서만 선택한다.
- Job credential은 단기·최소권한·단일 자산·단일 Job 범위로 제한하고 로그나 package에 평문 저장하지 않는다.
- 실패 시 무한 재시도하지 않고 제한된 backoff 후 오프라인 저장 선택지를 제공한다.

## 10. 로컬 파일과 정리

- 작업 directory는 접근 제어된 사용자 임시 directory 아래에 무작위 이름으로 생성한다.
- junction, symlink, reparse point와 예상 밖 path를 거부하고 package output과 임시 path를 분리한다.
- 기존 output을 자동 덮어쓰지 않으며 사용자가 명시한 허용 directory에 새 파일로 저장한다.
- 성공·실패 후 임시 평문 증적을 정리한다. 삭제 성공을 보장할 수 없는 경우 로그에 남기고 비밀정보를 애초에 쓰지 않는 설계를 우선한다.
- 암호학적 secure erase를 보장한다고 주장하지 않는다. SSD·filesystem 특성상 필요한 경우 조직의 매체 정책을 적용한다.
- 로컬 로그에는 token, Manifest credential, 사용자 문서 내용, 전체 Registry export와 원시 command output을 남기지 않는다.

### 11.2 Build 원칙

- Linux·Wine·비승인 host의 cross-build 결과를 배포하지 않는다.
- source commit, lockfile hash, Python·PyInstaller version, runner image ID와 build time을 manifest에 기록한다.
- UPX나 승인되지 않은 binary packer를 사용하지 않는다.
- build input을 잠그되 Authenticode timestamp 등의 이유로 byte-for-byte 재현 가능하다고 과장하지 않는다.
- 서명 전 hash와 Authenticode 서명·timestamp 후 배포 hash를 모두 기록한다.
- SBOM, dependency vulnerability scan, secret scan, 악성코드 검사와 clean VM 실행 결과를 release에 연결한다.
- 조직 코드서명 인증서의 private key는 repository나 일반 CI secret file에 두지 않고 승인된 HSM·managed signing service 등 non-exportable 방식으로 보호한다.
- 조직 인증서가 준비되지 않은 개발 build는 `DEV-UNTRUSTED`로 표시하고 운영 배포하지 않는다.

### 11.3 사용자 검증 가능성

배포 페이지와 release manifest는 최소한 다음을 제공한다.

- 파일명, version, size와 SHA-256
- Authenticode publisher와 서명 검증 방법
- 지원 OS·architecture, 발행·만료·폐기 정보
- 수집 범위와 요구 권한
- offline 검증 절차와 문의·신고 경로

Collector는 self-update하지 않는다. 새 version은 별도 서명 artifact로 배포하고 이전 version의 허용·거부 기간은 서버 호환 정책으로 통제한다.

|---|---|---|

## 14. Version 및 호환성 정책

- Collector release는 SemVer 형태의 product version과 별도 build ID를 가진다.
- Probe의 의미·필드·권한·source가 바뀌면 `probe_version`을 증가시킨다.
- Schema major version 불일치, 서명되지 않은 Manifest, 지원 범위를 벗어난 Collector는 안전하게 거부한다.
- Server Manifest는 최소·최대 Collector version과 필요한 Probe version을 선언한다.
- Collector는 알 수 없는 필드를 임의 실행 parameter로 해석하지 않는다.
- 과거 package 재판정은 당시 Collector·Probe·Schema·Audit Pack version과 원본 hash를 보존해 수행한다.

## 15. 보안 한계

One-shot Collector는 실행 당시 OS가 제공하는 값을 관찰한다. 대상 PC가 이미 관리자 malware, kernel rootkit 또는 보안 제품 변조에 장악된 경우 거짓 값을 반환할 수 있으며, Collector만으로 이를 완전히 증명할 수 없다.

따라서 결과는 다음 맥락과 함께 해석한다.

- 코드서명은 Collector 배포물의 출처와 변경 여부를 확인하지만 대상 OS의 신뢰성을 보증하지 않는다.
- hash는 변경 비교값이며 신뢰된 identity의 전자서명을 대신하지 않는다.
- 일반 사용자 One-shot 결과, 관리자 결과, 조직 인증 장비 결과의 assurance를 구분한다.
- 고신뢰 운영환경은 EDR/Wazuh, 조직 PKI, Secure Boot·TPM 상태와 별도 검증을 결합할 수 있다.

## 16. 검토한 대안

| 대안 | 결정 | 이유 |
|---|---|---|
| Python + PyInstaller One-shot | 채택 | 기존 Runtime·Schema code 재사용, Windows 기본 수집 연계, 설치 없는 배포 |
| PowerShell script package만 배포 | 채택하지 않음 | 실행 정책·변조·의존성·일관된 package 보안 및 parser 관리가 어려움 |
| 처음부터 Wazuh Agent 설치 | 1차 MVP 제외 | 설치·등록·지속 운영 부담이 크며 비관리·폐쇄망 장비를 포괄하지 못함 |
| Go 또는 Rust 단일 binary | 보류 | 작은 runtime과 배포 장점이 있으나 현재 팀·공통 Schema·기존 Python 결정 대비 초기 구현 비용이 큼 |
| 관리자 권한 필수 EXE | 채택하지 않음 | 모든 Probe에 과도한 권한을 부여하고 사용자 범위 정책 관찰을 왜곡할 수 있음 |
| 서버 원격 명령 실행 Agent | 채택하지 않음 | 임의 명령·자격증명·인바운드 통신의 공격 표면이 커짐 |
| Python source와 Runtime 배포 | 채택하지 않음 | 대상 PC dependency와 변조·재현성 관리 부담 증가 |

## 17. 결과와 trade-off

### 17.1 기대 효과

- 설치와 장기 상주 없이 Windows 11 및 폐쇄망 점검 가능
- Probe allowlist와 표준 사용자 기본 실행으로 공격 표면 축소
- Python·Schema·검증 code를 중앙 서비스와 공유 가능
- Control Matrix의 `AUTO`, `AUTO-CONDITIONAL`, `AUTO-APPLICABILITY` 증적 수집 지원
- 버전·hash·서명과 원문 근거를 Finding까지 역추적 가능

### 17.2 비용과 위험

- PyInstaller one-file의 크기, 시작 지연과 보안 제품 오탐을 시험해야 함
- PowerShell/CIM 출력과 권한은 Windows Edition·Build·GPO·MDM에 따라 달라질 수 있음
- 일반 권한과 관리자 권한 package 집계가 데이터 계약을 복잡하게 함
- offline identity와 package 인증 수준을 조직 PKI 유무에 따라 구분해야 함
- 새 Probe마다 Collector 재build·코드서명·배포가 필요함
- 대상 OS가 이미 장악된 경우 증적 진실성을 Collector 단독으로 보장할 수 없음

## 18. 구현 및 승인 Gate

다음 조건을 통과해야 ADR 구현을 완료한 것으로 본다.

1. Mock Collector와 첫 세로 기능인 PC-07 Probe 구현
2. `database/schemas`의 Manifest·Package·Evidence 정상/비정상 Fixture 계약시험 통과
3. Windows 11 x64 기준 VM에서 일반 사용자·관리자 권한 matrix 실측
4. PC-01~PC-18의 필수 증적에 대응하는 Probe Coverage 표 작성
5. `shell=False`, allowlist, timeout, 출력·parser 제한의 단위·보안시험 통과
6. 권한 부족·timeout·잘못된 encoding·큰 출력이 `FAIL`로 오판되지 않음
7. 온라인 upload와 네트워크 차단 시 offline 생성시험 통과
8. 만료·변조·재전송·다른 자산 package를 서버가 거부
9. CPython 3.14.6·잠긴 requirements로 Windows native PyInstaller build 성공
10. clean Windows 11 VM에서 별도 Runtime 없이 EXE 실행
11. SBOM·hash·악성코드·vulnerability scan과 Authenticode 서명 검증
12. 대상 설정·service·scheduled task·startup·방화벽 상태의 실행 전후 diff가 없음
13. 코드서명 key 보관과 offline package 인증 profile을 보안·운영 책임자가 승인

### 18.1 IMP-029 구현 확인

2026-07-23 `IMP-029`에서 Gate 1의 PC-07 읽기 전용 Probe와 Gate 6의 기본 오류 분리를 구현했다. 현재 Windows 11 x64에서 OS·Build·관리자 토큰 여부·SID 형식과 `win.storage.disks`, `win.storage.partitions`, `win.storage.volumes`를 실제로 읽었다. 실제 SID·호스트명·volume label·파일 목록은 저장하지 않았고 자동 상승·설정 변경·공식 Finding 생성은 없었다.

다만 이 확인만으로 ADR 전체 구현이 완료된 것은 아니다. 일반 사용자/관리자 matrix, process tree timeout·streaming output hard cap·설정 diff 0, PC-01~18 Coverage, online/offline 제출, PyInstaller·SBOM·Authenticode Gate는 `IMP-030~035`에서 계속 검증한다. 상세 기록은 `deploy/verification/IMP029_Windows_PC07_읽기전용_검증.md`를 따른다.

### 18.2 IMP-030 구현 확인

2026-07-23 `IMP-030`에서 검증된 실행 계획을 일반 사용자와 관리자 Probe로 분리했다. 관리자 대상은 항목·이유 안내와 명시적 사용자 동의 없이는 시작하지 않으며 자동 UAC 상승을 사용하지 않는다. 현재 PC-07 세 Probe는 모두 일반 권한이라 실제 Windows 실행에서 관리자 process는 시작되지 않았다.

Probe 실행에는 30초 timeout과 stdout·stderr 각각 65,536 bytes의 streaming hard cap을 적용한다. timeout·출력 초과 시 방금 시작한 정확한 자식 PID의 process tree만 종료한다. 실행 전후 PowerShell execution policy, disk flag, partition layout, volume filesystem과 BitLocker 상태를 읽기 전용으로 Snapshot 처리했으며 실제 Windows에서 차이 0건을 확인했다. 권한 부족·timeout·출력 초과·Snapshot 실패는 취약 `FAIL`로 바꾸지 않고 수집 오류 또는 안전 Gate 거부로 처리한다.

이로써 Gate 5의 실행 제한, Gate 6의 오류/판정 분리와 Gate 12의 PC-07 범위 설정 diff 0을 구현했다. Gate 3의 실제 관리자 Probe matrix, PC-01~18 Coverage, online/offline 제출, PyInstaller·SBOM·Authenticode는 `IMP-031~035`에 남아 있다. 상세 기록은 `deploy/verification/IMP030_권한_점검_안전성_검증.md`를 따른다.

### 18.3 IMP-031 구현 확인

2026-07-23 `IMP-031`에서 `0.6.0 DRAFT` Pack의 PC-01~18 host 요구를 20개 native Probe exact allowlist로 연결했다. 일반 권한 15개와 관리자 권한 5개로 분리했으며, 현재 Windows에서 일반 15개를 모두 실제로 읽고 설정 diff 0을 확인했다. 관리자 script는 이미 동의받은 별도 관리자 process가 아니면 거부하며 자동 UAC를 사용하지 않는다.

제품 Adapter는 기존 DRAFT catalog의 Microsoft Defender Antivirus와 Windows Firewall만 host 실행에 허용한다. synthetic third-party Adapter와 catalog 미등록 제품은 실제 host PASS 근거가 될 수 없다. PC-06은 승인 messenger catalog가 없어 inventory-only이고, 기관 정책과 `reference.windows-patch-baseline`·`reference.windows-lifecycle`은 host fact와 분리했다.

이로써 Gate 4의 PC-01~18 Probe Coverage 표와 일반 권한 실제 수집을 구현했다. Gate 3의 clean VM 관리자 5개 실측, 전체 normalized evidence 생성, online/offline 제출, PyInstaller·SBOM·Authenticode는 후속 IMP에 남아 있다. 상세 기록은 `deploy/verification/IMP031_PC01_PC18_점검_어댑터_범위.md`를 따른다.

### 18.4 IMP-032 구현 확인

2026-07-23 `IMP-032`에서 `ONLINE-AUTHENTICATED` 제출용 단기 Job credential과 Package commit 경계를 구현했다. credential은 256-bit 이상 opaque secret이며 기본 60분·최대 2시간, Organization·Asset·Job·Manifest ID/content hash·nonce·endpoint·Content-Type·schema version·최대 archive 크기에 정확히 묶인다. 서버 record에는 원문이 아니라 key version이 있는 HMAC-SHA256만 저장한다.

기존 `FullPackageValidator`가 Schema·ZIP·hash·scope·Manifest signature·staging·악성코드·content policy를 모두 통과시킨 뒤에만 credential과 nonce를 원자적으로 한 번 사용 완료 처리한다. 잘못된 Package는 성공 사용으로 소비하지 않으며 credential 재사용, 같은 nonce의 두 번째 credential, 만료, 취소, 다른 Asset·Manifest를 fail-closed로 거부한다.

현재는 로그인·Job RBAC가 없어 실제 발급·업로드 HTTP endpoint를 열지 않았다. DEV 인수는 비식별 합성 ZIP과 process-local memory store를 사용하며 Pilot에서는 PostgreSQL 원자 저장·HTTPS·감사 Event가 필수다. 상세 기록은 `deploy/verification/IMP032_온라인_인증_제출.md`를 따른다.

### 18.5 IMP-033 구현 확인

2026-07-23 `IMP-033`에서 `OFFLINE-SIGNED`와 `OFFLINE-USER-SUBMITTED` core 접수 경계를 구현했다. 서명 Profile은 Ed25519와 RFC 8785 JCS를 사용하고, 서버에 고정한 조직 루트·전용 EKU·Organization subject·Asset SAN·유효기간과 접수 시각 기준 24시간 이내의 폐기 확인 자료를 검증한다. Organization·Asset·Job·Manifest·nonce·실행 식별자·Package/ZIP hash 등 12개 payload 값이 Descriptor와 Manifest에 정확히 묶여야 `MEDIUM`으로 접수한다.

사용자 제출 Profile은 활성 로그인 session·CSRF·Asset/Job 권한을 요구하지만 장치 신원을 증명하지 못하므로 `LOW`로 고정한다. 두 Profile은 Organization·Asset·Job·nonce replay key를 공유해 제출 방식을 바꾼 이중 제출도 거부한다. 기존 `FullPackageValidator`의 Schema·ZIP·hash·staging·악성코드·content policy Gate는 동일하게 재사용한다.

DEV 인수용 인증서와 개인키는 실행 중 메모리에서만 임시 생성하고 source·결과·파일에 저장하지 않았다. 실제 조직 인증서, 원본 증적, 운영 POST endpoint와 공식 Finding은 없다. Pilot 전에는 조직 CA·non-exportable 장치 key, PostgreSQL 원자 replay 저장, 실제 session·CSRF·RBAC, HTTPS와 감사 Event가 필요하다. 상세 기록은 `deploy/verification/IMP033_오프라인_패키지_제출.md`를 따른다. Native build·SBOM과 Authenticode는 `IMP-034~035`에 남아 있다.

### 18.6 IMP-034 구현 확인

2026-07-23 Windows 11 x64에서 CPython `3.14.6`, PyInstaller `6.21.0`과 `requirements/lock/collector-build.lock`의 hash-locked 24개 dependency로 `SecAI-Collector-Windows-x64.exe`를 native one-file build했다. 최신 결과는 PE32+ AMD64 10,674,908 bytes이며 frozen self-check에서 Python Runtime, target architecture와 포함 자료 40개의 크기·SHA-256을 확인했다.

CycloneDX JSON SBOM과 pip-audit dependency set가 lock의 exact name·version과 일치했고 알려진 취약점은 0건이었다. 같은 artifact SHA-256 `050d1237a2b30954720d8f218d95ff41645fe6c04604410f009a5018b972430e`를 대상으로 ClamAV와 Microsoft Defender가 모두 `CLEAN`을 반환했다. manifest, `SHA256SUMS.txt`, build context, SBOM, vulnerability·malware scan 영수증과 10개 인수 기준 결과는 timestamp가 붙은 `runtime/imp034-artifacts` 하위에 생성한다.

현재 build는 의도적으로 `DEV-UNSIGNED`다. self-check만 제공하고 실제 수집 command, 자동 권한 상승, 설정 변경, 공식 Finding, Web 다운로드와 이동 묶음은 제공하지 않는다. Gate 9와 Gate 11의 SBOM·hash·악성코드·취약점 부분은 완료됐지만 Authenticode, 인증서 chain·폐기, clean VM의 최종 실행·관리자 5개 실측은 남아 있다. 상세 기록은 `deploy/verification/IMP034_Windows_실행파일_빌드_검증.md`를 따른다.

### 18.7 IMP-035 개발 구현 확인

2026-07-23 `DEV-EPHEMERAL-AUTHENTICODE` Profile로 Authenticode pipeline을 구현했다. 최신 unsigned 입력 SHA-256 `050d1237a2b30954720d8f218d95ff41645fe6c04604410f009a5018b972430e`에 RSA 3072·SHA-256·Code Signing EKU의 non-exportable self-signed 개발 키와 외부 timestamp를 적용했다. 서명 후 SHA-256은 `4a41267022faff84c5aa4a16a5dcb51356c8678a3eecd144c16755c057858a5c`다.

서명 후 한 byte 변조는 Windows Authenticode `HashMismatch`로 거부됐고 frozen self-check, ClamAV와 Microsoft Defender 재검사도 통과했다. 개발 인증서와 private key는 검증 뒤 제거했고 개발 root를 Windows trust store에 남기지 않았다. 따라서 clean PC의 `UnknownError/UntrustedRoot`는 예상 경계이며 이 파일을 운영 배포본으로 바꾸지 않는다.

구현 기준 12개는 통과했지만 Gate 10과 11 전체는 아직 완료되지 않았다. 조직 code-signing 인증서·승인된 Publisher, 운영 CRL/OCSP와 clean Windows 11 VM·SmartScreen 인수는 `DEFERRED`다. 이 세 항목을 실행하기 전에는 다운로드와 운영 배포를 열지 않는다. 상세 기록은 `deploy/verification/IMP035_Authenticode_수집기_인수.md`를 따른다.

## 21. 다중 플랫폼 후속 Collector 경계

Linux와 Switch 지원은 Windows EXE 내부에 분기문으로 붙이지 않는다.

- Linux는 비권한 읽기 전용 Probe와 선택적 `sudo` Probe를 분리하고 배포판·version을 manifest에 고정한다.
- Switch는 Cisco IOS XE와 HPE Aruba AOS-CX용 Adapter를 분리하며 구조화된 NETCONF/RESTCONF/REST 응답을 canonical evidence로 변환한다.
- SSH CLI fallback이 필요하면 승인된 명령 allowlist, prompt/locale/paging 처리, secret redaction과 transcript hash를 별도 Gate로 둔다.
- 수집 계정에는 구성 변경 권한을 주지 않고 `show/get`에 해당하는 최소 read-only 권한만 부여한다.
- Agent/MCP 조치는 Collector 프로세스와 분리한다. Collector는 계속 읽기 전용이며 임의 shell·PowerShell·SSH 명령을 실행하지 않는다.

상세 플랫폼·조치 계약은 제안 ADR 19와 `docs/plans/플랫폼_확장_및_보조_조치_계획.md`를 따른다.
