# Sec_AI 수집기·판정·점검 기준 유지보수 상세 가이드

| 항목 | 내용 |
|---|---|
| 기준일 | 2026-08-07 현재 기능 기준 |
| 대상 | Windows 10·11, Linux 6종 Catalog, Aruba AOS-CX 10.13, Windows 공개 취약점 후보 비교 |
| 목적 | 수집기 파일, 수집 방식, 판정 규칙, 기준 변경과 신규 항목 추가 절차를 한 문서에서 추적 |
| 현재 판정 성격 | 개발용 DRAFT 결과 |
| 운영 공식 Audit Pack | 없음 |
| 공식 Finding 생성 | 금지 |

이 문서는 현재 저장소의 실제 source와 최신 검증 기록을 기준으로 작성한다. 기능 상태가
`LIVE`라고 표시되더라도 개발 환경에서 실제 경로가 동작한다는 뜻이며, 운영 승인이나 공식
Audit Pack 승인을 뜻하지 않는다.

---

## 1. 먼저 알아야 할 핵심 원칙

### 1.1 수집기와 판정기는 분리되어 있다

Collector와 플랫폼 Adapter는 현재 상태를 읽어 Evidence 또는 비식별 fact를 만드는 역할만
한다. Collector가 설정을 변경하거나 공식 취약 상태를 만들지 않는다.

```text
사용자·조직 기준 선택
  + 승인된 Manifest·실행 계획
  + 대상 자산·권한 범위
        ↓
읽기 전용 Collector / Adapter
        ↓
Evidence, 수집 상태, 원본 hash
        ↓
Package·Schema·서명·범위·nonce 검증
        ↓
정규화된 fact 또는 플랫폼 projection
        ↓
결정론적 규칙 엔진
        ↓
PASS / FAIL / ERROR / REVIEW / N/A
        ↓
DRAFT 결과·실행 시점 기준 snapshot·hash 저장
        ↓
선택적인 AI 설명
```

공식 상태를 만들 수 있는 주체는 승인·서명된 Audit Pack과 결정론적 규칙 엔진뿐이다.
현재 Windows, Linux, Switch Pack은 모두 DRAFT이므로 운영 공식 Finding을 만들지 않는다.

### 1.2 상태 의미

| 상태 | 의미 | 사용하면 안 되는 경우 |
|---|---|---|
| `PASS` | 필요한 증적이 모두 있고 기준 충족이 입증됨 | 일부 자료만 성공했거나 parser가 이해하지 못한 경우 |
| `FAIL` | 필요한 증적이 있고 기준 위반이 입증됨 | 권한 부족, timeout, 미지원, 명령 실패 |
| `ERROR` | 필수 자료 수집·검증·정규화에 실패함 | 설정값이 취약하다는 의미로 사용하면 안 됨 |
| `REVIEW` | 자료는 있으나 조직 정책·업무 목적·외부 기준이 더 필요함 | 근거 없이 임의 PASS로 줄이면 안 됨 |
| `N/A` | 명시적 적용성 규칙으로 해당 기능이 적용되지 않음 | 단순 수집 실패나 기능 미확인 |

Package 서명, hash, scope 또는 nonce 검증이 실패하면 Control `ERROR`로 바꾸지 않고 Package
전체를 판정 전에 거부한다. 거부된 Package는 정규화·규칙 실행·Finding 저장 단계로 넘어가지
않는다.

| 플랫폼 | 실제 수집 단위 | 현재 기준 | 공식 Finding |
|---|---:|---|---|
| Windows 11 | PC-01~18, native Probe 20개 | `0.6.0 DRAFT` | 생성하지 않음 |
| Windows 10 | PC-01~18 공통 Probe | `SUPPORTED`·DRAFT | 생성하지 않음 |
| Ubuntu 24.04 | 고정 명령 42개 → U-01~U-67 | `2026-DRAFT` | 생성하지 않음 |
| Rocky Linux 9 | 고정 명령 42개 → U-01~U-67 | `2026-DRAFT` | 생성하지 않음 |
| Ubuntu 22.04·Debian 12·AlmaLinux 9 | 계열별 고정 명령 42개 → U-01~U-67 | `SUPPORTED`·DRAFT | 생성하지 않음 |
| RHEL 9 | RHEL 계열 고정 명령 42개 → U-01~U-67 | 공식 구독 image 인수 전 `PILOT`·DRAFT | 생성하지 않음 |

### 2.1 Package 검증 순서

Windows 제출 경로와 Linux one-shot 제출 경로는
[`FullPackageValidator`](../../src/security_audit/analysis/package_validation/full_validator.py)를
사용한다.

검증 순서는 다음과 같다.

1. Descriptor를 strict JSON으로 읽는다.
2. Descriptor Schema를 검증한다.
3. 신뢰된 Manifest Schema를 검증한다.
4. Manifest의 canonical content hash를 다시 계산한다.
5. 외부 Manifest signature 검증 결과를 확인한다.
6. 발급·만료 시간, Job, Asset, endpoint scope를 확인한다.
7. nonce가 Manifest와 일치하는지, 이미 사용된 nonce인지 확인한다.
8. 압축 파일 크기와 SHA-256을 Descriptor와 비교한다.
9. staging object가 같은 organization·asset·job·hash에 결합됐는지 확인한다.
10. 악성코드 검사와 content policy 결과를 확인한다.
11. ZIP 경로, 파일 수, 개별 크기, 압축 해제 크기와 hash를 확인한다.
12. 내장 Manifest가 신뢰된 Manifest와 정확히 일치하는지 확인한다.
13. 모든 Gate가 성공한 경우에만 `ValidatedPackage`를 반환한다.

정규화기는 `ValidatedPackage.eligible_for_original_promotion`이 참인 Package만 받는다. Probe
ID와 Probe version 조합이 등록되지 않았거나 raw field가 exact 목록과 다르면 정규화를 거부한다.

### 3.2 권한과 실행 순서

Windows 실행 계획은 일반 권한과 관리자 권한을 섞지 않는다.

1. 일반 권한 15개 Probe를 실행한다.
2. 일반 결과를 먼저 보존한다.
3. 관리자 항목 5개와 권한이 필요한 이유를 화면에 표시한다.
4. 사용자가 항목을 선택하고 별도 동의한다.
5. 제품이 Windows UAC를 한 번 요청한다.
6. 관리자 child가 선택된 exact Probe만 실행한다.
7. 관리자 실행 취소·실패 시 일반 결과는 유지한다.
8. 관리자 결과가 성공하면 Control ID별 allowlist 병합 후 canonical hash를 다시 계산한다.

각 Probe의 timeout 상한은 30초, 출력 상한은 65,536 bytes다. PowerShell은
`-NoLogo -NoProfile -NonInteractive`로 실행한다. 일반 Script는 SHA-256으로 고정한 source만
표준 입력으로 전달하고, 관리자 Script는 고정 파일과 검증된 Probe ID CSV만 받는다.

### 3.4 Control별 판정 규칙

#### PC-01 비밀번호의 주기적 변경

- 유효 `maximum_password_age_days`가 1~90이면 `PASS`다.
- 0은 무제한으로 해석해 `FAIL`이다.
- 90일을 초과해도 `FAIL`이다.
- 수집 실패 또는 정책값 해석 실패는 `ERROR`다.
- 사용자 Profile의 최대 기간은 별도 추가 기준 비교에 사용되며 기존 Pack의 90일 결과를
  소급 변경하지 않는다.

#### PC-02 비밀번호 정책

- 최소 길이, 복잡성 사용, 비밀번호 필수 세 필드를 조직 기준과 비교한다.
- 현재 제품 기본 최소 길이는 10자다.
- 조직 정책이 필요한 실행에서 기준이 없으면 `REVIEW`다.
- 권한 부족이나 정책 export 실패는 `ERROR`다.

#### PC-03 복구 콘솔 자동 로그온

- `DISABLED`, `NOT_DEFINED`는 `PASS`다.
- `ENABLED`는 `FAIL`이다.
- 알 수 없는 Registry 값은 `ERROR`다.

#### PC-04 공유 폴더와 공유 권한

다음 개수가 모두 0이고 `AutoShareWks`가 비활성일 때 기준을 충족한다.

- 기본 관리자 공유
- Everyone 무제한 공유
- 최소권한 위반
- 인증 누락

승인 공유 목록이 필요한데 조직 기준이 없으면 `REVIEW`다. 공유 이름은 외부 결과에서 직접
노출하지 않고 비식별 식별값과 개수로 축소한다.

#### PC-05 불필요 서비스

현재 SecAI 기본 목록은 다음 7개다.

```text
FTPSVC
MSFTPSVC
RemoteRegistry
SimpTcp
SNMP
SNMPTRAP
TlntSvr
```

평가 목록에 포함된 서비스가 실행 중이거나 자동 시작이면 `FAIL`이다. 조직이 필요한 서비스를
목록에서 제외할 수 있지만 최소 점검 목록을 빈 값으로 만들 수는 없다.

#### PC-06 불필요한 메신저

- 승인 목록 밖의 메신저가 설치되거나 실행 중이면 기준 위반 후보가 된다.
- 제품 식별 신뢰도가 낮으면 자동 FAIL 대신 `REVIEW`다.
- 전체 설치·실행 Coverage가 부족하면 `ERROR`다.
- 실제 사용자명, Process SID, 설치 경로의 개인정보는 결과에 넣지 않는다.

#### PC-07 파일시스템

- 평가 대상 모든 volume이 `NTFS`이면 `PASS`다.
- `ReFS`, `RAW`, 기타 non-NTFS는 `FAIL`이다.
- filesystem 또는 BitLocker 상태가 필요한데 알 수 없으면 `ERROR`다.
- EFI, MSR, Windows Recovery, 승인 OEM utility, optical, removable, network volume 등은
  명시적 적용성 규칙으로 제외한다.
- 평가 대상이 비어 있거나 volume class를 확정하지 못하면 PASS를 만들지 않는다.

#### PC-08 멀티부팅

- bootable OS 1개는 `PASS`다.
- 2개 이상은 `FAIL`이다.
- 0개 또는 BCD 해석 실패는 `ERROR`다.
- Recovery, diagnostic, virtualization entry는 제외한다.
- WSL과 Hyper-V guest는 호스트 멀티부팅 OS로 세지 않는다.

#### PC-09 WinINet cache

- WinINet을 사용하고 종료 시 cache 삭제가 활성화돼 있으면 `PASS`다.
- 사용하지만 삭제가 비활성이면 `FAIL`이다.
- WinINet 미사용과 평가 scope가 입증되면 `N/A`다.
- 미사용 주장만 있고 scope 확인이 없으면 `REVIEW`다.

#### PC-10 보안 업데이트

단순 `Get-HotFix`만으로 PASS하지 않는다. 다음을 함께 확인한다.

- 정확한 Microsoft 기준 snapshot ID·version·hash
- Windows Update Agent 또는 승인된 Inventory source
- 현재 Build·UBR
- 필수 보안 업데이트 누락 수
- 자동 업데이트 상태
- 마지막 성공 scan 시각
- 재시작 대기
- 조직 patch 관리 절차

필수 업데이트 누락·자동 업데이트 비활성·최소 Build 미달은 `FAIL`, 재시작 대기·조직 절차
미확인은 `REVIEW`, 오래된 scan이나 Build 불일치는 `ERROR`다.

#### PC-11 Windows 지원 수명

- 수집일이 지원 종료일 이내이면 `PASS` 후보가 된다.
- 지원 종료 후이면 `FAIL`이다.
- Edition 또는 Version을 snapshot과 연결하지 못하면 `REVIEW`다.
- snapshot과 조직 수명주기 절차가 모두 판정 입력에 포함된다.

#### PC-12 Windows 자동 로그인

- `AutoAdminLogon=1`은 `FAIL`이다.
- `0` 또는 `MISSING`은 `PASS`다.
- 알 수 없는 값은 `ERROR`다.
- `DefaultPassword`는 값 내용을 수집하지 않고 존재 여부만 수집한다.

#### PC-13 백신 업데이트

활성 백신 제품, 서비스, 자동 업데이트, 정상 상태와 signature 최신성을 확인한다. 현재 SecAI
제품 기본 최신성은 24시간이다. 미지원 Adapter는 `REVIEW`, 비활성 제품·오래된 signature·자동
업데이트 비활성·비정상 health는 `FAIL`이다.

#### PC-14 실시간 감시

- 제품과 서비스가 활성이고 실시간 보호가 켜져 있으면 `PASS`다.
- 실시간 보호가 꺼져 있으면 `FAIL`이다.
- Passive 또는 unknown mode는 `REVIEW`다.

#### PC-15 방화벽

- `ActiveStore`의 적용 가능한 Domain·Private·Public profile이 모두 활성이어야 한다.
- 적용 profile에 유효 방화벽이 없으면 `FAIL`이다.
- 미지원 타사 방화벽은 자동 PASS하지 않고 `REVIEW`다.
- Profile Coverage 또는 Policy Store가 불완전하면 `ERROR`다.

#### PC-16 화면보호기와 잠금

- `ScreenSaveActive=1`
- timeout 1~600초
- `ScreenSaverIsSecure=1`
- 평가 사용자 Coverage 완료

기술 설정이 하나라도 위반되면 `FAIL`, 수집·Coverage 불완전은 `ERROR` 또는 `REVIEW`다.

#### PC-17 이동식 미디어 자동실행

- 모든 Drive AutoPlay 차단
- AutoRun 기본 동작 `DO_NOT_EXECUTE`
- 비볼륨 장치 AutoPlay 차단
- 승인된 관리 절차

기술 설정 위반은 `FAIL`, 조직 절차 미확인은 `REVIEW`, 수집 실패는 `ERROR`다.

#### PC-18 원격 지원

- 요청형 `fAllowToGetHelp=0`
- 제공형 `fAllowUnsolicited=0`

두 값이 명시적으로 비활성이면 `PASS`, 하나라도 활성은 `FAIL`, 미설정은 `REVIEW`다.
Quick Assist와 Remote Desktop은 PC-18 판정 범위에 포함하지 않는다.

### 3.5 Windows 결과 생성 경로

현재 제품에는 두 경로가 공존한다.

#### 로컬 제품 DRAFT 경로

```text
실제 Probe observation
  → evaluate_live_draft_observations()
  → Control별 DRAFT 판정
  → 사용자 결과 화면
```

#### 제출·인수 정본 경로

```text
Probe observation
  → Evidence JSON
  → hash가 결합된 ZIP Package
  → FullPackageValidator
  → EvidenceNormalizer
  → Control별 Rule Registry
  → DRAFT Finding Schema
```

운영 제출을 연결할 때는 두 번째 fail-closed 경로를 정본으로 유지해야 한다.

### 4.2 지원 대상 탐지

Linux 로컬 수집기와 자동 식별 resolver는 다음을 fail-closed로 검사한다.

- OS 이름이 Linux인지
- 아키텍처가 `x86_64` 또는 `amd64`인지
- `/etc/os-release`가 8,192 bytes 이하인지
- `ID`·`VERSION_ID`가 Support Catalog의 Ubuntu 22.04·24.04, Debian 12, Rocky·RHEL·AlmaLinux 9 중 exact 항목과 일치하는지
- 수집기 Manifest·Adapter·architecture가 선택된 Catalog 항목과 호환되는지

사용자는 배포판을 직접 선택하지 않는다. 지원하지 않거나 불완전·충돌·다중 후보인 배포판을 비슷한 Ubuntu 또는 Rocky로 추정하지 않는다. 중앙 SSH의 일반 사용자 `ACTIVE` 목록은 실제 등록 인수를 통과한 Ubuntu 24.04·Rocky 9만 제공하고, 나머지 네 배포판은 Pilot로 유지한다.

### 4.3 실행 방식

#### 로컬 one-shot

- 일반 권한 Probe를 먼저 실행한다.
- 관리자 Probe는 `include_elevated`와 `elevated_consent`가 모두 참일 때만 실행한다.
- 이미 root가 아니면 `/usr/bin/sudo --` 뒤에 고정 argv를 붙인다.
- sudo 비밀번호는 애플리케이션이 받거나 저장하지 않는다.
- `shell=False`, 고정 `LANG=C`, `LC_ALL=C`, `TZ=UTC`, 고정 PATH를 사용한다.
- 새 process group을 만들고 timeout·취소·출력 초과 시 전체 group을 종료한다.

#### 등록 VM SSH

- 사용자가 Host·User·명령을 입력하지 않는다.
- 등록된 Asset key가 고정 target으로 해석된다.
- `StrictHostKeyChecking=yes`와 전용 `known_hosts`를 사용한다.
- `ForwardAgent=no`, `ClearAllForwardings=yes`를 강제한다.
- ROOT 명령은 `sudo -n -- <고정 argv>`다.
- `/etc/os-release` preflight를 최대 두 번 시도한다.

### 4.5 Linux 수집 결과와 redaction

로컬 수집기는 raw bytes SHA-256과 redacted normalized SHA-256을 별도로 만든다. 다음을
치환한다.

- token·secret·cookie·private key 형태의 할당값
- `rocommunity`, `rwcommunity` 뒤의 실제 community 값
- `/home/<사용자>` 또는 `/users/<사용자>` 경로의 사용자명
- NUL과 Windows 줄바꿈

다만 `getent passwd`, `getent group`의 계정 이름과 서비스 설정의 일부는 판정 입력으로 남는다.
원본 Evidence는 일반 사용자 화면에 직접 노출하지 않고 조직·자산 scope와 별도 권한으로 보호해야
한다.

### 4.6 U-01~U-67 판정 세부

#### U-01~U-13 계정 관리

| Control | 판정 요약 |
|---|---|
| U-01 | `permitrootlogin no` 또는 `prohibit-password`이면 PASS |
| U-02 | `PASS_MAX_DAYS` ≤ Profile, 최소 길이 ≥ Profile, `pam_pwquality` 존재 |
| U-03 | PAM `deny`가 1~Profile 잠금 상한이면 PASS, 누락은 FAIL |
| U-04 | passwd 비밀번호 필드가 `x`, `*`, `!`로 shadow 분리됐는지 확인 |
| U-05 | UID 0 계정이 root 하나뿐인지 확인 |
| U-06 | `pam_wheel` 또는 `pam_group`으로 `su`가 제한됐는지 확인 |
| U-07 | 로그인 가능한 계정이 승인 계정 목록 안인지 확인 |
| U-08 | root·wheel·sudo 그룹 계정이 승인 관리자 목록 안인지 확인 |
| U-09 | passwd의 모든 GID가 group DB에 존재하는지 확인 |
| U-10 | 중복 UID가 없는지 확인 |
| U-11 | UID 1~999 시스템 계정에 interactive shell이 없는지 확인 |
| U-12 | TMOUT이 있고 선택한 최대 세션 시간 이내인지 확인 |
| U-13 | yescrypt 또는 SHA-512 비밀번호 hash 정책 확인 |

#### U-14~U-33 파일·디렉터리

- U-14는 root 홈과 PATH directory 권한의 추가 확인이 필요해 `REVIEW`다.
- U-15,17,24,25,26,27,37은 검색 결과가 0이면 `PASS`, 하나 이상이면 `FAIL`이다.
- U-16,19,22는 root owner와 최대 644를 확인한다.
- U-18,21은 root owner, 허용 group, 최대 640을 확인한다.
- U-20,29는 레거시 파일이 없으면 `N/A`, 있으면 root owner·최대 600을 확인한다.
- U-23은 승인 SUID/SGID 경로 목록이 비어 있으면 `REVIEW`; 목록 밖 경로가 있으면 `FAIL`이다.
- U-28은 방화벽 활성과 모든 listening port가 승인 목록에 포함되는지 확인한다.
- U-30은 모든 UMASK 값이 최소 `022` 제한을 포함하는지 확인한다.
- U-31~33은 홈 사용 목적과 소유자 의미가 필요해 현재 `REVIEW`다.

#### U-34~U-63 서비스

- U-34,36,38,41,42,43,44,52,54는 금지·불필요 서비스 활성 시 `FAIL`이다.
- U-35는 공유 서비스 미사용이면 `N/A`, 명시적 익명 접근이면 `FAIL`, 그 외 `REVIEW`다.
- U-39와 U-58은 NFS·SNMP가 활성일 때 업무 필요성을 확인해야 하므로 `REVIEW`다.
- U-40은 NFS 미사용이면 `N/A`; wildcard 또는 `no_root_squash`는 `FAIL`이다.
- U-45와 U-49는 Mail·DNS 미사용이면 `N/A`; update 대기가 있으면 `FAIL`; 없더라도 공급자
  최신 version 확인이 필요해 `REVIEW`다.
- U-46,47,53,56은 서비스 미사용이면 `N/A`, 사용 중이면 조직 정책 대조가 필요해 `REVIEW`다.
- U-48은 Mail의 `noexpn`, `novrfy`가 모두 있으면 `PASS`다.
- U-50,51은 DNS의 `allow-transfer none`, `allow-update none`을 확인한다.
- U-55는 FTP 전용 계정의 shell이 `nologin` 또는 `false`인지 확인한다.
- U-57은 root·daemon 등 기본 계정이 FTP 차단 목록에 포함되는지 확인한다.
- U-59는 SNMPv3 `rouser` 또는 `rwuser` 설정을 확인한다.
- U-60,61은 `public/private` community 사용 시 `FAIL`, 다른 community는 원문을 보지 않으므로
  `REVIEW`다.
- U-62는 경고 배너가 있고 OS·kernel 정보가 없으면 `PASS`다.
- U-63은 `visudo -c` 실패 시 `FAIL`; 성공해도 관리자 승인 목록 대조가 필요해 `REVIEW`다.

#### U-64~U-67 패치·로그

- U-64는 대기 update가 0이면 `PASS`, 하나 이상이면 `FAIL`, 해석 불가는 `REVIEW`다.
- U-65는 `NTPSynchronized=yes`만 `PASS`다.
- U-66은 rsyslog active와 주요 로그 selector가 모두 있어야 `PASS`다.
- U-67은 `/var/log` 파일이 root owner이고 mode가 644 이하인지 확인한다.

필수 Probe가 하나라도 outputs에 없으면 해당 Control을 평가하지 않고 `ERROR`로 만든다.

### 5.3 대상과 TLS 검증

`ArubaRestTarget`은 다음을 검증한다.

- Host는 제한된 hostname 또는 IPv4 형식
- Username은 소문자 시작, 영숫자·`_`·`-`, 최대 32자
- Password는 비어 있지 않고 최대 512자
- Certificate pin은 소문자 SHA-256 64자리
- Port는 1~65,535
- API version은 정확히 `v10.13`
- Timeout은 1~60초
- 응답 상한은 4 KiB~4 MiB

TLS는 CA·hostname 검증 대신 장비 인증서 DER의 SHA-256을 등록 pin과 constant-time 비교한다.
pin이 다르면 연결을 즉시 종료하고 `CERTIFICATE_MISMATCH`로 실패한다.

### 5.4 세션과 Credential

- AOS-CX 공식 login·logout에만 `POST`를 허용한다.
- 나머지는 `_ENDPOINTS`와 `_TEXT_ENDPOINTS`에 등록된 GET만 허용한다.
- login 응답의 session cookie와 CSRF token은 짧은 세션 객체에만 둔다.
- 사용자 cookie의 privilege level 또는 현재 사용자 group으로 관리자 권한을 확인한다.
- 관리자 권한이 아니면 projection을 반환하지 않는다.
- Password는 API 응답·DB·event payload에 넣지 않는다.
- UI JavaScript는 요청 직후 password input과 request object를 비운다.
- 실행 Thread도 `finally`에서 password 변수에 빈 문자열을 대입한다.

### 5.6 Projection fact

REST 응답은 `secai.aruba-aos-cx.rest-projection.v5`로 즉시 축소된다.

주요 fact group은 다음과 같다.

- `auth.*`: 관리자 비밀번호 인증
- `identity.*`: 복잡성, 보호 저장, 사용자·역할·RBAC, SSH 인증 시도
- `management.*`: SSH allowlist, CLI·웹 timeout, Telnet, USB, Bluetooth, 배너, HTTPS VRF
- `logging.*`: remote syslog, auditable syslog, filter, persistent storage, timestamp
- `time.*`: NTP client·server
- `snmp.*`: 활성 VRF, v3-only, community 수, secure user, 관리망 외 노출
- `network.*`: routed interface, source lockdown, 물리 포트, directed broadcast, proxy ARP,
  DNS, ACL, CoPP
- `platform.*`: AOS-CX family, software version, hot patch 수

Projection은 `redaction_applied=true`, `raw_configuration_included=false`를 포함하고 canonical JSON
SHA-256 계산의 입력이 된다.

#### 판정에 직접 영향을 주는 기준

수정하지 않는다.

## 7. 점검 기준을 수정하는 방법

### 7.1 일반 사용자가 할 수 있는 변경

#### Windows

### 7.2 일반 사용자가 할 수 없는 변경

- 새로운 PC·U·N Control 추가
- PowerShell·Shell·SQL·Python expression 입력
- 임의 정규식 입력
- 새 REST URL·NETCONF payload·SSH 명령 입력
- raw JSON으로 Rule 작성
- AI가 만든 Rule을 검토 없이 실행
- 개인 기준으로 기존 KISA 결과 수정
- DRAFT를 운영 공식 Pack으로 승격

## 8. 개발자가 기준을 추가·수정하는 절차

### 8.1 기존 fact를 재사용해 임계값만 추가하는 경우

1. KISA·제조사·조직 원문과 정확한 page·section을 확인한다.
2. 기존 Control Source Mapping에 연결 가능한지 확인한다.
3. 기존 Evidence가 새 기준을 충분히 입증하는지 확인한다.
4. 값은 `integer`, `boolean`, 제한 목록 중 하나로 모델링한다.
5. 최소·최대·문자·목록 크기 제한을 정의한다.
6. Profile 계약에 key를 추가한다.
7. 실행 snapshot과 canonical hash 입력에 포함한다.
8. 실제 evaluator가 값을 읽어 판정하는 분기를 추가한다.
9. 기준을 완화했을 때 KISA 결과를 덮어쓰지 않는지 확인한다.
10. 기본값, 최소값, 최대값, 범위 밖, 잘못된 타입, 알 수 없는 key 시험을 추가한다.
11. 과거 Profile·결과를 수정하지 않고 새 version으로 저장한다.

### 8.2 새 Probe가 필요한 경우

#### 계약 먼저

1. Evidence Schema 또는 platform projection 계약을 먼저 변경한다.
2. valid·invalid Fixture를 추가한다.
3. Probe ID와 version을 새로 정한다.
4. 정확한 수집원과 최소 권한을 문서화한다.
5. timeout, 출력 상한, 허용 exit code를 정한다.

#### 수집기 구현

6. exact argv 또는 exact REST GET을 allowlist에 추가한다.
7. 사용자 입력이 command·path·regex·payload에 결합되지 않게 한다.
8. 원본 출력에서 secret·개인정보를 제거하거나 별도 보호 Evidence로 격리한다.
9. 수집 실패·권한 부족·미지원을 명시적 오류 코드로 변환한다.
10. 설정 변경·자동 권한 상승·네트워크 변경이 없는지 확인한다.

#### 정규화와 판정

11. Probe ID·version·exact raw field를 Normalizer Registry에 등록한다.
12. Control ↔ Probe Mapping을 추가한다.
13. 적용성 규칙을 먼저 작성한다.
14. PASS·FAIL·ERROR·REVIEW·N/A 분기를 모두 정의한다.
15. 부분 Evidence가 PASS가 되지 않게 한다.
16. Rule ID·version·parameter allowlist를 고정한다.

#### Pack과 승인

17. 기존 Pack 파일을 수정하지 않고 새 Pack version을 추가한다.
18. `content_sha256`과 `approval`을 제외한 payload의 RFC 8785 JCS SHA-256을 다시 계산한다.
19. PASS, FAIL, ERROR, REVIEW, N/A Fixture를 연결한다.
20. 같은 입력 100회 결과 hash가 하나인지 확인한다.
21. false PASS 0인지 확인한다.
22. 사람 검토·조직 서명·배포 승인 전까지 `DRAFT`를 유지한다.

### 8.3 플랫폼별 주요 변경 파일

| 변경 유형 | Windows | Linux | Switch |
|---|---|---|---|
| 새 수집원 | allowlist JSON, PowerShell, `expanded.py` | `linux_adapters.py`, local/SSH runner | `aruba_rest.py` 또는 새 vendor Adapter |
| 새 raw fact | PowerShell output·Normalizer field | command output parser | projection fact |
| Control Mapping | Pack evidence requirement·Normalizer | `_probe_ids()` | N Control definition·fact key |
| 판정 | `analysis/rule_engine/*` | `linux_kisa.py` | `kisa_network.py` |
| 사용자 기준 | `assessment_criteria.py` | `KisaUnixAssessmentProfile` | `KisaNetworkAssessmentProfile` |
| 계약 | 공통 Manifest·Evidence Schema | Linux 전용 3개 Schema | projection version·result contract |
| 실제 시험 | Windows host·VM | Ubuntu·Rocky snapshot | AOS-CX VM·실제 vendor version |

## 9. 유지보수와 장애 분석

### 9.1 결과 하나를 추적하는 방법

1. 결과의 `control_id`를 확인한다.
2. Control 정의에서 필요한 Probe ID를 확인한다.
3. 수집 이벤트의 `collection_status`와 `error_code`를 확인한다.
4. Probe version과 Adapter version을 확인한다.
5. Evidence hash와 result hash가 저장값과 일치하는지 확인한다.
6. 실행 당시 criteria snapshot과 criteria SHA-256을 확인한다.
7. Rule ID·version·result code를 확인한다.
8. `observed_summary`가 실제 Evidence에서 파생됐는지 확인한다.
9. 조직 보완 입력이 사용된 경우 장비 Evidence와 별도 출처인지 확인한다.
10. AI 설명이 공식 상태를 바꾸지 않았는지 확인한다.

### 9.2 수집 실패 분석 순서

| 증상 | 우선 확인 | 다음 확인 |
|---|---|---|
| Windows Probe 전체 실패 | Script hash, PowerShell 위치, OS context | timeout·출력 상한·실행 plan 순서 |
| Windows 관리자만 실패 | 사용자 동의·UAC·선택 Probe | localhost bridge 18482·관리자 결과 병합 |
| Windows 특정 항목 ERROR | 해당 Adapter·raw field | Normalizer exact field·Pack requirement |
| Linux preflight 실패 | `/etc/os-release`, 배포판 선택 | 아키텍처·파일 크기·일시 I/O 재시도 |
| Linux 일반만 성공 | elevated consent·sudo | ROOT command exit code·stderr 비노출 원인 |
| Linux 다수 ERROR | SSH host key·private key·sudo -n | 고정 argv 경로·패키지 설치 여부 |
| Switch 연결 실패 | VM 전원·Host-only network·443 | certificate pin·API v10.13 |
| Switch 인증 실패 | credential·관리자 role | login cookie encoding·현재 사용자 group |
| Switch 전체 GET 실패 | 실패 endpoint·content type | API version·응답 1 MiB 제한 |
| 결과 hash mismatch | append-only stored JSON | 표시 계층이 canonical 값을 수정했는지 |

### 9.3 버전 변경 원칙

- Probe 출력 의미가 바뀌면 Probe version을 올린다.
- Parser 또는 projection field 의미가 바뀌면 projection/Normalizer version을 올린다.
- Rule 기준이 바뀌면 Rule version과 Pack version을 올린다.
- Adapter가 지원하는 제품·version 범위가 바뀌면 Adapter Catalog 새 version을 만든다.
- 외부 OS 수명·patch 기준이 바뀌면 새 날짜의 reference snapshot을 만든다.
- 과거 계약·Pack·snapshot·Fixture를 덮어쓰지 않는다.
- 새 version과 구 version의 호환 여부를 검증 기록에 남긴다.

### 9.4 정기 점검 항목

#### 변경마다

- 관련 unit·contract test
- Schema valid·invalid 예제
- Ruff·mypy·JavaScript syntax
- secret·PII 누출 회귀
- 수집 오류가 FAIL/PASS가 아닌지
- criteria snapshot·hash 재현성
- 문서와 코드 version 일치

#### Pack 배포 전

- 전체 Control 정확히 한 번 Coverage
- PASS·FAIL·ERROR·REVIEW·N/A Fixture
- 100회 결정론
- false PASS 0
- Pack content hash
- 승인자·서명·폐기·rollback

#### 실제 플랫폼 변경 전

- Windows: clean VM, 설정 전후 diff 0, Defender·SmartScreen, Publisher
- Linux: Ubuntu·Rocky 정상/취약 snapshot 반복 재현
- Switch: exact vendor OS/API version, certificate rotation, 연결 보존, 실제 장비 재실행

## 10. 현재 확인된 유지보수 주의사항

### 10.1 현재 Switch 기준선

현재 source 기준은 `0.4.0-DRAFT`, 허용 REST GET 18개, N-01~N-38, projection v5다. 과거
`SW-01~06`, 13개 GET과 `0.3.0-DRAFT`는 검증 이력에서만 해석하고 새 구현 기준으로 사용하지 않는다.

### 10.2 Switch Boolean 기준의 실제 연결

26개 안전 기준 중 다수 Boolean은 현재 expected summary에는 포함되지만 device rule 분기를
직접 바꾸지 않는다. 기준 필드 추가만으로 동작했다고 판단하지 말고 evaluator에서 사용되는지
시험해야 한다.

### 10.3 Switch N-09 Bluetooth 조건

현재 N-09는 USB와 Bluetooth를 모두 수집하고 summary에 표시하지만 상태는 USB 차단 여부를
중심으로 결정한다. Bluetooth가 활성이고 USB만 차단된 경우의 기대 상태를 명시한 Fixture와 규칙
검토가 필요하다.

### 10.4 Ubuntu 보안 업데이트 의미

Ubuntu는 `apt-get -s upgrade`의 전체 upgrade 수 또는 `Inst` 줄을 센다. 보안 update만이 아닌
일반 update까지 포함될 수 있다. U-45, U-49, U-64를 KISA의 보안 patch 의미에 정확히 맞추려면
Ubuntu Security Pocket 또는 공급자 보안 metadata 기반 Adapter가 필요하다.

### 10.5 Linux 승인 계정 의미

`approved_admin_accounts`가 U-07의 모든 interactive login 계정 허용 목록에도 사용된다. 일반
업무 계정이 있는 서버에서 의도하지 않은 FAIL이 생길 수 있으므로 향후 승인 로그인 계정과 승인
관리자 계정을 분리하는 계약을 검토해야 한다.

### 10.6 실제 Switch 재검증

Aruba AOS-CX 10.13.1170 OVA의 안전·취약 설정과 인증서 고정 REST 기본 경로는 실제 VM에서
검증됐다. 현재 18개 GET·N-01~N-38·PDF·AI를 포함한 전체 제품 흐름의 반복 Browser E2E와
운영 Pack 승인은 별도 남은 Gate다. 새 실행을 만들고 기존 append-only 결과를 소급 변경하지 않는다.
